# Kinesis Edit

A modern, cross-platform replacement for the Kinesis SmartSet keyboard-configuration app. The legacy SmartSet apps are written in Pascal and no longer supported; this project rebuilds them with a modern architecture.

- **Stack:** C# with [Avalonia UI](https://avaloniaui.net/) for cross-platform portability.
- **Platforms:** macOS first, with Windows and Linux fully supported.
- **Status:** In development — specification complete, static domain data implemented (device catalog, key-token registry, layer geometries — see [`docs/app/domain-data.md`](docs/app/domain-data.md)), the in-memory keyboard/macro model built on it (see [`docs/app/keyboard-model.md`](docs/app/keyboard-model.md)), firmware version parsing and feature gating implemented (see [`docs/app/firmware.md`](docs/app/firmware.md)), v-Drive services implemented (drive discovery, file I/O, eject — see [`docs/app/vdrive.md`](docs/app/vdrive.md)), lighting model and led-file engine implemented (RGB, TKO, Advantage360 — see [`docs/app/lighting.md`](docs/app/lighting.md)), settings engine implemented (keyboard/app settings parsing and saving — see [`docs/app/settings.md`](docs/app/settings.md)), keystroke capture for remap and macro recording implemented (see [`docs/app/keystroke-capture.md`](docs/app/keystroke-capture.md)), layout and macro file parsers/serializers implemented (Freestyle, RGB/TKO, Advantage360, and Advantage2 dialects — see [`docs/app/layout-files.md`](docs/app/layout-files.md)), profile load/save/eject orchestration implemented for the numbered-profile devices — FS Edge/Pro, Edge RGB, TKO, Advantage360 (see [`docs/app/profiles.md`](docs/app/profiles.md)), the Savant Elite2 pedal-file engine implemented (`active/pedals.txt` parsing, saving, display text, and the edit session behind the pedal editor — see [`docs/app/savant-elite.md`](docs/app/savant-elite.md)), and the app now launches to a device dashboard that lists your keyboards as they are detected — keeping a card once a board has been seen, so unplugging it leaves a quiet resting card rather than making it vanish — opens them from a card, and reaches demo mode with no hardware attached (see [`docs/app/app-shell.md`](docs/app/app-shell.md)). The first keyboard editor is in: opening a Freestyle Edge RGB draws its keyboard, switches between the top and Fn layers, remaps a key by clicking it and pressing the key you want, resets a key/layer/layout, and saves the profile back to the v-Drive; its **Macros** tab records a macro on the selected key by pressing the keys you want, with macro slots, co-trigger modifiers, playback speed and repeat, live keystroke-budget readouts and a list of every macro in the profile; its **Lighting** tab picks an effect (filtered by the board's mode matrix and firmware gates), sets effect and base colours from a picker with twelve saved custom slots, adjusts speed and direction, and paints individual keys or whole zones; its **Settings** tab shows exactly the settings the connected device supports — startup profile, macro and status speeds, v-Drive behaviour, game mode and the rest — read-only with a plain explanation on an Advantage2 without the 4MB firmware, and read-only in demo mode, and below them a second section for the app's own per-device preferences: which prompts you have turned off, whether advisory warnings are explained in full or in one line, whether a layer reset asks first, and the twelve custom colour swatches every colour picker in the app shares (see [`docs/app/keyboard-editor.md`](docs/app/keyboard-editor.md)). Erasing a whole layer or layout now asks before it does it, with a "Don't ask this again" you can undo from that same Settings tab. The advanced surfaces sit alongside it — tap-and-hold, macro timing delays, a searchable key picker, exporting the layout/lighting files to a folder, and importing an external `.txt` back over the profile — each refusing politely when the keyboard's firmware is too old (see [`docs/app/feature-dialogs.md`](docs/app/feature-dialogs.md)); the Savant Elite2 programs its seven pedal inputs — click Edit on an input, press the keys you want it to send (one key or a whole macro), add mouse clicks, media keys, delays and shortcuts from the Special Actions menu, and save the file back to the pedal. The other devices still open a placeholder until their keyboard picture is drawn — which also gates the TKO edge-LED tab and the Advantage360 indicator editor. Progress is tracked in [GitHub issues](https://github.com/migus88/kinesis-edit/issues/1).
- **In flight — a UI redesign.** Everything above was built to mimic the legacy app closely. A design handoff now supersedes that look, and in places its behavior: a key inspector in place of the current dialogs, macros named and edited where the key is, lighting previewed on the board itself, and per-device board art for every model. It lives in [`docs/design/`](docs/design/README.md) and is tracked as its own epic. **Its foundation has landed:** the design system — colour, shape, type and motion tokens for both themes, a shared style layer, embedded IBM Plex Sans/Mono, an OS reduce-motion switch, the base Avalonia controls put on the palette, and a drawn icon set (the app bar carries the KinesisEdit mark, every device card shows its own board drawing, the device picker lists the seven models as silhouettes, and connection state, dialogs and lighting modes are drawn rather than spelled) — together with a headless UI test harness that renders the app offscreen so views, styles and tokens are covered by `dotnet test` like anything else (see [`docs/app/design-system.md`](docs/app/design-system.md)). Every control the app draws for itself — buttons, pills and chips, the layer switcher, the section tabs, the fields and the key caps — is now drawn by the app rather than restyled on top of the toolkit's own, and **the whole app has a keyboard focus ring**: a thin accent outline with a soft halo that appears when you Tab or arrow to something and stays out of the way when you click. Selecting a key and focusing it are shown as two separate rings, so a key can be both without either becoming unreadable, and locked keys and unlit LEDs are hatched rather than blacked out. The layer switcher is now a single control instead of a row of buttons, so it takes **one Tab stop** and the arrow keys move between layers inside it. The screens themselves are being rebuilt on it issue by issue, starting with **the app bar and the dashboard**: the window title now names the board you have open, the bar shows how long ago the app last looked for a v-Drive, and each device sits on a card that says in plain words what its drive is doing — connected, quietly resting with no drive mounted, or mounted but not writable, with what to try next. Cards keep their size and their buttons stay put while the app rescans, and a scan that lands while your pointer is on a card waits until you move away, so the list can never move a button out from under you. **The editor shell has been rebuilt on it too:** opening a keyboard now replaces that bar with the editor's own — Home, the device name, its drive path, Save and the connection chip on one row, with the section tabs and the layer switcher beneath — so there is never a second bar or a second status chip on screen. **Save turns amber the moment you have unsaved work**, so the prompt on leaving is rarely a surprise — and that prompt is now real: going Home, opening another device or closing the window all ask once whether to save, discard or stay, with an "always save on leaving" you can undo from the Settings tab. **Home no longer ejects your drive either**: ejecting is a deliberate button on the device card, so nothing is unmounted behind your back. A section the board cannot do is no longer greyed out, it is simply absent. Where a layout exceeds what the device can hold, the editor now says so in a calm amber strip — *"nothing is blocked"* — and never refuses the edit or the save: over-budget files still write, the board keeps what it can read. With no keyboard attached, a Demo Mode bar says plainly that nothing you change is written anywhere. **And the board itself has been redrawn:** a split keyboard is now two panels with a gap between them, as the real hardware is, and the whole picture grows to fill the window as one — the caps, the lettering and the marks on them all keep their proportions. Each key reads what is actually printed on it until you change it, shifted characters and all, and then says what it now does. What a key carries is shown by small marks on the cap rather than by recolouring it: a blue bar along the bottom for a key you have remapped, a dot for a macro, a folded corner for tap-and-hold, an amber bar for a key the app has a note about, and hatching for a key the firmware will not let anyone change. A **legend** under the board says what each mark means and counts how many keys on the layer you are looking at wear it — and carries two actions: **Copy key…**, which lets you click one key and then another to copy the first onto it, and **Reset layer**. The editor also **answers the keyboard now**: the arrow keys walk the selection across the board by physical position (including across the gap between a split board's halves), `⌥1`–`⌥5` jump to a layer, and `⌘F`, `⌘S` and `⌘W` open the key search, save, and return to the dashboard — `Ctrl` in place of `⌘` on Windows and Linux. `Esc` stays out of it while a key is listening, because `Esc` is itself a key you are allowed to remap. **With no keyboard plugged in the app now teaches rather than apologises:** it names the seven boards it knows, draws each one, and walks you through getting the one you own into a state it can see — while telling you, live, how many times it has looked since you opened the window. And the app's small interruptions have moved inside it: a question, a notice or a "loading…" is now a card that fades in over the dimmed window instead of a second window of its own, notices can be dismissed with an ×, and one that reports advisories arrives in amber rather than green. **Editing a key has moved out of dialogs entirely.** Clicking a key now opens a panel down the right-hand side of the window that stays there while you work: it names the position, says what the board shipped it doing and what it does now, and offers the one thing that key can carry — a remap, a tap-and-hold, or a macro — as tabs, warning you before a choice replaces what is already there. Assigning is now two ways round: press the key you want, as before, or **search the whole catalogue by name** — `⌘F` from anywhere puts the cursor in that search — filter it by letters, navigation, media, mouse or device hotkeys, or pick from what you have just used, and press ↵. If that leaves the same key on two positions the panel says so and assigns it anyway. Tap-and-hold is captured the same way, one press for the tap and one for the hold, with the delay on a slider that opens on your own board's default. A key the firmware will not let anyone change explains itself instead of going quiet — what it does on the board, and that you can still copy *from* it but never onto it. `Esc` closes the panel, and the board beside it stays live the whole time: nothing is greyed out behind a dimmed window any more.

## Building and running

Requires the .NET 10 SDK (pinned via `global.json`). From the repo root:

```sh
dotnet build src/KinesisEdit.sln    # build everything
dotnet test src/KinesisEdit.sln     # run the test suite
dotnet run --project src/KinesisEdit   # launch the app
```

## How it works

Kinesis programmable keyboards mount a small FAT volume (the "v-Drive") containing plain-text configuration files (layouts, macros, lighting, settings). The keyboard's firmware parses those files itself — there is no USB/HID configuration protocol. The app is a file editor with a keyboard-shaped UI: it discovers the drive, parses the files into an in-memory model, lets the user edit it visually, and writes the files back.

## Contributing notes

- Code follows the conventions in `docs/guides/Coding Conventions.md`: clean, SOLID, no god classes.
- Every module gets a token-efficient doc in `docs/app/` so AI agents (and humans) can understand a domain without reading its source. Documentation — `docs/app/`, `CLAUDE.md`, and this README — is maintained as part of every feature change.
- Feature work runs in isolated git worktrees under `.claude/worktrees/` (one per feature branch, based on `origin/main`), so several features can be in flight at once. Worktrees are removed once their PR merges; `/clean-worktree` sweeps up any leftovers.
