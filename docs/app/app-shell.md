# App shell and device dashboard (Services, ViewModels, Views)

The Avalonia layer of `KinesisEdit`: one window that swaps between a device dashboard and a per-device editor, the app-side detection loop that turns `KinesisEdit.Core.VDrive` scans into renderable snapshots, and the notification primitives (message box, toast, loading indicator) every later dialog reuses. It owns no domain knowledge — device facts come from `DeviceCatalog` ([domain-data.md](domain-data.md)), discovery/IO/eject from [vdrive.md](vdrive.md), version parsing and gates from [firmware.md](firmware.md) — and it owns no editor: the editor slot is filled by whatever `IEditorViewModelFactory` returns — the keyboard editor ([keyboard-editor.md](keyboard-editor.md)), the Savant Elite2's pedal editor ([savant-elite.md](savant-elite.md)), or `EditorPlaceholderViewModel` for every device that has neither yet. There is **no DI container**: `App.axaml.cs` is the composition root and every dependency is a constructor parameter.

## Composition root — `App`

`BuildServices` wires by hand, in this order: `VDriveFileService` → `VDriveMonitor(new VDriveScanner(PlatformVolumeEnumerator.Create()))` → `DeviceMonitorService(monitor, fileService, dispatcher, clock)` → `SettingsServiceAdapter(new SettingsService(fileService))` → `DeviceSessionManager(settings)` → `MessageBoxPresenter(FindMessageBoxHost, () => _captureService)` → `NotificationService(presenter, sessions)` → `VDriveEjectNotifier(new DeviceEjectService(VDriveEject.CreateForCurrentPlatform()), notifications)` → `ProcessUrlLauncher` → `PedalFileService(fileService)` → `EditorViewModelFactory(new ProfileSessionFactory(), settings, ResolveCaptureService, notifications, pedalFiles, new AvaloniaFolderPickerService(FindOwnerWindow), new AvaloniaFilePickerService(FindOwnerWindow), fileService, urlLauncher, sessions)` → `DashboardViewModel` → `MainWindowViewModel(…, clock, dispatcher)`. Then `desktop.MainWindow = new MainWindow(shell, notifications)` and **`DeviceMonitorService.Start()` last** — everything a scan can raise is reached through that window: the message box on its notification overlay, both file pickers on its storage provider. Each is therefore resolved through a callback (`Func<IMessageBoxPresenter?>`, `Func<Window?>`) rather than held as a reference. `desktop.Exit` disposes shell, dashboard, monitor, and — **last, after the shell has closed and disposed the open editor** — the keystroke capture service.

- **The keystroke capture service is built lazily, over the shell window.** `AvaloniaKeystrokeCaptureService` previews the key events of one `TopLevel` ([keystroke-capture.md](keystroke-capture.md)) and that window does not exist while the graph above is wired, so the editor factory takes a `Func<IKeystrokeCaptureService>` and `App.ResolveCaptureService` creates the single instance on first use — the same ordering problem the message-box presenter solves with its `Func<IMessageBoxPresenter?>` host. This is also what breaks the shell ↔ capture cycle; by the time a device is opened, the window is on screen. The presenter is handed `() => _captureService` — the **field**, not `ResolveCaptureService` — because a box raised before any editor has opened has nothing to suspend, and building a capture service in order to answer a dialog would be backwards.
- **Every editor's dependencies live in the factory, not in the shell.** `PedalFileService` and `ISettingsService` are stateless and one instance of each serves every session; they are handed to `EditorViewModelFactory` rather than to `MainWindowViewModel`, because the shell would otherwise accumulate one constructor parameter per device as editors are added. The keyboard editor's feature panels add four more to the same place — the two pickers, the file service, and the URL launcher the firmware-gate refusals use ([feature-dialogs.md](feature-dialogs.md)) — and the **`IDeviceSessionAccessor`** a fifth, which is how an editor reaches the open device's `app_settings.txt` (`Active?.Preferences`). It is passed last and is *optional* on both the factory and `KeyboardEditorViewModel`: a design scene or a unit test builds an editor with no session at all, and every preference then sits at its default. The shell opens the session before it asks the factory for an editor (spec 10's Configure order below), so in the running app `Active` is always the device being edited.
- **One `ISettingsService` for the whole app.** `SettingsServiceAdapter` ([settings.md](settings.md)) is built once and shared by `DeviceSessionManager` (whose suppression stores read and write `app_settings.txt`) and the editor factory (whose Settings tab writes the keyboard-settings file). `app_settings.txt` must have exactly one reader and one writer: a second, line-based implementation would clobber the twelve `cust_color_N` picker slots Core writes into the same file.
- **One `SystemClock` and one `AvaloniaUiDispatcher` for the whole shell.** The detection loop stamps each completed pass from the clock and `MainWindowViewModel`'s `refreshed Ns ago` readout ages against the same one, so the two can never disagree about the elapsed time; both marshal onto the UI thread through the one dispatcher. `ISystemClock` exists as a seam only — a toolkit-free `DateTimeOffset.UtcNow` (invariant 8) that lets the readout be tested without sleeping.
- **Both file pickers defer their owner window** through `Func<Window?>` (`App.FindOwnerWindow`): a picker reaches the platform dialog through `TopLevel.StorageProvider`, and no window exists while the graph is wired. They are the only remaining users of that resolver — the message box is no longer a window and needs no owner — and it still scans `desktop.Windows` **newest-first** for an active one, falling back to the last entry and then to `MainWindow`, so a picker raised from a dialog is not parented to a window that dialog blocks. `StorageProviderHost` is the single resolution point they share, and **no owner is reported to the caller as a cancel** — an export or import simply does not happen rather than throwing from a service.

- **The message box is not a window.** `App.FindMessageBoxHost` returns `(desktop.MainWindow as MainWindow)?.MessageBoxHost` — the shell's `NotificationOverlay`, which implements `IMessageBoxPresenter` itself — and `MessageBoxPresenter` is a lazy forwarder onto it. `DialogWindowHost` and `MessageBoxWindow` are **deleted**; see "Notifications" for the whole surface.

- **The composition root owns the loop's lifetime and it runs until exit.** No view model starts or stops polling. **`Start()`'s first pass is deliberately synchronous** (unlike every later scan): `DashboardViewModel` is constructed before the window, so the cards must exist before the first frame or the "Keyboard not detected" panel flashes on every launch.
- **One window, swapped views.** `MainWindowViewModel.CurrentView` is the dashboard or the open editor; `MainWindow.axaml` binds it to a `ContentControl` and `ViewLocator` (registered in `App.axaml`'s `DataTemplates`, matching any `ViewModelBase`) maps `KinesisEdit.ViewModels.XxxViewModel` → `KinesisEdit.Views.XxxView` in the same assembly, falling back to a diagnostic `TextBlock`. `MainWindowViewModel` is deliberately *not* resolvable this way (no `MainWindowView`) — the root window is constructed by hand.
- **Native chrome, OS theme.** Resizable 1000×680 window (min 720×480) with the platform title bar and a fixed 46-high in-window top bar carrying Home / Settings / Help plus the status chip. `RequestedThemeVariant="Default"` + `FluentTheme`, so the OS light/dark variant wins; every colour is a role token resolved by `DynamicResource` from the design system ([design-system.md](design-system.md)), and the base Fluent controls are re-pointed at the same palette by `Themes/Controls.axaml`. The legacy borderless chrome and fixed 1550×850 size are dropped (macOS-first).
- **The status indicator is a chip, not coloured text.** `Views/StatusChipView` — `Border.statusChip` takes `.ok`/`.error`/`.demo`/`.warning` from `StatusIndicatorSeverity`; its fill and border cross-fade over 220 ms when the detection loop changes its mind, while the text inside swaps instantly. The four states are fixed and never share a meaning — green connected and writable, red gone or unwritable, **purple demo mode**, amber an advisory that never blocks. Demo mode is `StatusSeverity.Demo`, deliberately not `Warning`: amber is the only warning colour in the app.
- **On the dashboard, a completed scan that found nothing reads `v-Drive Error`, not `Demo Mode`.** `GetDashboardHealth` returns `Ok` as soon as one device is `Connected` with `Health == Ok`, and `Error` for everything else a *finished* pass can report — mockup `1a` defines v-Drive Error as "gone · unwritable", and a drive that is absent is gone. **Before the first pass completes it stays `Unknown` → `Demo Mode`** (`_monitor.LastRefreshedUtc is null`): "gone" is a finding, and before the first scan there is none. In the shipped app that state is never on screen, because `Start()`'s first pass is synchronous. `Demo Mode` now means only what it says — an open demo session, reported by the session branch above it.

### The chrome hand-off — `ProvidesOwnChrome`, `IsShellChromeVisible`, `IShellChrome`

The mockups draw **exactly one 46 px bar while editing** (`1e`, `1f`, `2d`), carrying `Home`, the device name, the drive path, `Save` *and* the v-Drive chip — the same things this bar carries. So an editor that has been rebuilt on the redesign draws the whole bar itself and the shell **hides its own**:

- `DeviceEditorViewModel.ProvidesOwnChrome` — virtual `false`, overridden `true` on `KeyboardEditorViewModel` only. The Savant Elite2 pedal editor keeps the shell bar until issue [#53](https://github.com/migus88/kinesis-edit/issues/53); the placeholder always keeps it.
- `MainWindowViewModel.IsShellChromeVisible` — `_editor?.ProvidesOwnChrome != true`, bound to the app bar's `IsVisible`. Re-raised from the `Editor` setter, so it moves in **both** directions with one line and no navigation path can forget it.
- `IShellChrome : INotifyPropertyChanged` — `IAsyncRelayCommand HomeCommand`, `string StatusIndicatorText`, `StatusSeverity StatusIndicatorSeverity`. `MainWindowViewModel` implements it; `DeviceEditorViewModel.Shell` holds it. `OpenDeviceAsync` assigns it **before** the view swap, so the first frame already has its bindings; `CloseEditor` clears it in the `finally`, even when the disposal threw.

**Why an interface and not a `$parent[MainWindow]` binding.** Every headless suite renders an editor view standalone in `ThemedHost`, so a visual-tree lookup for the window's `DataContext` resolves to nothing: Home and the status pill would come out blank in the tests *and* in the frames used to verify the screen. A view must get its data from its own `DataContext`.

**`Views/StatusChipView`** is the chip, extracted because two surfaces draw it — this bar and the editor's toolbar (only ever one at a time). Its `x:DataType` is `IShellChrome`, so the shell binds it to itself and the editor binds it to `Shell`. Copying the markup instead would leave four bound classes on the border and four on the label to drift in two places.
- **MVVM** is `CommunityToolkit.Mvvm` (`ObservableObject` via `ViewModelBase`, `RelayCommand`/`AsyncRelayCommand`), compiled bindings on.
- **One escape hatch.** With `--keystroke-spike` in `desktop.Args` (`dotnet run --project src/KinesisEdit -- --keystroke-spike`) the root skips the whole graph and shows `Views/KeystrokeCaptureSpikeWindow` — the issue-#12 capture harness kept for hand-verification ([keystroke-capture.md](keystroke-capture.md)); no services are built and the detection loop never starts.

## Detection loop — `DeviceMonitorService`

Owns the `VDriveMonitor` (and disposes it). `Refresh()` = one `VDriveMonitor.Poll()`, then for every device with a `Location` **re-read and re-parse the version file**, producing an immutable `DeviceSnapshot` per tracked device in `DeviceCatalog.All` order, plus that poll's `VDriveStatusChange` list, published as one `DeviceMonitorUpdate`. `Start()` runs one synchronous `Refresh()` then arms a 2 s `System.Threading.Timer`; `Stop()` disarms it (`IsPolling` reports the state); tests call `Refresh()` directly. A throw inside a timer tick is swallowed — the next tick retries.

- **The loop is never stopped for an editing session.** Spec 10 requires an open editor to re-verify its version file every tick, and one loop serves both the dashboard and the editor — so `Start()`/`Stop()` belong to the composition root and to `Dispose`, not to navigation.
- **`Refresh()` coalesces rather than dropping.** A call arriving while another refresh runs marks the running one to *repeat* and returns; the repeat happens under the same gate. Concurrency is not an option because `VDriveMonitor.Poll()` discards an overlapping poll outright, which would silently turn a user's `Scan for v-Drive` landing on a timer tick into a no-op. Pending `VDriveStatusChange`s are copied, published, and only the published count removed afterwards, so a change the monitor raises mid-publish survives to the next pass instead of vanishing (this is what keeps `IsConnectionLost` reliable).
- **The gate and the refresh state live in `RefreshActivity`**, a small collaborator, so the service stays a detection loop instead of also being a state machine. It owns the repeat gate (`TryBegin`/`TryRepeat`/`End`) *and* the three facts the dashboard renders — `IsRefreshing` (the cards' `Scanning` state), `LastRefreshedUtc` (the app bar's `refreshed Ns ago`) and `CompletedRefreshCount` (the empty state's `rescanned N times`) — because they all change at the same three moments. Everything is under one lock; `Changed` fires outside it, on whatever thread caused the transition. `DeviceMonitorService` re-exposes both properties and raises `RefreshActivityChanged`.
- **`RefreshActivityChanged` is a second event, marshaled like `Updated`** (invariant 7, same `IUiDispatcher`): a refresh *starting* publishes no snapshots and yet must light the Scanning state, and a coalesced repeat changes neither snapshot list nor changes. A handler may therefore touch view-model state directly.
- **"Successful refresh" means the pass ran to completion**, not that it found anything. `Stamp(clock.UtcNow)` happens after the snapshots are built and **before** they are published — so an `Updated` handler reading `LastRefreshedUtc` never sees the previous pass's time. An empty scan stamps; a scan whose version files were all unreadable stamps (that device reports `VDriveHealth.Error`, which is a result); a pass that **throws** on the way there does not, so the readout keeps ageing rather than claiming a scan that never happened. **`CompletedRefreshCount` is incremented inside the same `Stamp`, under the same lock**, because the time and the count are one fact seen twice: *a pass finished*. It therefore counts **completed passes, not calls and not timer ticks** — a `Refresh()` coalesced into a running pass shares that pass's single increment, and a throwing pass unwinds through `End()` and adds nothing. That is exactly the claim the empty state's "rescanned N times" makes.
- **Nothing cancels a refresh.** `Refresh()` takes no cancellation token and `IsRefreshing` is a purely visual fact — see the deviation on the missing `Cancel` button.
- **The version file is re-read every refresh on purpose.** It is both the `v-Drive OK` / `v-Drive Error` probe (spec 10 "Startup / v-Drive scan / demo mode") and the Freestyle Edge↔Pro re-derivation (spec 10: the app "re-reads the device's version file on every connectivity check and resets the active model"). Read/parse failures are caught, never thrown: they yield `VDriveHealth.Error` and `VersionFileInfo.Empty`.
- **Freestyle re-derivation** runs through `VersionFileInfo.ResolveFreestyleModel()` **only when `Health == Ok`** — an unreadable file would otherwise report an Edge; the scanner's label match is the better answer there.
- **Demo-mode derivation**: `IsDemoMode = Status != Connected` (spec 03 §3.5, "not connected or no read/write access"), so a `CannotAccess` drive is a demo-mode device that still has a `Location`. `FirmwareState.FromVersionFile(versionFile, isDemoMode)` carries it into the gate service. `DeviceSnapshot.CreateDemo(device)` builds the hardware-free variant (`NotDetected`, `Health = Unknown`) the empty state's *Launch ‹device› in Demo Mode* uses.
- `VDriveHealth`: `Unknown` (no drive to check) / `Ok` / `Error`. `DeviceSnapshot.IsDetected` = `Connected` or `CannotAccess` — the dashboard's card filter.
- **`ScannedDeviceId` vs `DeviceId`.** `ScannedDeviceId` is the catalog slot the scanner matched — at most one location per catalog device, so it is unique within a refresh. `DeviceId`/`DisplayName` are the *resolved* device and are not unique: the Edge and Pro slots both re-derive from the version file and can land on the same definition. Cards and sessions key on the former and display the latter.
- **`Updated` is posted through `IUiDispatcher`** because `VDriveMonitor` polls on a thread-pool timer. `AvaloniaUiDispatcher` and the two file pickers with their `StorageProviderHost` are the only Avalonia-aware types in `Services/` (invariant 8) — `MessageBoxPresenter` stopped being one when its window went away; tests use an inline/deferrable dispatcher fake.

## Sessions and eject — `DeviceSessionManager`, `VDriveEjectNotifier`

`DeviceSessionManager` holds the single active `DeviceSession` (`Begin`/`End`/`ActiveChanged`), and `UpdateActive(snapshots)` re-points it every refresh — matched by `ScannedDeviceId`, so a Freestyle board that re-resolves Edge↔Pro mid-session still matches. `NotificationService` reads the session through the narrow `IDeviceSessionAccessor`.

- **`DeviceSession` separates what is fixed from what is live.** `OpenedDevice` (and therefore `IsDemoMode` and the suppression store) is frozen at open time — spec 10 has Configure set demo mode from the connected/writable state *once*. `Device` follows the loop, and `Health` derives from it: `Unknown` in demo mode, otherwise the snapshot's health, or `Error` if the drive stopped being detected. That is what flips the editor's indicator to `v-Drive Error` mid-session instead of freezing it at open-time state.
- **Preferences store by drive state** (`DeviceSession.Preferences`, of which `SuppressionStore` is the narrow view — one object, not two), all over `app_settings.txt` in the drive's `settings/` folder — the path is Core's `SettingsService.GetAppSettingsFilePath`, so it is `settings/` on **every** device including the Advantage2, whose *keyboard* settings live in `active/` (spec 08 §3, 03 §6): connected and writable → `VDriveAppPreferencesStore`; **demo mode over a drive that is present but not writable → `ReadOnlyAppPreferencesStore`**, which reads that store and discards its writes; no `Location` at all → `NullAppPreferencesStore`. Spec 08 §3 bans *saving* in demo mode, not loading, so a demo session on real hardware keeps the notifications the user hid on it.

`VDriveEjectNotifier` is the shared user-facing eject flow (card *Eject* button and Home): toast `Disconnecting v-Drive` → `IDeviceEjectService.EjectAsync` (which runs the blocking `IVDriveEjector` on the thread pool) → toast `Safe To Remove Hardware`, or an error message box on failure. It no-ops and returns false when `IsSupported` is false.

## Notifications — `INotificationService`, `MessageBoxRequest`, `INotificationSuppressionStore`

`INotificationService` is the UI-toolkit-free contract view models depend on: `ShowMessageBoxAsync`, `ShowToast`, `ShowLoading`/`HideLoading`. `NotificationService` adds the suppression policy over an `IMessageBoxPresenter`. **All three surfaces are drawn by one control, `Views/NotificationOverlay`, inside the shell window** (mockup 1k) — the message box is an in-app card over a scrim, not an OS window.

**The presenter chain.** `MessageBoxPresenter` (view layer) presents nothing itself: it is a lazy forwarder onto a `Func<IMessageBoxPresenter?>` host — `NotificationOverlay`, which implements `IMessageBoxPresenter`. Two things it owns and the overlay does not:

- **With no host registered it answers immediately rather than hanging**, with the request's escape outcome (`Cancel` when the box has a Cancel button, `None` when it has not). A never-completing `Task` would deadlock the caller; every call site already treats that branch as "the user did not answer", so nothing destructive runs off the back of a box nobody saw.
- **It suspends keystroke capture for a box's lifetime**, centrally, so every call site inherits it. This closes a regression the window → overlay move introduced: the box now shares the shell's `TopLevel`, where `AvaloniaKeystrokeCaptureService` previews keys in the tunnel phase — it swallowed the dialog's own Enter and Escape *and* assigned the Escape as a remap. The suspension is **depth-counted** (boxes queue, and resuming on the first answer would hand the keyboard back while the second card is still up) and **releases only what it took**: if the capture is already suspended by somebody else — `EditorOverlayHost` holds one for a text-entry panel's whole lifetime — the presenter takes no suspension and releases none.

**The surfaces.**

- `MessageBoxRequest`: title, message, `MessageBoxIcon`, `MessageBoxButtons` (None/Ok/OkCancel/YesNo/YesNoCancel), `CustomButtons`, the four optional `YesCaption`/`NoCaption`/`OkCaption`/`CancelCaption` overrides, optional `SuppressionKey`, `SuppressedResult`. `MessageBoxOutcome`: `Result` + `SuppressRequested` + `CustomButtonId` + `WasPresented`. **The legacy "+100 modal result" encoding of spec 11 §11.9 is deliberately replaced by this structured outcome** — never reintroduce the offset. `MessageBoxViewModel.Complete` is idempotent (first answer wins), so the awaiting presenter can never hang. Enter is honored **only when `HasAcceptButton`** (`ShowsOk || ShowsYes`): a `Buttons = None` dialog carrying just custom buttons — spec 11.9's "Update Firmware" shape — must not be answerable with a result no visible button offers, so Enter is left unhandled there. Escape yields `Cancel`, or `None` when there is no Cancel button.
- **The caption overrides rename buttons; they never move a result.** Mockup 1k labels the buttons by *outcome* ("Cancel · Key data only · Include macros"), so a request may relabel any standard button while `MessageBoxResult` stays Yes/No/Cancel — every caller's `switch` and every `SuppressedResult` keep their meaning, and Yes stays the primary affirmative whatever it is called. `MessageBoxViewModel` exposes `YesCaption`/`NoCaption`/`OkCaption`/`CancelCaption`, falling back to the `Default…Caption` consts. Four call sites use it today (see the string table).
- **A box is queued, never stacked.** A request arriving while one is up waits behind it in `NotificationOverlay`'s queue: two cards centred on the same scrim would hide one another, and answering an invisible box is worse than answering the first one. The caller is completed the instant its box is answered — not after the 140 ms fade — so no `await ShowMessageBoxAsync` depends on the dispatcher still pumping; the card lingers in the host only while it fades out, unless the next box in the queue claims the host first.
- **`MessageBoxView` is a view, resolved by `ViewLocator`** like any other, and takes focus on `Loaded` (the primary affirmative, else OK, else itself — an unrealised button cannot take focus). Its Enter/Escape handler is **tunneled**, so the spec's contract wins over "activate whatever has focus". The mock's 26 px title strip above the card is deliberately not drawn: that is window chrome, and this is not a window.
- **Suppression convention** (spec 08 §3): keys are the 16 names in `NotificationKeys` — the spec's twelve `*_msg` keys plus four this app adds — persisted in `app_settings.txt` as `on`/`off` where **`on` means hide**; a missing key or missing file means show. `NotificationKeys` is a *view* of `AppPreferenceCatalog` filtered to suppression polarity, so a key cannot exist without a descriptor, and the catalog's one *display* preference (`advisory_detail`, where `on` means **expand**) is excluded by construction and can never be a `SuppressionKey` (see [settings.md](settings.md)). `VDriveAppPreferencesStore` does **no line parsing of its own**: it holds the session's single `AppSettings`, loaded once through `ISettingsService` and written back through it — so Core's match rule, its read-modify-write merge (unknown/reserved lines survive, the file is created only if absent) and its custom-colour slots are the only implementation. A key outside the catalog is not modeled and is therefore never written. Every I/O failure is swallowed — a preference is never worth breaking a dialog over — though the answer still stands for the rest of the session. A request whose key is hidden returns `MessageBoxOutcome.ForSuppressed(request)` and is never shown — **the short-circuit is this service's policy and nothing above it may re-implement it**: a caller that also reads `IsHidden` gives one user decision two policies. A suppressible confirmation therefore sets `SuppressedResult` to its affirmative, because "never ask me again" means "go ahead". The first and (so far) only production call site is the editor's layer/layout reset ([keyboard-editor.md](keyboard-editor.md)). Reads happen in every mode; only writes are mode-dependent (see the store selection above).
- **Toasts**: `ToastRequest` (message, optional title, `Timeout` default **5 s**, `ToastPosition.BottomRight` default or `Center`, `ToastSeverity.Success` default or `Advisory`). `NotificationOverlay` hosts them in two collections and marshals to the UI thread itself. Each toast fades in and out over the budget's 180 ms and dwells for its own timeout in between ([design-system.md](design-system.md)): `ToastViewModel.IsShown` drives the `.shown` class and is raised on the *next* dispatcher pass, because the view does not exist yet when the request arrives and there would be nothing for the fade to run on.
  - **Severity is a face, not a volume.** Success is green, advisory amber (`StatusAdvisory*`) — **never red**: a failure is a message box the user must answer, never a notice that vanishes after five seconds. Only the dot and the card border change; the card, the shadow and the fade are shared.
  - **A toast can be dismissed early**, with an `×` (`Classes="ghost"` + `IconClose`) beside the message. Both of a toast's timers therefore live in one per-toast `ToastLifetime` in the overlay: an early dismiss **cancels** the pending dwell instead of racing it, so a toast cannot be scheduled for removal twice and a second removal cannot land while a *later* toast is mid-fade. `ToastViewModel.Dismiss` is idempotent and raises `DismissRequested` once. The fade duration is read from `DurationToast` rather than duplicated, with a 180 ms fallback for a host with no application resources.
- **Loading**: `LoadingCaptions.Default` = `Loading…`; `LoadingCaptions.ForDevice(name)` = `Loading <name>…` (U+2026, one character, as everywhere else in the app). `ShowLoading(null)` falls back to the default. **It is blocking**: mockup 1k draws it as "Loading · blocking", so the card sits on the same scrim the message box uses and the app takes no input while it is up. Guards that existed because it did *not* block are kept as second lines of defence — the pedal editor still refuses a mid-save navigation with a toast, because a path that is not a click (a shortcut, a direct caller) must say why rather than appear to do nothing.
- **Modality is geometry, not a flag.** `NotificationOverlay` sits at `Grid.Row="0" Grid.RowSpan="2"` in `MainWindow`, so a modal covers the app bar too — dimmed-but-clickable Home / Settings / Help is not modal — and it is the grid's topmost child, so it draws over the bar rather than under it. Its root is **no longer `IsHitTestVisible="False"`** (two of the three surfaces now take input). Instead: **the scrim is the only full-bleed element in the file, and it is hit-testable only while a message box or the blocking loading card is up**; every other child is alignment-constrained and sizes to its content, and neither the `Panel` nor the `UserControl` above them carries a background. A full-bleed transparent element anywhere in that file would silently swallow every click on the dashboard behind it. Z-order is scrim → modal host → loading → toasts, because a toast is a notice rather than an obstacle. The scrim stays in the tree and fades through `.open` rather than collapsing, so the 140 ms fade has something to run on.

## Dashboard view models — `DashboardViewModel`, `DashboardCardViewModel`, `NoDeviceViewModel`

**The roster is dynamic.** A card exists once its device has been detected **at least once this session**, and stays — as `DeviceCardState.Resting` — when its drive later goes away. `DashboardViewModel` keeps a session-lifetime `HashSet<DeviceId>` of every `ScannedDeviceId` ever seen detected, and each pass renders a card for every snapshot in that set. So the dashboard starts empty (`NoDeviceViewModel` still renders), a device appearing mid-session is a genuine *insertion*, and `Resting` is the state a card **falls to** rather than the state every catalog device is born in (see deviation 10 for why this beats a fixed catalog registry). **That set is accumulated in `Apply`, before the suspend check** — see invariant 10: it is the one thing a parked refresh cannot supersede, and recording it only when a list is applied loses a device that appeared and vanished inside one suspend window.

The header counts differently on purpose: `HeaderSubtitle` is `N of 7 known devices present · list updates itself`, where **7 is catalog-wide** and N is the drives detected *right now*, with `device`/`devices` pluralised on N. **Both come through one predicate**, `DashboardViewModel.IsDashboardDevice` (`device.IsProgrammable`): the denominator counts the catalog through it, the numerator counts snapshots through it, and it also decides whether a detected drive gets a card at all. One predicate rather than two conditions, because the sets are not the same by construction — the scanner walks the whole catalog, and the never-shipped CROSSFIRE keypad is not programmable but *is* detectable (it carries a volume label), so counting by detection alone yields an eighth card with an empty meta line beside a subtitle reading "1 of 7". `FormatSubtitle`, `KnownDeviceCount` and `IsDashboardDevice` are static so the wording and the rule are asserted without standing a dashboard up.

**Two card anatomies under one base.** `DashboardCardViewModel` declares only what every card has — `Key` (the reconciliation identity), `DisplayName`, `MetaLine` — and `Devices` is an `ObservableCollection<DashboardCardViewModel>`: the drive-backed `DeviceCardViewModel`s first, then at most one `WebToolCardViewModel` **pinned strictly last**. A second *type* rather than a fifth card state or a synthetic snapshot, because the Advantage 360 Professional has no `VolumeLabels`: the scanner never yields a status for it, so it can never have a `DeviceSnapshot`, and synthesising one would be a lie in the data (a snapshot means "what the scanner found"). `DeviceCardCount` bounds every reconciliation loop to the device-card region so the trailing card is never a removal candidate and never has to move.

- **`Apply` reconciles in place and never re-sorts.** Cards are keyed by `ScannedDeviceId` and updated through `DeviceCardViewModel.Update` (which returns early on an equal snapshot), so selection and scroll position survive a 2 s refresh. `MergeCards` **appends** a new card at the end of the device-card region and moves nothing that already exists — the old placement-counting `Move` logic is gone. That is what end-insertion requires: the design animates a device appearing mid-session as an insert at the end of the list, and re-sorting into catalog order would shift every card below it instead. The first pass fixes the order, because snapshots arrive in `DeviceCatalog.All` order.
- **`ScanAsync` runs off the UI thread** (`Task.Run(_monitor.Refresh)`; the header's `Scan all` and every card's secondary button are `IAsyncRelayCommand`s): a scan enumerates volumes and reads every present version file, and a stalled mount must not freeze the window. Results return on the UI thread through the monitor's `IUiDispatcher`. Only the startup pass is synchronous, and deliberately so (see the composition root).
- **Refreshes are deferred while the user is inside the card grid.** `SuspendRefresh()`/`ResumeRefresh()` park and release; noticing the pointer or keyboard focus is Avalonia's business, so it lives in `DashboardView.axaml.cs` (invariant 8), which watches `IsPointerOver`/`IsKeyboardFocusWithin` on the `Cards` items control — Avalonia raises both on every ancestor, so the container answers "is the user inside any card" without subscribing per card. While suspended the snapshot list is parked in a single field and **the newest wins — nothing is dropped**, because each list is a complete picture rather than a delta. The one exception is the ever-detected set, which is an *accumulation* and is therefore recorded on the way in rather than on the way out (invariant 10). `Suspend` while suspended is a no-op, so one `Resume` always un-sticks the list. **The scanning flag is deferred with the snapshots**, and for the same reason: it relabels and disables the very button under the pointer. **The view also resumes on detach**, so a dashboard leaving the visual tree with the pointer over a card cannot park the list forever.
- **`HasDevices`/`IsEmpty` count `DeviceCardViewModel` items only** — see invariant 9. The web-tool card is also shown only alongside at least one device card, for the same reason: alone it would fill a dashboard with nothing to configure and hide the empty state behind it.
- `DeviceCardViewModel` renders a **`DeviceCardState`**, not a `VDriveConnectionStatus`: `GetState(status, isScanning)` folds the drive fact together with whether a pass is in flight. `Connected` / `Resting` / `CannotAccess` / `Scanning`. The drive enum was not reused because it is a three-member fact about a drive rather than a card's face, and there is no `WebToolOnly` member because that card is a different type with a different anatomy. `Update`/`IsScanning` raise the derived notifications; `IsScanning` is pushed down from the dashboard rather than subscribed per card.
- **`Resting` maps to `StatusSeverity.Unknown`, not `Error`** (it used to be `Error`, which was exactly the "resting card shows red" defect). A known device whose drive is simply not mounted is not broken. There is **no `.unknown` face anywhere in the status vocabulary** — `Border.statusChip` has none and the card's status line has none — and that **absence is the resting treatment**: mockup `2e`'s "no red, no spinner". The card falls back to `.muted` text and renders no status rail at all. `Scanning` is `Unknown` too; its 3 px indeterminate bar is what reads as motion. Only `Connected` → `Ok` and `CannotAccess` → `Error` paint.
- **Which actions exist follows the drive, not the card state.** Every card carries Configure / secondary / Eject in every state and each keeps its column: a 2 s refresh puts every card through `Scanning`, and a button that appeared, vanished or moved for the duration would shift the layout under the cursor. `PrimaryActionCaption` is `Configure` when `IsDetected` (an unwritable drive still opens its editor, in demo mode) and `Demo Mode` otherwise; a scan never changes it, so it cannot flicker twice a second.
- **The secondary button's caption is now three-valued.** `Retry access` over a mounted-but-unwritable drive (mockup `1b`), `Scanning` — with `CanRunSecondaryAction` false — while the pass it would start is already running, and `Scan for v-Drive` otherwise. It always rescans: spec 10 has a connected card "swap the scan button to 'Check for Updates'", but there is no update check (issue #45), so nothing reroutes `SecondaryActionCommand` in any device or drive state.
- **`ShowsEject`/`CanEject` include `CannotAccess`**, deliberately: `ShowsEject = IsDetected`, and `CanEject = ejectNotifier.IsSupported && IsDetected && Location is not null`. Mockup `1b` puts `⏏ Eject` on the unwritable card, and unmounting is precisely the remedy that card's own explanation names. The button is rendered but merely unusable where the platform cannot eject — one that vanished would move Configure under the cursor. Configure raises `ConfigureRequested` upward; the card never navigates.
- **The per-state explanation** is `RestingExplanationText`, the templated `CannotAccessExplanationTemplate` (whose `{0}` is `DriveName` — the mounted folder name, falling back to the catalog's primary volume label and then the device name), and empty for `Connected`/`Scanning` where the status line says everything.
- **The meta line comes from Core.** `MetaLine` is `DeviceMetaLine.Describe(device)` on both card types, so the view holds **no per-device code** — see [domain-data.md](domain-data.md) for `DeviceFormFactor`, `AccessoryNote` and the composed strings.
- `WebToolCardViewModel` — `Description`, `OpenWebToolCaption`, and an `OpenWebToolCommand` that hands `DeviceDefinition.ConfigurationUrl` to `IUrlLauncher` (disabled when the URL is null). Its device is found by catalog query (`!IsProgrammable && ConfigurationUrl is not null`), not named, so a second such board would be picked up without touching the class. No status, no mount path, nothing to eject or scan for — and no device art at all (see deviation 16).

### The empty state — `NoDeviceViewModel`, `DevicePickerOption`, `ConnectionSteps`

Mockup `1d`: spec 11 §11.8's troubleshoot dialog rebuilt as a teaching screen. A headline and body, then two panels side by side — a picker of all seven programmable boards on the left, the picked board's numbered connection steps on the right — then the live reassurance line, then three actions: `primaryAction` **Launch ‹device› in Demo Mode**, `secondary` **Scan now** (`IconRefresh`; reads `Scanning` and is disabled while a pass is in flight), `link` **Troubleshooting tips** (`IconExternalLink`). **Nothing on it asks the user to press anything to make detection happen** — the 2 s loop is already running and `DashboardViewModel.IsEmpty` drops the whole surface the moment a drive is seen; `Scan now` exists because a user who just plugged something in wants to ask.

- **The picker is a `ListBox`**, not a `ComboBox`: the pick is one-of-N, the rows' faces come from `ItemContainerTheme="{StaticResource SelectableListRow}"`, and the group takes one tab stop with arrow keys inside it. A drop-down hid six of the seven silhouettes behind a click, which is the opposite of what `1d` asks for. `DevicePickerOption` is the row — the definition, the caption (with `" (pedal)"` derived from the form factor, not spelled per device) and the `IsDefault` tag. Order is the **mockup's** (`_pickerOrder`: the two contoured boards, the three Freestyles, the TKO, the pedal), but the rows are still sourced from `DeviceCatalog.All.Where(IsProgrammable)`, so a programmable device the order has never heard of appears at the end rather than vanishing.
- **A null selection is refused, not stored.** A single-selection `ListBox` deselects the selected row when it is Ctrl/Cmd-clicked and the binding writes that through as null, but this screen has no "nothing picked" state — the title, the steps, the demo target and the support link all describe one board. `SelectedOption` keeps the pick and re-raises, and `NoDeviceView.OnDeviceSelectionChanged` posts the row back onto the list (posted, because a `SelectingItemsControl` ignores a selection written from inside its own `SelectionChanged`). `SelectionMode="AlwaysSelected"` is **not** the fix — it re-selects the *first* row, silently moving the pick to the Advantage2.
- **Every device-specific word in the steps comes from `DeviceDefinition`** — `VDriveShortcutHint` for the mount step, `VolumeLabels[0]` for the drive step, `FormFactor` (through `ConnectionSteps.IsPedal`) for keyboard-vs-pedal nouns and for the mount mechanism. There is **no per-device prose and no per-device markup**: a device added to the catalog gets correct steps without touching `ConnectionSteps` or `NoDeviceView`. `ConnectionStep` is deliberately three parts — lead / value / trail — because the middle one is a literal that exists on the hardware or on the drive, and the mono law reserves mono for exactly those; the view draws the three as adjacent `Run`s of one sentence so the type changes mid-line and the whole thing still wraps as prose (the spacing lives inside the strings — `InlineCollection` is whitespace-significant).
- **The step count is data.** `Article(name)` picks `a`/`an` from the written vowel and `FormatStepsTitle` puts the count in the panel title, so the Advantage2 — the one device that gets a Power User Mode step of its own — reads *4 steps* and everything else *3 steps*, and the title can never disagree with the list under it.
- **`RescanText` counts completed detection passes since this screen was built.** `NoDeviceViewModel` captures `DeviceMonitorService.CompletedRefreshCount` as a baseline in its constructor and renders the delta, which is what makes "since you opened this window" true (the dashboard and its empty state are built once, at app start). `DashboardViewModel.OnRefreshActivityChanged` pushes `SetRefreshActivity(isRefreshing, completedRefreshCount)` down — the same push-don't-subscribe rule the cards follow, so this screen adds no second subscription to the loop.

### The shell view model — `MainWindowViewModel`

- `MainWindowViewModel` — `OpenDeviceAsync` follows spec 10's Configure order: **ask the open editor whether it may be closed** → set `IsDemoMode` → `sessions.Begin` → show loading → dispose any open editor, ask `IEditorViewModelFactory.Create(device)` for the new one and swap `CurrentView` → refresh indicator → hide loading → **fire the editor's own `LoadAsync()` and forget it**. (`OpenDevice` is the void wrapper that forgets *that* task, because `DashboardViewModel.ConfigureRequested` is an `Action<DeviceSnapshot>` with nowhere to await one.) **The editor choice lives in the factory and nowhere else**: `DeviceId.SavantElite2` → `SavantElitePedalViewModel(device, pedalFiles, capture, notifications)` ([savant-elite.md](savant-elite.md)), a device both `GeometryCatalog` and `VisualCatalog` resolve → `KeyboardEditorViewModel` ([keyboard-editor.md](keyboard-editor.md)), everything else → `EditorPlaceholderViewModel`. `Editor` is typed `DeviceEditorViewModel?` — the abstract base holding `Device`/`DeviceName`/`IsDemoMode` plus the virtual `LoadAsync()` and `ConfirmCloseAsync()`, which is all the shell ever reads — so the shell never learns which editor a device resolved to. `LoadAsync` is the seam for post-swap work: the default does nothing (the placeholder reads nothing), and both real editors override it to read the drive against their own `IsLoading` rather than under the shell's splash; it is total and idempotent, which is what makes forgetting the task safe. **`ConfirmCloseAsync` is the unsaved-work gate**, awaited before `CloseEditor()` on **both** exits — Home and opening another device — with `false` aborting the navigation and leaving the editor exactly where it was (no session begun, nothing ejected). The default returns true, so only the pedal editor uses it today; like `LoadAsync` it must be total, because the shell awaits it inside a command. `CloseEditor()` disposes the outgoing editor on both paths, because an editor may hold the app-wide capture service and would otherwise keep swallowing the dashboard's keystrokes; it drops the reference in a `finally`, so an editor whose `Dispose` throws is still gone rather than left behind a Home button pointing at it. **Hiding the loading splash is in a `finally`**, so a failure while an editor is built cannot leave the shell wedged behind an overlay with no editor and a disabled Home button. **`OpenDeviceAsync` is itself total**, for the same reason `LoadAsync` is: the void wrapper forgets the task, so a throw from the session manager or an editor's constructor would otherwise be an unobserved exception leaving the shell on the dashboard with a session open, `IsDemoMode` already flipped and nothing said. Instead the half-done navigation is undone (`sessions.End()`, `CloseEditor()`, dashboard back, demo mode cleared, indicator recomputed) and the failure is shown as an `Open Device` error box — best effort, since a box that cannot be shown must not re-throw out of the method whose contract is that it never throws. Two boundaries make that totality real rather than nominal: **the confirmation runs outside the undo region** (`ConfirmOpenAsync` guards the null check and `ConfirmCloseAsync` itself, reporting a failure and answering "no"), because treating a failed *question* as a failed *open* would drop the editor and discard the unsaved changes the question exists to protect; and **`AbandonOpenDevice` guards every step of its own** — it runs inside the `catch` with the error box still to come, and `CloseEditor()` → an editor's `Dispose()` → the capture service is a real throw path. **Polling is untouched in both directions.** `HomeCommand` (a *navigation*: runnable whenever `!IsBusy`, and a no-op inside `GoHomeAsync` when no editor is open — invariant 11) ends the session, returns to the dashboard, and **ejects only when the session was not demo mode and had a `Location`**. `IsBusy` guards re-entrancy for *both* navigations now — each may put a modal question on screen and Home awaits the eject, so without it a second Configure could open a session underneath the first one's continuation. Every refresh calls `sessions.UpdateActive` then re-evaluates the indicator: the open session's `Health`, or — on the dashboard — `Unknown` → `Demo Mode` until the first pass completes, then `Ok` if any device is `Connected` with `Health == Ok` and `Error` otherwise (see the status-chip rule above).
- **`WindowTitle` lives on `MainWindowViewModel`**, built by the static `BuildWindowTitle(deviceName, isDemoMode)`: `KinesisEdit` on the dashboard, `‹Device› — KinesisEdit` while editing, `‹Device› (Demo) — KinesisEdit` in demo mode. It is re-raised from both `Editor` and `IsDemoMode`. This is editor *chrome* and so overlaps issue #90, but the binding is `MainWindow.axaml`'s `Title` — this layer's own file — so it is implemented here (deviation 15).
- **`LastRefreshedText` is the app bar's `refreshed 0.4s ago` readout**, `FormatLastRefreshed(monitor.LastRefreshedUtc, clock.UtcNow)` — one decimal, invariant culture, **empty (and `HasLastRefreshed` false) until the first pass completes**, since a zero would claim a scan that never happened; a timestamp in the future reads `0.0s` rather than negative. It is aged by a **`System.Threading.Timer` marshaled through `IUiDispatcher`, not a `DispatcherTimer`** — a `DispatcherTimer` would put Avalonia inside a view model (invariant 8) — at **200 ms**, not the 100 ms one decimal could justify: at 5 Hz the tenths digit steps by an even 2 and costs half the property traffic. `PropertyChanged` is raised **only when the formatted string actually changed**, so a still readout costs nothing, and `RefreshActivityChanged` re-reads it immediately so a completed pass snaps to `0.0s` instead of waiting for a tick. Disposed with the shell.
- `SettingsCommand`/`HelpCommand` are **permanently disabled** (`CanExecute` → false) rather than silently no-oping; `SettingsRequested`/`HelpRequested` remain as unconsumed hooks for the app-settings and help dialogs. All three top-bar buttons are now `Classes="navPill"`, with `.selected` bound to `IsHomeSelected` (`!IsEditorOpen`) — Home is the only one with a location to be at, and its command stays runnable there so the selected face is reachable at all (invariant 11). See deviation 17 for Settings' and Help's disabled face.

Recorded deviations — each is intentional, do not "restore" the spec literal:

1. **The Savant Elite 2's mount step is a slide switch, not `Program + F1`.** Its catalog hint and `specs/12-savant-elite.md` §3 both quote that combination, but it is the same legacy copy-paste artefact §11.8 carries — the device has no keyboard. §1 of that spec documents the real mechanism, a physical switch between play mode and programming mode, and §3's own remedy for a drive that does not appear (replug the pedal) is carried as the sentence's second half. **User-approved decision.**
2. **The v-Drive shortcut in the mount step is templated from `DeviceDefinition.VDriveShortcutHint`**, not hard-coded — spec 11 §11.8's RGB/TKO row quotes `+ F8` for both, but the TKO's real shortcut is `SmartSet + Right Shift + V` (spec 03 §1). The spec's inline SmartSet-key images are rendered as text.
3. **Only the Advantage2 gets a Power User Mode step**; every other device goes straight to its mount shortcut. Spec 11 §11.8's first row is the mode's only mention anywhere in `specs/`, and it lumps four devices together while being wrong about three of them: the FS Edge and FS Pro have no such mode and simply open their v-Drive with `SmartSet + F8`, and the Savant Elite 2 is a three-button foot pedal that can no more be sent `Program + Shift + Esc` than the `Program + F1` the same row prescribes — which deviation 2 already rejects for exactly that reason. `specs/12-savant-elite.md` never mentions Power User Mode at all. Telling a user to press keys their hardware does not have is the one failure this panel exists to prevent, so the preamble stays on the Advantage2. A departure from the row's grouping, not from its wording.
4. **The Advantage2 therefore renders 4 steps where mockup `1d` draws 3.** Power User Mode is its own numbered action rather than a clause hidden inside the mount step, because a step that says "do this, and first do that" is two instructions wearing one number. The count in the panel title is data, so the panel stays self-consistent either way.
5. **Step 2 reads `press ‹combination›` where the mock writes "hold Progrm and tap F1".** One mono slot per step keeps the combination whole — and lets every device template its step from the catalog instead of carrying prose of its own.
6. **§11.8's instruction *paragraph* is gone.** The panel draws `1d`'s numbered steps instead; the paragraph's own wording (including `Please connect the v-Drive and then click the "Scan for v-Drive" button below.`, which used to complete the spec's elided rows) is no longer rendered anywhere. Deviations 2 and 3 survive it unchanged, now expressed as steps.
7. **`Loading <DeviceName>…` is not a spec string** — spec 11 §11.9 quotes only the default, and quotes it as `Loading...`; the one-character ellipsis is mockup 1k's and the per-device form is this app's.
8. **The eject-failure dialog title `Eject` is unspecified** — spec 10 quotes the message only.
9. **Eject is gated on `IDeviceEjectService.IsSupported`, never on an OS check.** The legacy apps hid eject on macOS; the issue #6 decision implements macOS `diskutil unmount`, so a platform gains the button the moment its ejector exists.
10. **The dashboard has no fixed device registry; the roster is dynamic.** The legacy dashboards carried exactly two cards including `Coming Soon` placeholders. This app serves the whole catalog, and shows **devices detected at least once this session** — a card appears the first time its drive is seen and stays, `Resting`, when the drive goes away. A fixed registry (one card per programmable catalog device, always) was considered and rejected: mockup `2b`'s *"a newly detected device animates in at the end of the list"* can never fire under it, because every known device would already have a card and a device appearing would go `Resting` → `Connected` **in place**, leaving the insert animation as dead code. The header's `N of 7 known devices present` is what carries the catalog-wide count instead, so nothing is lost by not rendering the absent six. Consequence to keep in mind: the empty state is reachable only *before* the first detection, never after one.
11. **Toast placement is window-relative**, not primary-monitor-relative (single-window app).
12. **Home does not "resume the detection loop"** (spec 10 "Home") — there is nothing to resume, because Configure never suspended it.
13. **No `Cancel` button in the `Scanning` state**, against mockup `2e`. `DeviceMonitorService.Refresh()` has no cancellation token and `VDriveMonitor.Poll()` discards overlapping polls, so a Cancel button would name work it cannot stop — worse than not offering it. The state stays purely visual: status line, spinner mark and the 3 px indeterminate bar, with the buttons holding their positions. Real cancellation would change invariant 5 and belongs in its own issue.
14. **The card keeps the pinned spec literal `Not Detected`**, not mockup `1b`'s `Pedal not detected`, on every device including the SE2 — the card's status line names a *drive* state and reads identically across the seven boards. Unrelated and unchanged: the §11.8 **empty state** still says `Pedal not detected` for the SE2 (spec 12 §3).
15. **`WindowTitle` is implemented here, not in issue #90** (editor shell chrome), because the binding is `MainWindow.axaml`'s `Title` — this layer's own file. #90 may restyle the bar; the title string is already correct.
16. **The Advantage 360 Professional's web-tool card draws no device art at all** — not a frame hidden by the `IsNotNull` converter, the way `DeviceCardView` hides its own. `WebToolCardViewModel` exposes no `DeviceId` to convert, and `Themes/DeviceArt.axaml` has no drawing for the Pro; the design's rule is that a thing the app cannot show is not rendered, so there is no frame to hide.
17. **`NavPill`'s disabled face is `BaseButton`'s inset one**, so the permanently disabled Settings and Help read as recessed pills rather than the mock's bare `TextDisabled` text. Logged as a known gap in [design-system.md](design-system.md) with a test row pinning it — do not re-litigate it here; flipping it is a design decision, not a style tweak.
18. **Nothing detected reads `v-Drive Error`, not `Demo Mode`.** Mockup `1a`'s status vocabulary defines v-Drive Error as "gone · unwritable" and `1d` draws the chip that way beside the empty state; `Demo Mode` is reserved for a session that writes nothing. The pre-first-scan instant deliberately keeps the `Demo` face — see the status-chip rule above. **User-approved decision.**
19. **The message box is an in-app overlay, not an OS window.** Mockup `1k` specifies a 140 ms fade over a 62 % scrim with `ShadowModal`, none of which a separate `Window` can carry, and the queue and the capture suspension both need one host. `MessageBoxWindow` and `DialogWindowHost` are deleted; `App.FindOwnerWindow` stays, for the two file pickers. **User-approved decision.**
20. **The device picker does not set `SelectionMode="AlwaysSelected"`.** It snaps to row 0, so a Ctrl/Cmd-click on the selected row would silently move the user's pick to the Advantage2. The view model refuses a null and the view restores the row instead — see the empty-state section.
21. **The picker draws silhouettes at a 0.6 px pen**, against the icon law's 1.5. `handoff.md:123` asks for the silhouettes (mockup `1d` itself lists the seven by name only) and at `Size="33"` a 1.5 pen welds the key rects into a slab. Both halves were already recorded in [design-system.md](design-system.md)'s icon deviations as hypotheticals; this screen is their first real call site, and they are now live.

## Load-bearing invariants

1. **Home ejects only when not in demo mode** (spec 10 "Home"; 03 §3.5). Demo mode never touched the drive, so there is nothing to flush — and `Location` may be a read-only mount.
2. **Demo mode = not connected *or* not writable.** A `Cannot Access` card opens the editor in demo mode. Do not narrow it to "not detected".
3. **Suppression is per-v-Drive and never *written* in demo mode** (spec 08 §3 "Never saved in demo mode"). `app_settings.txt` lives on the device, so preferences follow the keyboard; a demo session over a present drive still *reads* them through `ReadOnlyAppPreferencesStore`. `on` = hide is the polarity — inverting it silently hides every dialog.
4. **Cards and sessions are keyed by `ScannedDeviceId`, never by the resolved `DeviceId`.** Freestyle resolution is many-to-one, so two attached Freestyle drives can resolve to one definition; keying on the resolved id previously crashed the card merge. The resolved device is for display only.
5. **The detection loop runs for the app's whole lifetime.** Do not "optimize" it by stopping it while an editor is open: the editor's `v-Drive OK` / `v-Drive Error` indicator is exactly that per-tick re-verification (spec 10), and `DeviceSession.Device` is re-pointed from it every pass.
6. **View models expose enums and strings, never Avalonia brushes.** `StatusSeverity`/`MessageBoxIcon` reach XAML through `EnumMatchConverter` as style classes so the view models stay testable without a UI toolkit *and* so `DynamicResource` re-resolves the palette when the OS theme flips at runtime.
7. **Monitor events arrive off the UI thread and must be marshaled.** Anything new that subscribes to `DeviceMonitorService.Updated` inherits the `IUiDispatcher` guarantee; anything that subscribes to `VDriveMonitor` directly does not.
8. **Services and view models stay toolkit-free.** Only `App`, `Views/`, `Controls/`, `Themes/`, `Styles/`, `Converters/`, `Input/`, and the bridging services `AvaloniaUiDispatcher`, `AvaloniaFolderPickerService`, `AvaloniaFilePickerService`, `StorageProviderHost` and `MotionResourceBinder` reference Avalonia (`MessageBoxPresenter` used to and no longer does — its window became a view); `KinesisEdit.Tests` exercises everything else without starting a UI runtime, and covers the UI itself in separate headless suites that boot the real `App` with no display ([design-system.md](design-system.md)). Each bridging service stays as thin as the platform allows — the pickers' decoding rules live in the toolkit-free `PickedFileReader` for exactly that reason. This is why `ISystemClock` and the plain `System.Threading.Timer` exist where a `DispatcherTimer` would have been shorter, and why the dashboard's refresh deferral is split: the *rule* is `SuspendRefresh`/`ResumeRefresh` on the view model, the *pointer and focus detection* is `DashboardView.axaml.cs`.
9. **`HasDevices`/`IsEmpty` count `DeviceCardViewModel` items only.** The web-tool card is in the same collection and must never be counted: it exists whenever any device card does, so counting it would make `HasDevices` permanently true and `NoDeviceViewModel`'s empty state (issue #89) unreachable forever. Any new card kind added to `Devices` inherits this rule.
10. **A parked refresh is never dropped, only superseded — except for what accumulates.** `SuspendRefresh` parks the *latest* snapshot list, not a queue: each list is a complete picture of every device, so the newest one subsumes the ones before it. Do not "fix" this into a queue that replays intermediate states, and do not make a suspend path that discards instead of parking — a card would then be showing a drive state the user never had a chance to see change. **"Detected at least once this session" is the exception, because it is an accumulation rather than a picture**: a newer list does not subsume its predecessors for it. A drive plugged in and pulled out again entirely inside one suspend window is detected only in lists that are never applied, so `Apply` records the ever-seen set *before* the suspend check. Anything else derived by accumulation rather than by reading the newest list belongs on the same side of that check.
11. **The Home nav pill's command may not be gated on an editor being open.** `IsHomeSelected` is `!IsEditorOpen` and `NavPill`'s selected face is written `.selected:not(:disabled)`, so gating `HomeCommand` on `IsEditorOpen` disables the pill in exactly the state it is selected: the face is unreachable and the dashboard renders Home identically to the permanently-disabled Settings and Help. Home is a *navigation* — runnable everywhere, a no-op inside `GoHomeAsync` when there is no editor to leave. See [design-system.md](design-system.md)'s deviation table.
12. **Exactly one 46 px bar is on screen.** `ProvidesOwnChrome` and `IsShellChromeVisible` are the whole mechanism, and the second is derived from the first rather than set by a navigation path. An editor that starts drawing its own bar sets `ProvidesOwnChrome`; nothing else may put a second status pill on screen.
13. **An editor reaches the shell through `IShellChrome`, as data.** Never up the visual tree: the editor views are rendered standalone in every headless scene, which is also where the screen is verified by frame. The shell hands it over on open and takes it back on close.
14. **A message box suspends keystroke capture, centrally, and releases only what it took.** The box shares the shell's `TopLevel`, so a live capture would swallow its Enter and Escape and assign them to whatever is recording. `MessageBoxPresenter` is the one place that brackets it — never a call site — the count is by depth because boxes queue, and a suspension somebody else already holds (a text-entry feature panel) is left alone.
15. **The scrim is the only full-bleed element in the notification overlay, and it is hit-testable only while something blocks.** The overlay's root is not `IsHitTestVisible="False"` any more, so any other full-bleed child added to that file would silently swallow every click on the screen behind it.

## Deliberately not here

- **No card startup-profile line** (`Profile <n>`, Adv2 `Layout <name>`, spec 10 "Detection loop") — needs the settings engine, issue #10.
- **No first-run Intro dialog, Adv360 startup firmware-age check, or TKO macro-firmware startup warning** (specs 11 §11.9, 10 "Detection loop", 09 §2, §4) — the `NotificationKeys` and gate data they need already exist, but nothing in *this* layer passes a `SuppressionKey` yet. The one production call site anywhere is the editor's layer/layout reset confirmation under `NotificationKeys.ResetLayer` ([keyboard-editor.md](keyboard-editor.md)), which is what proves the pipeline end to end; the shell's own unsaved-changes prompt is issue [#52](https://github.com/migus88/kinesis-edit/issues/52). The shell's Settings and Help buttons stay disabled until their own dialogs exist; the editor's Settings **tab** is unrelated to them (it edits the *device's* settings file — [keyboard-editor.md](keyboard-editor.md)).
- **No update check at all** (issue #45) — nothing compares local versions against the vendor's published-versions endpoint, and there is no update dialog, no `update.upd` hands-free flow and no app self-update; spec 09 §3–§4 describes those for the legacy app only. The card's second button only rescans, and the app makes no HTTP request of any kind.
- **No `Watch Tutorial` button** — neither the specs nor the device catalog contain tutorial URLs.
- **No cancellable scan.** `IsRefreshing` is a display fact and nothing in this layer can stop a pass in flight; the `Scanning` card state therefore has no `Cancel` (deviation 13). Adding one means giving `Refresh()` a cancellation token and teaching `VDriveMonitor.Poll()` to be interrupted — its own issue, and it moves invariant 5.
- **No global notification switches — permanently, not pending.** Spec 08 §4 / spec 10 gate display additionally on registry-backed `ShowAllNotifs`/`HideAllNotifs`; the epic ([#1](https://github.com/migus88/kinesis-edit/issues/1)) lists "Windows-registry notification globals" as out of scope, so the display rule here reduces to "shown unless hidden". Do not add them to a later issue's scope.
- **No keystroke capture in the shell** (spec 10 "Keyboard-input capture") — it lives in `KinesisEdit.Core.Input` + `KinesisEdit.Input` ([keystroke-capture.md](keystroke-capture.md)); the shell only *builds* it (lazily, over its own window) and hands it to the editor factory. Nothing in this layer starts, stops or consumes capture — that is the editor's ([keyboard-editor.md](keyboard-editor.md)).
- **No `Keyboard Connection Lost` dialog** (03 §3.5) — it is save/load-time behavior, owned by the editor issues. The transition is already surfaced as `DeviceMonitorUpdate.HasConnectionLoss`, and a mid-session loss does flip the indicator to `v-Drive Error`; only the dialog is missing.
- **No editor content, and no knowledge of which device has one.** The keyboard picture, the remap workflow, the macro panel, the lighting tab and the settings panel are their own module ([keyboard-editor.md](keyboard-editor.md)), the spec 11 panels a second ([feature-dialogs.md](feature-dialogs.md)), and the SE2's pedal editor a third ([savant-elite.md](savant-elite.md)); `EditorPlaceholderViewModel`/`View` remain the stand-in for every device with neither — every board but the Freestyle Edge RGB, whose picture is the only one authored (issues #39–#42). Settings is capability-driven, so every board picks it up as its picture lands; lighting is RGB-only until the TKO and Advantage360 pictures unblock their own editors (#40/#41). This layer only routes through `IEditorViewModelFactory` and asks `ConfirmCloseAsync` before it swaps an editor out.
- **No editor dialogs of its own.** The spec 11 feature panels render *inside* the editor view over their own scrim; this layer supplies only the message box, the toast, the loading indicator and the two file pickers they use. Since the box became an overlay the two are the same *kind* of surface — but they are hosted separately, the editor's by `EditorOverlayHost` and the shell's by `NotificationOverlay`, and a box raised from a feature panel therefore draws over it.
- **No second window of any kind.** The app has exactly one `Window` (plus the `--keystroke-spike` harness): the message box is a view, and the only remaining owner-window lookup exists for the platform file pickers.
