# App shell and device dashboard (Services, ViewModels, Views)

The Avalonia layer of `KinesisEdit`: one window that swaps between a device dashboard and a per-device editor, the app-side detection service that turns `KinesisEdit.Core.VDrive` scans into renderable snapshots (**on demand only** — nothing polls), and the notification primitives (message box, toast, loading indicator) every later dialog reuses. It owns no domain knowledge — device facts come from `DeviceCatalog` ([domain-data.md](domain-data.md)), discovery/IO/eject from [vdrive.md](vdrive.md), version parsing and gates from [firmware.md](firmware.md) — and it owns no editor: the editor slot is filled by whatever `IEditorViewModelFactory` returns — the keyboard editor ([keyboard-editor.md](keyboard-editor.md)), the Savant Elite2's pedal editor ([savant-elite.md](savant-elite.md)), or `EditorPlaceholderViewModel` for every device that has neither yet. There is **no DI container**: `App.axaml.cs` is the composition root and every dependency is a constructor parameter.

## Composition root — `App`

`BuildServices` wires by hand, in this order: `DemoVDriveFileService(new VDriveFileService())` → `VDriveMonitor(new VDriveScanner(PlatformVolumeEnumerator.Create()))` → `DeviceMonitorService(monitor, fileService, dispatcher)` → `SettingsServiceAdapter(new SettingsService(fileService))` → `DeviceSessionManager(settings)` → `MessageBoxPresenter(FindMessageBoxHost, () => _captureService)` → `NotificationService(presenter, sessions)` → `VDriveEjectNotifier(new DeviceEjectService(VDriveEject.CreateForCurrentPlatform()), notifications)` — handed to `DashboardViewModel` **and to nothing else**, since Home stopped ejecting — → `ProcessUrlLauncher` → `PedalFileService(fileService)` → `EditorViewModelFactory(new ProfileSessionFactory(fileService), settings, ResolveCaptureService, notifications, pedalFiles, new AvaloniaFolderPickerService(FindOwnerWindow), new AvaloniaFilePickerService(FindOwnerWindow), fileService, urlLauncher, sessions)` → `SettingsScreenViewModel(preferences, applyTheme, applyMotion)` → `HelpScreenViewModel(urlLauncher)` → `DashboardViewModel` → `MainWindowViewModel(…, settingsScreen, helpScreen)`. Then `desktop.MainWindow = new MainWindow(shell, notifications, preferences)` and **one `DeviceMonitorService.Refresh()` last** — everything a scan can raise is reached through that window: the message box on its notification overlay, both file pickers on its storage provider. Each is therefore resolved through a callback (`Func<IMessageBoxPresenter?>`, `Func<Window?>`) rather than held as a reference. `desktop.Exit` disposes shell, dashboard, monitor, and — **last, after the shell has closed and disposed the open editor** — the keystroke capture service.

- **The demo decorator is *the* file service for the whole app, not a demo-only one.** `DemoVDriveFileService` wraps the real `VDriveFileService` once, at the root, and every consumer below it — the detection service's version re-reads, the settings service, the pedal file service, the editor factory's Export/Import, and `ProfileSessionFactory` — gets that one instance. It delegates every path outside `kinesis-edit://demo/` untouched, so live hardware is unaffected; what it buys is that a demo session's profile load resolves against the embedded fixtures instead of failing on a path the real service cannot open. **Handing it to `ProfileSessionFactory` is the whole of what makes demo mode a populated editor** (see "The demo v-Drive"); `IDemoDeviceProvider` needs no wiring at all, because `DeviceSnapshot.CreateDemo` defaults to the real provider.
- **Host preferences are read and applied before any window exists**, inside the desktop-lifetime branch and *ahead* of `BuildServices`: `JsonHostPreferencesStore(HostPreferencesPathProvider.CreateForCurrentPlatform())`, then `ThemeApplier.Apply(this, stored.Theme)` and `MotionPreferenceApplier.Apply(this, motionSettings, stored.Motion)` — the second replacing the bare `MotionResourceBinder.Apply` for the app, so the first frame is already wearing both. The bare bind stays outside the branch for a session that has no desktop lifetime and therefore no user behind it: **the headless test harness boots this same `App`**, and it must never read or apply the developer's own preferences file. This is the only place in the app that names the real per-user location ([host-preferences.md](host-preferences.md) invariant 2) and the only object holding an `Application`, which is why `SettingsScreenViewModel` gets its two appliers as delegates closed over here rather than calling them itself (invariant 8).

- **The keystroke capture service is built lazily, over the shell window.** `AvaloniaKeystrokeCaptureService` previews the key events of one `TopLevel` ([keystroke-capture.md](keystroke-capture.md)) and that window does not exist while the graph above is wired, so the editor factory takes a `Func<IKeystrokeCaptureService>` and `App.ResolveCaptureService` creates the single instance on first use — the same ordering problem the message-box presenter solves with its `Func<IMessageBoxPresenter?>` host. This is also what breaks the shell ↔ capture cycle; by the time a device is opened, the window is on screen. The presenter is handed `() => _captureService` — the **field**, not `ResolveCaptureService` — because a box raised before any editor has opened has nothing to suspend, and building a capture service in order to answer a dialog would be backwards.
- **Every editor's dependencies live in the factory, not in the shell.** `PedalFileService` and `ISettingsService` are stateless and one instance of each serves every session; they are handed to `EditorViewModelFactory` rather than to `MainWindowViewModel`, because the shell would otherwise accumulate one constructor parameter per device as editors are added. The keyboard editor's feature panels add four more to the same place — the two pickers, the file service, and the URL launcher the firmware-gate refusals use ([feature-dialogs.md](feature-dialogs.md)) — and the **`IDeviceSessionAccessor`** a fifth, which is how an editor reaches the open device's `app_settings.txt` (`Active?.Preferences`). It is passed last and is *optional* on both the factory and `KeyboardEditorViewModel`: a design scene or a unit test builds an editor with no session at all, and every preference then sits at its default. The shell opens the session before it asks the factory for an editor (spec 10's Configure order below), so in the running app `Active` is always the device being edited.
- **One `ISettingsService` for the whole app.** `SettingsServiceAdapter` ([settings.md](settings.md)) is built once and shared by `DeviceSessionManager` (whose suppression stores read and write `app_settings.txt`) and the editor factory (whose Settings tab writes the keyboard-settings file). `app_settings.txt` must have exactly one reader and one writer: a second, line-based implementation would clobber the twelve `cust_color_N` picker slots Core writes into the same file.
- **One `AvaloniaUiDispatcher` for the whole shell.** A scan runs off the UI thread, so both of the detection service's events are marshaled back onto it through that one dispatcher (invariant 7). **Nothing in the app measures elapsed wall-clock time**, so there is no clock service in `Services/` at all — the `ISystemClock` seam existed only for the readout that aged against it (deviation 24) and went with it. A future elapsed-time surface should reintroduce that seam rather than reach for `DateTimeOffset.UtcNow` directly (invariant 8).
- **Both file pickers defer their owner window** through `Func<Window?>` (`App.FindOwnerWindow`): a picker reaches the platform dialog through `TopLevel.StorageProvider`, and no window exists while the graph is wired. They are the only remaining users of that resolver — the message box is no longer a window and needs no owner — and it still scans `desktop.Windows` **newest-first** for an active one, falling back to the last entry and then to `MainWindow`, so a picker raised from a dialog is not parented to a window that dialog blocks. `StorageProviderHost` is the single resolution point they share, and **no owner is reported to the caller as a cancel** — an export or import simply does not happen rather than throwing from a service.

- **The message box is not a window.** `App.FindMessageBoxHost` returns `(desktop.MainWindow as MainWindow)?.MessageBoxHost` — the shell's `NotificationOverlay`, which implements `IMessageBoxPresenter` itself — and `MessageBoxPresenter` is a lazy forwarder onto it. `DialogWindowHost` and `MessageBoxWindow` are **deleted**; see "Notifications" for the whole surface.

- **The composition root runs the app's one unattended scan, and there is no second one.** `Refresh()` is called once, after the window exists, and **deliberately synchronously** (unlike every later scan): `DashboardViewModel` is constructed before the window, so the cards must exist before the first frame or the "Keyboard not detected" panel flashes on every launch. Every scan after it has a user behind it — the dashboard header's `Scan all`, a `Cannot Access` card's `Retry access`, or the empty state's `Scan now` — and all three route to the same `Refresh()`. Nothing arms a timer; see deviation 25.
- **One window, swapped views.** `MainWindowViewModel.CurrentView` is the dashboard or the open editor; `MainWindow.axaml` binds it to a `ContentControl` and `ViewLocator` (registered in `App.axaml`'s `DataTemplates`, matching any `ViewModelBase`) maps `KinesisEdit.ViewModels.XxxViewModel` → `KinesisEdit.Views.XxxView` in the same assembly, falling back to a diagnostic `TextBlock`. `MainWindowViewModel` is deliberately *not* resolvable this way (no `MainWindowView`) — the root window is constructed by hand.
- **Native chrome, remembered geometry, and a theme the user may pin.** Resizable 1000×680 window (min 720×480) with the platform title bar and a fixed 46-high in-window top bar carrying Home / Settings / Help plus the status chip. `App.axaml` still declares `RequestedThemeVariant="Default"` + `FluentTheme`, so the OS light/dark variant wins **unless the stored host preference says otherwise** — `ThemeApplier` assigns the variant before the first frame and the Settings screen may move it live ([host-preferences.md](host-preferences.md)). Every colour is a role token resolved by `DynamicResource` from the design system ([design-system.md](design-system.md)), which is what makes that live flip re-resolve the whole palette; the base Fluent controls are re-pointed at the same palette by `Themes/Controls.axaml`. The legacy borderless chrome and fixed 1550×850 size are dropped (macOS-first).
- **The status indicator is a chip, not coloured text.** `Views/StatusChipView` — `Border.statusChip` takes `.ok`/`.error`/`.demo`/`.warning` from `StatusIndicatorSeverity`; its fill and border cross-fade over 220 ms when a scan changes its mind, while the text inside swaps instantly. The four states are fixed and never share a meaning — green connected and writable, red gone or unwritable, **purple demo mode**, amber an advisory that never blocks. Demo mode is `StatusSeverity.Demo`, deliberately not `Warning`: amber is the only warning colour in the app.
- **On the dashboard, a completed scan that found nothing reads `v-Drive Error`, not `Demo Mode`.** `GetDashboardHealth` returns `Ok` as soon as one device is `Connected` with `Health == Ok`, and `Error` for everything else a *finished* pass can report — mockup `1a` defines v-Drive Error as "gone · unwritable", and a drive that is absent is gone. **Before the first pass completes it stays `Unknown` → `Demo Mode`**, and "no pass has completed" is now read as `_monitor.Snapshots.Count == 0`: a completed pass publishes one snapshot per detectable catalog device whether or not it found anything, so an empty list can only mean nobody has looked. ("Gone" is a finding, and before the first scan there is none.) In the shipped app that state is never on screen, because the startup scan is synchronous. `Demo Mode` means only what it says — an open demo session, reported by the session branch above it.

### The chrome hand-off — `ProvidesOwnChrome`, `IsShellChromeVisible`, `IShellChrome`

The mockups draw **exactly one 46 px bar while editing** (`1e`, `1f`, `2d`), carrying `Home`, the device name, the drive path, `Save` *and* the v-Drive chip — the same things this bar carries. So an editor that has been rebuilt on the redesign draws the whole bar itself and the shell **hides its own**:

- `DeviceEditorViewModel.ProvidesOwnChrome` — virtual `false`, overridden `true` on `KeyboardEditorViewModel` only. The Savant Elite2 pedal editor keeps the shell bar until issue [#53](https://github.com/migus88/kinesis-edit/issues/53); the placeholder always keeps it.
- `MainWindowViewModel.IsShellChromeVisible` — `_editor?.ProvidesOwnChrome != true`, bound to the app bar's `IsVisible`. Re-raised from the `Editor` setter, so it moves in **both** directions with one line and no navigation path can forget it.
- `IShellChrome : INotifyPropertyChanged` — `IAsyncRelayCommand HomeCommand`, `string StatusIndicatorText`, `StatusSeverity StatusIndicatorSeverity`. `MainWindowViewModel` implements it; `DeviceEditorViewModel.Shell` holds it. `OpenDeviceAsync` assigns it **before** the view swap, so the first frame already has its bindings; `CloseEditor` clears it in the `finally`, even when the disposal threw.

**Why an interface and not a `$parent[MainWindow]` binding.** Every headless suite renders an editor view standalone in `ThemedHost`, so a visual-tree lookup for the window's `DataContext` resolves to nothing: Home and the status pill would come out blank in the tests *and* in the frames used to verify the screen. A view must get its data from its own `DataContext`.

**`Views/StatusChipView`** is the chip, extracted because two surfaces draw it — this bar and the editor's toolbar (only ever one at a time). Its `x:DataType` is `IShellChrome`, so the shell binds it to itself and the editor binds it to `Shell`. Copying the markup instead would leave four bound classes on the border and four on the label to drift in two places.
- **MVVM** is `CommunityToolkit.Mvvm` (`ObservableObject` via `ViewModelBase`, `RelayCommand`/`AsyncRelayCommand`), compiled bindings on.
- **One escape hatch.** With `--keystroke-spike` in `desktop.Args` (`dotnet run --project src/KinesisEdit -- --keystroke-spike`) the root skips the whole graph and shows `Views/KeystrokeCaptureSpikeWindow` — the issue-#12 capture harness kept for hand-verification ([keystroke-capture.md](keystroke-capture.md)); no services are built and nothing ever scans.

## Device detection — `DeviceMonitorService`

Owns the `VDriveMonitor` (and disposes it). `Refresh()` = one `VDriveMonitor.Poll()`, then for every device with a `Location` **re-read and re-parse the version file**, producing an immutable `DeviceSnapshot` per tracked device in `DeviceCatalog.All` order, plus that poll's `VDriveStatusChange` list, published as one `DeviceMonitorUpdate`.

**`Refresh()` is the whole surface. There is no timer, no `Start`/`Stop`, and no `IsPolling`** — a scan happens because something asked for one, which is the composition root once at launch and the user thereafter (deviation 25). Nothing in the app may say, imply or draw that the list keeps itself up to date, because it does not.

- **Detection is never suspended for an editing session; it is simply not automatic.** Spec 10 drives the open editor's `v-Drive OK` / `v-Drive Error` indicator off a per-tick re-verification of the version file; here it is re-verified on every scan, and one detection service still serves both the dashboard and the editor. `DeviceSession.Device` is re-pointed from every pass exactly as before — there are simply fewer passes, and each has a cause.
- **`Refresh()` coalesces rather than dropping.** A call arriving while another refresh runs marks the running one to *repeat* and returns; the repeat happens under the same gate. Concurrency is not an option because `VDriveMonitor.Poll()` discards an overlapping poll outright, which would silently turn a second scan landing on a running one into a no-op. Pending `VDriveStatusChange`s are copied, published, and only the published count removed afterwards, so a change the monitor raises mid-publish survives to the next pass instead of vanishing (this is what keeps `IsConnectionLost` reliable).
- **The gate lives in `RefreshActivity`**, a small collaborator, so the service stays a detection service instead of also being a state machine. It owns the repeat gate (`TryBegin`/`TryRepeat`/`End`) and the one fact the UI renders from it — `IsRefreshing`, which is the cards' `Scanning` state and the two scan buttons' `Scanning` caption. It records **nothing about past passes**: no timestamp and no count, because the two surfaces that read them (the app bar's readout, the empty state's rescan line) were the app claiming to watch (deviations 24 and 25). Everything is under one lock; `Changed` fires outside it, on whatever thread caused the transition. `DeviceMonitorService` re-exposes `IsRefreshing` and raises `RefreshActivityChanged`.
- **`RefreshActivityChanged` is a second event, marshaled like `Updated`** (invariant 7, same `IUiDispatcher`): a refresh *starting* publishes no snapshots and yet must light the Scanning state, and a coalesced repeat changes neither snapshot list nor changes. A handler may therefore touch view-model state directly.
- **`Snapshots` is what "a pass has completed" means.** It is assigned after the pass has built its list and before `Updated` is raised, and it is empty only until the first completed pass: a pass that found nothing still publishes one snapshot per detectable catalog device, and a pass that **threw** on the way there assigns nothing at all. `MainWindowViewModel.GetDashboardHealth` is the one reader that depends on the distinction (the status-chip rule above).
- **Nothing cancels a refresh.** `Refresh()` takes no cancellation token and `IsRefreshing` is a purely visual fact — see deviation 13, the missing `Cancel` button.
- **The version file is re-read on every scan on purpose.** It is both the `v-Drive OK` / `v-Drive Error` probe (spec 10 "Startup / v-Drive scan / demo mode") and the Freestyle Edge↔Pro re-derivation (spec 10: the app "re-reads the device's version file on every connectivity check and resets the active model"). Read/parse failures are caught, never thrown: they yield `VDriveHealth.Error` and `VersionFileInfo.Empty`.
- **Freestyle re-derivation** runs through `VersionFileInfo.ResolveFreestyleModel()` **only when `Health == Ok`** — an unreadable file would otherwise report an Edge; the scanner's label match is the better answer there.
- **Demo-mode derivation**: `IsDemoMode = Status != Connected` (spec 03 §3.5, "not connected or no read/write access"), so a `CannotAccess` drive is a demo-mode device that still has a `Location`. `FirmwareState.FromVersionFile(versionFile, isDemoMode)` carries it into the gate service. `DeviceSnapshot.CreateDemo(device)` builds the hardware-free variant (`NotDetected`, `Health = Unknown`) the empty state's *Launch ‹device› in Demo Mode* uses.
- `VDriveHealth`: `Unknown` (no drive to check) / `Ok` / `Error`. `DeviceSnapshot.IsDetected` = `Connected` or `CannotAccess` — the dashboard's card filter.
- **`ScannedDeviceId` vs `DeviceId`.** `ScannedDeviceId` is the catalog slot the scanner matched — at most one location per catalog device, so it is unique within a refresh. `DeviceId`/`DisplayName` are the *resolved* device and are not unique: the Edge and Pro slots both re-derive from the version file and can land on the same definition. Cards and sessions key on the former and display the latter.
- **`Updated` is posted through `IUiDispatcher`** because a scan is run off the UI thread — `DashboardViewModel.ScanAsync` is `Task.Run(_monitor.Refresh)`, so a stalled mount cannot freeze the window. `AvaloniaUiDispatcher` and the two file pickers with their `StorageProviderHost` are the only Avalonia-aware types in `Services/` (invariant 8) — `MessageBoxPresenter` stopped being one when its window went away; tests use an inline/deferrable dispatcher fake.

## Sessions and eject — `DeviceSessionManager`, `VDriveEjectNotifier`

`DeviceSessionManager` holds the single active `DeviceSession` (`Begin`/`End`/`ActiveChanged`), and `UpdateActive(snapshots)` re-points it every refresh — matched by `ScannedDeviceId`, so a Freestyle board that re-resolves Edge↔Pro mid-session still matches. `NotificationService` reads the session through the narrow `IDeviceSessionAccessor`.

- **`DeviceSession` separates what is fixed from what is live.** `OpenedDevice` (and therefore `IsDemoMode` and the suppression store) is frozen at open time — spec 10 has Configure set demo mode from the connected/writable state *once*. `Device` follows each scan, and `Health` derives from it: `Unknown` in demo mode, otherwise the snapshot's health, or `Error` if the drive stopped being detected. That is what flips the editor's indicator to `v-Drive Error` mid-session instead of freezing it at open-time state.
- **Preferences store by drive state** (`DeviceSession.Preferences`, of which `SuppressionStore` is the narrow view — one object, not two), all over `app_settings.txt` in the drive's `settings/` folder — the path is Core's `SettingsService.GetAppSettingsFilePath`, so it is `settings/` on **every** device including the Advantage2, whose *keyboard* settings live in `active/` (spec 08 §3, 03 §6): connected and writable → `VDriveAppPreferencesStore`; **demo mode over a drive that is present but not writable → `ReadOnlyAppPreferencesStore`**, which reads that store and discards its writes; no `Location` at all → `NullAppPreferencesStore`. Spec 08 §3 bans *saving* in demo mode, not loading, so a demo session on real hardware keeps the notifications the user hid on it.

`VDriveEjectNotifier` is the user-facing eject flow: toast `Disconnecting v-Drive` → `IDeviceEjectService.EjectAsync` (which runs the blocking `IVDriveEjector` on the thread pool) → toast `Safe To Remove Hardware`, or an error message box on failure. It no-ops and returns false when `IsSupported` is false.

**It has exactly one consumer, the dashboard card's `Eject` button**, and `MainWindowViewModel` does not take it at all — Home does not eject (deviation 22, invariant 1). Anything that wants a drive released asks the user for it on the card; nothing releases one as a side effect of a navigation.

## The demo v-Drive — `DemoVDrive`, `DemoVDriveFixtures`, `DemoVDriveFileService`, `IDemoDeviceProvider`

Demo mode (spec 03 §3.5) used to open an *empty* editor: a demo `DeviceSnapshot` carries no `Location`, so no profile was ever read. The fix is not a demo branch in the editor — it is a **fixture drive** the same code paths read through, so a demo session is an ordinary session pointed at a drive that happens to live in the assembly.

- **`DemoVDrive`** — the synthetic drive. `RootPrefix` is `kinesis-edit://demo/` and a root is that plus the `DeviceId` name; `CreateLocation(device)` returns a `VDriveLocation` with that root and **`IsWritable = false`**, which is the flag the whole app already reads for "demo" (spec 08 §3's never-saved preferences route to `ReadOnlyAppPreferencesStore` with no new branch). `IsUnderRoot(path)` is the one test everything else is scoped by. **The root is URI-shaped on purpose**: every mount root the enumerators produce is a fully qualified path (`/Volumes/…`, `E:\`, `/media/…/…`) and no demo path ever is, so the two can never collide for any volume label anyone ships — and a demo path that escaped the demo file service resolves against nothing rather than against a real file.
- **`DemoVDriveFixtures`** — the content, embedded as `EmbeddedResource` items under `Assets/Demo/<DeviceId>/` and read back with `Assembly.GetManifestResourceStream` + `Encoding.Latin1` + `StreamReader.ReadLine` (CRLF/LF/lone-CR, no empty last line — the same tolerance as `VDriveFileService`, borrowed rather than restated). **Deliberately not `AvaloniaResource`**: reading one needs `AssetLoader`, which would put the toolkit inside a service `ProfileSession` runs on and break invariant 8. A fixture's on-drive path is **derived, never spelled** — the folder names and the settings file name come from `VDriveLocation`'s computed properties and `SettingsService.GetAppSettingsFilePath`, so the fixture tree names *roles* (`Version.txt`, `KeyboardSettings.txt`, `AppSettings.txt`, `Layouts/`, `Lighting/`) and only the per-profile file names inside the two folder roles are the fixture's own. The index is built eagerly, so a mis-filed fixture throws instead of producing a demo session with nothing behind it. Manifest names are parsed on the dot, so **no fixture folder or file name may contain a dot of its own**.
- **`DemoVDriveFileService`** — an `IVDriveFileService` decorator: reads under the demo root come from the fixtures, writes under it throw `DemoVDriveWriteException`, everything else delegates untouched. **The refusal is scoped by path, never by mode**, and that is the load-bearing part: `Export layout to file…` writes through this same interface to a folder the user picked ([feature-dialogs.md](feature-dialogs.md)), and demo mode is where export matters most — a service that refused every write would break export silently, one that refused none would break "demo mode saves nothing". `DemoVDriveWriteException` is an `InvalidOperationException` and **not** an `IOException`, because the app's I/O call sites already swallow `IOException` as "the drive went away"; a demo write is a programming error and has to be loud enough to fail a test.
- **`IDemoDeviceProvider`/`DemoDeviceProvider`** — `TryCreateLocation(device)` answers **only for boards that have fixtures** (today the Freestyle Edge RGB), `null` for every other. There is no list of demo devices anywhere: the embedded fixtures *are* the list. The gate is not decoration — every scan builds a demo snapshot for every undetected catalog device, so handing out a location for a board with no fixtures would point that board's editor at files which are not there and turn six boards that open an empty demo session into six that fail to open one.

**The RGB fixture set** is a full drive: `layout1.txt` with remaps on both layers (`fn ` prefix), one tap-and-hold and three macros — one with two co-triggers, one with a `d500` delay; `led1.txt` with Breathe + per-key colours on the top layer and Rain over a base colour on the Fn layer; a complete `kbd_settings.txt` (**mandatory** — `SettingsService.LoadKeyboardSettings` throws `FileNotFoundException` when it is missing, which aborts the whole profile load into an error dialog); an `app_settings.txt` with six of the twelve `cust_color_N` slots filled; and the spec 09 §1 RGB version file, whose `1.0.1709` / `1.0.521` pair opens every firmware gate. Both `layout1.txt` and `led1.txt` are **canonical** — a save would rewrite them byte for byte — and the tests assert that plus **zero invalid lines**, because the layout parser collects lines it cannot apply rather than failing (04 §5), so a typo would load fine, show nothing, and vanish on the first save.

## Notifications — `INotificationService`, `MessageBoxRequest`, `INotificationSuppressionStore`

`INotificationService` is the UI-toolkit-free contract view models depend on: `ShowMessageBoxAsync`, `ShowToast`, `ShowLoading`/`HideLoading`. `NotificationService` adds the suppression policy over an `IMessageBoxPresenter`. **All three surfaces are drawn by one control, `Views/NotificationOverlay`, inside the shell window** (mockup 1k) — the message box is an in-app card over a scrim, not an OS window.

**The presenter chain.** `MessageBoxPresenter` (view layer) presents nothing itself: it is a lazy forwarder onto a `Func<IMessageBoxPresenter?>` host — `NotificationOverlay`, which implements `IMessageBoxPresenter`. Two things it owns and the overlay does not:

- **With no host registered it answers immediately rather than hanging**, with the request's escape outcome (`Cancel` when the box has a Cancel button, `None` when it has not). A never-completing `Task` would deadlock the caller; every call site already treats that branch as "the user did not answer", so nothing destructive runs off the back of a box nobody saw.
- **It suspends keystroke capture for a box's lifetime**, centrally, so every call site inherits it. This closes a regression the window → overlay move introduced: the box now shares the shell's `TopLevel`, where `AvaloniaKeystrokeCaptureService` previews keys in the tunnel phase — it swallowed the dialog's own Enter and Escape *and* assigned the Escape as a remap. The suspension is **depth-counted** (boxes queue, and resuming on the first answer would hand the keyboard back while the second card is still up) and **releases only what it took**: if the capture is already suspended by somebody else — `EditorOverlayHost` holds one for a text-entry panel's whole lifetime — the presenter takes no suspension and releases none.

**The surfaces.**

- `MessageBoxRequest`: title, message, `MessageBoxIcon`, `MessageBoxButtons` (None/Ok/OkCancel/YesNo/YesNoCancel), `CustomButtons`, the four optional `YesCaption`/`NoCaption`/`OkCaption`/`CancelCaption` overrides, optional `SuppressionKey`, `SuppressedResult`, and four more that dress the card: **`SuppressionCaption`** (per-request opt-out wording; null keeps `Don't ask this again`), **`IsWide`** (the design's 420 px card instead of the default 330), **`DestructiveResult`** (the answer that loses data, drawn on the red `discard` theme) and **`SuppressionResult`** (record the opt-out only when the answer is this one). All four default to the behaviour every existing caller already had, so a request that names none of them is unchanged. `MessageBoxOutcome`: `Result` + `SuppressRequested` + `CustomButtonId` + `WasPresented`.
- **A destructive answer is a request's statement, not the view's guess.** `MessageBoxViewModel` projects it as `IsYesDestructive`/`IsNoDestructive`/`IsOkDestructive` and `MessageBoxView` **binds every answer's role class** (`Classes.secondary="{Binding !IsNoDestructive}"` beside `Classes.discard="{Binding IsNoDestructive}"`) rather than writing one statically — a static class beside a bound one leaves two bridge styles setting `Theme` on the same button, and which wins is an accident of declaration order ([design-system.md](design-system.md)). There is deliberately **no destructive flag for Cancel**: the way out of a dialog cannot be the answer that loses data. **The legacy "+100 modal result" encoding of spec 11 §11.9 is deliberately replaced by this structured outcome** — never reintroduce the offset. `MessageBoxViewModel.Complete` is idempotent (first answer wins), so the awaiting presenter can never hang. Enter is honored **only when `HasAcceptButton`** (`ShowsOk || ShowsYes`): a `Buttons = None` dialog carrying just custom buttons — spec 11.9's "Update Firmware" shape — must not be answerable with a result no visible button offers, so Enter is left unhandled there. Escape yields `Cancel`, or `None` when there is no Cancel button.
- **The caption overrides rename buttons; they never move a result.** Mockup 1k labels the buttons by *outcome* ("Cancel · Key data only · Include macros"), so a request may relabel any standard button while `MessageBoxResult` stays Yes/No/Cancel — every caller's `switch` and every `SuppressedResult` keep their meaning, and Yes stays the primary affirmative whatever it is called. `MessageBoxViewModel` exposes `YesCaption`/`NoCaption`/`OkCaption`/`CancelCaption`, falling back to the `Default…Caption` consts. Four call sites use it today (see the string table).
- **A box is queued, never stacked.** A request arriving while one is up waits behind it in `NotificationOverlay`'s queue: two cards centred on the same scrim would hide one another, and answering an invisible box is worse than answering the first one. The caller is completed the instant its box is answered — not after the 140 ms fade — so no `await ShowMessageBoxAsync` depends on the dispatcher still pumping; the card lingers in the host only while it fades out, unless the next box in the queue claims the host first.
- **`MessageBoxView` is a view, resolved by `ViewLocator`** like any other, and takes focus on `Loaded` (the primary affirmative, else OK, else itself — an unrealised button cannot take focus). Its Enter/Escape handler is **tunneled**, so the spec's contract wins over "activate whatever has focus". The mock's 26 px title strip above the card is deliberately not drawn: that is window chrome, and this is not a window.
- **Suppression convention** (spec 08 §3): keys are the 16 names in `NotificationKeys` — the spec's twelve `*_msg` keys plus four this app adds — persisted in `app_settings.txt` as `on`/`off` where **`on` means hide**; a missing key or missing file means show. `NotificationKeys` is a *view* of `AppPreferenceCatalog` filtered to suppression polarity, so a key cannot exist without a descriptor, and the catalog's one *display* preference (`advisory_detail`, where `on` means **expand**) is excluded by construction and can never be a `SuppressionKey` (see [settings.md](settings.md)). `VDriveAppPreferencesStore` does **no line parsing of its own**: it holds the session's single `AppSettings`, loaded once through `ISettingsService` and written back through it — so Core's match rule, its read-modify-write merge (unknown/reserved lines survive, the file is created only if absent) and its custom-colour slots are the only implementation. A key outside the catalog is not modeled and is therefore never written. Every I/O failure is swallowed — a preference is never worth breaking a dialog over — though the answer still stands for the rest of the session. A request whose key is hidden returns `MessageBoxOutcome.ForSuppressed(request)` and is never shown — **the short-circuit is this service's policy and nothing above it may re-implement it**: a caller that also reads `IsHidden` gives one user decision two policies. A suppressible confirmation therefore sets `SuppressedResult` to its affirmative, because "never ask me again" means "go ahead". Two production call sites today: the editor's layer/layout reset under `reset_layer_msg` ([keyboard-editor.md](keyboard-editor.md)) and the keyboard editor's unsaved-changes prompt under `warn_unsaved_msg` (below). Reads happen in every mode; only writes are mode-dependent (see the store selection above).
- **A ticked box is written back only when the answer beside it can keep the promise it made.** `SuppressionResult` narrows the write: with it set, `NotificationService` records the flag only when `outcome.Result` matches; without it, any answer records, which is what every `Don't ask this again` box has always done. The unsaved-changes prompt is why — its opt-out reads `Don't ask again — always save on leaving`, so ticking it and then pressing Discard or Cancel must arm nothing, or one "throw this away" becomes every future one.
- **Toasts**: `ToastRequest` (message, optional title, `Timeout` default **5 s**, `ToastPosition.BottomRight` default or `Center`, `ToastSeverity.Success` default or `Advisory`). `NotificationOverlay` hosts them in two collections and marshals to the UI thread itself. Each toast fades in and out over the budget's 180 ms and dwells for its own timeout in between ([design-system.md](design-system.md)): `ToastViewModel.IsShown` drives the `.shown` class and is raised on the *next* dispatcher pass, because the view does not exist yet when the request arrives and there would be nothing for the fade to run on.
  - **Severity is a face, not a volume.** Success is green, advisory amber (`StatusAdvisory*`) — **never red**: a failure is a message box the user must answer, never a notice that vanishes after five seconds. Only the dot and the card border change; the card, the shadow and the fade are shared.
  - **A toast can be dismissed early**, with an `×` (`Classes="ghost"` + `IconClose`) beside the message. Both of a toast's timers therefore live in one per-toast `ToastLifetime` in the overlay: an early dismiss **cancels** the pending dwell instead of racing it, so a toast cannot be scheduled for removal twice and a second removal cannot land while a *later* toast is mid-fade. `ToastViewModel.Dismiss` is idempotent and raises `DismissRequested` once. The fade duration is read from `DurationToast` rather than duplicated, with a 180 ms fallback for a host with no application resources.
- **Loading**: `LoadingCaptions.Default` = `Loading…`; `LoadingCaptions.ForDevice(name)` = `Loading <name>…` (U+2026, one character, as everywhere else in the app). `ShowLoading(null)` falls back to the default. **It is blocking**: mockup 1k draws it as "Loading · blocking", so the card sits on the same scrim the message box uses and the app takes no input while it is up. Guards that existed because it did *not* block are kept as second lines of defence — **both** editors still refuse a mid-save navigation with a toast (`UnsavedChangesPrompt.SaveInProgressTitle`/`…Message`), because a path that is not a click (a shortcut, a direct caller) must say why rather than appear to do nothing.
- **Modality is geometry, not a flag.** `NotificationOverlay` sits at `Grid.Row="0" Grid.RowSpan="2"` in `MainWindow`, so a modal covers the app bar too — dimmed-but-clickable Home / Settings / Help is not modal — and it is the grid's topmost child, so it draws over the bar rather than under it. Its root is **no longer `IsHitTestVisible="False"`** (two of the three surfaces now take input). Instead: **the scrim is the only full-bleed element in the file, and it is hit-testable only while a message box or the blocking loading card is up**; every other child is alignment-constrained and sizes to its content, and neither the `Panel` nor the `UserControl` above them carries a background. A full-bleed transparent element anywhere in that file would silently swallow every click on the dashboard behind it. Z-order is scrim → modal host → loading → toasts, because a toast is a notice rather than an obstacle. The scrim stays in the tree and fades through `.open` rather than collapsing, so the 140 ms fade has something to run on.

## Dashboard view models — `DashboardViewModel`, `DeviceCardViewModel`, `NoDeviceViewModel`

**The roster is what the last scan found.** `Apply` renders a card for every snapshot passing `snapshot.IsDetected && IsDashboardDevice(snapshot.Device)` and for nothing else. Plug a board in and scan, and its card inserts at the end of the list; unplug it and scan, and the card goes; when the last one goes, `HasDevices` turns false and the empty state renders again. There is **no ever-detected set and no `Resting` state** — a card is always backed by a mounted drive (deviation 10).

The header counts the same devices the grid draws: `HeaderSubtitle` is `N of 7 known devices present`, where **7 is catalog-wide** and N is the drives present right now, with `device`/`devices` pluralised on N. **Both come through one predicate**, `DashboardViewModel.IsDashboardDevice` (`device.IsProgrammable`): the denominator counts the catalog through it, the numerator counts snapshots through it, and it also decides whether a detected drive gets a card at all — it is the **single gate on whether a board is shown anywhere**, here and in the empty state's picker. One predicate rather than two conditions, because the sets are not the same by construction — the scanner walks the whole catalog, and the never-shipped CROSSFIRE keypad is not programmable but *is* detectable (it carries a volume label), so counting by detection alone yields an eighth card with an empty meta line beside a subtitle reading "1 of 7". `FormatSubtitle`, `KnownDeviceCount` and `IsDashboardDevice` are static so the wording and the rule are asserted without standing a dashboard up.

**One card kind.** `Devices` is an `ObservableCollection<DeviceCardViewModel>` — no base class, no trailing pinned item, no `DeviceCardCount`/`DeviceCards` split, and `HasDevices` is simply `Devices.Count > 0`. A board this app cannot edit is not on this screen at all (deviation 16), which is the design's own capability law rather than a card with nothing to configure on it.

- **`Apply` reconciles in place and never re-sorts.** Cards are keyed by `ScannedDeviceId` and updated through `DeviceCardViewModel.Update` (which returns early on an equal snapshot), so selection and scroll position survive a scan. `RemoveMissingCards` drops the ones the roster no longer contains and `MergeCards` **appends** a new card at the end, moving nothing that already exists. That is what end-insertion requires: the design animates a newly found device as an insert at the end of the list, and re-sorting into catalog order would shift every card below it instead. The first pass fixes the order, because snapshots arrive in `DeviceCatalog.All` order.
- **`ScanAsync` runs off the UI thread** (`Task.Run(_monitor.Refresh)`; the header's `Scan all`, the card's secondary button and the empty state's `Scan now` are `IAsyncRelayCommand`s): a scan enumerates volumes and reads every present version file, and a stalled mount must not freeze the window. Results return on the UI thread through the monitor's `IUiDispatcher`. Only the startup pass is synchronous, and deliberately so (see the composition root).
- **Nothing arrives unbidden, so nothing is deferred.** There is no refresh-deferral choreography — no parking a list while the pointer or keyboard focus is inside the card grid, and no `SuspendRefresh`/`ResumeRefresh` — and none is needed: a scan happens because the user asked for one, and a list that lands as the direct result of a click cannot steal it (deviation 25). Do not add one back without adding back the poll it existed for.
- **`IsRefreshing` is pushed down, never subscribed to.** `OnRefreshActivityChanged` sets `IsRefreshing`, calls `EmptyState.SetRefreshActivity(isRefreshing)` and writes `IsScanning` onto every card, so this screen holds exactly one subscription to the detection service.
- `DeviceCardViewModel` renders a **`DeviceCardState`**, not a `VDriveConnectionStatus`: `GetState(status, isScanning)` folds the drive fact together with whether a pass is in flight. Three members — `Connected` / `CannotAccess` / `Scanning`. The drive enum was not reused because it is a three-member fact about a drive rather than a card's face; there is no `Resting` member because a card outlives no drive, and no `WebToolOnly` one because an unsupported board has no card. `Update`/`IsScanning` raise the derived notifications.
- **`Scanning` maps to `StatusSeverity.Unknown`, not `Error`.** There is **no `.unknown` face anywhere in the status vocabulary** — `Border.statusChip` has none and the card's status line has none — and that **absence is the treatment**: mockup `2e`'s "no red, no spinner". A scanning card falls back to `.muted` text and renders no status rail at all; its 3 px indeterminate bar is what reads as motion. Only `Connected` → `Ok` and `CannotAccess` → `Error` paint.
- **Whether an action exists follows the drive; only its caption and its enablement follow the scan.** `GetState` reports `Scanning` for *every* card while a pass is in flight, so a visibility bound to `State` would flash a button on and off under the cursor twice per scan. Both of the card's conditional buttons are therefore gated on `_snapshot.Status`:
  - `PrimaryActionCaption` is always `Configure` — a card exists only for a mounted drive, and an unwritable one still opens its editor in demo mode. Demo mode without hardware is reached from the empty state's own button, never from a card, so no card ever reads `Demo Mode`.
  - **`ShowsSecondaryAction` is `_snapshot.Status == VDriveConnectionStatus.CannotAccess`** — the button is drawn only over a drive that is mounted but unreadable, where re-reading it is the one thing that can help. `SecondaryActionCaption` is then `Scanning` (with `CanRunSecondaryAction` false) while a pass runs and `Retry access` otherwise — those are the only two captions it can hold, because a connected card renders no secondary button at all (deviation 26). It always rescans: spec 10 has a connected card "swap the scan button to 'Check for Updates'", but there is no update check (issue #45).
  - **`ShowsEject`/`CanEject` include `CannotAccess`**, deliberately: `ShowsEject = IsDetected` (true for every card that exists) and `CanEject = ejectNotifier.IsSupported && IsDetected && Location is not null`. Mockup `1b` puts `⏏ Eject` on the unwritable card, and unmounting is precisely the remedy that card's own explanation names. The button is rendered but merely unusable where the platform cannot eject. Configure raises `ConfigureRequested` upward; the card never navigates.
  - A hidden button is not measured, so its `Auto` column and the 6 px gap beside it close up rather than leaving a hole — which is why the row can carry two buttons on one card and three on another without either looking gappy.
- **The per-state explanation** is the templated `CannotAccessExplanationTemplate` (whose `{0}` is `DriveName` — the mounted folder name, falling back to the catalog's primary volume label and then the device name), and empty for `Connected`/`Scanning`, where the status line says everything. It is the only explanation left.
- **The meta line comes from Core.** `MetaLine` is `DeviceMetaLine.Describe(device)`, so the view holds **no per-device code** — see [domain-data.md](domain-data.md) for `DeviceFormFactor`, `AccessoryNote` and the composed strings.
- **The insert animation is kept.** `HasBeenPresented`/`MarkPresented`, the `collapsed` class and `DurationListInsert` are unchanged: a manual scan still inserts cards, so `2b`'s "a newly detected device animates in at the end of the list, height-only, 160 ms ease-out" still has its call site and the motion budget is untouched.

### The empty state — `NoDeviceViewModel`, `DevicePickerOption`, `ConnectionSteps`

Mockup `1d`: spec 11 §11.8's troubleshoot dialog rebuilt as a teaching screen. A headline and body, then two panels side by side — a picker of all seven programmable boards on the left, the picked board's numbered connection steps on the right — then three actions: `primaryAction` **Launch ‹device› in Demo Mode**, `secondary` **Scan now** (`IconRefresh`; reads `Scanning` and is disabled while a pass is in flight), `link` **Troubleshooting tips** (`IconExternalLink`).

**This screen is where the user is asked to scan, and its copy says so.** Nothing looks at the drives on its own, so `BodyText` asks for the drive to be mounted and `Scan now` to be pressed, the last connection step ends `…Press Scan now and your device card takes over this screen.`, and the mock's live `Still watching · rescanned N times…` line is not drawn at all — there is no loop for it to report on (deviation 25). `Scan now` is the working half of the screen rather than a convenience. It is also reachable **at any time**, not only before the first detection: the roster is present-only, so unplugging the last board brings this screen back.

- **The default board is the Freestyle Edge RGB.** `NoDeviceViewModel.DefaultDevice` names it and `_pickerOrder` puts it first, so it is the row tagged `default`, the board the steps describe on arrival, and the target of `Launch ‹device› in Demo Mode`. It is the one board with an authored editor *and* the only one `DemoVDriveFixtures` answers for ([keyboard-editor.md](keyboard-editor.md)), so the demo button now opens a populated editor instead of an empty one. `StepsTitle`'s article, `DemoModeCaption` and `TroubleshootingUrl` all follow the pick and need no per-board code.
- **The picker is a `ListBox`**, not a `ComboBox`: the pick is one-of-N, the rows' faces come from `ItemContainerTheme="{StaticResource SelectableListRow}"`, and the group takes one tab stop with arrow keys inside it. A drop-down hid six of the seven silhouettes behind a click, which is the opposite of what `1d` asks for. `DevicePickerOption` is the row — the definition, the caption (with `" (pedal)"` derived from the form factor, not spelled per device) and the `IsDefault` tag. Order is the default board followed by the **mockup's** (`_pickerOrder`: the two contoured boards, the remaining Freestyles, the TKO, the pedal), but the rows are still sourced from `DeviceCatalog.All.Where(IsProgrammable)` — the same `IsProgrammable` gate the dashboard uses — so a programmable device the order has never heard of appears at the end rather than vanishing, and a non-programmable one is never offered.
- **A null selection is refused, not stored.** A single-selection `ListBox` deselects the selected row when it is Ctrl/Cmd-clicked and the binding writes that through as null, but this screen has no "nothing picked" state — the title, the steps, the demo target and the support link all describe one board. `SelectedOption` keeps the pick and re-raises, and `NoDeviceView.OnDeviceSelectionChanged` posts the row back onto the list (posted, because a `SelectingItemsControl` ignores a selection written from inside its own `SelectionChanged`). `SelectionMode="AlwaysSelected"` is **not** the fix — it re-selects the *first* row, silently moving the pick to whichever board `_pickerOrder` happens to lead with.
- **Every device-specific word in the steps comes from `DeviceDefinition`** — `VDriveShortcutHint` for the mount step, `VolumeLabels[0]` for the drive step, `FormFactor` (through `ConnectionSteps.IsPedal`) for keyboard-vs-pedal nouns and for the mount mechanism. There is **no per-device prose and no per-device markup**: a device added to the catalog gets correct steps without touching `ConnectionSteps` or `NoDeviceView`. `ConnectionStep` is deliberately three parts — lead / value / trail — because the middle one is a literal that exists on the hardware or on the drive, and the mono law reserves mono for exactly those; the view draws the three as adjacent `Run`s of one sentence so the type changes mid-line and the whole thing still wraps as prose (the spacing lives inside the strings — `InlineCollection` is whitespace-significant).
- **The step count is data.** `Article(name)` picks `a`/`an` from the written vowel and `FormatStepsTitle` puts the count in the panel title, so the Advantage2 — the one device that gets a Power User Mode step of its own — reads *4 steps* and everything else *3 steps*, and the title can never disagree with the list under it.
- **The only live fact on the screen is `IsRefreshing`.** `DashboardViewModel.OnRefreshActivityChanged` pushes `SetRefreshActivity(isRefreshing)` down — the same push-don't-subscribe rule the cards follow, so this screen adds no second subscription — and it drives one thing: `ScanCaption` swapping to `Scanning` with the command disabled. There is no pass counter and no baseline to count from.

### The shell view model — `MainWindowViewModel`

- `MainWindowViewModel` — `OpenDeviceAsync` follows spec 10's Configure order: **ask the open editor whether it may be closed** → set `IsDemoMode` → `sessions.Begin` → show loading → dispose any open editor, ask `IEditorViewModelFactory.Create(device)` for the new one and swap `CurrentView` → refresh indicator → hide loading → **fire the editor's own `LoadAsync()` and forget it**. (`OpenDevice` is the void wrapper that forgets *that* task, because `DashboardViewModel.ConfigureRequested` is an `Action<DeviceSnapshot>` with nowhere to await one.) **The editor choice lives in the factory and nowhere else**: `DeviceId.SavantElite2` → `SavantElitePedalViewModel(device, pedalFiles, capture, notifications)` ([savant-elite.md](savant-elite.md)), a device both `GeometryCatalog` and `VisualCatalog` resolve → `KeyboardEditorViewModel` ([keyboard-editor.md](keyboard-editor.md)), everything else → `EditorPlaceholderViewModel`. `Editor` is typed `DeviceEditorViewModel?` — the abstract base holding `Device`/`DeviceName`/`IsDemoMode` plus the virtual `LoadAsync()` and `ConfirmCloseAsync()`, which is all the shell ever reads — so the shell never learns which editor a device resolved to. `LoadAsync` is the seam for post-swap work: the default does nothing (the placeholder reads nothing), and both real editors override it to read the drive against their own `IsLoading` rather than under the shell's splash; it is total and idempotent, which is what makes forgetting the task safe. **`ConfirmCloseAsync` is the unsaved-work gate**, awaited before `CloseEditor()` on **all three** exits — Home, opening another device, and closing the window — with `false` aborting the exit and leaving the editor exactly where it was (no session begun, nothing closed). The default returns true, so the placeholder leaves silently; both real editors override it (see "The unsaved-changes guard"). Like `LoadAsync` it must be total, because the shell awaits it inside a command. `CloseEditor()` disposes the outgoing editor on both paths, because an editor may hold the app-wide capture service and would otherwise keep swallowing the dashboard's keystrokes; it drops the reference in a `finally`, so an editor whose `Dispose` throws is still gone rather than left behind a Home button pointing at it. **Hiding the loading splash is in a `finally`**, so a failure while an editor is built cannot leave the shell wedged behind an overlay with no editor and a disabled Home button. **`OpenDeviceAsync` is itself total**, for the same reason `LoadAsync` is: the void wrapper forgets the task, so a throw from the session manager or an editor's constructor would otherwise be an unobserved exception leaving the shell on the dashboard with a session open, `IsDemoMode` already flipped and nothing said. Instead the half-done navigation is undone (`sessions.End()`, `CloseEditor()`, dashboard back, demo mode cleared, indicator recomputed) and the failure is shown as an `Open Device` error box — best effort, since a box that cannot be shown must not re-throw out of the method whose contract is that it never throws. Two boundaries make that totality real rather than nominal: **the confirmation runs outside the undo region** (`ConfirmOpenAsync` guards the null check and `ConfirmCloseAsync` itself, reporting a failure and answering "no"), because treating a failed *question* as a failed *open* would drop the editor and discard the unsaved changes the question exists to protect; and **`AbandonOpenDevice` guards every step of its own** — it runs inside the `catch` with the error box still to come, and `CloseEditor()` → an editor's `Dispose()` → the capture service is a real throw path. **Detection is untouched in both directions** — no navigation starts, stops or triggers a scan. `HomeCommand` (a *navigation*: runnable whenever `!IsBusy`, and a no-op inside `GoHomeAsync` when no editor is open — invariant 11) confirms the close, ends the session, and returns to the dashboard. **It ejects nothing** (deviation 22, invariant 1). `IsBusy` guards re-entrancy for *all three* exits — each may put a modal question on screen and none of them blocks the top bar, so without it a Configure could open a second session underneath the answer to the first question, and a second close attempt could stack a second prompt. Every refresh calls `sessions.UpdateActive` then re-evaluates the indicator: the open session's `Health`, or — on the dashboard — `Unknown` → `Demo Mode` until the first pass completes, then `Ok` if any device is `Connected` with `Health == Ok` and `Error` otherwise (see the status-chip rule above).
- **`WindowTitle` lives on `MainWindowViewModel`**, built by the static `BuildWindowTitle(deviceName, isDemoMode)`: `KinesisEdit` on the dashboard, `‹Device› — KinesisEdit` while editing, `‹Device› (Demo) — KinesisEdit` in demo mode. It is re-raised from both `Editor` and `IsDemoMode`. This is editor *chrome* and so overlaps issue #90, but the binding is `MainWindow.axaml`'s `Title` — this layer's own file — so it is implemented here (deviation 15).
- **The app bar's right-hand end carries the status chip and nothing else.** There is no `refreshed Ns ago` readout, and with it went `LastRefreshedText`/`HasLastRefreshed`/`FormatLastRefreshed`, the 200 ms ticker that aged them, and the clock, `IUiDispatcher` and tick-interval constructor parameters that existed only to serve them — the shell's constructor is now dashboard, monitor, sessions, notifications, editor factory, Settings screen, Help screen. It subscribes to `DeviceMonitorService.Updated` alone; `RefreshActivityChanged` is the dashboard's business (deviation 24).
- **`CurrentView` is one of four: the dashboard, the open editor, `SettingsScreen` or `HelpScreen`** (issue [#96](https://github.com/migus88/kinesis-edit/issues/96)). `HomeCommand`/`SettingsCommand`/`HelpCommand` are three `IAsyncRelayCommand`s over one private `NavigateAsync(destination)`, and all three top-bar buttons are `Classes="navPill"` with `.selected` bound to `IsHomeSelected` / `IsSettingsSelected` / `IsHelpSelected`. The old `SettingsRequested`/`HelpRequested` placeholder events are **gone**.
  - **Each flag is `ReferenceEquals(CurrentView, thatScreen)`, and all three are raised from the `CurrentView` setter** — the one place every navigation path ends, the same trick the `Editor` setter already uses for `IsEditorOpen` / `WindowTitle` / `IsShellChromeVisible`. `IsHomeSelected` is therefore no longer `!IsEditorOpen`: on Settings and Help, Home is somewhere to go rather than where you are, and the editor is the one view with no pill of its own.
  - **All three stay runnable everywhere and no-op on their own screen** — `NavigateAsync` returns early on `ReferenceEquals(CurrentView, destination)`. That is invariant 11 generalised: a pill disabled in exactly the state it is selected can never wear the active face.
  - **Leaving an open editor for Settings or Help goes through the same `ConfirmCloseAsync` gate Home and Configure use** (invariant 16), and a refusal leaves the editor open with its session intact and the view unmoved. Session end, editor disposal and `IsDemoMode = false` all happen in the one shared path, so the three pills can never disagree about what leaving an editor means. **None of them ejects** (invariant 1).
  - **All three take part in `IsBusy`**, for the reason it already existed: none of them blocks the top bar, so without it a second navigation would land underneath the answer to the first.
  - Deviation 17's disabled-pill face now has no call site in the app bar; see [design-system.md](design-system.md)'s "Known gaps".

### The unsaved-changes guard — `UnsavedChangesPrompt`, `ConfirmShutdownAsync`, `MainWindow.OnClosing`

**Three exits can drop unsaved editor work, and all three now ask the same question through `DeviceEditorViewModel.ConfirmCloseAsync`:** Home, Configure-another-device, and closing the window. Mockup `1l`: *"Blocking Save / Discard / Cancel on Home, with a 'don't ask again' opt-out. The Save button is amber whenever the session is dirty, so the modal is rarely a surprise."*

**`Services/UnsavedChangesPrompt`** is that question as data, so neither editor owns the strings — the keyboard editor ([keyboard-editor.md](keyboard-editor.md)) and the pedal editor ([savant-elite.md](savant-elite.md)) differ by one sentence, which sentence is the parameter. It decides nothing: the suppression policy is `NotificationService`'s and what to do with an answer is the editor's.

- `Build(message, canSave, canSuppress)` → the `MessageBoxRequest`, in one of **two shapes**. Savable: `YesNoCancel` labelled `Cancel · Discard · Save` (mockup `1f`'s order), `DestructiveResult = No`, `Confirmation` icon, `IsWide`, `SuppressedResult = Yes`, and — when `canSuppress` — `SuppressionKey = NotificationKeys.UnsavedChanges` (`warn_unsaved_msg`) with `SuppressionResult = Yes`: a hidden preference therefore means "save and go", and the promise is recorded only beside the answer that can keep it. Unsavable (`canSave: false`): a `YesNo` **discard** question with its **own title** `Leave without saving?` and its own body, `DestructiveResult = Yes`, `Warning` icon, no opt-out. It is a different card rather than the first one with a button hidden — every clause of the savable body describes a save, and "Saving writes the layout files to the v-Drive" over a card offering only Cancel and Discard is a promise the app cannot keep.
- `Interpret(outcome, canSave) → UnsavedChangesAnswer` — one reading for both editors, because `Yes` means Save in the three-button box and Discard in the two-button one. **Everything that is not an explicit answer is `Cancel`**: a null outcome (the box could not be presented), an Escape, `None`. `Cancel = 0`, so an unset value is the safe answer too. Losing work because the *question* failed is the exact outcome the guard exists to prevent.
- It also owns the mid-save refusal's toast wording (`SaveInProgressTitle`/`SaveInProgressMessage`), which the pedal aliases rather than restating — both boards refuse a navigation during a write in the same words.

**`MainWindowViewModel.ConfirmShutdownAsync()`** is the window's half. True at once when no editor is open; otherwise it routes through the same private `ConfirmEditorCloseAsync()` helper Home and Configure use, so one prompt covers all three. **Total, and its safe answer is "no"**: it is awaited from a detached closing handler, so a throw would land on the UI thread with nobody to catch it — a confirmation that throws is reported as a `Close KinesisEdit` error box and answered false, a box that cannot even report the failure is swallowed, and `IsBusy` (which it takes part in, like both navigations) turns a second attempt into a refusal rather than a second prompt. It **only answers**; tearing the editor down stays with `Dispose`, which the composition root still runs from `desktop.Exit`, still asks nothing, and must stay correct for anything that tears the shell down without going through the window.

### The window's geometry — `MainWindow.RestoreGeometry`, `PersistGeometry`

The other half of the host preferences ([host-preferences.md](host-preferences.md)) lives on the window itself, because reading a live window's size, position and state is Avalonia's business and cannot be done from a view model (invariant 8). `MainWindow`'s third constructor parameter is an **optional** `IHostPreferencesStore`: the composition root passes one, every headless scene passes none, and a window with none restores nothing and writes nothing — which is exactly what a test must do.

- **The restore runs in the constructor**, so the size, the position and the maximised state are all in place before anything is shown.
- **A stored size below the window's own `MinWidth`/`MinHeight` is clamped up to it.** `WindowGeometry`'s own floor is 1 — it rejects garbage rather than restating a minimum that belongs to the window — so 720×480 is enforced here and nowhere else.
- **A stored position on no currently connected screen is dropped** (`Screens.ScreenFromPoint` on the window's top-left corner): a window last closed on a monitor that has since been unplugged would otherwise open where the user cannot reach it. The **size still applies** and `WindowStartupLocation` falls back to `CenterScreen`, so the platform picks the place. The corner rather than the whole rectangle, because it is the end of the title bar the user grabs.
- **Nothing is ever restored into a minimised state.** The only state the restore sets is `Maximized`, and only when the file says so.
- **The save runs in `ConfirmAndCloseAsync`, immediately after the close is approved and before `Close()` — deliberately not in `OnClosing`.** That override cancels *every* first-pass close and re-issues it only once the question has been answered, so a save there would record geometry for closes the user then aborts. The point after approval is the one place the close is certain and the window is still fully alive.
- **A maximised window is stored as maximised *and* with a restore size.** `ClientSize` is the screen while maximised and Avalonia surfaces no platform restore bounds, so the window keeps the last size it had as an ordinary window (updated from `ClientSizeProperty` only while `WindowState == Normal`, because the resize that maximises would otherwise overwrite the very number being kept). A minimised or full-screen window is stored the same way, as the ordinary window it last was.
- **A position the restore would refuse is not stored either** — a minimised window reports an off-screen position on some platforms, and overwriting a good stored position with it would cost the user their placement.
- **Persisting never throws into the close path.** A preference is not worth a window that refuses to shut; the store already swallows its own I/O failures and this guards the rest. It writes through `Update(current => current with { Window = … })`, so it cannot clobber a theme the Settings screen wrote a moment earlier.

**`MainWindow.OnClosing`** is the seam. It **always cancels the close first** and re-issues it once the shell has answered, because the answer needs a dialog and the event cannot wait for one; the re-issued `Close()` runs under an `_isClosingConfirmed` latch so it does not ask again. The confirmation is **posted to the dispatcher, never started inline** — a shell with nothing to ask answers synchronously, which would re-enter `Close()` while the framework is still cancelling the first one. **Every close reason is guarded, OS shutdown included, and `IsProgrammatic` is not special-cased**: the editor holds the same unsaved edits whichever is happening, and asking is never worse than not asking — if the cancellation is honoured the work is saved, and if the platform ignores it the app dies exactly as it would have without the guard.

## The shell's own screens — `SettingsScreenViewModel`, `HelpScreenViewModel`

The app bar's other two nav pills, added by issue [#96](https://github.com/migus88/kinesis-edit/issues/96). **Neither screen is in `docs/design/` at all** — the handoff draws the dashboard, the empty state and the editor, and mockup `1j` is the **editor's** Settings tab, a different file on a different device — so their layout is this app's own and deviates from nothing. Both are composed out of what the redesign already owns: a `pageTitle`, `card` panels, `sectionLabel` captions where a section really groups several rows, and (for the one-of-N switches) the same `SegmentedControl` the layer switchers are.

**`SettingsScreenViewModel` is the host preferences, and it is not `KeyboardSettingsViewModel` or `AppPreferencesViewModel`.** The three names all say "settings" and mean three different files:

| Screen | Store | File | Scope |
|---|---|---|---|
| **This one** (shell → Settings) | `IHostPreferencesStore` | `<per-user config>/KinesisEdit/preferences.json` | Per user, per machine |
| Editor → Settings tab, upper half (`KeyboardSettingsViewModel`) | `ISettingsService` | `settings/kbd_settings.txt` on the v-Drive | Per device |
| Editor → Settings tab, lower half (`AppPreferencesViewModel`) | `IAppPreferencesStore` | `settings/app_settings.txt` on the v-Drive | Per device |

The screen's subtitle says so out loud — *"These are yours, not a keyboard's — stored for this user on this computer… A board's own settings live on the board, in its editor's Settings tab"* — because a reader arriving from that tab has just been told the opposite ([host-preferences.md](host-preferences.md)).

**The whole screen is a page title, a subtitle and one unlabelled card holding two rows** — the theme (`AppThemePreference`: Follow system / Light / Dark), a 1 px hairline on `SurfaceLineBrush`, and the animation budget (`MotionPreference`: Follow system / Reduced / Full). There are **no section labels**: a `sectionLabel` over a single row names that row a second time ("Appearance" over "Theme"), and with two rows in the whole screen there is no grouping left for a caption to do. The hairline is hand-placed rather than the `listRow` class, whose "no border on the first row" rule is written against the `ContentPresenter` an `ItemsControl` generates and which a hand-placed row does not have — used here it would draw a line flush inside the card's own top edge. The headless shell-screen suite renders this screen and pins that shape: two switches, one card, and no `sectionLabel` on it.

**The store's third field is not on this screen.** The window's size and position are restored and persisted by `MainWindow` (see "The window's geometry" above) with no way to turn it off, so it is not a choice; a screen of choices is the wrong place to narrate something that has no switch. A disabled toggle would claim a choice that does not exist and a live one would offer to break something nobody asked to break, so the screen says nothing about it and the behaviour is documented here instead.

**Every pick is persisted *and* applied live, and the two halves are one code path.** `SelectTheme`/`SelectMotion` write through `IHostPreferencesStore.Update(current => current with { … })` — a function, never a whole record, so the shell's window-geometry write and the screen's theme write cannot clobber each other — and the screen then re-reads `Current` and applies whatever moved. It applies from `IHostPreferencesStore.Changed` rather than from the click, so a preference changed by anything else lands too, and it **remembers what it last applied**, so a write of some *other* field (the geometry, on window close) re-applies nothing.

**The two appliers arrive as `Action<T>` delegates, not as calls.** `ThemeApplier.Apply` and `MotionPreferenceApplier.Apply` both need an Avalonia `Application`, and a view model may not have one (invariant 8). The composition root closes over the running application; a test passes a recorder. Nothing is applied on construction — the root already applied the stored preferences at startup, and both appliers are idempotent, so a root that also listens to `Changed` is harmless.

**The switches are `ListBox`es on `SegmentedControl`, bound `Mode=OneWay` with a `SelectionChanged` handler** — the same shape as the editor's layer switch and for the same reason: the view model stays the single owner of which segment is lit, so a pick the store refuses snaps the segment back rather than leaving the control showing something nothing switched to. `AppThemeOption`/`MotionOption` are plain records rather than view models, like `SettingsChoice`, so `ViewLocator` never tries to resolve a view for a segment.

**`HelpScreenViewModel` is a link table plus an about card.** Two sections of links and one card:

- **Start here** — `Which board do I have?` → `https://kinesis-ergo.com/support/`. This is **the app's first and only app-level URL constant** (`HelpScreenViewModel.KinesisSupportUrl`). Every other address in the codebase hangs off a `DeviceDefinition`, because it is about one board; this one is the root of all of them and belongs to no device, so it cannot live in the catalog. `HelpScreenViewModelTests.KinesisSupportUrl_Always_IsTheOnlyAddressThisScreenDeclares` reflects over the type's string constants and fails if a second one appears — a per-device page belongs in the catalog, and a new app-level one belongs in this doc first. The caption is `SettingsMessageCatalog.WhichBoardLinkCaption`, reused rather than re-spelled, so the app asks the question one way.
- **Troubleshooting, by device** — one row per catalogued board with a `TroubleshootingUrl`, in catalog order, captioned `‹DisplayName› support`. Seven today; the two catalog entries with no page (the CROSSFIRE keypad, the Advantage 360 Professional) simply have no row. **There is no "Configured somewhere else" section** — a board this app cannot edit is not named on any screen, here or on the dashboard (deviation 16), so `WebToolLinks`/`HasWebToolLinks`/`WebToolSectionLabel`/`WebToolSectionNote`/`WebToolLinkCaption` do not exist.
- **About** — the product name and `HelpScreenViewModel.ReadVersion(assembly)`, which is the assembly's `AssemblyInformationalVersionAttribute` with any `+‹commit›` build metadata cut, falling back to the assembly version and then to `unknown`. **Nothing else in the repo reads an assembly version**; the version is sans, not mono — the mono law reserves that face for a string that exists verbatim in a config file, and a version the app reads out of itself is the app speaking.

Every row is `Button.link` + `IconExternalLink` + `IUrlLauncher`, the triad the empty state and the read-only settings banner already use, and **never the `↗` character** — the arrow is geometry. `HelpLink` is a plain record carrying no command: the screen holds the one `IUrlLauncher` and the row template reaches `OpenLinkCommand` through `$parent[views:HelpScreenView]`.

**Neither view model owns its navigation.** They are constructed with what they need and hosted like any other `CurrentView`; which pill shows which is the shell's. Both are **constructor parameters of `MainWindowViewModel`**, built once by the composition root and held for the app's lifetime — not built per navigation. That is what settles the one obligation that comes with them: **`SettingsScreenViewModel` is `IDisposable`** — it subscribes to `IHostPreferencesStore.Changed`, which outlives it — and `MainWindowViewModel.Dispose` is what unsubscribes it. One built per visit would leave a listener behind on every visit, each of them still applying preferences to a screen that is no longer on show. `HelpScreenViewModel` holds nothing and needs none.

This app draws a card only for a mounted drive: the roster is `snapshots.Where(s => s.IsDetected && IsDashboardDevice(s.Device))`, `DeviceCardState.Resting` does not exist, and unplugging the last board returns the whole screen to the empty state. The legacy dashboards' fixed two-card registry with `Coming Soon` placeholders is rejected for the same reason — a card that outlives its drive is a promise about hardware the app cannot see. What the resting card was *for* is carried by two things that remain: the header's `N of 7 known devices present` states the catalog-wide count, and the empty state's picker teaches any of the seven boards into a detectable state. Mockup `2b`'s *"a newly detected device animates in at the end of the list"* still fires — a scan that finds a new board is exactly an insertion.
11. **Toast placement is window-relative**, not primary-monitor-relative (single-window app).
12. **Home does not "resume the detection loop"** (spec 10 "Home") — there is nothing to resume: Configure never suspended detection, and since deviation 25 there is no loop to suspend in the first place.
13. **No `Cancel` button in the `Scanning` state**, against mockup `2e`. `DeviceMonitorService.Refresh()` has no cancellation token and `VDriveMonitor.Poll()` discards overlapping polls, so a Cancel button would name work it cannot stop — worse than not offering it. The state stays purely visual: status line, spinner mark and the 3 px indeterminate bar, with the buttons holding their positions. Real cancellation means giving `Refresh()` a token and teaching `VDriveMonitor.Poll()` to be interrupted, and belongs in its own issue.
14. **The card's status line names a *drive* state and reads identically across the seven boards.** Mockup `1b` writes the Savant Elite 2's as `Pedal not detected`; no card carries a per-device status wording, and since deviation 10 no card carries a not-detected status at all. Unrelated and unchanged: the §11.8 **empty state** still says `Pedal not detected` for the SE2 (spec 12 §3) — that is the *screen's* headline, not a card.
15. **`WindowTitle` is implemented here, not in issue #90** (editor shell chrome), because the binding is `MainWindow.axaml`'s `Title` — this layer's own file. #90 may restyle the bar; the title string is already correct.
16. **The Advantage 360 Professional appears on no screen at all.** Mockup `1b` gives it a dashboard card of its own — *"Configured in Kinesis' web tool — KinesisEdit doesn't edit this board."* with a single `Open web tool ↗` action — and the Help screen grew a `Configured somewhere else` section to match. Both are gone: `WebToolCardViewModel`, `WebToolCardView` and `HelpScreenViewModel`'s web-tool links are deleted, and `DeviceDefinition.IsProgrammable` is the one gate deciding whether a board is shown anywhere. The justification is the handoff's own competing law, *"Capability-driven UI: absent features are not shown, not disabled"* — a card the app cannot configure is a permanently absent feature drawn as a panel, and the board has no `VolumeLabels`, so the scanner can never produce a `DeviceSnapshot` for it and its card could only ever have been a synthetic one. The card also never had device art (`Themes/DeviceArt.axaml` draws the seven programmable boards only), which was the first sign it did not belong on a screen of drives. A user who owns one is not stranded: Kinesis' own support index is the Help screen's `Which board do I have?` row.
17. **`NavPill`'s disabled face is `BaseButton`'s inset one**, where the mock draws a bare `TextDisabled` text. It used to be what the permanently disabled Settings and Help wore; since issue [#96](https://github.com/migus88/kinesis-edit/issues/96) made both real navigations **no pill in the app bar is ever disabled**, so the deviation survives only in the theme. Logged as a known gap in [design-system.md](design-system.md) with a test row pinning it — do not re-litigate it here; flipping it is a design decision, not a style tweak.
18. **Nothing detected reads `v-Drive Error`, not `Demo Mode`.** Mockup `1a`'s status vocabulary defines v-Drive Error as "gone · unwritable" and `1d` draws the chip that way beside the empty state; `Demo Mode` is reserved for a session that writes nothing. The pre-first-scan instant deliberately keeps the `Demo` face, read off an empty `Snapshots` list — see the status-chip rule above. **User-approved decision.**
19. **The message box is an in-app overlay, not an OS window.** Mockup `1k` specifies a 140 ms fade over a 62 % scrim with `ShadowModal`, none of which a separate `Window` can carry, and the queue and the capture suspension both need one host. `MessageBoxWindow` and `DialogWindowHost` are deleted; `App.FindOwnerWindow` stays, for the two file pickers. **User-approved decision.**
20. **The device picker does not set `SelectionMode="AlwaysSelected"`.** It snaps to row 0, so a Ctrl/Cmd-click on the selected row would silently move the user's pick to whichever board leads `_pickerOrder` — the Freestyle Edge RGB today. The view model refuses a null and the view restores the row instead — see the empty-state section.
21. **The picker draws silhouettes at a 0.6 px pen**, against the icon law's 1.5. `handoff.md:123` asks for the silhouettes (mockup `1d` itself lists the seven by name only) and at `Size="33"` a 1.5 pen welds the key rects into a slab. Both halves were already recorded in [design-system.md](design-system.md)'s icon deviations as hypotheticals; this screen is their first real call site, and they are now live.
22. **Home never ejects**, against spec 10 "Home" ("closes the active editor, **ejects the v-Drive when not in demo mode**, and resumes the detection loop"). Mockup `1l` overrules it: *"Home just goes home — it never ejects. Ejecting is its own deliberate action on the dashboard card, so nothing is released behind the user's back."* A drive released as a side effect of a navigation is exactly what that forbids, and the demo-mode carve-out the spec needed disappears with it. `MainWindowViewModel` no longer takes a `VDriveEjectNotifier` at all — the card's `Eject` is the only eject in the app. (Deviation 12 already dropped the same sentence's "resumes the detection loop", for its own reason.)
23. **The prompt's body carries no edit counts**, where mockup `1f` opens with *"You've edited `7 keys` across `2 layers`"*. Nothing in the app counts edits **since load**: `KeyboardLayout.ModifiedKeyCount` means "remapped relative to the original key", so a profile carrying seven pre-existing remaps would claim seven the instant it opens with nothing touched — a mono figure that is wrong is worse than no figure, and mono is reserved for values that are verbatim true. The only honest since-load signal is `IProfileSession.IsDirty`, a boolean over serialized line lists ([profiles.md](profiles.md)). The body therefore opens `You have unsaved changes.` and keeps `1f`'s remaining two sentences verbatim. Restoring the counts needs a per-key baseline diff captured at load, which is its own issue.
24. **The app bar carries no `refreshed 0.4s ago` readout.** `handoff.md`'s app-bar spec puts it there — *"right side: mono `refreshed 0.4s ago` + global status pill"* — and mockups `1b`/`1c` draw it in both themes. It is not shipped. The readout's only content is *how long ago the app last looked on its own*, and since deviation 25 the app never looks on its own: after the startup scan the number would be the age of the user's own last click, ticking upward beside a list that is exactly as current as they left it. A readout whose true reading is "nothing has happened since you asked" is noise, and one that keeps counting reads as a promise that something is still watching. The status chip stays and is now the only thing on that end of the bar. What went with it: `MainWindowViewModel.LastRefreshedText`/`HasLastRefreshed`/`FormatLastRefreshed`, its 200 ms ticker, and `RefreshActivity.Stamp`/`LastRefreshedUtc`. The mono-law stretch this readout justified is recorded in [design-system.md](design-system.md)'s deviation table and is now a note about a string the app no longer prints.
25. **There is no 2 s poll, and the two cross-screen laws that governed it do not apply.** `handoff.md`'s suggested state shape opens with *"`DeviceMonitorService` — 2s `DispatcherTimer` poll of mounted volumes"*, `docs/design/README.md` carries *"The 2 s refresh must not move anything"* as a law, and `mockups.md` `2b` spells it in two rules: *"Cards are keyed by drive identity and never reordered by a refresh — a newly detected device animates in at the end of the list, height-only, 160 ms ease-out"* and *"A refresh that arrives while a card's own button is under the cursor or focused is deferred until focus leaves — the list never steals a click"*. This app scans **only when asked**: once at startup, then from `Scan all`, a `Cannot Access` card's `Retry access`, or the empty state's `Scan now`. A background poll of every mounted volume, reading a file on each, is work done on the user's machine for a picture they are usually not looking at — and everything it bought is bought better by a button whose result is expected. **The first rule survives and is kept** (cards are keyed by `ScannedDeviceId`, never reordered, and a new one animates in at the end over `DurationListInsert` — the motion budget is unchanged, because a manual scan still inserts cards); **the second is withdrawn as unnecessary**, since a list that lands as the direct result of a click cannot steal it, taking `SuspendRefresh`/`ResumeRefresh`/`IsRefreshSuspended` and `DashboardView.axaml.cs`'s pointer/focus watching with it. Every surface that told the user the app was watching goes too: the subtitle's `· list updates itself` clause, the empty state's `Still watching · rescanned {n} time{s} since you opened this window` line and its body paragraph's *"no need to press anything"*, and the last connection step's *"will replace itself with your device card automatically"*. **Nothing in the app may claim, imply or draw that the list refreshes itself.**
26. **A connected card offers `Configure` and `Eject` only — no `Scan for v-Drive`.** `handoff.md`'s connected card state reads *"green rail, `Configure` (accent primary) + `Scan for v-Drive` + `Eject`"* and mockup `1b` draws all three. The middle one is not rendered: re-scanning a drive the app is already talking to changes nothing the user can see, and the two states where a scan *is* the remedy each have their own affordance — `Retry access` on the unwritable card (kept, and the only caption the secondary button can hold) and `Scan now` on the empty state. `Scan all` in the header covers "look again at everything". The button is gated on `_snapshot.Status`, never on `DeviceCardState`, because `GetState` reports `Scanning` for every card mid-pass and a state-based predicate would flash it back onto a connected card twice per scan.

## Load-bearing invariants

**The numbering is stable and never reused** — source comments and other module docs cite these by number, so a rule whose subject was deleted is replaced in place by the rule that now holds that ground.

1. **Home never ejects, and neither does anything else that is not the dashboard card's `Eject`** (mockup `1l`; deviation 22). Do not "restore" spec 10's eject-on-Home, and do not add an eject to a save, a close or a device swap: nothing is released behind the user's back. `MainWindowViewModel` has no `VDriveEjectNotifier` to reach for.
2. **Demo mode = not connected *or* not writable.** A `Cannot Access` card opens the editor in demo mode. Do not narrow it to "not detected".
3. **Suppression is per-v-Drive and never *written* in demo mode** (spec 08 §3 "Never saved in demo mode"). `app_settings.txt` lives on the device, so preferences follow the keyboard; a demo session over a present drive still *reads* them through `ReadOnlyAppPreferencesStore`. `on` = hide is the polarity — inverting it silently hides every dialog.
4. **Cards and sessions are keyed by `ScannedDeviceId`, never by the resolved `DeviceId`.** Freestyle resolution is many-to-one, so two attached Freestyle drives can resolve to one definition; keying on the resolved id previously crashed the card merge. The resolved device is for display only.
5. **Nothing scans on its own — every pass has a caller.** `DeviceMonitorService` has no timer, no `Start`/`Stop` and no `IsPolling`; the composition root calls `Refresh()` once at launch and thereafter only a user action does (deviation 25). Do not "restore" a background poll, and do not add an implicit scan to a navigation, a save or a device open. The rule reaches the words too: no string, comment or affordance may say the list keeps itself up to date. An editor still gets its `v-Drive OK` / `v-Drive Error` indicator re-verified — `DeviceSession.Device` is re-pointed from every pass, there are simply only the passes the user asked for.
6. **View models expose enums and strings, never Avalonia brushes.** `StatusSeverity`/`MessageBoxIcon` reach XAML through `EnumMatchConverter` as style classes so the view models stay testable without a UI toolkit *and* so `DynamicResource` re-resolves the palette when the OS theme flips at runtime.
7. **Monitor events arrive off the UI thread and must be marshaled.** Anything new that subscribes to `DeviceMonitorService.Updated` inherits the `IUiDispatcher` guarantee; anything that subscribes to `VDriveMonitor` directly does not.
8. **Services and view models stay toolkit-free.** Only `App`, `Views/`, `Controls/`, `Themes/`, `Styles/`, `Converters/`, `Input/`, and the bridging services `AvaloniaUiDispatcher`, `AvaloniaFolderPickerService`, `AvaloniaFilePickerService`, `StorageProviderHost` and `MotionResourceBinder` reference Avalonia (`MessageBoxPresenter` used to and no longer does — its window became a view); `KinesisEdit.Tests` exercises everything else without starting a UI runtime, and covers the UI itself in separate headless suites that boot the real `App` with no display ([design-system.md](design-system.md)). Each bridging service stays as thin as the platform allows — the pickers' decoding rules live in the toolkit-free `PickedFileReader` for exactly that reason. This is why anything ambient a view model needs arrives as an injected seam rather than as a static call, and why the card's insert animation is split: the *fact* is `DeviceCardViewModel.HasBeenPresented`/`MarkPresented`, a bool on the view model, and the *transition* is `DeviceCardView.axaml.cs` dropping the `collapsed` class.
9. **A card exists exactly while its drive does, and the empty state is always one unplug away.** `Devices` holds one kind of card, `HasDevices` is `Devices.Count > 0`, and the roster is rebuilt from `IsDetected && IsDashboardDevice` on every pass — so losing the last device brings `NoDeviceViewModel` back (issue [#118](https://github.com/migus88/kinesis-edit/issues/118)'s headline fix). Nothing may be added to `Devices` that is not backed by a detected drive: a permanently present card makes `HasDevices` permanently true and the empty state unreachable forever, which is exactly what the deleted web-tool card did.
10. **A card's *actions* are gated on the drive's `VDriveConnectionStatus`, never on `DeviceCardState`.** `GetState` folds in "a pass is in flight", so every card reports `Scanning` mid-pass; a visibility or a caption derived from the state would therefore appear, vanish or move under the cursor twice per scan. `ShowsSecondaryAction` and `ShowsEject` both read `_snapshot`, and `PrimaryActionCaption` is constant. What the state *may* drive is the face and the enablement — the status line, the rail, the spinner, the `Scanning` caption and `CanRunSecondaryAction` — because none of those changes where a button is.
11. **No nav pill's command may be gated on being somewhere else.** `NavPill`'s selected face is written `.selected:not(:disabled)` and a `Button` takes its enablement from its `Command`, so a pill gated on "there is somewhere to go" is disabled in exactly the state its `Is…Selected` is true: the active face is unreachable and the bar renders that pill as a dead one. All three — Home, Settings, Help — are *navigations*: runnable everywhere, and a no-op inside `NavigateAsync` when `CurrentView` is already the destination. The three selection flags are raised from the `CurrentView` setter and nowhere else, so a navigation path added later cannot move the window and leave the bar showing the screen you left. See [design-system.md](design-system.md)'s deviation table.
12. **Exactly one 46 px bar is on screen.** `ProvidesOwnChrome` and `IsShellChromeVisible` are the whole mechanism, and the second is derived from the first rather than set by a navigation path. An editor that starts drawing its own bar sets `ProvidesOwnChrome`; nothing else may put a second status pill on screen.
13. **An editor reaches the shell through `IShellChrome`, as data.** Never up the visual tree: the editor views are rendered standalone in every headless scene, which is also where the screen is verified by frame. The shell hands it over on open and takes it back on close.
14. **A message box suspends keystroke capture, centrally, and releases only what it took.** The box shares the shell's `TopLevel`, so a live capture would swallow its Enter and Escape and assign them to whatever is recording. `MessageBoxPresenter` is the one place that brackets it — never a call site — the count is by depth because boxes queue, and a suspension somebody else already holds (a text-entry feature panel) is left alone.
15. **The scrim is the only full-bleed element in the notification overlay, and it is hit-testable only while something blocks.** The overlay's root is not `IsHitTestVisible="False"` any more, so any other full-bleed child added to that file would silently swallow every click on the screen behind it.
16. **Every way out of an editing session goes through `ConfirmCloseAsync`, and no answer means Cancel.** Home, Configure-another-device and the window's `Closing` all ask the one gate; a fourth exit added anywhere inherits the obligation. Its failure modes — a throw, a box that cannot be presented, an Escape, a question already on screen — all resolve to "stay", never to "discard". `Dispose` is the teardown *after* the question, never a substitute for it: it cannot await, so it asks nothing.
17. **The demo file service refuses writes by *path*, and demo content is offered only where fixtures exist.** Both halves fail silently if inverted: refusing writes by "am I in demo mode" breaks Export, which writes through the same `IVDriveFileService` to a folder the user picked; and offering a demo location for a board with no fixtures turns an empty demo session into a failed one, because every scan builds a demo snapshot for every undetected catalog device. Neither is visible from one side, so both are tested from both sides. Nothing about any of this reaches `KinesisEdit.Core` — Core has no demo concept and cannot tell a fixture-backed file service from a drive-backed one ([profiles.md](profiles.md), "The service seam").

## Deliberately not here

- **No card startup-profile line** (`Profile <n>`, Adv2 `Layout <name>`, spec 10 "Detection loop") — needs the settings engine, issue #10.
- **No first-run Intro dialog, Adv360 startup firmware-age check, or TKO macro-firmware startup warning** (specs 11 §11.9, 10 "Detection loop", 09 §2, §4) — the `NotificationKeys` and gate data they need already exist, but nothing in *this* layer passes a `SuppressionKey` yet. The two production call sites are both the editor's — the layer/layout reset under `NotificationKeys.ResetLayer` ([keyboard-editor.md](keyboard-editor.md)) and the unsaved-changes prompt under `NotificationKeys.UnsavedChanges` — and between them they prove the pipeline end to end in both its shapes, unconditional and answer-scoped. The shell's Settings and Help pills are **live** and go to the two screens above; neither is one of those dialogs, and the editor's Settings **tab** is unrelated to both (it edits the *device's* settings file — [keyboard-editor.md](keyboard-editor.md)).
- **No update check at all** (issue #45) — nothing compares local versions against the vendor's published-versions endpoint, and there is no update dialog, no `update.upd` hands-free flow and no app self-update; spec 09 §3–§4 describes those for the legacy app only. The card's second button only rescans, and the app makes no HTTP request of any kind.
- **No `Watch Tutorial` button** — neither the specs nor the device catalog contain tutorial URLs.
- **No cancellable scan.** `IsRefreshing` is a display fact and nothing in this layer can stop a pass in flight; the `Scanning` card state therefore has no `Cancel` (deviation 13). Adding one means giving `Refresh()` a cancellation token and teaching `VDriveMonitor.Poll()` to be interrupted — its own issue.
- **No automatic detection of any kind** (deviation 25, invariant 5) — no timer, no filesystem watcher, no volume-mount notification. A device plugged in while the app is open appears when the user scans, and not before. Anything that would change that is a design decision, not an implementation detail.
- **No global notification switches — permanently, not pending.** Spec 08 §4 / spec 10 gate display additionally on registry-backed `ShowAllNotifs`/`HideAllNotifs`; the epic ([#1](https://github.com/migus88/kinesis-edit/issues/1)) lists "Windows-registry notification globals" as out of scope, so the display rule here reduces to "shown unless hidden". Do not add them to a later issue's scope.
- **No keystroke capture in the shell** (spec 10 "Keyboard-input capture") — it lives in `KinesisEdit.Core.Input` + `KinesisEdit.Input` ([keystroke-capture.md](keystroke-capture.md)); the shell only *builds* it (lazily, over its own window) and hands it to the editor factory. Nothing in this layer starts, stops or consumes capture — that is the editor's ([keyboard-editor.md](keyboard-editor.md)).
- **No `Keyboard Connection Lost` dialog** (03 §3.5) — it is save/load-time behavior, owned by the editor issues. The transition is already surfaced as `DeviceMonitorUpdate.HasConnectionLoss`, and a mid-session loss does flip the indicator to `v-Drive Error`; only the dialog is missing.
- **No editor content, and no knowledge of which device has one.** The keyboard picture, the remap workflow, the macro panel, the lighting tab and the settings panel are their own module ([keyboard-editor.md](keyboard-editor.md)), the spec 11 panels a second ([feature-dialogs.md](feature-dialogs.md)), and the SE2's pedal editor a third ([savant-elite.md](savant-elite.md)); `EditorPlaceholderViewModel`/`View` remain the stand-in for every device with neither — every board but the Freestyle Edge RGB, whose picture is the only one authored (issues #39–#42). Settings is capability-driven, so every board picks it up as its picture lands; lighting is RGB-only until the TKO and Advantage360 pictures unblock their own editors (#40/#41). This layer only routes through `IEditorViewModelFactory` and asks `ConfirmCloseAsync` before any of the three exits closes an editor — what the question *says* is the editors' and `UnsavedChangesPrompt`'s.
- **No editor dialogs of its own.** The spec 11 feature panels render *inside* the editor view over their own scrim; this layer supplies only the message box, the toast, the loading indicator and the two file pickers they use. Since the box became an overlay the two are the same *kind* of surface — but they are hosted separately, the editor's by `EditorOverlayHost` and the shell's by `NotificationOverlay`, and a box raised from a feature panel therefore draws over it.
- **No second window of any kind.** The app has exactly one `Window` (plus the `--keystroke-spike` harness): the message box is a view, and the only remaining owner-window lookup exists for the platform file pickers.
