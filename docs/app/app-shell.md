# App shell and device dashboard (Services, ViewModels, Views)

The Avalonia layer of `KinesisEdit`: one window that swaps between a device dashboard and a per-device editor, the app-side detection loop that turns `KinesisEdit.Core.VDrive` scans into renderable snapshots, and the notification primitives (message box, toast, loading indicator) every later dialog reuses. It owns no domain knowledge — device facts come from `DeviceCatalog` ([domain-data.md](domain-data.md)), discovery/IO/eject from [vdrive.md](vdrive.md), version parsing and gates from [firmware.md](firmware.md) — and it owns no editor: the editor slot is filled by whatever `IEditorViewModelFactory` returns — the keyboard editor ([keyboard-editor.md](keyboard-editor.md)), the Savant Elite2's pedal editor ([savant-elite.md](savant-elite.md)), or `EditorPlaceholderViewModel` for every device that has neither yet. There is **no DI container**: `App.axaml.cs` is the composition root and every dependency is a constructor parameter.

## Composition root — `App`

`BuildServices` wires by hand, in this order: `VDriveFileService` → `VDriveMonitor(new VDriveScanner(PlatformVolumeEnumerator.Create()))` → `DeviceMonitorService(monitor, fileService, AvaloniaUiDispatcher)` → `SettingsServiceAdapter(new SettingsService(fileService))` → `DeviceSessionManager(settings)` → `MessageBoxPresenter(FindOwnerWindow)` → `NotificationService(presenter, sessions)` → `VDriveEjectNotifier(new DeviceEjectService(VDriveEject.CreateForCurrentPlatform()), notifications)` → `ProcessUrlLauncher` → `PedalFileService(fileService)` → `EditorViewModelFactory(new ProfileSessionFactory(), settings, ResolveCaptureService, notifications, pedalFiles, new AvaloniaFolderPickerService(FindOwnerWindow), new AvaloniaFilePickerService(FindOwnerWindow), fileService, urlLauncher)` → `DashboardViewModel` → `MainWindowViewModel`. Then `desktop.MainWindow = new MainWindow(shell, notifications)` and **`DeviceMonitorService.Start()` last** — the message-box presenter and both file pickers need the window as their owner, which is why the owner is a `Func<Window?>` rather than a reference. `desktop.Exit` disposes shell, dashboard, monitor, and — **last, after the shell has closed and disposed the open editor** — the keystroke capture service.

- **The keystroke capture service is built lazily, over the shell window.** `AvaloniaKeystrokeCaptureService` previews the key events of one `TopLevel` ([keystroke-capture.md](keystroke-capture.md)) and that window does not exist while the graph above is wired, so the editor factory takes a `Func<IKeystrokeCaptureService>` and `App.ResolveCaptureService` creates the single instance on first use — the same ordering problem the message-box presenter solves with its `Func<Window?>` owner. This is also what breaks the shell ↔ capture cycle; by the time a device is opened, the window is on screen.
- **Every editor's dependencies live in the factory, not in the shell.** `PedalFileService` and `ISettingsService` are stateless and one instance of each serves every session; they are handed to `EditorViewModelFactory` rather than to `MainWindowViewModel`, because the shell would otherwise accumulate one constructor parameter per device as editors are added. The keyboard editor's feature panels add four more to the same place — the two pickers, the file service, and the URL launcher the firmware-gate refusals use ([feature-dialogs.md](feature-dialogs.md)).
- **One `ISettingsService` for the whole app.** `SettingsServiceAdapter` ([settings.md](settings.md)) is built once and shared by `DeviceSessionManager` (whose suppression stores read and write `app_settings.txt`) and the editor factory (whose Settings tab writes the keyboard-settings file). `app_settings.txt` must have exactly one reader and one writer: a second, line-based implementation would clobber the twelve `cust_color_N` picker slots Core writes into the same file.
- **Both file pickers defer their owner window** through the same `Func<Window?>` (`FindOwnerWindow`) the presenters use: a picker reaches the platform dialog through `TopLevel.StorageProvider`, and no window exists while the graph is wired. `StorageProviderHost` is the single resolution point they share, and **no owner is reported to the caller as a cancel** — an export or import simply does not happen rather than throwing from a service.

- **The message-box presenter resolves its owner as the *topmost* window**, not `desktop.MainWindow`: a dialog that raises a box of its own must not own it by a window it already blocks, which would nest a modal under a disabled parent. `App.FindOwnerWindow` scans `desktop.Windows` newest-first for an active one and otherwise takes the last entry — the most recently opened window — falling back to `MainWindow` only when the list is empty. **Activation alone is not enough**: nothing reports `IsActive` while the user is in another app, so a box raised while the user is alt-tabbed away would otherwise be parented to the shell. `MessageBoxPresenter` puts its window on screen through the shared `DialogWindowHost` (modal over the owner, standalone when there is none yet).

- **The composition root owns the loop's lifetime and it runs until exit.** No view model starts or stops polling. **`Start()`'s first pass is deliberately synchronous** (unlike every later scan): `DashboardViewModel` is constructed before the window, so the cards must exist before the first frame or the "Keyboard not detected" panel flashes on every launch.
- **One window, swapped views.** `MainWindowViewModel.CurrentView` is the dashboard or the open editor; `MainWindow.axaml` binds it to a `ContentControl` and `ViewLocator` (registered in `App.axaml`'s `DataTemplates`, matching any `ViewModelBase`) maps `KinesisEdit.ViewModels.XxxViewModel` → `KinesisEdit.Views.XxxView` in the same assembly, falling back to a diagnostic `TextBlock`. `MainWindowViewModel` is deliberately *not* resolvable this way (no `MainWindowView`) — the root window is constructed by hand.
- **Native chrome, OS theme.** Resizable 1000×680 window (min 720×480) with the platform title bar and a fixed 46-high in-window top bar carrying Home / Settings / Help plus the status chip. `RequestedThemeVariant="Default"` + `FluentTheme`, so the OS light/dark variant wins; every colour is a role token resolved by `DynamicResource` from the design system ([design-system.md](design-system.md)), and the base Fluent controls are re-pointed at the same palette by `Themes/Controls.axaml`. The legacy borderless chrome and fixed 1550×850 size are dropped (macOS-first).
- **The status indicator is a chip, not coloured text.** `Border.statusChip` takes `.ok`/`.error`/`.demo`/`.warning` from `StatusIndicatorSeverity`; its fill and border cross-fade over 220 ms when the detection loop changes its mind, while the text inside swaps instantly. The four states are fixed and never share a meaning — green connected and writable, red gone or unwritable, **purple demo mode**, amber an advisory that never blocks. Demo mode is `StatusSeverity.Demo`, deliberately not `Warning`: amber is the only warning colour in the app.
- **MVVM** is `CommunityToolkit.Mvvm` (`ObservableObject` via `ViewModelBase`, `RelayCommand`/`AsyncRelayCommand`), compiled bindings on.
- **One escape hatch.** With `--keystroke-spike` in `desktop.Args` (`dotnet run --project src/KinesisEdit -- --keystroke-spike`) the root skips the whole graph and shows `Views/KeystrokeCaptureSpikeWindow` — the issue-#12 capture harness kept for hand-verification ([keystroke-capture.md](keystroke-capture.md)); no services are built and the detection loop never starts.

## Detection loop — `DeviceMonitorService`

Owns the `VDriveMonitor` (and disposes it). `Refresh()` = one `VDriveMonitor.Poll()`, then for every device with a `Location` **re-read and re-parse the version file**, producing an immutable `DeviceSnapshot` per tracked device in `DeviceCatalog.All` order, plus that poll's `VDriveStatusChange` list, published as one `DeviceMonitorUpdate`. `Start()` runs one synchronous `Refresh()` then arms a 2 s `System.Threading.Timer`; `Stop()` disarms it (`IsPolling` reports the state); tests call `Refresh()` directly. A throw inside a timer tick is swallowed — the next tick retries.

- **The loop is never stopped for an editing session.** Spec 10 requires an open editor to re-verify its version file every tick, and one loop serves both the dashboard and the editor — so `Start()`/`Stop()` belong to the composition root and to `Dispose`, not to navigation.
- **`Refresh()` coalesces rather than dropping.** A call arriving while another refresh runs marks the running one to *repeat* and returns; the repeat happens under the same gate. Concurrency is not an option because `VDriveMonitor.Poll()` discards an overlapping poll outright, which would silently turn a user's `Scan for v-Drive` landing on a timer tick into a no-op. Pending `VDriveStatusChange`s are copied, published, and only the published count removed afterwards, so a change the monitor raises mid-publish survives to the next pass instead of vanishing (this is what keeps `IsConnectionLost` reliable).
- **The version file is re-read every refresh on purpose.** It is both the `v-Drive OK` / `v-Drive Error` probe (spec 10 "Startup / v-Drive scan / demo mode") and the Freestyle Edge↔Pro re-derivation (spec 10: the app "re-reads the device's version file on every connectivity check and resets the active model"). Read/parse failures are caught, never thrown: they yield `VDriveHealth.Error` and `VersionFileInfo.Empty`.
- **Freestyle re-derivation** runs through `VersionFileInfo.ResolveFreestyleModel()` **only when `Health == Ok`** — an unreadable file would otherwise report an Edge; the scanner's label match is the better answer there.
- **Demo-mode derivation**: `IsDemoMode = Status != Connected` (spec 03 §3.5, "not connected or no read/write access"), so a `CannotAccess` drive is a demo-mode device that still has a `Location`. `FirmwareState.FromVersionFile(versionFile, isDemoMode)` carries it into the gate service. `DeviceSnapshot.CreateDemo(device)` builds the hardware-free variant (`NotDetected`, `Health = Unknown`) the empty state's *Launch in Demo Mode* uses.
- `VDriveHealth`: `Unknown` (no drive to check) / `Ok` / `Error`. `DeviceSnapshot.IsDetected` = `Connected` or `CannotAccess` — the dashboard's card filter.
- **`ScannedDeviceId` vs `DeviceId`.** `ScannedDeviceId` is the catalog slot the scanner matched — at most one location per catalog device, so it is unique within a refresh. `DeviceId`/`DisplayName` are the *resolved* device and are not unique: the Edge and Pro slots both re-derive from the version file and can land on the same definition. Cards and sessions key on the former and display the latter.
- **`Updated` is posted through `IUiDispatcher`** because `VDriveMonitor` polls on a thread-pool timer. `AvaloniaUiDispatcher`, `MessageBoxPresenter` with its `DialogWindowHost` helper, and the two file pickers with their `StorageProviderHost` are the only Avalonia-aware types in `Services/` (invariant 8); tests use an inline/deferrable dispatcher fake.

## Sessions and eject — `DeviceSessionManager`, `VDriveEjectNotifier`

`DeviceSessionManager` holds the single active `DeviceSession` (`Begin`/`End`/`ActiveChanged`), and `UpdateActive(snapshots)` re-points it every refresh — matched by `ScannedDeviceId`, so a Freestyle board that re-resolves Edge↔Pro mid-session still matches. `NotificationService` reads the session through the narrow `IDeviceSessionAccessor`.

- **`DeviceSession` separates what is fixed from what is live.** `OpenedDevice` (and therefore `IsDemoMode` and the suppression store) is frozen at open time — spec 10 has Configure set demo mode from the connected/writable state *once*. `Device` follows the loop, and `Health` derives from it: `Unknown` in demo mode, otherwise the snapshot's health, or `Error` if the drive stopped being detected. That is what flips the editor's indicator to `v-Drive Error` mid-session instead of freezing it at open-time state.
- **Suppression store by drive state**, all over `app_settings.txt` in the drive's `settings/` folder — the path is Core's `SettingsService.GetAppSettingsFilePath`, so it is `settings/` on **every** device including the Advantage2, whose *keyboard* settings live in `active/` (spec 08 §3, 03 §6): connected and writable → `VDriveNotificationSuppressionStore`; **demo mode over a drive that is present but not writable → `ReadOnlyNotificationSuppressionStore`**, which reads that store and discards its writes; no `Location` at all → `NullNotificationSuppressionStore`. Spec 08 §3 bans *saving* in demo mode, not loading, so a demo session on real hardware keeps the notifications the user hid on it.

`VDriveEjectNotifier` is the shared user-facing eject flow (card *Eject* button and Home): toast `Disconnecting v-Drive` → `IDeviceEjectService.EjectAsync` (which runs the blocking `IVDriveEjector` on the thread pool) → toast `Safe To Remove Hardware`, or an error message box on failure. It no-ops and returns false when `IsSupported` is false.

## Notifications — `INotificationService`, `MessageBoxRequest`, `INotificationSuppressionStore`

`INotificationService` is the UI-toolkit-free contract view models depend on: `ShowMessageBoxAsync`, `ShowToast`, `ShowLoading`/`HideLoading`. `NotificationService` adds the suppression policy over an `IMessageBoxPresenter`; `MessageBoxPresenter` (view layer) shows `MessageBoxWindow` modally over the shell, or standalone when no owner exists yet.

- `MessageBoxRequest`: title, message, `MessageBoxIcon`, `MessageBoxButtons` (None/Ok/OkCancel/YesNo/YesNoCancel), `CustomButtons`, optional `SuppressionKey`, `SuppressedResult`. `MessageBoxOutcome`: `Result` + `SuppressRequested` + `CustomButtonId` + `WasPresented`. **The legacy "+100 modal result" encoding of spec 11 §11.9 is deliberately replaced by this structured outcome** — never reintroduce the offset. `MessageBoxViewModel.Complete` is idempotent (first answer wins) and `MessageBoxWindow.OnClosed` always records one, so the awaiting presenter can never hang. Enter is honored **only when `HasAcceptButton`** (`ShowsOk || ShowsYes`): a `Buttons = None` dialog carrying just custom buttons — spec 11.9's "Update Firmware" shape — must not be answerable with a result no visible button offers, so Enter is left unhandled there. Escape yields `Cancel`, or `None` when there is no Cancel button.
- **Suppression convention** (spec 08 §3): keys are the 12 `*_msg` names in `NotificationKeys`, persisted in `app_settings.txt` as `on`/`off` where **`on` means hide**; a missing key or missing file means show. `VDriveNotificationSuppressionStore` does **no line parsing of its own**: `IsHidden`/`SetHidden` load the whole `AppSettings` through `ISettingsService`, map the key onto its flag, and save it back — so Core's match rule, its read-modify-write merge (unknown/reserved lines survive, the file is created only if absent) and its custom-colour slots are the only implementation. A key outside the twelve is not modeled and is therefore never written. Every I/O failure is swallowed — a preference is never worth breaking a dialog over. A request whose key is hidden returns `MessageBoxOutcome.ForSuppressed(request)` and is never shown. Reads happen in every mode; only writes are mode-dependent (see the store selection above).
- **Toasts**: `ToastRequest` (message, optional title, `Timeout` default **5 s**, `ToastPosition.BottomRight` default or `Center`). `NotificationOverlay` hosts them in two collections, marshals to the UI thread itself, and is `IsHitTestVisible="False"` because nothing there is modal. Each toast fades in and out over the budget's 180 ms and dwells for its own timeout in between ([design-system.md](design-system.md)): `ToastViewModel.IsShown` drives the `.shown` class and is raised on the *next* dispatcher pass, because the view does not exist yet when the request arrives and there would be nothing for the fade to run on. Removal is two chained one-shot `DispatcherTimer`s — dwell, then lower `IsShown`, then drop the toast after `DurationToast` — so it is never removed mid-animation. The duration is read from the resource rather than duplicated, with a 180 ms fallback for a host with no application resources.
- **Loading**: `LoadingCaptions.Default` = `Loading...`; `LoadingCaptions.ForDevice(name)` = `Loading <name>...`. `ShowLoading(null)` falls back to the default.

## Dashboard view models — `DashboardViewModel`, `DeviceCardViewModel`, `NoDeviceViewModel`

`DashboardViewModel.Apply` reconciles `Devices` against the detected snapshots: cards are keyed by `ScannedDeviceId`, updated **in place** (`DeviceCardViewModel.Update`, which returns early on an equal snapshot) and moved rather than recreated, so selection and scroll position survive a 2 s refresh. `MergeCards` counts placements rather than trusting the snapshot index, so a duplicate key could never move a card past the end of the list. `HasDevices`/`IsEmpty` toggle between the card list and `NoDeviceViewModel`.

- **`ScanAsync` runs off the UI thread** (`Task.Run(_monitor.Refresh)`; every `Scan for v-Drive` button is an `IAsyncRelayCommand`): a scan enumerates volumes and reads every present version file, and a stalled mount must not freeze the window. Results return on the UI thread through the monitor's `IUiDispatcher`. Only the startup pass is synchronous, and deliberately so (see the composition root).
- `DeviceCardViewModel` — `StatusText`/`StatusSeverity`, `PrimaryActionCaption` (`Configure` vs `Demo Mode`), `SecondaryActionCaption`/`SecondaryActionCommand`, `EjectCommand` enabled only when `ejectNotifier.IsSupported && Status == Connected && Location is not null`. Configure raises `ConfigureRequested` upward; the card never navigates.
- **The card's second button always reads `Scan for v-Drive`** and always rescans. Spec 10 has a connected card "swap the scan button to 'Check for Updates'"; there is no update check (issue #45), so nothing swaps the caption or reroutes `SecondaryActionCommand` in any device or drive state.
- `NoDeviceViewModel` — spec 11 §11.8 rendered inline, plus **this app's device picker** (`DeviceCatalog.All` where `IsProgrammable`, default Advantage2). The selection drives `Title`, `InstructionText`, `TroubleshootingUrl`, and which device `Launch in Demo Mode` opens.
- `MainWindowViewModel` — `OpenDeviceAsync` follows spec 10's Configure order: **ask the open editor whether it may be closed** → set `IsDemoMode` → `sessions.Begin` → show loading → dispose any open editor, ask `IEditorViewModelFactory.Create(device)` for the new one and swap `CurrentView` → refresh indicator → hide loading → **fire the editor's own `LoadAsync()` and forget it**. (`OpenDevice` is the void wrapper that forgets *that* task, because `DashboardViewModel.ConfigureRequested` is an `Action<DeviceSnapshot>` with nowhere to await one.) **The editor choice lives in the factory and nowhere else**: `DeviceId.SavantElite2` → `SavantElitePedalViewModel(device, pedalFiles, capture, notifications)` ([savant-elite.md](savant-elite.md)), a device both `GeometryCatalog` and `VisualCatalog` resolve → `KeyboardEditorViewModel` ([keyboard-editor.md](keyboard-editor.md)), everything else → `EditorPlaceholderViewModel`. `Editor` is typed `DeviceEditorViewModel?` — the abstract base holding `Device`/`DeviceName`/`IsDemoMode` plus the virtual `LoadAsync()` and `ConfirmCloseAsync()`, which is all the shell ever reads — so the shell never learns which editor a device resolved to. `LoadAsync` is the seam for post-swap work: the default does nothing (the placeholder reads nothing), and both real editors override it to read the drive against their own `IsLoading` rather than under the shell's splash; it is total and idempotent, which is what makes forgetting the task safe. **`ConfirmCloseAsync` is the unsaved-work gate**, awaited before `CloseEditor()` on **both** exits — Home and opening another device — with `false` aborting the navigation and leaving the editor exactly where it was (no session begun, nothing ejected). The default returns true, so only the pedal editor uses it today; like `LoadAsync` it must be total, because the shell awaits it inside a command. `CloseEditor()` disposes the outgoing editor on both paths, because an editor may hold the app-wide capture service and would otherwise keep swallowing the dashboard's keystrokes; it drops the reference in a `finally`, so an editor whose `Dispose` throws is still gone rather than left behind a Home button pointing at it. **Hiding the loading splash is in a `finally`**, so a failure while an editor is built cannot leave the shell wedged behind an overlay with no editor and a disabled Home button. **`OpenDeviceAsync` is itself total**, for the same reason `LoadAsync` is: the void wrapper forgets the task, so a throw from the session manager or an editor's constructor would otherwise be an unobserved exception leaving the shell on the dashboard with a session open, `IsDemoMode` already flipped and nothing said. Instead the half-done navigation is undone (`sessions.End()`, `CloseEditor()`, dashboard back, demo mode cleared, indicator recomputed) and the failure is shown as an `Open Device` error box — best effort, since a box that cannot be shown must not re-throw out of the method whose contract is that it never throws. Two boundaries make that totality real rather than nominal: **the confirmation runs outside the undo region** (`ConfirmOpenAsync` guards the null check and `ConfirmCloseAsync` itself, reporting a failure and answering "no"), because treating a failed *question* as a failed *open* would drop the editor and discard the unsaved changes the question exists to protect; and **`AbandonOpenDevice` guards every step of its own** — it runs inside the `catch` with the error box still to come, and `CloseEditor()` → an editor's `Dispose()` → the capture service is a real throw path. **Polling is untouched in both directions.** `HomeCommand` (enabled while an editor is open and `!IsBusy`) ends the session, returns to the dashboard, and **ejects only when the session was not demo mode and had a `Location`**. `IsBusy` guards re-entrancy for *both* navigations now — each may put a modal question on screen and Home awaits the eject, so without it a second Configure could open a session underneath the first one's continuation. Every refresh calls `sessions.UpdateActive` then re-evaluates the indicator: the open session's `Health`, or — on the dashboard — `Ok` if any device is `Connected` with `Health == Ok`, `Error` if any device is detected but not, else `Unknown` → `Demo Mode`.
- `SettingsCommand`/`HelpCommand` are **permanently disabled** (`CanExecute` → false) rather than silently no-oping; `SettingsRequested`/`HelpRequested` remain as unconsumed hooks for the app-settings and help dialogs.

## Spec strings and deliberate deviations

Pinned verbatim as consts (tests assert them): card status `Connected` / `Not Detected` / `Cannot Access`; card buttons `Configure`, `Demo Mode`, `Scan for v-Drive`, `Eject`; shell indicator `v-Drive OK` / `v-Drive Error` / `Demo Mode`; empty state `Keyboard not detected` (`Pedal not detected` for the SE2, spec 12 §3) with `Scan for v-Drive`, `Launch in Demo Mode`, `Troubleshooting Tips`; `Hide this notification?` with Enter = OK/Yes and Escape = Cancel; `Loading...`; `Disconnecting v-Drive`, `Safe To Remove Hardware`, `Cannot eject v-Drive — Close all open files and folders on the v-Drive, and try ejecting again.`

Recorded deviations — each is intentional, do not "restore" the spec literal:

1. **The v-Drive shortcut in the §11.8 instruction is templated from `DeviceDefinition.VDriveShortcutHint`**, not hard-coded — the spec's RGB/TKO row quotes `+ F8` for both, but the TKO's real shortcut is `SmartSet + Right Shift + V` (spec 03 §1). The spec's inline SmartSet-key images are rendered as text.
2. **Only the Advantage2 and the Savant Elite 2 get the Power User Mode preamble**; every other device gets the short "by using the onboard shortcut {0}" form. Spec 11 §11.8's first row lumps the FS Edge and FS Pro in with the Adv2/SE2 text, but Power User Mode is an Adv2/SE2 concept — the Freestyle boards have no such mode and simply open their v-Drive with `SmartSet + F8`, so keeping the preamble would tell the user to press keys that do not exist. This is a deliberate departure from the spec's row grouping, not from its wording.
3. **The elided (`...`) RGB/TKO and Adv360 rows are completed** with row 1's closing sentence (`Please connect the v-Drive and then click the "Scan for v-Drive" button below.`), which is identical wording.
4. **`Loading <DeviceName>...` is not a spec string** — spec 11 §11.9 quotes only the default `Loading...`; the per-device form is this app's.
5. **The eject-failure dialog title `Eject` is unspecified** — spec 10 quotes the message only.
6. **Eject is gated on `IDeviceEjectService.IsSupported`, never on an OS check.** The legacy apps hid eject on macOS; the issue #6 decision implements macOS `diskutil unmount`, so a platform gains the button the moment its ejector exists.
7. **The dashboard has no fixed device registry.** The legacy dashboards carried exactly two cards including `Coming Soon` placeholders; this app serves the whole catalog and shows detected devices only.
8. **Toast placement is window-relative**, not primary-monitor-relative (single-window app).
9. **Home does not "resume the detection loop"** (spec 10 "Home") — there is nothing to resume, because Configure never suspended it.

## Load-bearing invariants

1. **Home ejects only when not in demo mode** (spec 10 "Home"; 03 §3.5). Demo mode never touched the drive, so there is nothing to flush — and `Location` may be a read-only mount.
2. **Demo mode = not connected *or* not writable.** A `Cannot Access` card opens the editor in demo mode. Do not narrow it to "not detected".
3. **Suppression is per-v-Drive and never *written* in demo mode** (spec 08 §3 "Never saved in demo mode"). `app_settings.txt` lives on the device, so preferences follow the keyboard; a demo session over a present drive still *reads* them through `ReadOnlyNotificationSuppressionStore`. `on` = hide is the polarity — inverting it silently hides every dialog.
4. **Cards and sessions are keyed by `ScannedDeviceId`, never by the resolved `DeviceId`.** Freestyle resolution is many-to-one, so two attached Freestyle drives can resolve to one definition; keying on the resolved id previously crashed the card merge. The resolved device is for display only.
5. **The detection loop runs for the app's whole lifetime.** Do not "optimize" it by stopping it while an editor is open: the editor's `v-Drive OK` / `v-Drive Error` indicator is exactly that per-tick re-verification (spec 10), and `DeviceSession.Device` is re-pointed from it every pass.
6. **View models expose enums and strings, never Avalonia brushes.** `StatusSeverity`/`MessageBoxIcon` reach XAML through `EnumMatchConverter` as style classes so the view models stay testable without a UI toolkit *and* so `DynamicResource` re-resolves the palette when the OS theme flips at runtime.
7. **Monitor events arrive off the UI thread and must be marshaled.** Anything new that subscribes to `DeviceMonitorService.Updated` inherits the `IUiDispatcher` guarantee; anything that subscribes to `VDriveMonitor` directly does not.
8. **Services and view models stay toolkit-free.** Only `App`, `Views/`, `Controls/`, `Themes/`, `Styles/`, `Converters/`, `Input/`, and the bridging services `AvaloniaUiDispatcher`, `MessageBoxPresenter`, `DialogWindowHost`, `AvaloniaFolderPickerService`, `AvaloniaFilePickerService`, `StorageProviderHost` and `MotionResourceBinder` reference Avalonia; `KinesisEdit.Tests` exercises everything else without starting a UI runtime, and covers the UI itself in separate headless suites that boot the real `App` with no display ([design-system.md](design-system.md)). Each bridging service stays as thin as the platform allows — the pickers' decoding rules live in the toolkit-free `PickedFileReader` for exactly that reason.

## Deliberately not here

- **No card startup-profile line** (`Profile <n>`, Adv2 `Layout <name>`, spec 10 "Detection loop") — needs the settings engine, issue #10.
- **No first-run Intro dialog, Adv360 startup firmware-age check, or TKO macro-firmware startup warning** (specs 11 §11.9, 10 "Detection loop", 09 §2, §4) — the `NotificationKeys` and gate data they need already exist, but nothing in this layer passes a `SuppressionKey` yet. The shell's Settings and Help buttons stay disabled until their own dialogs exist; the editor's Settings **tab** is unrelated to them (it edits the *device's* settings file — [keyboard-editor.md](keyboard-editor.md)).
- **No update check at all** (issue #45) — nothing compares local versions against the vendor's published-versions endpoint, and there is no update dialog, no `update.upd` hands-free flow and no app self-update; spec 09 §3–§4 describes those for the legacy app only. The card's second button only rescans, and the app makes no HTTP request of any kind.
- **No `Watch Tutorial` button** — neither the specs nor the device catalog contain tutorial URLs.
- **No global notification switches — permanently, not pending.** Spec 08 §4 / spec 10 gate display additionally on registry-backed `ShowAllNotifs`/`HideAllNotifs`; the epic ([#1](https://github.com/migus88/kinesis-edit/issues/1)) lists "Windows-registry notification globals" as out of scope, so the display rule here reduces to "shown unless hidden". Do not add them to a later issue's scope.
- **No keystroke capture in the shell** (spec 10 "Keyboard-input capture") — it lives in `KinesisEdit.Core.Input` + `KinesisEdit.Input` ([keystroke-capture.md](keystroke-capture.md)); the shell only *builds* it (lazily, over its own window) and hands it to the editor factory. Nothing in this layer starts, stops or consumes capture — that is the editor's ([keyboard-editor.md](keyboard-editor.md)).
- **No `Keyboard Connection Lost` dialog** (03 §3.5) — it is save/load-time behavior, owned by the editor issues. The transition is already surfaced as `DeviceMonitorUpdate.HasConnectionLoss`, and a mid-session loss does flip the indicator to `v-Drive Error`; only the dialog is missing.
- **No editor content, and no knowledge of which device has one.** The keyboard picture, the remap workflow, the macro panel, the lighting tab and the settings panel are their own module ([keyboard-editor.md](keyboard-editor.md)), the spec 11 panels a second ([feature-dialogs.md](feature-dialogs.md)), and the SE2's pedal editor a third ([savant-elite.md](savant-elite.md)); `EditorPlaceholderViewModel`/`View` remain the stand-in for every device with neither — every board but the Freestyle Edge RGB, whose picture is the only one authored (issues #39–#42). Settings is capability-driven, so every board picks it up as its picture lands; lighting is RGB-only until the TKO and Advantage360 pictures unblock their own editors (#40/#41). This layer only routes through `IEditorViewModelFactory` and asks `ConfirmCloseAsync` before it swaps an editor out.
- **No editor dialogs of its own.** The spec 11 feature panels render *inside* the editor view over a scrim, not through `DialogWindowHost`; this layer supplies only the message box, the toast, the loading indicator and the two file pickers they use.
