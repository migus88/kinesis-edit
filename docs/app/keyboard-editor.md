# Keyboard editor (keyboard picture, remaps, macros, lighting, settings)

The editor the shell swaps in on Configure for a programmable keyboard: a keyboard-shaped picture of one loaded profile, the click-then-press remap workflow of spec 10 ("click an on-screen key — the key enters 'listening' state; the next physical keypress captured by the app becomes the new assignment"), the macro panel behind the *Macros* tab, the *Lighting* and *Settings* tabs, and the reset/save/export/import actions around them. It owns **no** domain rules — placements come from `VisualCatalog` ([domain-data.md](domain-data.md)), the model and its edit paths from `KinesisEdit.Core.Model` ([keyboard-model.md](keyboard-model.md)), load/save/import from `ProfileSession` ([profiles.md](profiles.md)), keystrokes from `IKeystrokeCaptureService` ([keystroke-capture.md](keystroke-capture.md)), the led model from `KinesisEdit.Core.Lighting` ([lighting.md](lighting.md)), the settings files from `ISettingsService` ([settings.md](settings.md)), the spec 11 panels it hosts from [feature-dialogs.md](feature-dialogs.md), and window/navigation/notifications from the shell ([app-shell.md](app-shell.md)).

**Device coverage: Freestyle Edge RGB only.** Every other device opens `EditorPlaceholderViewModel` — except the Savant Elite2, which has an editor of its own ([savant-elite.md](savant-elite.md)) and no keyboard picture at all — because only that one board's picture is authored. Adding a device is adding data to `VisualCatalog` — issues [#39](https://github.com/migus88/kinesis-edit/issues/39) (FS Edge / FS Pro), [#40](https://github.com/migus88/kinesis-edit/issues/40) (TKO), [#41](https://github.com/migus88/kinesis-edit/issues/41) (Advantage 360), [#42](https://github.com/migus88/kinesis-edit/issues/42) (Advantage2) — never editing anything below.

## The chain: visual data → control → view model

1. **`VisualCatalog`** (Core) answers *where* — `KeyVisual { Index, X, Y, Width, Height, Cluster }` in **key units** (`1.0` = one 1U cap), board-absolute, top-left origin. One `KeyboardVisual` serves **all** of a device's layers (05 §7.4: the same position keeps its index in every layer).
2. **`KeyboardLayerViewModel.BuildAll(layout, visual, lighting)`** joins the two **by key index**: for every `KeyboardKey` of every `KeyboardLayer` it looks up `KeyboardVisual.TryGetKey(key.Index, …)` and produces a `KeyboardKeyViewModel`. A key with no placement is **skipped**, a placement with no key produces no cap — Core's tests already assert the two index sets match exactly for every authored device, so a mismatch must degrade into a missing cap, never a crashed editor.
3. **`KeyboardView`** renders `KeyboardLayerViewModel.Keys` as an `ItemsControl` whose `ItemsPanel` is a `KeyboardPanel` (fed `BoardWidth`/`BoardHeight`) and whose `ItemTemplate` is a `KeyCapView`. An `ItemsControl.Styles` entry projects each item's `X`/`Y`/`Width`/`Height` onto the generated `ContentPresenter`'s attached `KeyboardPanel.UnitX`…`UnitHeight`.
4. **`KeyCapView`** is one `Button` carrying the caption, the state classes and — only on a lighting picture — the LED strip.

Core's model raises no change notification (plain mutable POCOs), so `KeyboardKeyViewModel.RefreshFromModel()` — re-reading `Caption` and `IsModified` — is what the UI learns from; **every path that writes to `KeyboardKey` must end in it**, or the cap keeps showing the old assignment. `KeyboardLayerViewModel.RefreshFromModel()` is the layer-wide form.

## The generic component

`KeyboardView` is device-agnostic on purpose: it binds only to a `KeyboardLayerViewModel` and exposes a single `KeySelectedCommand` styled property that `KeyCapView` invokes through `$parent[KeyboardView]` with the clicked `KeyboardKeyViewModel` as the parameter. Neither the picture nor the cap knows the editor exists; `KeyboardEditorView` supplies `SelectKeyCommand`. **What a new device must supply is a `KeyboardVisual` and nothing else** — no XAML, no control, no view-model subclass. `EditorViewModelFactory` then resolves it automatically (it requires *both* `VisualCatalog` and `GeometryCatalog` to answer).

`KeyboardPanel` is a `Panel` subclass and the only piece doing arithmetic:

- Placement travels on **attached** `UnitX`/`UnitY`/`UnitWidth`/`UnitHeight` doubles, not off each child's `DataContext`, so the panel works with any item type. They are named `Unit*` because a static `WidthProperty`/`HeightProperty` declared here would hide `Layoutable`'s — a warning and a genuine XAML ambiguity.
- `BoardWidth`/`BoardHeight` are styled properties (`AffectsMeasure`); the four attached ones are `AffectsParentArrange`.
- `MeasureOverride` reports the board at the scale the offered space allows; `ArrangeOverride` scales **uniformly** (`min` of the two ratios), **centres** the result, and shrinks every cap by `KeyGapUnits` (**0.06** U) so neighbours never touch. A dimension that is infinite/NaN/non-positive contributes nothing, and a board that nothing constrains falls back to `NaturalUnitSize` (**44** px per unit). A board with no size still arranges every child to `default` — an unarranged child keeps stale bounds and would be painted over the empty picture.

`KeyCapView` sets the state classes `selected` / `listening` / `modified` / `locked` (`locked` = `!CanEdit`) plus the LED strip. The strip has **three** states and needs two answers from two places: the picture says whether lighting is on screen at all (`KeyboardView.ShowsLedStrips`, handed to each cap as `KeyCapView.ShowsLedStrip`), and the cap's own `HasColorOverlay` says whether *this* key is lit. No strip at all on the Keys tab; the hatch on a lighting board where the LED is off ("off is hatched, never black"); the colour where it is lit. The surface has to own the first answer because **both tabs render the same layer and cap view models** — see "The Lighting tab" — so nothing on the `DataContext` could separate them. All chrome lives in the design system ([design-system.md](design-system.md)), which is the authority on it; what the editor needs to know is where each piece went. The cap is the **`KeyCapButton` control theme** (`Themes/ControlThemes/Keycap.axaml`), which replaces Fluent's template outright rather than reaching into it — `Styles/Keyboard.axaml` only bridges `Button.keyCap` to that theme, and otherwise carries the `keyboardBoard` surface, the `keyCapText*` legend roles and the listening pulse. Cap precedence lives in the selectors, not in the file's order: every state names the ones it loses to (and `:disabled`, which beats them all), so a listening key always reads as listening and a dimmed board keeps no live face. The **layer switcher is a `ListBox` on the `SegmentedControl` theme** and the **section strip a `TabStrip` on `TabStrip`**, named at the call site in `KeyboardEditorView`; the `layerTab` / `editorTab` classes are gone, and the cleared `Transitions` both controls need — layer switching is deliberately unanimated — comes with the theme.

## The editor shell — the chrome `KeyboardEditorView` draws

The redesign gives the editor its own chrome (`docs/design/handoff.md` § "Editor shell", mockups `1e`/`1f`/`2a`), and it **replaces the shell's app bar** rather than sitting under it. The seam is two properties:

- `DeviceEditorViewModel.ProvidesOwnChrome` — virtual, `false`; `true` only on `KeyboardEditorViewModel`. The Savant Elite2 pedal editor keeps the shell bar until issue [#53](https://github.com/migus88/kinesis-edit/issues/53).
- `MainWindowViewModel.IsShellChromeVisible` — false while such an editor is open, bound to the app bar's `IsVisible` ([app-shell.md](app-shell.md)). Otherwise there would be 92 px of chrome and **two** status pills.

Home and the status chip are the shell's, so the editor is handed the shell **as data**: `DeviceEditorViewModel.Shell` (an `IShellChrome`), assigned by `MainWindowViewModel.OpenDeviceAsync` before the view swap and cleared by `CloseEditor`. **Not a `$parent[MainWindow]` binding** — every headless suite renders `KeyboardEditorView` standalone, where a visual-tree lookup resolves to nothing and the Home button and the chip would render blank in the tests *and* in the frames used to verify the screen. A view gets its data from its own `DataContext`.

Anatomy, top to bottom. The first three are **full-bleed**; only the content area is padded (`24,16`):

| Row | Height | Carries |
|---|---|---|
| Toolbar | `HeightToolbar` 46, `SurfaceBar` + 1 px `SurfaceLine` bottom | `Home` (`secondary`, → `Shell.HomeCommand`) · a 1 px divider · `DeviceName` (`toolbarDevice`) · `MountPath` in mono (`HasMountPath`) · `ProfileCaption` · right: the two counters, `Saving…`, **`Save`**, `StatusChipView` bound through `Shell` |

**No eject button**, though mockup `1e` draws one — see "Spec strings and deliberate deviations".

**`Save` turns amber whenever the session is dirty.** The view writes `Classes.dirty="{Binding IsDirty}"` and nothing else; the amber ramp is painted inside the `PrimaryActionButton` control theme ([design-system.md](design-system.md)), which is the only layer allowed to name a template part.

`IsDirty` is a **pull** from `IProfileSession.IsDirty`, which compares serialized lines. Core's model announces nothing, so *every* path that can move the layout or the lighting model has to re-ask it. `RefreshCounters()` is the hook for the layout paths and now ends in `RefreshDirtyState()`; the lighting tab has no counter to move and calls `RefreshDirtyState()` on its own. The complete list, each with a test:

| Path | Refreshed by |
|---|---|
| a captured remap (`ApplyRemap`) | `RefreshCounters()` |
| `ResetKey` / `ResetLayer` / `ResetLayout` | `RefreshCounters()` |
| an accepted Tap and Hold (`OnTapAndHoldClosed`) | `RefreshCounters()` |
| every macro-panel write (`MacrosChanged`: assign, delete, paste, steps, co-triggers, speed/repeat) | `RefreshCounters()` |
| a load, and an **import** (both go through `Apply`) | `RefreshCounters()` |
| every lighting write — mode, speed, direction, either colour swatch, a painted key, a painted zone, Reset All | `LightingTabViewModel.ModelChanged` → `RefreshDirtyState()` |
| a lighting **direction normalization** (`RefreshDirections`) | the same, and it is a write like the others — see below |
| a **successful save** | cleared outright, see below |
| a **settings** edit | *nothing, and it cannot be otherwise* — see "Settings are outside the dirty model" below |

**A successful save sets `IsDirty = false` rather than re-reading.** Core captures the dirty baseline at load and `ProfileSession.Save` does not move it ([profiles.md](profiles.md)), so the session goes on reporting itself dirty once it has been written; the next real edit re-asks and gets `true` again. A save that validation stopped, or that threw, leaves the flag set — nothing was written.

**`LightingTabViewModel.ModelChanged`** is new and exists only for this. It may fire for a write that changed nothing (re-reading a layer assigns the speed it just read); harmless, because the consumer re-asks the session rather than trusting the notification.

**The eighth lighting write site is the one that hides.** `RefreshDirections` writes `state.Direction` back whenever the layer's persisted direction is not one the mode offers — Rebound offers only `Left` and `Up` (07 §3), so a file carrying `down` is rewritten the moment that layer is *shown*: a mode pick, a layer switch, or `Attach` during the load itself. It has no counter to move, so it is easy to mistake for a read; it is a write into the profile's `LightingModel` and it raises `ModelChanged` like the other seven. Without that, clicking the **Fn** segment left the session dirty with Save still grey. It only announces a write that actually changed the value, so a layer whose direction the mode already accepts reports nothing.

The three reset buttons and the five spec 11 feature buttons live in a **provisional action row** under the content, commented as such: issue [#91](https://github.com/migus88/kinesis-edit/issues/91) gives the resets their real home in the legend row under the board, and [#92](https://github.com/migus88/kinesis-edit/issues/92)/[#93](https://github.com/migus88/kinesis-edit/issues/93) turn the feature panels into inspector panels. It sits under the whole content area rather than under the board so Export and Import stay reachable from the Lighting and Settings tabs too.

### Settings are outside the dirty model, deliberately

**The editor screen has two Save buttons, and the amber one does not cover the other.** `IProfileSession.IsDirty` compares the serialized **layout and lighting** files against the baseline captured at load ([profiles.md](profiles.md)) — the settings file is not in that comparison, and could not be: `KeyboardSettingsViewModel` reads and writes the device's settings file through `ISettingsService` on its own, with its own `SaveCommand` inside the Settings tab ([settings.md](settings.md)). So a settings edit moves nothing the session can see, and the toolbar's `Save` neither turns amber for it nor writes it.

That is the shape spec 08 §5 already has (settings are a separate file with a separate write), and this app keeps it. The consequence to know: the toolbar `Save` is the *profile's*, and leaving the editor with an unsaved settings row loses it just as silently as leaving with an unsaved remap — because there is **no unsaved-changes guard at all** (see "Deliberately not here"). `KeyboardEditorViewModel` does not override `ConfirmCloseAsync`, and the base returns `true` unconditionally.

## The advisory system — `ViewModels/Advisories/`

**The law first** (`docs/design/README.md`): *"Advisories never block. Amber, never red; nothing is clamped or refused; always shown twice — a mark on the exact key or row, and one calm summary strip per tab."* Everything below is that sentence made mechanical.

Five types, all under `KinesisEdit.ViewModels.Advisories`:

| Type | Is |
|---|---|
| `AdvisoryAnchor` | `EditorTab Tab` + `int? LayerIndex` / `KeyIndex` / `MacroIndex` — where it belongs on screen, and what `Review` selects. `MacroIndex` is the 1-based **slot** (06 §1), null for a flat-list macro |
| `AdvisoryViewModel` | One anchored sentence: `Anchor`, `Message`, `Detail`, and a `Severity` that is **always** `StatusSeverity.Warning`. Immutable, and not a `ViewModelBase` — an advisory is never edited, it is replaced |
| `EditorAdvisories` | The immutable set. `Build(KeyboardLayout?)`, `All`, `Total`, `ForTab(tab, layerIndex?)`, `CountForTab`, `CountForLayer`, `ForKey`, `HasAdvisoryForKey`, `HasAdvisoryForMacro`, `SummaryFor(tab, layerIndex?)` |
| `AdvisoryText` | **Every sentence template, in one static class**, so the wording lives once and is unit-testable on its own |
| `AdvisoryStripViewModel` | The strip itself: `AdvisoryCount` / `AdvisorySummary` / `HasAdvisories` / `ReviewCaption` / **`IsExpanded`**, `ReviewAdvisoriesCommand`, the `_reviewIndex` walk, `Project(set, tab, layerIndex)`, and the static `BuildPostSaveMessage`. It **projects, it never builds** — and it selects through two callbacks (`Action<AdvisoryAnchor>` for a key, one for a macro row), because the board and the macro panel are the editor's. That makes it constructible, and testable, with no loaded editor anywhere near it. Its one dependency is the session's `IAppPreferencesStore` (optional), which it follows until `Dispose` |

### The two sources, and what is deliberately not one

`Build` reads a `KeyboardLayout` and nothing else. Both sources already report rather than enforce:

| Source | Becomes | Anchored by |
|---|---|---|
| `Validate()`'s `TapAndHoldCountExceeded` | `Tap-and-hold count is 11 of 10. Files from older firmware…` | Layout tab, **layout-wide** (the validator reports no layer) |
| `Validate()`'s `MacroLengthExceeded` | `512 of 500 characters — over the device budget. Saved as-is.` | Macros tab, layer + key + slot |
| `Validate()`'s `MacroKeystrokeBudgetExceeded` | `layout keystroke budget 5 140 / 7 200 — over the device budget. Saved as-is.` | Macros tab, layout-wide |
| `Validate()`'s `MacroCoTriggerLimitExceeded` | `6 co-trigger modifiers — legacy budget is 4` | Macros tab, layer + key + slot |
| `DuplicateKeyScan.Find(layout)` | `[esc] is on 2 positions of this layer — 0, 20. Duplicates are allowed.` | Layout tab, **one advisory per position** of the group |

- **The other `ModelViolationKind`s are deliberately skipped.** They describe a model that cannot be written faithfully — a remap on a locked position, a macro on a board with no macros — which is a *failure* the save path reports, not something the amber strip should reassure the user about.
- **`DuplicateKeyScan.Find(layout)`, never `Find(layer)`.** The layer overload defaults to `TokenDialect.None`, which spells the token with whichever dialect the key-table entry carries first — a token the user's file may not contain ([keyboard-model.md](keyboard-model.md)). The layout overload passes `layout.Dialect`.
- **One advisory per position**, not one per finding, so every cap in the group carries the note and mockup 1e's "*3 keys carry advisory notes on this layer*" counts what it says it counts.
- **A flat-list macro gets no row dot.** The Advantage360 keeps its macros in one list and `Validate()` anchors a finding there by layer alone — there is no per-macro identity in the report to match a row against, and marking every row of that layer would say "this macro is over budget" about macros that are not. Those advisories are still counted and still shown in the strip; only the dot is missing, on the one board whose editor is [#41](https://github.com/migus88/kinesis-edit/issues/41).

### Where it is shown — twice, always

| Surface | What |
|---|---|
| `KeyboardKeyViewModel.HasAdvisory` | Per-cap flag, pushed in by `RebuildAdvisories()`. **Exposed and deliberately not rendered** — the design's 12×3 px `StatusAdvisoryStrong` cap bar belongs to the badge vocabulary of [#91](https://github.com/migus88/kinesis-edit/issues/91) (remap bar, macro dot, tap-and-hold corner, the legend row's live counts), and one badge drawn to a different rule than the four beside it is worse than none |
| `MacroListEntryViewModel.HasAdvisory` | An amber dot on the macro row, via `MacroPanelViewModel.Advisories` |
| `AdvisoryStripView` | The summary — **one control, one row, all four tabs** |
| The save toast | `AdvisoryText.SavedWithAdvisories(n)`, appended to the device's own post-save wording |

**One strip, not four.** "One summary strip per tab" is satisfied by a single control whose sentence and count are the *open* section's: `AdvisoryStripViewModel.AdvisorySummary` / `.AdvisoryCount` are already narrowed to `SelectedTab` and, on the Layout tab, to `SelectedLayer`. Four copies would be four things to keep in step.

**The strip is its own view model, not a face of the editor's.** The editor keeps `Advisories` (the whole set) and hands the narrowed view to `AdvisoryStrip` — everything the strip shows and does lives there. `AdvisoryStripView` therefore sets `DataContext="{Binding AdvisoryStrip}"` rather than inheriting the editor's, and is one of the few view models `ViewLocator` never resolves by name (it is hosted by property; `ViewResolutionTests` lists the reason).

`SummaryFor` says the least it can: one advisory speaks for itself (`Message`); several are summarised (`LayerSummary` on the Layout tab, `SectionSummary` elsewhere) using the **first** advisory's `Detail` fragment — which is why the layout-wide facts are added before the per-position ones and mockup 1e's sentence comes out in its own shape.

**One preference reaches the strip: `advisory_detail`** ("Explain advisory warnings in full instead of one line", mockup 1j). `AdvisoryStripViewModel` is handed the session's `IAppPreferencesStore` — the editor resolves it from `IDeviceSessionAccessor.Active?.Preferences`, falling back to `NullAppPreferencesStore` when there is no session — and exposes `IsExpanded`, read through `AppPreferenceCatalog.AdvisoryDetail.GetValue(...)` and **never off the stored flag**: it is the catalog's one *display* preference, where `on` means expand, the opposite polarity to every `*_msg` beside it ([settings.md](settings.md)). It re-reads on `Changed`, because the preference is edited on the Settings tab of the very editor the strip is drawn in, and the strip is `IDisposable` so it comes off a store that outlives the editor (`KeyboardEditorViewModel.Dispose`).

In the view this is a **layout change only**: `TextTrimming="CharacterEllipsis"` becomes `TextWrapping="Wrap"` through a `TextBlock.advisorySentence.expanded` class, and the Border's fixed `HeightAdvisoryStrip` becomes a `MinHeight` (`VerticalAlignment="Top"`, so a host that offers more room cannot inflate the bar; the editor's row 3 is `Auto`). Same tint, same dot, same `Review N`, and **no animation** — the growth is a state the user asked for rather than a transition, and the motion budget is fixed and small. Expanded-with-one-line still measures 30 px, so only a sentence that really wraps moves anything.

### The rebuild hook, and the one place it is not

`RebuildAdvisories()` is called from **`RefreshCounters()`** — the funnel every layout-mutation path already ends in (see the `IsDirty` table above), so a remap, a reset, an accepted tap-and-hold, any macro write, a load and an import all produce a fresh set. It is deliberately **not** called from `RefreshDirtyState()`, the lighting tab's own hook: the set is derived from the `KeyboardLayout` alone, a lighting write cannot move it, and `Validate()` walks every key of every layer — paying for that on each click of the colour picker would be felt for a set that cannot have changed.

`RefreshAdvisorySummary()` is the cheap half: it hands the existing set to `AdvisoryStrip.Project(...)` narrowed to the open tab and layer, and is called from `SelectTab` and `SelectLayer`, neither of which changes the model.

### `Review N`

`AdvisoryStripViewModel.ReviewAdvisoriesCommand` walks the open section's anchored advisories, one per press, wrapping at the end (`_reviewIndex`, reset to −1 by every `Project`, i.e. whenever the set, the tab or the layer moves). It dispatches on the projected tab and calls one of its two callbacks; the editor supplies both. `SelectAnchoredKey` selects the anchored cap **through `SelectKeyDirectly`, never `SelectKey`** — the second-click promotion to listening would eat the user's next keystroke, and reviewing is reading. `SelectAnchoredMacro` runs `MacroPanel.SelectMacroCommand` for the matching row. The command carries **no `CanExecute`**: an advisory never disables anything, so with nothing anchored the press is a no-op. Nothing here has to switch layers, because the Layout strip is already narrowed to the shown layer.

### Amber, never red

- The macro panel's three budget readouts bind **`Classes.statusWarning`** (→ `StatusAdvisoryTextBrush`), not `statusError`. A budget is reported, never refused; red is for a genuine failure. `KeyboardEditorView.axaml` now names no error role at all, and `AdvisoryStripTests` fails if either changes.
- The strip is `StatusAdvisoryTintBrush` on `StatusAdvisoryTintBorderBrush` with a `StatusAdvisoryBrush` dot; the macro row's dot is the same role.

## `KeyboardEditorViewModel`

`DeviceEditorViewModel` — the shell's abstract editor base, shared with `EditorPlaceholderViewModel` and `SavantElitePedalViewModel` ([savant-elite.md](savant-elite.md)) — supplies `Device`, `DeviceName`, `IsDemoMode`, `ProvidesOwnChrome`, `Shell` and the virtual `LoadAsync()`/`ConfirmCloseAsync()`; `MainWindowViewModel.Editor` is typed as that base so navigation is independent of which editor a device resolves to. This class overrides `LoadAsync` and keeps the default `ConfirmCloseAsync` (always true): the unsaved-remap question is not built here yet — the pedal editor is the only one that gates its close ([savant-elite.md](savant-elite.md)).

State: `IsLoading` (true until the first load finishes), `IsBusy` (a save is in flight), **`IsDirty`**, `Layout`, `Layers`, `SelectedLayer`, `SelectedKey`, `ListeningKey`/`IsListening`, `ProfileCaption`, **`MountPath`/`HasMountPath`**, `ModifiedKeyCount`/`RemapCounterCaption`, `MacroCount`/`MacroCounterCaption`, `InvalidLineMessages`/`HasInvalidLines`, `BoardWidth`/`BoardHeight`, `Tabs`/`SelectedTab`, `MacroPanel`/`IsMacroPanelVisible`, `ActiveOverlay`/`HasActiveOverlay`/**`IsCaptureActive`** (the keyboard grammar's gate 1), the advisory set **`Advisories`**, and the strip it projects onto, **`AdvisoryStrip`**.

Commands and what gates them (`NotifyCommands()` re-evaluates all of them on every state move):

| Command | Enabled when |
|---|---|
| `SelectKeyCommand(KeyboardKeyViewModel?)` | always (the click contract below) |
| `SelectLayerCommand(KeyboardLayerViewModel)` | always |
| `SelectTabCommand(EditorTabViewModel)` | the strip carries that tab — every tab it carries works (table below) |
| `BeginRemapCommand` | `SelectedKey is not null && SelectedKey.CanEdit && !IsLoading && !IsBusy && !MacroPanel.IsRecording && ActiveOverlay is null` |
| `CancelRemapCommand` | `IsListening` |
| `ResetKeyCommand` | `SelectedKey is not null && SelectedKey.CanEdit && !IsLoading && !IsBusy` |
| `ResetLayerCommand` | `SelectedLayer is not null && !IsLoading && !IsBusy` — async; confirms under `NotificationKeys.ResetLayer` before erasing |
| `ResetLayoutCommand` | `Layout is not null && !IsLoading && !IsBusy` — async; same key, its own wording |
| `SaveCommand` (async) | `_session is not null && _session.CanSave && !IsDemoMode && !IsLoading && !IsBusy` |
| `TapAndHoldCommand` (async) | `Layout`, `SelectedLayer`, `SelectedKey` all set + **`Layout.Device.TapAndHold.IsSupported`** + `SelectedKey.CanEdit` + `!IsLoading && !IsBusy && ActiveOverlay is null` |
| `InsertDelayCommand` (async), `InsertSpecialActionCommand` | `Layout is not null && IsMacroPanelVisible && MacroPanel.EditedMacro is not null && !IsLoading && !IsBusy && ActiveOverlay is null` — the **`IsMacroPanelVisible`** half is new, see below |
| `ExportCommand` | `_session is not null && !IsDemoMode && !IsLoading && !IsBusy && ActiveOverlay is null` |
| `ImportCommand` (async) | `_session is { CanSave: true } && !IsDemoMode && !IsLoading && !IsBusy && ActiveOverlay is null` — `CanSave` is what carries the Adv360 profile-0 guard |
| `OpenSearchCommand` | `Layout is not null && !IsLoading && !IsBusy` — ⌘F, see "The keyboard grammar" |
| `CloseOverlayCommand` | `ActiveOverlay is not null` |
| `AdvisoryStrip.ReviewAdvisoriesCommand` | **always** — an advisory never disables anything; with nothing anchored the press is a no-op |

The three reset commands share the save guard (`!IsLoading && !IsBusy`) because a save serializes the model on a background thread and mutating it mid-save would race it. **Every feature command additionally requires no open panel** — an inline panel is modal and must not be raced by the editor underneath it.

Two of those gates are less obvious than they look:

- **Tap and Hold asks whether the *device* has the feature** before the firmware gate and before §11.1's four pre-dialog checks. A board without it also states no delay range, so the panel would open at 0 ms and the assignment would be reported as `TapAndHoldNotSupported` — which blocks the entire save, not just that key ([feature-dialogs.md](feature-dialogs.md)).
- **The two insertion commands need the macro panel on screen**, not merely a macro open. Selecting any macro-capable key opens an unassigned draft, so on the Keys tab the picked delay or action would be appended to a macro the user cannot see and never assigns. `SelectTab` therefore re-evaluates the commands.

`SelectedTab` is a two-way-bindable property whose setter runs the same guard as the command, so a binding cannot open a tab the strip does not carry. **Switching tabs cancels an in-flight remap**, because listening belongs to the keyboard picture and capture is never left running (invariant 4); leaving the Macros tab additionally stops any macro recording, the other consumer of the same service.

### The tab strip is device-driven — absent, never disabled

`EditorTabViewModel.CreateAll(DeviceDefinition device, bool isLightingSupported)`. **There is no `IsEnabled`.** The design's capability law is "absent features are not shown, not disabled" (`docs/design/README.md`), so a section this app cannot open for this board is not rendered at all:

| Tab | Present when |
|---|---|
| `Keys` (captioned **`Layout`**) | always |
| `Macros` | always — the panel behind it reads `MacroCapability` and says `This device does not support macros.` itself |
| `Lighting` | `device.Lighting.Kind != LightingKind.None` **and** `LightingTabViewModel.IsSupported(device)` — the Freestyle Edge RGB only. Absent on the Freestyle Pro and Advantage2 (no lighting hardware) *and* on the TKO and Advantage 360, whose led files this app cannot edit yet (#40/#41) |
| `Settings` | `device.Settings != SettingsCapability.None` — absent on the Savant Elite2, CROSSFIRE and Advantage 360 Professional |

Three things worth keeping in mind:

- **The enum member `EditorTab.Keys` keeps its name** even though the caption is now `Layout`: the identifier is carried inside `EnumMatch` converter-parameter *strings* in XAML (`ConverterParameter='Keys,Macros'`), so renaming it is a string-coupled change with no user-visible payoff.
- **`Macros` is neither filtered nor gated**: its panel already answers the capability question in its own `Message`, and a second answer here is a second place for the two to disagree.
- **The lighting flag is a device-level question on purpose**: the editor's constructor runs before any profile is read, and demo mode never reads one, so it cannot be `session.Lighting is LightingModel`. The strip is therefore fixed at construction, and `SelectTabCommand`'s predicate reads nothing but whether it was handed a tab, which is why `NotifyCommands()` deliberately does not re-ask it.

`EditorTabViewModelTests` asserts, for every catalog device, that the Settings tab exists exactly when `KeyboardSettingsRows.Create` yields rows and that the Lighting tab exists exactly where the panel can edit the led file — a tab and its panel can never disagree — plus that no strip ever carries a section the editor would have to refuse.

### The Settings tab — `KeyboardSettingsViewModel`

The device-side settings of spec 08 §5, hosted as `KeyboardEditorViewModel.Settings` and rendered by `KeyboardSettingsView` through `ViewLocator`. It is always constructed (cheap, no I/O) and only reachable when the tab exists.

- **Rows come from the capability, never from a device id.** `KeyboardSettingsRows.Create(SettingsCapability)` emits, in spec 08 §2 table order: active profile (1–9), `led_mode` (only in its `ModeString` form), macro speed, status report speed, the v-Drive switch in whichever of its two key forms applies, then game mode / program lock / key clicks / key tones. Every board therefore gets its panel the moment its picture is authored, with no per-device code. Row kinds are `SettingsSliderRowViewModel`, `SettingsToggleRowViewModel` and `SettingsChoiceRowViewModel`, each carrying a reader/writer delegate pair — no row knows a key name, and the `led_mode` options are Core's `LedModeValues.All` (the serializer's own domain) with captions added here.
- **The active-profile row writes through `StartupProfileSettings.ApplyStartupProfile`**, so the paired `led_mode=led<N>.txt` of 08 §5.1 / 07 §1.2 cannot drift from `ProfileSession.SaveAs`.
- **Clamping is the slider's job.** `KeyboardSettingsSerializer` throws on a value outside `SettingsValueRanges`, and an exception must never escape into the UI, so `Value` is clamped in its setter *and* in `ApplyTo`. The "Disable" checkbox writes `0`; it only exists where the slider floor is above 0 (`SettingsCapability.MacroSpeedMinimum`).
- **A key absent from the file reads as its unset default** — spec 08 §2's "missing keys leave zero/false/empty values": speeds load as *disabled*, toggles as off, and the profile number as 1 (it has no zero). The choice row is the exception, and deliberately so: absent means **unset**, not `Options[0]`. `SelectedOption` is nullable, an unrecognised value (a `led_mode` newer firmware wrote) is held in `UnrecognizedValue` for the `ComboBox`'s `Placeholder`, and an unset row writes **null** — which is exactly what preserves the device's line, because a null property emits no pair and a save only passes managed pairs to `UpdateSettingsFile` (08 §1). Handing the unknown text back to the serializer would preserve nothing: it throws outside `LedModeValues`, taking the whole panel's Save with it. Mapping absent → `0` would switch a Freestyle Edge's backlight fully off on the first save.
- **Advantage2 4MB lock** (08 §5.4): `KeyboardSettingsGate.CanEditKeyboardSettings(DeviceId, VersionFile)` false ⇒ `IsLocked`, every row disabled, Save unavailable. **Demo mode passes the gate**, as every firmware gate does (`FirmwareGateService`, 09 §2): it supplies `VersionFileInfo.Empty`, and a 2MB diagnosis about an unattached board would be fabricated. Nothing is written there anyway.
- **The lock is drawn as read-only, never as an error** (mockup 1j). `IsLocked` puts a banner over the section carrying `ReadOnlyBanner` + `ReadOnlyExplanation` (Core's verbatim 1j strings) and `LockHint` (08 §5.4's own wording, kept as the footnote that names the condition the gate actually tested), plus a `Which board do I have?` link — `Button.link` + `IconExternalLink` + `IUrlLauncher` against the catalog's `TroubleshootingUrl`, the same three parts as the empty state's `Troubleshooting tips`. Each row then carries `IsReadOnly`, rendered as `SettingsMessageCatalog.ReadOnlyRowMarker` (`(read-only)`) on muted meta type **outside** the disabled part, so the value stays live and readable, and `ShowsSaveAction` drops the Save button entirely rather than greying it. **Every surface on the screen is on the advisory ramp or a plain muted one; no `StatusError*` brush is reachable from `KeyboardSettingsView`** — a board that refuses writes is a hardware fact, not a failure. `IsReadOnly` is deliberately *not* `!IsEnabled`: a row is also disabled while loading, while saving and after a failed read, none of which may carry the marker.
- **The tab is a list of sections.** `KeyboardSettingsView`'s root is one `StackPanel` whose children are sections; the device rows are the first, headed by `KeyboardSettingsViewModel.DeviceSectionLabel` (`"Written to the keyboard"`) on `.sectionLabel`. The label is a view-layer const rather than a Core string, because it names a piece of screen rather than a settings rule — the split `NoDeviceViewModel.TroubleshootingButtonCaption` already makes.
- **Demo mode never writes, but it does read** (03 §3.5, 08 §3 — the ban is on *saving*): with a `Location` the file is loaded exactly as usual and `DemoModeHint` explains that Save is unavailable, the same rule the colour picker's custom slots follow. Demo mode is entered for a drive that is merely not writable, so inventing values there would be showing wrong settings for connected hardware. Only a device with **no `Location`** reads nothing, and it says so with `NoDriveHint` rather than claiming the rows are the device's.
- **Save is unavailable until a read has succeeded.** `HasLoadedSettings` — not `!IsLoading`, which is also true after a read that threw — gates `SaveCommand` *and* the rows' `IsEnabled`, so the panel can never write its constructor defaults (`v_drive=manual` among them) over a file nobody managed to read.
- **Load and save are total.** `LoadAsync` (fired by the editor's own `LoadAsync`, idempotent) reports a read failure *inline* rather than stacking a second modal on the editor's, and `StatusMessage` is composed from its two independent parts (demo/no-drive hint, read failure) so one never hides the other; `SaveAsync` mirrors the profile save — `IsBusy`, `ShowLoading`/`HideLoading` in a `finally`, failures through `TryShowMessageBoxAsync` titled `Save Settings`, success as a toast carrying Core's `SettingsSavedTitle`/`SettingsSavedMessage`.

#### The tab's second section — `AppPreferencesViewModel` + `Views/AppPreferencesView`

Below the device rows, and unrelated to them in everything but the screen they share: **this app's** per-device preferences and the custom-swatch strip, both in `app_settings.txt` and both over the session's one `IAppPreferencesStore` ([settings.md](settings.md)). `KeyboardSettingsViewModel` **owns** it as `Preferences` and `KeyboardSettingsView` hosts `AppPreferencesView` explicitly (like `KeyboardEditorView` hosts `AdvisoryStripView`) — the section's own markup reaches its owner with `$parent[views:AppPreferencesView]`, which needs the real control in the tree.

- **The store is a required constructor parameter of both `KeyboardSettingsViewModel` and `LightingTabViewModel`, with no default.** A defaulted `NullAppPreferencesStore` is exactly the failure this section cannot survive: a host that forgot to thread it would render a whole screen that reads and writes nothing while every unit test on both classes still passed. A host with no drive passes `NullAppPreferencesStore.Instance` in as many words. `EditorViewModelFactoryTests.Create_ForAnOpenSession_GivesBothPreferenceConsumersThatSessionsOwnStore` walks the composition root's own path — session first, then factory — and asserts one write on the session's store reaches both tabs.
- **It is drawn for every board, including one with no keyboard settings at all.** These preferences describe the app's behaviour on this device, not the hardware's, so the capability gate above has no say over them. `LoadAsync` reads it **first and outside** the device-settings guards, or a board with no settings capability would leave the section on its constructor defaults.
- **Rows come from `AppPreferenceCatalog`**: five featured (mockup 1j's own, in 1j's order) plus the rest behind a disclosure whose caption carries a **computed** count (`+N more`), because 1j's literal `+7` assumed twelve keys and there are seventeen. Each row is an `AppPreferenceRowViewModel` over one descriptor, so the polarity — `on` = *hide* for the `*_msg` prompts, `on` = *expand* for `advisory_detail` — lives in the catalog and never in this class.
- **Demo mode moves the boxes but persists nothing**, and says so with `SettingsMessageCatalog.DemoModePreferencesCaveat`: spec 08 §3 bans *saving* app settings there, not loading them, so the section still shows what the drive carries. The **swatch strip** is the one genuinely frozen part (`CanEdit` = `IsWritable`), so that it agrees with the lighting picker's already-unavailable `Add to Custom Colors`.
- **`CustomSwatchesViewModel` is the second consumer of the twelve `cust_color_N` slots** and the reason the store exists. It and `ColorPickerViewModel` both read `Current` and re-read on `Changed`, so a swatch stored in the lighting picker is on this strip immediately and one cleared here disappears from the picker, with no reload on either side. The colour is typed as `#RRGGBB` in a mono `TextBox` — the mono law's own case — rather than picked from a ring: the ring belongs to the tab where a colour is being chosen *for* something, and this strip exists to manage the twelve values a config file carries.

### The Lighting tab — `LightingTabViewModel`

The per-layer LED editor of spec 07 §3/§4, hosted as `KeyboardEditorViewModel.Lighting` and rendered by `LightingTabView`. Like the settings panel it is always constructed and only reachable when its tab is enabled; unlike it, **it has no save path of its own** — `ProfileSession.Save` serializes whatever `IProfileSession.Lighting` holds, so mutating that model *is* the save (see [profiles.md](profiles.md)). The editor's `Apply` hands it the model and the same `KeyboardLayerViewModel`s the Keys tab draws.

- **Every rule is Core's.** Mode membership and gating are `LightingAvailability.IsKeyBacklightModeAvailable`, captions are `LightingModeDefinition.DisplayName`, directions are `LightingAvailability.GetKeyBacklightDirections` (device-aware, so Fireball shows no arrows on the RGB), zones are `LightingZoneCatalog`, speed bounds are `LayerLightingState.MinimumSpeed`/`MaximumSpeed` ([lighting.md](lighting.md)). No mode name is spelled out in this layer.
- **`LightingPanelVisibility.For(deviceId, mode, isLayerCustomizationAvailable)`** is the §3 "which panels each mode shows" table, derived from the catalog flags rather than restated: effect colour = `WritesEffectColor || HasPerKeyColors` (§3 lists Freestyle and Breathe alongside the eight that write one), base colour = `HasBaseMonoLine` **and** the firmware gate, speed = `WritesSpeed`, direction = a non-empty availability list, per-key/zones/Reset All = `HasPerKeyColors`. It is one value on the view model, so the tab has one property instead of seven and the matrix is unit-tested on its own.
- **Two layers, fully independent** (§4). `Layers` is always Top + Fn — the two a led file describes — regardless of how many layers the picture has. A layer switch re-reads mode, colours, speed, direction and the picture from the new state; the Fn pill **and** the base-colour swatch sit behind `LightingAvailability.IsFnLayerLightingAvailable` (`LightingLayerCustomization`, LED ≥ 1.0.44), read from `DeviceSnapshot.Firmware`. Demo mode reports every gate as passing.
- **One picker, two targets.** `EffectColor`/`BaseColor` are `LightingColorSlotViewModel`s carrying a reader/writer pair onto `LayerLightingState` (the same shape the settings rows use); `SelectColorSlotCommand` points the picker at one, and the picker's `ColorChanged` writes through. A mode change re-selects the first *visible* slot, so the picker never edits a swatch the mode does not have — and the picker itself is bound to `Panels.ShowsAnyColor`, so in Disabled/Spectrum/Wave/Pulse it is **hidden** rather than rendered with nothing to write to (`ShowsAnyColor` covers per-key painting too, because a per-key mode's effect colour is the colour a click paints with).
- **Per-key painting and zones use `Picker.Color`** (§4: "clicking a key applies the currently selected picker color"). Keys are addressed by **memory key code** (`key.Key.OriginalKey.Code`), and **black clears the entry** — `SetKeyColor`'s contract (§2.1) is honoured rather than worked around, which also makes the black premixed swatch the eraser. **Zone codes are authored against the top layer**, so on the Fn layer each is re-resolved top code → top index → the Fn key at that index (§2.4 item 6): the Function zone lands on the Fn layer's media keys, not on F1–F6 it does not have.
- **A direction the mode rejects is normalised** on mode change (§2.4 item 5 writes it as the default anyway), so the control and the file agree before the save rather than after it.
- **"Reset All"** is offered for the per-key modes only (§4) and calls `LayerLightingState.ClearKeyColors()` after a Yes/No box whose message is the spec's wording verbatim. A box that cannot be shown erases nothing.
- **Repainting.** After every model write the tab rebuilds `KeyColorOverlay.Build(...)` and pushes it through `KeyboardLayerViewModel.ApplyColorOverlays`, which is whole-layer (a key the map no longer mentions goes back to unlit). Both tabs share the cap view models, so the colours land on the Keys tab's caps as well — but only this picture asks for an LED row (`ShowsLedStrips="True"` on its `KeyboardView`), so only this one draws any of it. The Keys tab has no LED row at all.

#### The colour picker — `ColorPickerViewModel` + `Controls/ColorPickerView`

`ColorPickerView` wraps Avalonia's `ColorView` (package `Avalonia.Controls.ColorPicker`, pinned to the same **11.3.12** as every other Avalonia package) for the HSV ring, the R/G/B sliders and the hex field, and adds the two things the stock control has no notion of:

- **The ten premixed swatches of §4**, in the spec's order (white, yellow, red, lime, blue, fuchsia, orange 255/128/0, azure 0/128/255, aqua, black), as a static list on the view model.
- **The twelve custom slots**, `cust_color_1`…`cust_color_12` in `app_settings.txt`. The picker **no longer touches that file itself**: it reads `IAppPreferencesStore.Current` on `LoadAsync` (any drive, even in demo mode — spec 08 §3 bans *saving*, not loading), writes through `Update(settings => settings.WithCustomColor(...))`, and re-reads on `Changed` — so the Settings tab's swatch strip and this picker can never show each other stale slots. Its own read-modify-write is gone; the store owns that now ([settings.md](settings.md)). `LedColorConverter` does the `LedColor` ↔ `SettingsColor` conversion. `Add to Custom Colors` fills the first empty slot, then rotates. **`CanStoreCustomColors` is `IsWritable`** — false in demo mode and without a drive — and the command is disabled rather than silently forgetting the slot. Every I/O failure is swallowed by the store — a picker preference is not worth a dialog.

`ColorView` ships its control theme in its own assembly, so `App.axaml` includes `avares://Avalonia.Controls.ColorPicker/Themes/Fluent/Fluent.xaml` after `FluentTheme`; without it the picker renders untemplated. The `#RRGGBB` ↔ `Color` conversion is `HexColorToColorConverter` (two-way, alpha dropped, `BindingOperations.DoNothing` on a non-colour), so no Avalonia colour ever reaches a view model.

### Lifecycle — `LoadAsync`, `Dispose`

**Construction is deliberately cheap**: it resolves the device's `KeyboardVisual`, builds the tab strip and commands, and subscribes to `IKeystrokeCaptureService.KeystrokeCaptured`. No file is touched, so the shell can swap the view in immediately — `MainWindowViewModel.OpenDevice` fires `_ = editor.LoadAsync()` **after** the view swap and after hiding its own loading splash; the drive read runs against the editor's own `IsLoading`.

`LoadAsync` is **total and idempotent** (`_hasLoadStarted` / `_isDisposed` guards; a second call is a no-op), which is what makes forgetting the task safe:

- The read runs off the UI thread (`Task.Run`, resumed with `ConfigureAwait(true)`).
- **Demo mode, or a device with no `Location`** → `KeyboardLayout.Create(Device.DeviceId)` in memory, no session: `ProfileCaption` stays empty and Save is permanently unavailable (03 §3.5 — demo mode never touches the drive).
- **Otherwise** → `IProfileSessionFactory.Load(Device.Location, Device.DeviceId, Device.Device.LayoutScheme.FirstProfileNumber)`, i.e. profile 1 on every numbered-profile device.
- **Any failure** (vanished drive, unreadable file, unsupported device) degrades to the same in-memory layout plus a `LoadFailureTitle` message box — the editor never crashes the shell. If even `KeyboardLayout.Create` throws (a device with no geometry), `Layout` stays null and the picture is empty.
- `Apply` then sets `Layout`, `ProfileCaption`, `InvalidLineMessages`, builds `Layers`, **rebuilds the macro panel** (`AttachMacroPanel`, which detaches the old one first and subscribes to `RecordingChanged`/`MacrosChanged`/`PropertyChanged`), selects layer 0, and refreshes both counters. A successful **import** re-runs the very same `Apply` over the session, because the imported file built a brand-new model exactly as a load would have.

`Dispose` (called by `MainWindowViewModel.CloseEditor` on navigate-home and on re-open, and by `App`'s exit path through the shell) detaches from `KeystrokeCaptured`, drops the Tap and Hold hooks, **closes the overlay host**, detaches the macro panel (stopping any recording) and stops capture. It is idempotent. **Leaving capture started would swallow every keystroke of the dashboard behind the closed editor** — the capture service is app-wide and outlives the editor. The host *cancels* the open panel rather than dropping it, because the one-shot insertion hooks come off on the panel's own `Closed`; the Tap and Hold hooks are dropped **before** that, which is why a half-finished assignment cannot write back into a disposed editor.

### Remap state machine

One key listens at a time; capture is started **only** on entering listening and always stopped again on the way out.

| State | Input | Next state | Side effect |
|---|---|---|---|
| nothing selected | click key *K* | *K* selected | — |
| *K* selected | click *K* | *K* listening (only if `CanBeginRemap`) | `capture.Start()` |
| *K* selected | click *L* | *L* selected | — |
| *K* listening | click *K* | *K* selected | `capture.Stop()` |
| *K* listening | click *L* | *L* selected | `capture.Stop()` |
| *K* listening | keystroke captured | *K* selected | `Remap`, `capture.Stop()`, refresh cap + counter |
| *K* listening | `CancelRemapCommand` (Cancel button, Escape fallback) | *K* selected | `capture.Stop()`, model untouched |
| any | layer switch | nothing selected | `capture.Stop()` |
| *K* listening | tab switch | *K* selected | `capture.Stop()` |
| any | `SelectKeyCommand(null)` | nothing selected | `capture.Stop()` |
| any | macro recording starts | listening cancelled | `capture.Start()` for the recording instead |
| any | a feature panel opens | listening cancelled | the panel owns capture from there ([feature-dialogs.md](feature-dialogs.md)) |
| *K* listening | `Dispose` | — | `capture.Stop()`, unsubscribe |

`CanBeginRemap` is false for a locked position (`CanEdit == false`, 05 §5.3), while loading, while saving, **while the macro panel is recording, and while a feature panel is open** — the last two would fight over the same keystrokes. Clicking a locked key twice selects it and does nothing else. `BeginRemapCommand` is the same entry point without the click (bindable, and what the tests use).

**Escape is not the cancel key — this is the single most surprising thing about the workflow.** While a key listens, the capture service previews the window's key events in the tunnel phase and swallows every physical key it resolves, Escape included, so **Escape is assigned like any other key**: a keyboard must be able to carry an Escape remap. The same holds while a Tap and Hold field is armed. Cancelling is a pointer action — the *Cancel* button beside the listening banner, clicking the listening key again, clicking another key, or switching layer. `KeyboardEditorView` registers a tunneled `KeyDown` handler (`handledEventsToo: true`, as in `MessageBoxView`) for the two things Escape may still do. **An open feature panel goes first and is dismissed whatever `e.Handled` says** — capture may be running for something else entirely (a macro recording used to swallow the Escape and leave the panel unclosable), and a panel that cannot be dismissed from the keyboard is worse than an Escape that also lands somewhere. The one exception is a panel that is itself waiting for a keystroke, which the view reads off `KeyboardEditorViewModel.IsOverlayAwaitingKeystroke` — an armed Tap and Hold field takes the Escape and disarms, so the next Escape closes the panel. With no panel open, `CancelRemapCommand` runs if it can: while a key is listening the capture handler on the `TopLevel` above has already assigned the Escape and left listening state, so the command is unavailable and nothing double-fires.

**Applying a captured keystroke goes through the editor path `KeyboardKey.Remap(keystroke.Key)`**, which means capturing a key's *own original action* clears the remap (04 §2.1), exactly like the legacy apps. `ResetKeyCommand` deliberately calls `ClearRemap()` instead: `Remap(OriginalKey)` also clears the position's tap-and-hold and multi-modifier as a side effect ([keyboard-model.md](keyboard-model.md), "Watch out"), which is not what "reset this key's remap" means. `ResetLayerCommand`/`ResetLayoutCommand` call Core's `KeyboardLayer.Reset()`/`KeyboardLayout.Reset()` (which clear all four rule kinds; `KeyColor` survives) and then re-read every cap.

`ResetLayerCommand`/`ResetLayoutCommand` also stop macro recording and call `MacroPanelViewModel.RefreshFromModel()` afterwards — `Reset()` empties the macro slots too, so the panel would otherwise sit on macros that no longer exist.

**Both of them confirm first, and the confirmation is the app's first suppressible dialog.** They are `AsyncRelayCommand`s that raise a `Confirmation` / `YesNo` box through `INotificationService` carrying **`SuppressionKey = NotificationKeys.ResetLayer`** and `SuppressedResult = Yes`, so the "Don't ask this again" checkbox appears and the answer is written to `app_settings.txt` as `reset_layer_msg=on` ([settings.md](settings.md)). Four rules hold here:

- **The editor never reads `IsHidden`.** `NotificationService` short-circuits a hidden key to `MessageBoxOutcome.ForSuppressed(request)`; checking the flag at the call site as well would be two policies for one decision. Hence `SuppressedResult = Yes` — a switched-off confirmation means "go ahead", not "do nothing".
- **Anything but `Yes` erases nothing**, a box that could not be shown at all included (the rule the Lighting tab's Reset All already follows).
- **`ResetLayout` shares the key** and differs only in wording (`ResetLayoutConfirmation` names every layer). The catalog models one reset confirmation — "Confirm before resetting a layer", mockup 1j — and a user who switched it off has answered for both scopes; leaving the wider one unsuppressible would put two policies behind one checkbox and leave a prompt the settings screen cannot re-enable. A reset is in-memory either way: nothing reaches the drive until Save.
- **`ResetKeyCommand` stays unguarded**, deliberately. Spec 08's other reset flag (`reset_key_msg`) guards resetting a *macro*, which that command does not do — it drops one position's remap — and the catalog marks it forward-declared. `KeyboardEditorViewModelTests` pins the asymmetry so it cannot become an accident.

This is the **first production call site of the suppression pipeline**; `NotificationKeys`, the checkbox and the store existed before it and were reached by nothing ([app-shell.md](app-shell.md)).

Both counters of spec 10 are recomputed together by `RefreshCounters()`: `ModifiedKeyCount` → `Remap (n)` (`KeyboardLayout.ModifiedKeyCount`) and `MacroCount` → `Macro (n)` (`KeyboardLayout.MacroCount`). It runs after a load or import, after a captured remap, after each reset, after an accepted tap-and-hold, and on every `MacrosChanged` the macro panel raises — **and it ends in `RefreshDirtyState()`**, which is what keeps the amber Save honest (see "The editor shell" above).

### Keystroke routing

The editor owns the **single** subscription to `IKeystrokeCaptureService.KeystrokeCaptured`, so spec 10's routing rule lives in one method (`OnKeystrokeCaptured`) and one keystroke reaches exactly one target, in this order:

1. **The open feature panel**, if it is an `IKeystrokeSink` — Tap and Hold. It takes the keystroke on being *open*, which is spec 10's own wording ("forwarded to the Tap and Hold dialog **if that dialog is open**"); an unarmed panel swallows it and drops it, so nothing under a modal panel can consume keys aimed at it.
2. **The macro panel**, if it is recording — the keystroke is appended to the macro under edit, with the modifiers held at that moment folded into the step (05 §5.1).
3. **The listening key**, applied as a remap.

Capture is *started* by whichever of the three needs it and by nobody else: `BeginRemap` for a listening key, `OnMacroRecordingChanged` for a recording (the panel only announces `RecordingChanged`; the editor turns the service on and off around it), and `EditorOverlayHost` for an armed sink. Entering recording cancels a listening key first, and opening a panel ends both.

### The keyboard grammar — `Input/EditorShortcuts`, `KeyboardEditorView.OnPreviewKeyDown`

Mockup `2b`'s shortcut table, verbatim, and the whole of it:

| Keys | Intent | Runs |
|---|---|---|
| `↑ ↓ ← →` | move the key selection across the **physical** board | `KeyboardEditorViewModel.MoveSelection(NavigationDirection)` |
| `⌥1`–`⌥5` | show layer *n* — a number past the layer count is a no-op | `SelectLayerCommand` |
| `⌘F` | open Search Keys (§11.6) and put the caret in its field | `OpenSearchCommand` |
| `⌘S` | save | `SaveCommand` |
| `⌘W` | back to the dashboard | `Shell.HomeCommand` |
| `Esc` | *not in this table* — see below |

**`Input/EditorShortcuts.Map(Key, KeyModifiers, bool isMacOs)` → `EditorShortcut`** is the whole platform question, in one pure function: ⌘ is `Meta` on macOS and `Control` elsewhere, ⌥ is `Alt` on every platform (Alt *is* Option on macOS, so only the spelling on the layer chip changes). `isMacOs` is a **parameter**, the same shape `KeyCaption.For` uses — a test that only passes on a Mac is a test that fails in CI. `ToDirection` and `ToLayerNumber` are its two projections; `ToDirection` never answers `NavigationDirection.None` for a move, because `KeyAdjacency.Next` throws on it. **The modifier set is matched exactly, never masked**: `⌘⇧S` is not `⌘S`, and an arrow with anything held is not an arrow.

**One handler carries it, and there are deliberately no `KeyBinding`s or `KeyGesture`s anywhere in this app.** `KeyboardEditorView.OnPreviewKeyDown` — tunnelled, `handledEventsToo: true` — is the same handler Escape already used. An accelerator fires wherever it is in scope, and neither gate below is expressible as a gesture.

**The view is focusable and takes focus on attach** (`Focusable = true`, `IsTabStop = false`). A tunnelling key event travels only the chain between the window and whatever holds focus, so a handler on this control sees nothing while focus is outside it — and a freshly opened editor has focus nowhere inside it, which would leave ⌘S dead until the first click. It is not a tab stop, so Tab still walks the toolbar, the tabs, the layer switcher and the board exactly as before.

**Gate 1 — capture wins, always.** `KeyboardEditorViewModel.IsCaptureActive` (a listening key **or** a recording macro **or** an armed sink panel — the three consumers of invariant 5) turns the entire grammar off. A user assigning ⌘S to a key must get `s`-with-Meta recorded, not a save. It is read on demand and is deliberately not observable; nothing binds it.

**Gate 2 — an open modal owns the keyboard.** While `HasActiveOverlay` is true, *no* shortcut fires — `Esc` excepted, which is what closes the panel. Gate 1 does not cover this: a text-entry panel with nothing armed is not capturing, so `⌘S` would otherwise reach the editor **through the scrim**. That is not only a UX slip. The overlay `Border` is a sibling of the content grid, *outside* the `IsEnabled="{Binding !IsBusy}"` panel, so the panel stays interactive while `Task.Run(session.Save)` serializes the model on a background thread; an *Ok* clicked at that moment writes to a `KeyboardKey` the serializer is walking. The rule is therefore the whole grammar, not just the navigation keys.

**Gate 3 — the focused surface keeps what is its own, and the two navigation keys are gated differently.** Arrows are left untouched when the focused element's **ancestry** contains a `TextBox`, `NumericUpDown`, `AutoCompleteBox`, `SelectingItemsControl` or `RangeBase` — the tab strip and the layer switcher are one-of-N controls that move their own selection with arrows, and stealing those would break the segmented control outright. **`⌥1`–`⌥5` keep only the text-input clause**: no `SelectingItemsControl` or `RangeBase` consumes `Alt`+digit, and gating the layer jumps on them made them die silently the moment the user clicked a layer segment or a tab with the mouse — the very control the `⌥n` legend is printed on. A focused field still wins, because `⌥1` types `¡` on macOS. Both are ancestry walks rather than lists of control names, so a field nested in a future composite is covered without the view learning about it; the walk stops at the editor view. `⌘S`/`⌘W`/`⌘F` pass this gate by design — a save accelerator that stops working while the caret is in a field is not an accelerator.

**A move lands through `SelectKeyDirectly`, never `SelectKeyCommand`.** The click contract promotes a second hit on the already-selected cap into listening, and arrowing onto a key must never arm the keyboard. `MoveSelection` lives on the view model because the board picture does (`_visual` is the editor's); with nothing selected yet the first cap of the shown layer is where an arrow lands, so the grammar has an entry point that needs no click. The geometry is Core's `KeyAdjacency` ([domain-data.md](domain-data.md)) — rectangle overlap plus centre distance, so **crossing the split halves falls out of the scoring** and needs no special case.

**The cap it landed on takes the focus ring**, through `KeyboardView.TryFocusKey(int)` with `NavigationMethod.Directional` — which is what raises `:focus-visible` (`2b`: "mouse clicks suppress it, arrow/Tab summon it"). Selection and focus then coexist on one cap as concentric bands ([design-system.md](design-system.md), "Focus + selection on a key cap"). `TryFocusKey` reaches a cap's own `Content`, never a template part, and the view picks whichever `KeyboardView` is *effectively visible* — the Layout/Macros board and the Lighting tab's are two pictures over the same layer.

**⌘F is dual-purpose, deliberately.** With a macro open on the Macros tab it *is* the insertion picker (`InsertSpecialActionCommand`) — finding a token there means inserting it; everywhere else it is the plain §11.6 picker, whose Ok simply closes, because this app assigns a key only from a captured physical keypress. [#92](https://github.com/migus88/kinesis-edit/issues/92) repoints it at the inspector's own token picker. The field is focused by **`SearchKeysOverlayView` itself** on attach, not by the caller: the panel is materialised by `ViewLocator` a layout pass after the command runs, so the caller has nothing to focus at the moment it executes.

**A shortcut whose command cannot run does nothing and leaves the key unhandled**, rather than swallowing it — including `⌘W` with no `Shell` (null in every headless scene that does not assign one, and in the design-time preview).

### Escape — the resolution, and the constraint it is resolved against

The design says (`2b`, verbatim): *"Esc — leaves capture mode first, closes the inspector second."* **This app satisfies the second half and cannot satisfy the first**, and the reason is structural rather than an omission:

> The keystroke-capture service previews the window's key events in the **tunnel** phase and swallows every physical position it can resolve — Escape included — because a keyboard must be able to carry an Escape remap (05 §3). By the time any handler of this view runs, a listening key has *already been assigned Escape* and listening is over.

So Escape is **a remappable key, not a shortcut** (invariant 6). Cancelling a remap is a pointer action: the *Cancel* button beside the listening banner, clicking the listening key again, clicking another key, or switching layer. The branches, all pinned by tests:

| State | Escape does | Why |
|---|---|---|
| A feature panel is open and is **not** awaiting a keystroke | closes the panel, whatever `e.Handled` says | Capture may be running for something else entirely; a panel that cannot be closed from the keyboard is worse than an Escape that also lands elsewhere. Read off `IsOverlayAwaitingKeystroke`, never guessed from `Handled` |
| A feature panel is open and **is** awaiting a keystroke (an armed Tap and Hold field) | goes to the panel's field, which disarms | The next Escape then closes the panel — the two-stage rule, as far as the constraint allows. "Is awaiting" is **two** questions; see the latch below |
| A key is listening, no panel | **is assigned to that key** by the capture service; `CancelRemapCommand` is unavailable by the time the view's handler runs, so nothing double-fires | 05 §3 — an Escape remap has to be expressible |
| A key is listening, no panel, **and nothing consumed the key** | cancels the remap | The documented safety net. It is the state every headless scene is in, because those use a fake capture service |
| Nothing open, nothing listening | nothing | — |

**The armed-field carve-out needs a latch, not just `IsOverlayAwaitingKeystroke`.** The capture service previews on the `TopLevel` **above** this view, so on one Escape it runs first: the sink takes the key and *disarms*, and by the time `HandleEscape` runs `IsOverlayAwaitingKeystroke` is already `false` — the panel looks idle, and one Escape both filled the field and destroyed the panel. `KeyboardEditorViewModel.OnKeystrokeCaptured` therefore records that a sink took this keystroke, and `KeyboardEditorView.OnPreviewKeyDown` reads-and-clears it (`TryTakeOverlayKeystroke`) on **every** key down, so a latch set by an ordinary keystroke cannot answer for a later Escape. It is also cleared whenever the open panel changes. `e.Handled` is deliberately *not* the signal: capture may be running for something else entirely.

**Escape never comes out of `EditorShortcuts.Map`**, under any modifier — `EditorShortcutsTests` asserts that specifically. Do not add an accelerator that steals Escape anywhere else.

### The macro panel

`MacroPanelViewModel` is built by `Apply` once a model exists and is shown behind the *Macros* tab (`IsMacroPanelVisible`); the board stays on screen next to it, because **the selected key is the macro's trigger** — `SetTrigger(SelectedKey, SelectedLayer?.Layer)` is called on every selection and layer change, and switching trigger stops any recording. Its UI is deliberately plain pending a later editor-wide visual pass; the rules below are the substance.

- **Every limit comes from `MacroCapability`** ([domain-data.md](domain-data.md)): slot count, co-trigger cap, speed/repeat ranges and defaults, the per-macro and per-layout keystroke budgets, and the macro count — the last raised from `MaxMacroCount` to `GatedMaxMacroCount` by `ResolveMaxMacroCount(device)`, the editor's only firmware-gate read (`FirmwareFeature.ExpandedMacroCount`, 09 §2; demo mode passes). Nothing hard-codes the RGB's numbers, and **both** macro stores of 06 §1 are supported — per-key slots and the Adv360 flat list — even though only the RGB can be opened today.
- **Trigger state**: `TriggerKey`/`HasTriggerKey`/`TriggerCaption` (the caption names `KeyboardKey.TriggerKey`, not the remapped action, because that is what a macro matches on, 05 §1.3), `CanEditMacro` = device supports macros **and** a key is selected **and** `CanAssignMacro`. `Message` carries the one line the panel has to say: `This device does not support macros.`, `Select a key on the keyboard to give it a macro.`, or spec 02's verbatim `You cannot assign a macro to a modifier key`.
- **Slots** (`MacroSlotViewModel`, one per **`PersistedSlotsPerKey`** — 3 on the Advantage2 and Freestyle Edge/Pro, 5 on the RGB family; none on the flat-list families): the strip offers what the dialect *writes*, not the five the model owns, because `LayoutFileSerializer` emits exactly the persisted count and a macro put in slot 4 of a Freestyle Edge would be gone after save+reload with nothing said. Selecting one opens `key.GetMacro(slot)` or a fresh `Layout.CreateMacro()` draft, and writes `KeyboardKey.ActiveMacroIndex` — an in-memory field only, never serialized. Each slot shows `MacroKeystrokeRenderer.RenderKeystrokes` as its preview.
- **Steps** (`MacroStepListViewModel`/`MacroStepViewModel`): append (recording or insertion), remove last, remove one, clear. **Backspace is the panel's button, never a captured key** — 06 §2.2 makes every physical key recordable content, so pressing Backspace types a backspace into the macro. A step renders as `LS + A` with `↓`/`↑` for an explicit key direction.
- **Co-triggers** (`MacroCoTriggerViewModel`): the six left/right Shift/Ctrl/Alt toggles of 06 §5. `Macro.AddCoTrigger` neither de-duplicates nor refuses, so the cap is held here — and it is **`PersistedCoTriggersPerMacro`** (`MacroPanelViewModel.MaxCoTriggers`), for the same reason as the slots: the old Freestyle serializer writes only the first, so the other three would vanish on save. Turning a toggle off clears **every** slot carrying that key.
- **Speed/repeat** are clamped to the device's `ValueRange` on assignment and written to the macro under edit; loading a macro moves the fields without writing back. **`HasRepeat` also requires `MacroCapability.PersistsRepeat`** — the Advantage2 has a repeat range in the model but its serializer writes no `{xN}` token at all (06 §3), so the control is hidden there rather than offering a value the next save discards. `HasSpeed` stays true on it: `{speedN}` *is* written.
- **Budgets** (`MacroBudgetViewModel`): `MacroLength / MaxMacroLength`, `profile keystrokes / MaxTotalKeystrokes`, `macros / MaxMacroCount`, each with an over-budget flag rendered **amber** (`Classes.statusWarning`, never `statusError` — see "The advisory system"), plus 06 §6's verbatim `Macros are limited to approximately {0} characters.` The per-macro figure goes through **`MacroLengthMetric`**, so the Advantage360's 500 is measured as serialized macro-text characters and every other family's 300 as weighted keystrokes — the same code `Validate()` uses, which is what keeps the readout and the save gate from disagreeing. **A null limit means no limit, never zero**: the Advantage2 states no macro count, so its caption is a bare number and nothing is refused. **Breaching a budget is reported, never refused** — `Validate()` at save time is the backstop ([keyboard-model.md](keyboard-model.md), invariant 1).
- **Assign / Delete / Copy / Paste**: `Assign` stamps the macro's trigger and layer (as `MacroLineParser` does, 04 §4.2) and puts it in the chosen slot with `SetMacro` — not `AssignMacro`, which always takes the *first* free slot — or appends it to the flat list; it refuses with `This profile already holds its maximum of {0} macros.` only when the assignment really *adds* a macro, and with `Every macro slot of this key is taken.` when no slot was targeted and none is free. `Delete` removes it and re-opens the same slot with a fresh draft. `Copy`/`Paste` go through **`MacroClipboard`**, a one-key clipboard (slot families only) holding a **deep-copied snapshot**, never the source key: between the two the source can be emptied by Reset Key / Reset Layer / Reset Layout, and a live reference would then paste nothing and wipe the target. A paste replaces all five slots at once, so it is measured against the same macro count Assign is — `clipboard − target` macros added — and refused with the same wording.
- **The macro list** (`MacroListEntryViewModel.BuildAll`) is the Adv360's "macro repository" shown on every device: the flat list first, then every populated key slot in layer/key/slot order, each row rendered as the line the file will carry — **layer prefix included** (`MacroKeystrokeRenderer.LayerPrefixFor`), so a bottom-layer Gen1 macro reads `fn {q}>{s5}{x1}{a}` exactly as `LayoutFileSerializer` writes it (06 §3, 04 §3.1) — and captioned `Top · A (1)`. Selecting a row opens that macro for editing **without** moving the board's selection, but **the panel's own trigger, slot strip and every key-scoped action follow the macro** (`MacroEditTarget` = macro + key + layer + slot). Otherwise the header names the board's key while Record, Clear, Backspace, the co-triggers and the sliders all write to the row's key.
- **`Advisories`** is a *pushed* `EditorAdvisories`, set by the editor's `RebuildAdvisories()`. Setting it re-marks the rows, and rebuilding the rows re-applies it — both orders happen in practice (a macro edit rebuilds rows then advisories; a layer reset the other way round), so neither may be the only place it is done. The panel never runs `Validate()` itself, which would run that walk twice per edit.
- The panel raises `MacrosChanged` after every write (the editor recounts) and `RecordingChanged` (the editor drives capture). It writes to the model directly and announces nothing else, so `RefreshFromModel()` is what an outside write (the resets) must call.

### Feature commands (spec 11)

Five commands open the inline panels; the panels themselves and every rule and message they carry are in [feature-dialogs.md](feature-dialogs.md). The editor's part is the sequencing:

| Command | Sequence |
|---|---|
| `TapAndHoldCommand` | firmware gate (awaited — the selection is re-checked afterwards, since a message box was up) → `TapAndHoldOverlayViewModel.TryCreate` → message box on a refusal, otherwise show the panel and hook `SearchRequested` (nested picker) and `Closed` (refresh the cap + counters when it was accepted) |
| `InsertDelayCommand` | firmware gate (`CustomMacroDelays`) → show `MacroDelayOverlayViewModel`, whose `Accepted` key is appended to the macro under edit |
| `InsertSpecialActionCommand` | show `SearchKeysOverlayViewModel` titled `Search Keys (Macro)`; its `Selected` key is appended the same way |
| `ExportCommand` | show `ExportOverlayViewModel` over the current session |
| `ImportCommand` | cancel listening + stop recording → `ProfileImporter.ImportAsync` → on success re-run `Apply` and toast, on failure a message box |

`ShowOverlay(overlay)` is the one entry point: it drops any Tap and Hold hooks, cancels listening, **stops any macro recording**, and hands the panel to `EditorOverlayHost`. Stopping the recording is what hands the capture service back — a recording underneath owns it, the host would then never start or stop it, and every key aimed at the panel would land in the macro instead. The two insertion panels are wired through `ShowMacroInsertOverlay`, which subscribes the "append to macro" action and **unsubscribes it on the panel's `Closed`**, so a dismissed panel can never write into the macro afterwards.

### Save

`SaveAsync` cancels any listening and stops any macro recording first, then: `IsBusy = true` → `try { ShowLoading("Saving…") → Task.Run(session.Save) }` → `IsBusy = false` **then** `HideLoading()` in a `finally` → report. Everything else is Core's ([profiles.md](profiles.md)): validation gating, file writes, eject, post-save wording. The ordering is load-bearing: both indicator calls fan out to the overlay and can fail, so `ShowLoading` sits inside the `try` (its failure is reported as the save failure it is) and the flag is cleared before `HideLoading`, because a stranded `IsBusy` disables Save and every editing command for as long as the editor is open.

- **Threw** → message box `Save Profile` / `SaveErrorMessagePrefix + message`.
- **`Success == false`** → message box listing `SaveRejectedMessage` followed by one line per `ModelViolation.Message` (04 §5.3's gate, surfaced rather than silently dropped).
- **Success** → toast titled `Save Profile` carrying the device's refresh wording verbatim, plus `Saved with N advisories.` when the profile carries any (`BuildPostSaveMessage`). Either half alone is enough to raise the toast; with neither there is none. **An advisory never stopped the save** — the toast has already been reached only on success, so the count is stated in the same breath rather than warned about separately. It does change the toast's *face*: `Advisories.Total > 0` sends `ToastSeverity.Advisory`, so a message that counts advisories arrives amber instead of on the green success face. It stays a toast and never becomes a message box — advisories never block.

Both boxes go through `TryShowMessageBoxAsync`, which swallows a box that cannot be put on screen — the editor state already carries the outcome, and a shell that cannot host a card must not bring the app down. (Since issue #89 the box is an in-app overlay rather than a window: with no host registered the presenter answers with the escape outcome rather than hanging, so this guard covers a throw rather than a missing owner — see [app-shell.md](app-shell.md).)

## Presentation rules

**`KeyCaption`** — the caption of `KeyboardKey.ModifiedOrOriginalKey` (so a remapped cap reads its new action), resolved in this order: `GlyphText` → `MacDisplayText` when `OperatingSystem.IsMacOS()` → `GetDisplayText(dialect)` → **the dialect's file token when all of those are blank**. That last step exists because 05 §3.11 registers `hk0`–`hk8` with `' '` (the physical caps are unlabelled), which would otherwise draw a column of indistinguishable empty caps; the token is what the user sees for that position in the layout file, which makes it the honest fallback rather than an invented label. `\n` is preserved verbatim — splitting it into a two-line cap (05 §1.1) is the view's job. `KeyCaption.For(key, dialect, isMacOs)` takes the platform as a parameter so both directions are testable; `IsMacOs` is resolved once as a static.

**`LayerCaptions`** — the geometry's `Name` is the spec-literal file-side name (`Qwerty-top`/`Qwerty-keypad`), which is not what an editor shows. Gen2 keeps the raw names (Base, Keypad, Fn1–Fn3 are already presentation-ready); Legacy/Gen1 map index **0 → `Top`**, **1 → `Fn`** (spec 10 describes both switches that way); anything else falls back to the raw name.

**`KeyColorOverlay`** — projects a profile's lighting onto the picture as `key index → #RRGGBB`. It is more than a lookup for two reasons, which is why it lives in one tested place: `LayerLightingState.KeyColors` is keyed by **memory key code** (07 §4), not by key index, so every entry is resolved through `KeyboardLayer.FindByOriginalKeyCode`; and `KeyboardKey.KeyColor` exists but **no parser ever fills it** (the led file is parsed into the lighting model, never into the layout model), so reading the key would always show nothing — which is also why `KeyboardKeyViewModel.RefreshFromModel()` cannot reach the overlay and the Lighting tab pushes a fresh map in through `KeyboardLayerViewModel.ApplyColorOverlays` instead. Empty unless the device is `LightingKind.PerKeyRgb` *and* `IProfileSession.Lighting` is a `LightingModel` (TKO's `TkoLightingModel` is deliberately not matched yet) *and* the layer is one of the two that model describes — layout layer **0 ↔ `LightingModel.TopLayer`**, **1 ↔ `FnLayer`**. `LedColor.IsBlack` is "no colour" (07 §2.1) and yields no entry; an unknown key code is skipped. `ToHex`/`TryParseHex` are the module's `LedColor` ↔ `#RRGGBB` pair, used in both directions by the picker.

## Seams and composition

- **`IProfileSession` / `IProfileSessionFactory`** exist because Core's `ProfileSession` is sealed with a static `Load` — unsubstitutable in a test. `ProfileSessionAdapter` is a pass-through with no behaviour of its own; `ProfileSessionFactory` calls `ProfileSession.Load` and wraps it. Same shape as `IMessageBoxPresenter`.
- **`ISettingsService` / `SettingsServiceAdapter`** are the same seam over Core's sealed `SettingsService` ([settings.md](settings.md)), and the app builds **one** instance: the settings panel, the lighting picker's custom slots and the notification-suppression store all go through it, so `app_settings.txt` has a single reader and a single writer.
- **`EditorViewModelFactory`** is the one place that picks an editor: `DeviceId.SavantElite2` → `SavantElitePedalViewModel` ([savant-elite.md](savant-elite.md)); otherwise "can this device be drawn?", answered with `VisualCatalog.TryGet(id, out _) && GeometryCatalog.TryGet(id, out _)`, → `KeyboardEditorViewModel` or `EditorPlaceholderViewModel`. The shell asks for one and swaps in whatever it gets, which is also what keeps every editor's dependencies out of `MainWindowViewModel` — the profile-session factory, the settings seam, the capture-service accessor, `PedalFileService`, and the keyboard editor's feature-panel set: `IFolderPickerService`, `IFilePickerService`, `IVDriveFileService` and `IUrlLauncher`.
- **The capture service is resolved through a `Func<IKeystrokeCaptureService>`**, not held: `AvaloniaKeystrokeCaptureService` attaches to the shell `TopLevel`, which does not exist while `App.BuildServices` wires the graph — the same ordering problem the message-box presenter solves with its `Func<Window?>` owner. `App` builds it lazily on first use, keeps the single instance, and disposes it in `OnExit` **after** the shell (which closes and disposes the editor, which stops capture first).
- `MainWindowViewModel` delegates the choice to `IEditorViewModelFactory`, keeps `Editor` typed as the abstract `DeviceEditorViewModel?`, fires `editor.LoadAsync()` once after the view swap, and disposes the outgoing editor in `CloseEditor()` on both navigate-home and re-open.

Everything else here is this app's wording: `Profile n`, `Saving…`, `Loading profile...`, the `Save Profile` / `Load Profile` dialog titles, `The profile was not saved because it exceeds the device's limits:`, `Line <n>: <text>`, `Press a key to assign it to the highlighted key.`, `Some lines of this profile could not be applied`, the macro panel's other lines (`Select a key on the keyboard to give it a macro.`, `This device does not support macros.`, `A macro can hold at most {0} co-triggers.`, `This profile already holds its maximum of {0} macros.`, `Every macro slot of this key is taken.`, `Copy a key's macros first.`), the tab captions `Layout` / `Macros` / `Lighting` / `Settings` (spec 10's RGB app has `Layout` / `Lighting` tabs with the macro editor as an in-window panel and settings in a modal dialog; the four-tab shape gives each of those a home of its own), the two reset confirmations and their outcome-named buttons (`Reset Layer` / `Reset Layout`, `Do you want to clear every remap and macro on this layer? Nothing is written to the keyboard until you save.` and its every-layer twin, `Clear layer` / `Clear all layers` / `Cancel` — the specs give no wording for a reset prompt, and mockup 1k's rule that buttons are named by outcome is followed), and the advisory sentences the mockups do not give: `AdvisoryText.SectionSummary`, the duplicate-key sentence's position list, and `Saved with N advisories.`. The strings the view models own are consts on `KeyboardEditorViewModel`/`EditorTabViewModel`/`LayerCaptions`/`MacroPanelViewModel`/`MacroBudgetViewModel`/`AdvisoryText` and asserted by tests; the ones only the view uses are XAML literals.

Recorded deviations:

1. **No per-key Done/Cancel commit step.** Spec 10's Adv2 flow has "**Done** validates and marks the layout modified; **Cancel** reverts". Here a captured keystroke is applied to the model immediately, and Cancel means "stop listening" only. Validation happens once, at save time, where 04 §5.3 puts it.
2. **The layer switch is built from the model's layers**, not from a two-state toggle — two pills on a Freestyle Edge RGB, five on an Advantage 360 (#41) with no change to the view.
3. **Invalid lines are an inline collapsed block**, not the Adv360's modal "Invalid Lines dialog" (spec 10). Same content (04 §5.2), less interruption; `LayoutInvalidLine.Keep` is untouched, so they are still re-serialized as Core decides.
4. **The colour overlay is a strip under the caption**, not the cap background: the cap background already carries the four remap states, and 07 §2.1 colours must stay distinguishable next to them. It is drawn **only on a lighting picture** — the design hatches an LED that is off, and hatching every cap on the Keys tab would answer a question nobody asked there.
5. **The macro panel is a tab, not a docked strip or a separate window**, and its layout is deliberately plain — spec 10's Adv2 docks it at the bottom and the RGB app opens it in place. The board stays visible beside it because the selected key *is* the trigger; a visual pass over the whole editor is a later change.
6. **The spec 11 dialogs are inline panels over the editor**, not modal windows ([feature-dialogs.md](feature-dialogs.md)).
7. **The settings panel is one list of rows for every device**, not the four different forms of 08 §5.1–§5.4 (a modal dialog on RGB/TKO/Adv360, controls embedded in the main window on FS/Adv2). Same keys, same ranges, one shape — and it is a tab, so nothing is modal and nothing saves as you type.
8. **The status-report slider is always 1–4 plus a "Disable" checkbox** (the §5.1/§5.2 shape). §5.3/§5.4 draw it as a plain 0–4 slider for the FS boards and the Adv2; both write exactly the same values, so one control serves every device. The macro-speed slider keeps its per-device floor, because Core supplies it (`SettingsCapability.MacroSpeedMinimum`).
9. **The RGB/TKO settings panel shows a v-Drive row that §5.1's control table does not list.** It comes from `SettingsCapability.VDriveSetting`, i.e. spec 08 §2's written-by column, where `v_drive` *is* an RGB/TKO key — the panel is capability-driven, so it renders every key the app writes rather than the legacy dialog's subset. Worth knowing because it is also the row with the nastiest failure mode: `v_drive=manual` stops the drive auto-mounting, which is why the panel refuses to save anything until a read has actually succeeded.
10. **"Settings Saved" is a toast, not a modal** — the same deviation the profile save already records. Its wording is Core's `SettingsMessageCatalog` verbatim.
11. **The lighting editor is a tab, not the legacy app's second window mode**, and it has **one Save — the editor's**. Spec 07 §1.3 has the app write layout then led then eject in one sequence, which is exactly `ProfileSession.Save`; there is no separate "save lighting" action and no `savelighting_msg` notification.
12. **One picker, not two.** Spec 07 §4 describes a shared *dialog* with 10 premixed + 6 custom slots and a *main panel* with 20 premixed + 12 custom. This app has one inline picker with the 10 named swatches (the 20 are never enumerated in the spec) and the full 12 custom slots, because those are the twelve keys `app_settings.txt` actually persists.
13. **The two colour swatches are selectable targets**, not two separate pickers: clicking Effect Color or Base Color points the single picker at it. The spec does not say how the legacy panel routed the picker, and one picker is what fits beside the mode menu.
14. **No animated effect preview** (07 §7) — the mode list is captions only.
15. **No eject button in the editor toolbar**, though mockup `1e` draws one. `docs/design/README.md`'s own law is that *nothing ejects implicitly* and that eject is the dashboard card's deliberate action ([#88](https://github.com/migus88/kinesis-edit/issues/88)); the issue body's toolbar anatomy omits it too. Also recorded in [design-system.md](design-system.md).
16. **The Demo Mode bar carries one action, not the mockup's two.** `1f` draws `Export layout to file…` beside `Connect a device`; it is not rendered. `CanExport` requires a session and demo mode opens none (03 §3.5), while the bar itself is visible *only* in demo mode — the two are mutually exclusive, so the button would be disabled 100% of the time it is on screen. *"Features a device lacks are not shown, not disabled"* is the design law, and every other CanExecute-disabled control in this editor can become live; this one could not. The mock draws it because it assumes demo mode has a layout to export. Export stays reachable from the provisional action row.
17. **The tab caption is `Layout`, the enum member is `Keys`.** The mockups' caption, and a name the XAML's `EnumMatch` converter parameters are coupled to by string.
18. **The advisory strip is one control, not one per tab.** The design says "one summary strip per tab (max)"; a single row whose sentence and count are the open section's satisfies that with one thing to keep correct instead of four.
19. **A duplicate-key advisory names positions by index, not by place.** Mockup 1e reads *"Esc already exists on the top-left position of this layer"*; no data in this app can produce "top-left" (`KeyVisual` has coordinates, not names), so the sentence is `[esc] is on 2 positions of this layer — 0, 20.` The verbatim half — *"Duplicates are allowed."* — is kept exactly.
20. **The advisory cap badge is not drawn here.** `KeyboardKeyViewModel.HasAdvisory` is exposed and unrendered; the 12×3 px bar lands with the rest of the badge vocabulary in [#91](https://github.com/migus88/kinesis-edit/issues/91).
21. **The Macros/Lighting/Settings strip sentence is this app's wording.** The mockups give copy only for the Layout tab's strip (1e) and for the budget rows themselves (1i); `AdvisoryText.SectionSummary` is built to the same shape so the strip reads the same wherever it appears.
22. **Escape does not "leave capture mode first".** `2b` asks for a two-stage Escape; capture swallows the key and makes it the assignment, because an Escape remap has to be expressible (05 §3). The second stage — closing the panel — is implemented in full. Spelled out under "Escape — the resolution".
23. **⌘F opens the §11.6 Search Keys picker, and outside a macro its Ok has nowhere to write.** `2b` calls it "the token search"; this app assigns a key only from a captured physical keypress, so the plain picker is a lookup until [#92](https://github.com/migus88/kinesis-edit/issues/92) gives ⌘F the inspector's own token picker. On the Macros tab with a macro open it *is* the insertion picker.
24. **The editor view is focusable and takes focus when it is attached.** Not a design decision — a tunnelling handler only sees keys on the chain between the window and whatever holds focus, so without it the whole grammar would be dead until the first click. `IsTabStop` is false, so Tab order is unchanged.
25. **The layer switcher's label ships as `LAYER`, where `docs/design/mockups.md` gives `Layer`.** A copy change, kept: the type scale sanctions 10/600 UPPERCASE mono section labels (`sectionLabel`), and the label sits in a row of them. Recorded here because it is a deviation from the mockup's own wording, not from its type.

## Load-bearing invariants

1. **One visual per device, all layers.** Layers differ only in the tokens bound to a position (05 §7.4), so the picture is rebuilt per layer from the *same* rectangles; a per-layer visual would be data waiting to disagree with itself.
2. **The join is by key index, and mismatches degrade.** `KeyboardVisual.TryGetKey(key.Index, …)`; a miss skips the cap. Core's `Geometry/Visual` tests assert set equality with the logical geometry in both directions, so a mismatch is a data bug caught in CI, not a runtime crash.
3. **Every model write is followed by `RefreshFromModel()`.** Core announces nothing — on the cap (`KeyboardKeyViewModel`), on the layer, and on the macro panel after an outside write. The colour strip is the exception that proves it: it lives in the lighting model, so it is refreshed by `ApplyColorOverlays` — but a lighting write that skips it leaves a stale picture just the same.
4. **Capture is never left running, and the editor owns it.** It is started only by a key entering listening, a macro recording, or an armed Tap and Hold field, and stopped on the keystroke, on cancel, on a layer switch, on a tab switch (away from Macros for a recording, on any switch for a listening key), on a save, on an import, and on `Dispose` — the app-wide service swallows keystrokes from the whole window while it is on. The macro panel never touches the service; it raises `RecordingChanged` and the editor drives it.
5. **One keystroke, one target.** The subscription to `KeystrokeCaptured` is single and lives here; the precedence (open sink panel → recording macro → listening key) is the one place spec 10's routing rule is written down. The sink wins on being *open*, and `ShowOverlay` stands the other two down before the panel appears, so there is never a second consumer to race.
6. **Escape is a remappable key, not a shortcut** (see "Escape — the resolution") — with one carve-out: an open feature panel that is not itself awaiting a keystroke is always dismissible with it. "Not awaiting" means *both* that no field is armed now **and** that no sink took this very keystroke (`TryTakeOverlayKeystroke`), because the capture service runs above this view and a field disarms as it takes a key. Do not add an accelerator that steals Escape anywhere else, and never let it out of `EditorShortcuts.Map`.
7. **Captured keystrokes go through the editor path, resets through `ClearRemap`.** `Remap` implements 04 §2.1's remap-to-self clearing; `Remap(OriginalKey)` would additionally destroy tap-and-hold and multi-modifiers.
8. **View models expose enums and strings, never brushes** ([app-shell.md](app-shell.md), invariant 6). The overlay travels as `#RRGGBB` and becomes a brush in XAML through `HexColorToBrushConverter`, which converts anything unparseable to `null` rather than throwing inside a binding.
9. **Demo mode never writes** (03 §3.5): no session is created at all, so `SaveCommand`, `ExportCommand` and `ImportCommand` cannot become available by any other property moving. The Lighting tab still opens on an **in-memory** `LightingModel` so it stays explorable, and the picker's custom slots are read-only there. Reading, on the other hand, is *not* forbidden — the picker's slots and the settings panel both load whenever a `VDriveLocation` exists, because demo mode is entered for a drive that is merely not writable and showing invented values for connected hardware is worse than showing none.
10. **A panel never writes what it did not read.** The settings panel's `HasLoadedSettings` gate exists because its rows have plausible-looking defaults that are pure invention; anything else on this tab that grows a save path needs the same "a read succeeded" flag, not `!IsLoading`.
11. **Keystroke budgets are reported, never refused** — the macro panel shows the breach and lets the edit stand; `Validate()` at save time is what stops the write ([keyboard-model.md](keyboard-model.md), invariant 1). It refuses at input time in exactly three places, all of which `Validate()` would also report: a position that cannot hold a macro (05 §5.3), the co-trigger cap, and the macro count — the counts because there is no meaningful "half-added" macro to leave on screen.
12. **`LoadAsync` is total and idempotent.** The shell fires and forgets it; an escaping exception would be an unhandled crash, and a second call must not re-read the drive.
13. **Adding a device is adding data.** `EditorViewModelFactory`, `KeyboardView`, `KeyCapView` and `KeyboardPanel` contain no device identity; only `VisualCatalog` does. The macro panel is device-agnostic too — it reads `MacroCapability` and supports both macro stores, and the settings rows come from `SettingsCapability`.
14. **What the panel offers is what the file keeps.** Where the model holds more than the dialect persists — five slots against three, four co-triggers against one, a repeat value the Advantage2 never writes — the panel offers the persisted figure. An edit the next save would silently drop is worse than one the UI never allowed.
15. **The panel edits one macro, and names it.** `MacroEditTarget` is the single answer to "what is open"; the displayed trigger, the highlighted slot and every key-scoped command read it, never the board's selection directly.
16. **Every path that writes to the model ends in `RefreshCounters()`, and every path that writes to the *lighting* model raises `ModelChanged`.** `IsDirty` is a pull, not a push, so a path that skips either leaves Save grey while the user has unsaved work. This is the same invariant as 3, one level up: 3 keeps the cap honest, this keeps the chrome honest.
17. **Exactly one 46 px bar is on screen while editing.** `ProvidesOwnChrome` + `IsShellChromeVisible` are the whole mechanism; an editor that starts drawing its own bar must set the first, and nothing else may put a second status pill on screen.
18. **The editor reaches the shell through `IShellChrome`, never up the visual tree.** A `$parent[MainWindow]` binding renders blank in every headless scene, which is where this screen is verified.
19. **A tab that exists, works.** There is no disabled tab and no `EditorTabViewModel.IsEnabled`; a section the board cannot carry is simply absent from `CreateAll`.
20. **No advisory blocks, clamps or refuses anything.** Nothing in `ViewModels/Advisories/` is reachable from a `CanExecute`, a guard or a modal; a layout with advisories saves, and the board truncates. `ReviewAdvisoriesCommand` is the one command with no predicate at all, deliberately. If a future advisory ever needs to stop something, it is not an advisory.
21. **Every advisory appears exactly twice**: a mark on the exact key or row (`KeyboardKeyViewModel.HasAdvisory`, `MacroListEntryViewModel.HasAdvisory`) and one summary strip per tab. A source added to `EditorAdvisories.Build` that no anchor can reach is half-built.
22. **Amber is the only colour an advisory ever has.** No advisory-carrying control resolves to the `StatusError*` ramp anywhere; red means a genuine failure (and the macro Record dot).
23. **Capture outranks the whole keyboard grammar, and so does an open panel.** `IsCaptureActive` and `HasActiveOverlay` are both checked before any shortcut is even looked up. The first is invariant 5 restated for the keyboard: a keystroke that belongs to a listening key, a recording macro or an armed field is never also a shortcut. The second is the scrim restated for it: what a modal covers, the keyboard may not reach either — including `⌘S`, which would otherwise race the open panel against a background serialization.
24. **An arrow moves the selection and nothing else.** It lands through `SelectKeyDirectly`; `SelectKeyCommand` would promote the second press on the already-selected cap into listening. The same rule `Review N` follows, for the same reason.
25. **The grammar is a pure map plus a dispatcher.** Every platform and modifier decision lives in `EditorShortcuts` and is unit-tested with `isMacOs` as a parameter; the view only dispatches, and respects `CanExecute` on everything it runs. There are no `KeyBinding`s or `KeyGesture`s in this app — a gesture cannot express either gate.

## Deliberately not here

- **No way to assign a key other than a captured physical keypress.** Search Keys (§11.6) reaches only the Tap and Hold fields and the macro under edit; spec 10's categorized *Special Actions* popups (F13–F24, keypad, multimedia, mouse clicks, alt layouts, Hyper/Meh) do not exist as a per-key palette, and there is no right-click menu on a cap.
- **No multi-modifier UI (11 §11.2) and no Select Macro dialog (11 §11.4)** — both are Advantage 360 surfaces and follow that board's picture in issue [#41](https://github.com/migus88/kinesis-edit/issues/41). The model supports multi-modifiers, and `ResetKeyCommand` is careful not to destroy them or a tap-and-hold.
- **No Diagnostics report (11 §11.7) or Troubleshoot dialog (11 §11.8) in the editor** — issue [#46](https://github.com/migus88/kinesis-edit/issues/46).
- **No TKO edge-lighting editor and no Advantage 360 indicator editor.** The Lighting tab edits the plain two-layer key-backlight model only (`LightingTabViewModel.IsSupported`: per-key RGB **without** an edge strip = the Freestyle Edge RGB). The TKO's key backlight + 33-zone edge tab needs its board picture first (issue [#40](https://github.com/migus88/kinesis-edit/issues/40)) and the Adv360's six-indicator editor needs its own (issue [#41](https://github.com/migus88/kinesis-edit/issues/41)); both boards' tabs are therefore present but disabled, and Core's `TkoLightingModel`/`Advantage360LightingModel` deliberately do not light the tab up. On those boards an **imported led file** still replaces the session's model without the editor showing it anywhere but the per-key colour strip.
- **No "Lighting Expansion Pack" dialog** (07 §3, §2.6) — `LightingAvailability.HasNoFnLayerLines` and `ExpansionPackDefaults` exist in Core, but nothing offers to mirror the Top layer into Fn or to write the factory pack across all nine profiles.
- **No animated effect previews** (07 §7) and no per-key preview of an effect — the picture shows stored per-key colours only.
- **No `savelighting_msg` suppression** and no separate lighting save — lighting rides the profile save (07 §1.3).
- **No settings beyond the keys spec 08 §2 lists.** The reserved keys (`thumb_mode`, `power_user`, `country`, …) are parsed into state and have no control, as Core intends; there is no eject after a settings save, no "Do you want to save changes?" prompt on leaving the tab, and no app-settings dialog for the twelve `*_msg` flags.
- **No profile picker, Save As, or New** (spec 10) — the editor always opens `LayoutScheme.FirstProfileNumber` and `SaveCommand` writes back to that same slot; Export and Import work on that one profile. `ProfileSession.SaveAs` already exists in Core ([profiles.md](profiles.md)).
- **No unsaved-changes guard.** `IProfileSession.IsDirty` now drives the amber Save, but nothing *blocks* on it: `KeyboardEditorViewModel` does not override `ConfirmCloseAsync` and the base returns `true` unconditionally (only the pedal editor overrides it), so Home ends the session without asking (spec 10's Adv2 "Do you want to save changes?" prompt and the leave-with-unsaved modal of mockup `1f` are unimplemented), there is no undo buffer, and an import is therefore irreversible short of not saving. The amber `Save` is the only thing between the user and silently discarded work — and it does not cover the Settings tab's own Save at all (see "Settings are outside the dirty model").
- **No `Keyboard Connection Lost` dialog** (03 §3.5) — a drive that vanishes mid-save surfaces as the generic save-error box. Still owned by a later issue, as [app-shell.md](app-shell.md) records.
- **No alternate-layout generators** (Dvorak/Colemak/Workman onto chosen layers, spec 10) and **no key-data copy/paste** — the macro panel's Copy/Paste uses `KeyboardKey.CopyFrom` with `KeyCopyScopes.Macros` only; the remap/tap-and-hold half of that method is still unused here.
- **No per-device visuals beyond the Freestyle Edge RGB** — issues #39–#42, data only. The TKO's 33 edge lighting zones (`KeyCluster.EdgeZone`, `KeyboardLayer.EdgeKeys`) arrive with #40 and are lighting zones, not typing keys.
