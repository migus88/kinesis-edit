# Keyboard editor (keyboard picture, remaps, macros, lighting, settings)

The editor the shell swaps in on Configure for a programmable keyboard: a keyboard-shaped picture of one loaded profile, the click-then-press remap workflow of spec 10 ("click an on-screen key — the key enters 'listening' state; the next physical keypress captured by the app becomes the new assignment"), the **key inspector rail** beside it, the macro **library** behind the *Macros* tab, the *Lighting* and *Settings* tabs, and the reset/save/export/import actions around them. It owns **no** domain rules — placements come from `VisualCatalog` ([domain-data.md](domain-data.md)), the model and its edit paths from `KinesisEdit.Core.Model` ([keyboard-model.md](keyboard-model.md)), load/save/import from `ProfileSession` ([profiles.md](profiles.md)), keystrokes from `IKeystrokeCaptureService` ([keystroke-capture.md](keystroke-capture.md)), the led model from `KinesisEdit.Core.Lighting` ([lighting.md](lighting.md)), the settings files from `ISettingsService` ([settings.md](settings.md)), the spec 11 panels it hosts from [feature-dialogs.md](feature-dialogs.md), and window/navigation/notifications from the shell ([app-shell.md](app-shell.md)).

**Device coverage: Freestyle Edge RGB only.** Every other device opens `EditorPlaceholderViewModel` — except the Savant Elite2, which has an editor of its own ([savant-elite.md](savant-elite.md)) and no keyboard picture at all — because only that one board's picture is authored. Adding a device is adding data to `VisualCatalog` — issues [#39](https://github.com/migus88/kinesis-edit/issues/39) (FS Edge / FS Pro), [#40](https://github.com/migus88/kinesis-edit/issues/40) (TKO), [#41](https://github.com/migus88/kinesis-edit/issues/41) (Advantage 360), [#42](https://github.com/migus88/kinesis-edit/issues/42) (Advantage2) — never editing anything below.

## The chain: visual data → control → view model

1. **`VisualCatalog`** (Core) answers *where*, *in which panel* and *what is printed* — `KeyVisual { Index, X, Y, Width, Height, Cluster, Section, Legend, SecondaryLegend }` in **key units** (`1.0` = one 1U cap), board-absolute, top-left origin. One `KeyboardVisual` serves **all** of a device's layers (05 §7.4: the same position keeps its index in every layer).
2. **`KeyboardVisual.Sections`** groups those keys by `KeyVisual.Section` into `KeyboardSection { Index, Keys, X, Y, Width, Height }` — one **drawn panel** each, with its board-absolute bounding box. It is a *view* of `Keys`, not a second list: every key appears in exactly one section, indices must be dense from 0 (a gap throws, like a duplicate key index), and **no coordinate is re-based** — `KeyAdjacency` navigates the one continuous space, and the authored split gap is what an arrow crosses.
3. **`KeyboardLayerViewModel.BuildAll(layout, visual, lighting)`** joins model to picture **by key index**: for every `KeyboardKey` of every `KeyboardLayer` it looks up `KeyboardVisual.TryGetKey(key.Index, …)` and produces a `KeyboardKeyViewModel`. A key with no placement is **skipped**, a placement with no key produces no cap — Core's tests already assert the two index sets match exactly for every authored device, so a mismatch must degrade into a missing cap, never a crashed editor.
4. **`KeyboardLayerViewModel.Sections`** distributes those caps into one `KeyboardSectionViewModel` per `KeyboardSection`, holding **the same `KeyboardKeyViewModel` instances** as the flat `Keys` list. That identity is load-bearing: the editor resolves a cap through `Keys` (`FindByIndex`, `MoveSelection`, `ApplyLighting`) and the picture renders `Sections`, so a copy would leave the board showing state nothing updates. A section the layer has no key for is still listed — the panel roster is the board's, not the layout file's.
5. **`KeyboardView`** renders `Sections` as an `ItemsControl` whose panel is a horizontal `StackPanel` spaced by `GutterSplit`; each item is a bordered `Border` (the section box) around a second `ItemsControl` over that section's `Keys`, whose `ItemsPanel` is a `KeyboardPanel` fed the section's `BoardWidth`/`BoardHeight`/`OriginX`/`OriginY` and the `KeycapPitchX`/`KeycapPitchY`/`KeycapGap` tokens. An `ItemsControl.Styles` entry projects each cap's `X`/`Y`/`Width`/`Height` onto the generated `ContentPresenter`'s attached `KeyboardPanel.UnitX`…`UnitHeight`. The whole thing sits inside one `BoardScaleHost`.
6. **`KeyCapView`** is one `Button` carrying the caption, the secondary legend, the state classes, the four badges and — only on a lighting picture — the LED strip. Its content is a three-row grid, **caption first**, then the silkscreen sub-legend, then the strip; the grid takes `Margin="0,-2"` to step back over the cap's 2 px padding (which exists for the badges and is therefore not reduced), so the content box is the cap's whole inner area, 28×24. The vertical budget of those 24 px, in all five states the cap is drawn in, is written out at the head of `Controls/KeyCapView.axaml` — it is tight enough that changing any one number needs the arithmetic.

Core's model raises no change notification (plain mutable POCOs), so `KeyboardKeyViewModel.RefreshFromModel()` — re-reading `Caption`, `IsModified`, `IsMacro` and `IsTapAndHold` — is what the UI learns from; **every path that writes to `KeyboardKey` must end in it**, or the cap keeps showing the old assignment. `KeyboardLayerViewModel.RefreshFromModel()` is the layer-wide form, and it ends in `RefreshCounts()` so the legend row's derived totals follow.

**A cap's caption is the silkscreen until it is remapped.** `KeyboardKeyViewModel.ResolveCaption()` is the one rule, shared by the constructor and `RefreshFromModel` so the two cannot drift: an *unmodified* key with an authored `KeyVisual.Legend` reads that legend, everything else reads `KeyCaption.ForKey`. So an untouched digit reads `1` rather than the token's `1 !` (the `!` is the `SecondaryLegend`), the hotkey column reads its printed marks rather than `hk0`…, and a remapped cap always reads what it now *does*. `Legend`/`SecondaryLegend` are authored only where the print differs from what the caption already says, so null means "use the caption", never "draw nothing"; both come off the immutable `KeyVisual`, so neither ever changes and neither notifies.

## The generic component

`KeyboardView` is device-agnostic on purpose: it binds only to a `KeyboardLayerViewModel` and exposes a single `KeySelectedCommand` styled property that `KeyCapView` invokes through `$parent[KeyboardView]` with the clicked `KeyboardKeyViewModel` as the parameter. Neither the picture nor the cap knows the editor exists; `KeyboardEditorView` supplies `SelectKeyCommand`. **What a new device must supply is a `KeyboardVisual` and nothing else** — no XAML, no control, no view-model subclass. `EditorViewModelFactory` then resolves it automatically (it requires *both* `VisualCatalog` and `GeometryCatalog` to answer).

**The picture is drawn at mock scale and grown as one transform.** Two controls, two jobs, and neither does the other's:

**`BoardScaleHost`** is a `Decorator` and the only thing that scales. It measures its child at `Size.Infinity` — the child's *mock-scale* size is the thing being scaled, so it must never be talked down by the space on offer — resolves one uniform factor (`min` of the two ratios, clamped to `MaxScale`), applies a `ScaleTransform` with `RenderTransformOrigin = TopLeft`, and centres the scaled result inside the slot. Because it is a render transform over the finished board, **the whole picture** grows together: the caps, the 1 px borders, the 9/400 legends, the 2 px badges, the 9 px section padding and the 26 px gutter. A layout-time scale would grow the cells and leave everything drawn on top of them behind — that is the entire reason this control exists. `Scale` is published after each arrange (1 is mock scale, 0 is "nothing drawable"). Edge cases: a dimension that is infinite/NaN/non-positive **constrains nothing** during measure (an auto-sizing or scrolling parent offers infinity), and with no candidate at all the answer is 1, never infinity; during *arrange* the same dimension means no room at all, so the child is arranged away and its transform cleared rather than painted at mock scale through a slot that has none. `Decorator.Padding` is deliberately not honoured — the board's inset is the section panel's `PaddingBoardSection`, which scales with everything else, and padding here would be the one measurement that did not.

**The picture stops growing at `BoardScaleMax` (1.5), and it is fitted to the height it actually has.** Both halves are [#123](https://github.com/migus88/kinesis-edit/issues/123), and both are deliberate departures from what shipped before it.

- **The ceiling.** `BoardScaleHost.MaxScale` clamps the resolved factor, on the measure path and the arrange path alike, including the "no candidate → mock scale" fallback. It defaults to `double.PositiveInfinity`, so **the control carries no policy**: the ceiling reaches it from `Controls/KeyboardView.axaml`, which names the `BoardScaleMax` geometry token, and a host used anywhere else is unaffected. The handoff states no maximum — recorded as a deviation in [design-system.md](design-system.md) — but "scale the whole board up with available space" was written against its own 1000 px canvas: at 2560 wide the Freestyle Edge RGB's 695×196 picture was drawn **2238×631**, a wall of caps under 40 px legends. 1.5 is reached at ~1050 px of board width, a little above the 1000 px default, so the default window and the 720×480 floor are both below the cap and unchanged by it. Above it the board stays **centred** and the rest becomes canvas.
- **The fit.** **No vertically-oriented `StackPanel` may be an ancestor of a `BoardScaleHost`.** One measures its children with `double.PositiveInfinity` down its own stack axis, so the host's vertical candidate abstained, the scale came from the **width alone**, and the block's desired height exceeded the slot it had been given — which, because `ClipToBounds` is deliberately false on every link of this chain, was *painted over* its neighbours rather than cut. Both boards hung under one: at 1600×520 the Layout tab's legend row landed 18 px below the bottom of the window and the Lighting tab's paint line landed 1 px below it. Both containers are `Grid`s now — `*,Auto` on the Layout tab (board, legend) and `Auto,*,Auto,Auto` on the Lighting tab (header, board, paint line, zones) — and a star row hands the picture the height that is really there. `KeyboardViewTests.NoScreenTheAppCanShow_PutsAVerticalStackPanelAboveTheBoard` walks every screen and fails if one comes back. **Anchoring and fitting are independent**, and #124 moved only the first: both blocks are `VerticalAlignment="Center"` now, which decides where the finished block sits in its column and changes nothing about the star row that sizes the picture inside it. Turning either back into a centred `StackPanel` would reintroduce this defect *and* fail the rule it left behind.
- **The floor the fit needed.** Fitting the board makes every row sharing its column a claim on the picture, and a `Grid` measures its `Auto` rows before its star one. On the Lighting tab those rows win: at 720×480 the header, the paint line and the wrapped zone buttons want 231 of the column's 235 px, which drew the board **four pixels tall** — a board that fits its content area perfectly and is not a board any more. Its row therefore carries `MinHeight="{StaticResource HeightBoardMin}"` (100). Below that the picture stops giving way and the zone row runs past the column instead, exactly as it does today at that window. The Layout tab needs no floor: the only thing sharing its column is the 34 px legend row.

Nothing was added to the chain to achieve any of it — **no `ScrollViewer` and no clip**. The board *shrinks* to fit at every window size; that is the chosen behaviour, and a clip anywhere here would erase the focused cap's 3 px halo.

**The two tabs are offered the same width, so where width binds they draw the same board** ([#124](https://github.com/migus88/kinesis-edit/issues/124)). Two things used to make the Lighting picture smaller for reasons that had nothing to do with the picture: its board column carried a 16 px right gutter the Layout column does not, and its rail was a fixed 300 where the key inspector's was 268. Both are gone — no gutter on either column, and one shared rail width (see "The rail's width, and the seam that moves it") — so `BoardScaleHost` resolves one factor from one slot width. `EditorChromeTests.BothTabsDrawTheBoardAtTheSameScale` asserts it on one editor at one window, at the default rail and at a dragged one, because the defect is a *difference between two tabs* and no single-tab assertion can see it.

They still part where **height** binds, and that is structural rather than a residue: the Lighting board's column also carries the board header, the paint line and the wrapping zone row, so its star row is handed less height than the Layout board's, which shares its column with a 34 px legend row alone.

**`KeyboardPanel`** is a `Panel` subclass, a pure arranger, and knows nothing about keys, layers or remaps:

- The cell is **not square**. Every 1U cell is `PitchX` (`KeycapPitchX`, **34**) wide and `PitchY` (`KeycapPitchY`, **30**) tall, and the cap inside it is inset by `Gap` (`KeycapGap`, **4**) — so *pitch minus gap is the cap the handoff specifies*: 34 − 4 = 30 wide, 30 − 4 = 26 tall. The gap is a **single inset**, not half a gap each side, which is what makes a wide cap its span in pitches minus *one* gap: a 2U Backspace is 2 × 34 − 4 = 64, and a row of six 1U caps is 6 × 34 − 4 = 200. The three tokens are passed in from `KeyboardView` rather than baked in, and `ShapeAndTypeTokenTests` asserts the subtraction, so the numbers cannot drift apart in silence.
- **It scales nothing.** `MeasureOverride` reports the section at mock scale whatever space is offered; shrinking here would scale the picture twice.
- `UnitOriginX`/`UnitOriginY` are what let one panel draw a **section** without any coordinate being re-based: caps keep the board-absolute units `KeyAdjacency` needs, and the panel subtracts its own origin as it places them.
- Placement travels on **attached** `UnitX`/`UnitY`/`UnitWidth`/`UnitHeight` doubles, not off each child's `DataContext`, so the panel works with any item type. They are named `Unit*` because a static `WidthProperty`/`HeightProperty` declared here would hide `Layoutable`'s — a warning and a genuine XAML ambiguity.
- `BoardWidth`/`BoardHeight`/`PitchX`/`PitchY`/`Gap` are `AffectsMeasure`; `UnitOriginX`/`UnitOriginY` are `AffectsArrange`; the four attached ones are `AffectsParentArrange`.
- A board with no usable size still arranges every child to `default` — an unarranged child keeps stale bounds and would be painted over the empty picture. Cap spans clamp at 0, because a negative `Rect` throws.

**`ClipToBounds` is false on every link of the chain** — `KeyboardView`, the scale host, both `ItemsControl`s, the section `Border`, the panel, each `ContentPresenter`, `KeyCapView` and the cap's own template parts. A focused cap casts a 3 px halo past its own bounds into a grid whose caps are 4 px apart, and a clip anywhere along the chain erases it.

`KeyCapView` sets the state classes `selected` / `listening` / `modified` / `macro` / `tapHold` / `advisory` / `locked` (`locked` = `!CanEdit`) plus the picture-level `stateBadges` and `lighting`, the caption's `stacked` (from `IsCaptionStacked`), the secondary legend and the cap's lighting face. That face is **three stacked layers** — hatch, paint, effect — drawn from **four** `Border`s, because which *side* of the effect the paint goes on is the mode's answer. It needs two answers from two places: the picture says whether lighting is on screen at all (`KeyboardView.ShowsLighting`, handed to each cap as `KeyCapView.ShowsLighting`), and the cap's own `HasPaintColor` / `HasEffectColor` say what *this* key shows. Nothing at all on the Keys tab; on a lighting board, the `HatchBrush` underneath always — so an off or unpainted key is **hatched, never black** — then the painted colour at `PaintOpacity` and the sampled effect colour at `EffectIntensity`, in the order the mode dictates. A mode that **renders** the paint (`PaintOpacity` 1.0 — Freestyle, Breathe, Frozen Wave) draws it *under* the effect, so the effect modulates the painted colour, which is what makes Breathe pulse. A mode that **ignores** it (0.4) draws the same layer, at that same 0.4, *over* the effect: Wave, Solid and Spectrum light every key at intensity 1.0, so a paint layer under them renders at 0 % rather than at the 40 % mockup 2f promises, and over it composites to `effect·0.6 + paint·0.4` — the effect still travelling, the colours still visibly on file. The two are `KeyboardKeyViewModel.ShowsPaintUnderEffect` / `ShowsPaintOverEffect`; exactly one is ever true, neither is on an **unpainted** key — whose effect therefore keeps its full strength, since there is nothing under it to reveal — and neither is under Off or Pitch Black, where `PaintOpacity` is 0 and the cap stays hatched. There is no second constant: the paint layer's own opacity is the only number, and the effect keeps whatever share of the cap it leaves. The surface has to own the first answer because **both tabs render the same layer and cap view models** — see "The Lighting tab" — so nothing on the `DataContext` could separate them. `ShowsLighting` answers three more questions: the caption's colour, the paint-selection ring (drawn only on the lighting board) and, by implication, the sub-legend — **withheld wherever the face is lit**, because a 26 px cap has one band to give and a lighting board is about colour. On that board the caption survives any fill because it is coloured from that fill's own relative luminance (`KeycapLitLabelDarkBrush` / `KeycapLitLabelLightBrush`, the app's only variant-independent pair), not from the theme; on the Keys tab it keeps the ordinary `TextPrimary` role, because `ShowsLighting` gates the colour exactly as it gates the face (**#131** — the caps are painted at load, so an ungated caption was drawn for a fill nothing painted, at 1.15:1 in dark and 1.09:1 in light). All chrome lives in the design system ([design-system.md](design-system.md)), which is the authority on it; what the editor needs to know is where each piece went. The cap is the **`KeyCapButton` control theme** (`Themes/ControlThemes/Keycap.axaml`), which replaces Fluent's template outright rather than reaching into it — `Styles/Keyboard.axaml` only bridges `Button.keyCap` to that theme, and otherwise carries only the `keyCapText`/`keyCapSubText` legend roles and the listening pulse. Cap precedence lives in the selectors, not in the file's order: every state names the ones it loses to (and `:disabled`, which beats them all), so a listening key always reads as listening and a dimmed board keeps no live face. The **layer switcher is a `ListBox` on the `SegmentedControl` theme** and the **section strip a `TabStrip` on `TabStrip`**, named at the call site in `KeyboardEditorView`; the `layerTab` / `editorTab` classes are gone, and the cleared `Transitions` both controls need — layer switching is deliberately unanimated — comes with the theme.

### The badge vocabulary

Four marks on a 30×26 cap, one hue and one corner each (`docs/design/handoff.md` § "Focus, selection, key badges"). Each is a **part of the `KeyCapButton` template**, never a style reaching in — that is what the control-theme layer exists to remove.

| Class | Part | Mark | Size token | Brush |
|---|---|---|---|---|
| `.modified` | `Border#RemapBar` | 2 px bar flush along the **bottom edge**, its lower corners following the cap's | `BadgeRemapBarHeight` | `AccentBrush` |
| `.macro` | `Ellipse#MacroDot` | 5 px dot, **top-right** | `BadgeMacroDotSize` | `BadgeMacroBrush` |
| `.tapHold` | `Path#TapHoldMark` | ~6 px right-triangle whose right angle *is* the cap's **bottom-right** corner | `BadgeTapHoldSize` | `BadgeTapHoldBrush` |
| `.advisory` | `Border#AdvisoryBar` | 12×3 rounded bar, **top-right** | `BadgeAdvisoryBarWidth`/`Height` | `StatusAdvisoryStrongBrush` |

Three of the four need no margin: the template's inner `Panel` already sits 3 px inside the cap's outer edge (`Root`'s 1 px border + its 2 px padding), which is exactly the mockups' "2 px in from the inside of the border", so an alignment is the whole placement. The remap bar is the exception — it is flush rather than inset, so it carries `Margin="-2"` to cancel that padding, the same pair `Rectangle#Locked` uses.

**The collision the design does not answer.** The macro dot and the advisory bar are both specified top-right. Settled in the theme: **the advisory bar keeps the corner**, and the macro dot insets left by `BadgeAdvisoryBarWidth` + `BadgeGap` (12 + 2) whenever both are true. Both stay visible and the state that wants attention keeps the position the eye is trained on. The 14 is spelled as a literal because a `Thickness` cannot be composed from an `x:Double` in markup — move either resource and it moves with it.

**A badge is a fact, like the hatch.** None of the four is qualified against `:disabled`, against the face ladder, or against each other beyond that one collision: "this key carries a macro" does not stop being true because a pointer crossed it or because the board is loading.

**Whether to draw them at all is the picture's answer, not the key's.** `KeyboardView.ShowsStateBadges` (default **true**) is handed to each cap as `KeyCapView.ShowsStateBadge` and reaches the `.stateBadges` class every badge selector is qualified with. Same shape and same reason as `ShowsLighting`, mirrored: the Layout tab is the surface these states belong to, so a board opts *out* (the Lighting tab does, to stay about colour) rather than in. The four state classes are written whatever the surface is — they say what the **key** is; `.stateBadges` says whether this **surface** draws it. It is a fifth class rather than a `MultiBinding` on each badge because `Classes.x="{Binding}"` takes a single binding and cannot take one.

### The legend row — `BoardLegendViewModel`, `Views/BoardLegendView`

Mockups 1e/2a put a row under the board that restates the badge vocabulary at legend size, each mark beside a live count, plus two actions. `BoardLegendViewModel` is a type of its own rather than five more properties on `KeyboardEditorViewModel` (already the largest class in the app), and it decides nothing: the counts are pushed in and both commands are the editor's.

- **Five counts, all scoped to the shown layer**: `Remapped` / `Macro` / `Tap-and-hold` / `Advisory` / `Locked`. Four are derived by `KeyboardLayerViewModel.RefreshCounts()` from the layer's own caps (`IsModified`, `IsMacro`, `IsTapAndHold`, `!CanEdit`). `AdvisoryCount` cannot be — the fact lives in `EditorAdvisories`, outside `KeyboardKey` — so `RebuildAdvisories()` pushes `_advisories.CountForLayer(layer.Index)` onto each layer, exactly as it pushes `HasAdvisory` onto each cap.
- **One funnel, and its order matters by one step**: `RefreshCounters()` → `RebuildAdvisories()` → `RefreshLegend()` → `RefreshDirtyState()`. The advisory rebuild has to run first, because the legend reads its count back *off the layer*. `SelectLayer` calls `RefreshLegend()` directly (a layer switch writes nothing, so it does not go through `RefreshCounters`), and so does every copy-key transition.
- **`RefreshLegend()` re-reads the whole shown layer** (`SelectedLayer?.RefreshFromModel()`) before handing the counts over. It has to: a single-key edit refreshes only its own cap (invariant 3), and a macro assigned from the macro panel refreshes **no** cap at all — so a derived count taken without the re-read would be yesterday's board. It is the shown layer only, because the row is layer-scoped.
- **The swatches are the cap's badges redrawn**, out of the same token brushes, at legend size (the cap's 2–6 px marks would disappear in a text row). The counts are sans and the `LEGEND` label is mono — a count is the app talking, and a section label is 10/600 uppercase mono.
- **Scope: the Layout/Macros board only.** The Lighting tab draws no state badges, so it counts no states and carries no row. The handoff's "every board view carries a legend row" is honoured where state is on screen.
- **The counts give way, the actions never do** (`*,Auto` with the counts column clipped). The row was `Auto,*,Auto` until #92, which was correct until the rail took 268 px of the same line: a horizontal `StackPanel` measures its children at **infinite width**, so an `Auto` counts column does not shrink when the row runs short — it overflows, and because `ClipToBounds` is deliberately false along the whole board chain, `Reset layer` arranged 4 px *under* the rail. **~5 900 tests passed through it.** Every assertion about the row was true — both buttons existed, were bound, carried their captions and their theme — and only *where they landed* was wrong, which nothing that asks a control about itself can see; it took a captured frame. `BoardLegendTests.TheRowsActions_AreNotArrangedUnderTheKeyInspectorRail` pins it now, at the window rather than at the row, because the row's own bounds were exactly what was lying. The count spacing is `Space12` rather than `Space16` for the same reason: at the 1000 px floor the six items and the two actions want ~4 px more than there is, and the clip would otherwise take it out of the last count's digit.

### Copy key — `KeyboardEditorViewModel.Legend.cs`

**One action, three entry points**: the legend row's `Copy key…` (mockup 1e), the key inspector footer's `Copy to…` and the locked-key panel's. All three run this same `CopyKeyCommand` — a second copy path would be a second set of refusals to keep in step. It is the editor's existing click-then-press grammar with the press replaced by a **second click**: arm from the selected key, then the next cap clicked is the target.

| Step | What happens |
|---|---|
| **Arm** (`CopyKeyCommand`) | Requires a `SelectedKey`, `!IsLoading` and `!IsBusy` — **and nothing else**; see the two relaxations below. Ends any listening key first, sets `CopySource`, puts `CopyTargetPrompt` (`Pick a target key · Esc to cancel`) in the row |
| **Target** | `SelectKey` intercepts the click ahead of the whole click contract — without that, the second half of the pick would be read as "a second hit on the selected cap" and start a remap on the very key being copied *from*. A click that selects nothing disarms and falls through |
| **Refuse** | The source itself → nothing is written, and the click reads as "never mind": disarm. A position that can never be remapped (05 §5.3) → `CopyTargetLockedPrompt`, and the copy **stays armed**, because the refusal is about that one cap |
| **Commit** | `target.Key.CopyFrom(source.Key, CopyScopeFor(target))`, disarm, `target.RefreshFromModel()`, `_macroPanel?.RefreshFromModel()` (the macro half adds rows to the profile's list), then `RefreshCounters()` |
| **Disarm** | `CancelCopyKeyCommand`, and implicitly on a layer switch, a tab switch, a feature panel opening, a remap starting, an import, a save and `Dispose` |

**Arming and listening are mutually exclusive by construction** — they are two different answers to "what does the next input mean" (invariant 5's shape, one level up), so arming ends a listen and starting a remap ends an armed copy.

**Escape's order is stated, not lucky**: panel → capture → armed copy → the selection. `2b`'s grammar says Escape "leaves capture mode first", so `CancelRemapCommand` is tried before `CancelCopyKeyCommand` even though the editor never lets both be live at once. A copy is armed by a click and finished by a click, so nothing swallows the Escape that cancels it. The last stage used to close the key inspector; since #119 it clears the key selection instead, and the rail falls to its empty state.

**The copy scope is a decision, not `All` by default.** `CopyScopeFor` returns `KeyCopyScopes.All` where the target may carry a macro and `KeyCopyScopes.KeyData` where it may not (`!CanAssignMacro`, 05 §5.3). `KeyboardKey.CopyFrom` deliberately copies macros onto a restricted position anyway, which leaves `KeyboardLayout.Validate()` reporting `MacroOnRestrictedKey` — **not** one of the four budget breaches `EditorAdvisories` reports, but a violation that stops the save outright (04 §5.3). A copy that quietly made the profile unsavable would be worse than one that carried a little less.

**What commits is the source's *assignment*, not its remap fields.** `KeyboardKey.CopyFrom` transfers the action the source performs (`ModifiedOrOriginalKey` — the same readout the cap caption and the rail's `now [x]` are drawn from) and re-derives the target's remap by `Remap`'s own rules: equal to the target's `OriginalKey` clears it, anything else stores it. Before #119 it copied `ModifiedKey`/`IsModified` verbatim, which made the whole action a **no-op from an untouched source** — that flag says "no remap", so the target simply kept its own factory action — silently **wiped** a remapped target when the source carried none, and left a **redundant** remap whenever the source's action was what the target already did, inflating the row's `Remap (n)` and writing a pointless layout line. A source carrying a **tap-and-hold or a multi-modifier** is exempt: that rule *is* its assignment and is copied as itself, and adding a remap beside it would put two single-key rules on one position, which 04 §4.3 cannot write. One consequence is deliberate — a **locked source now copies its factory action across**, which is what makes "a locked key can be a copy source, never a target" worth offering at all.

**`CanCopyKey` lost two clauses with #92, and both losses are the point.**

- **The source no longer has to be editable.** A locked position (05 §5.3) can be copied *from* — its assignment is perfectly readable — and never *onto*, which the `!target.CanEdit` refusal above already covers. Requiring `CanEdit` on the source refused the whole action rather than one direction of it, which is exactly what made the locked-key panel's `Copy from…` / `Copy to…` asymmetry cosmetic.
- **It no longer consults the open overlay.** The key inspector footer runs this very command and the rail is **not modal**, so nothing about it may be phrased in terms of `HasActiveOverlay`. Nothing is lost: `ShowOverlay` disarms an armed copy on the way in, and the scrim over the board is what stops a pick being finished under a panel.

### The key inspector rail — `KeyInspectorViewModel`, `KeyboardEditorViewModel.Inspector.cs`

The third column of the Layout tab (mockups `1e` dark / `2a` light, `docs/design/handoff.md` § "Layout tab"). It names the position, says what the board shipped it doing and what it does now, offers the position's **one rule slot** as tabs, hosts whichever mode panel is showing, and carries a footer under all of them.

**It is always on screen, and it is drag-adjustable ([#119](https://github.com/migus88/kinesis-edit/issues/119)).** Both facts replace what the rail used to do. It used to hide its own frame whenever nothing was selected — and the host bound `IsVisible` to the same flag, so the `Auto` column measured zero and the board **jumped sideways to re-centre** the moment a cap was clicked or the header's `×` was pressed. It is a permanent column now: `KeyInspectorViewModel.HasSelection` switches between the rail's three rows and a single centred `NoSelectionMessage`, and neither state changes the column's width. There is no close button, and Escape's last stage clears the **selection** instead (see "Escape — the resolution").

**It is not modal, and everything below depends on that.** The rail never sets and never reads `HasActiveOverlay`: the board beside it stays clickable, the remap workflow and the armed copy go on working underneath it, and selecting another cap simply refreshes it. That is the whole reason it replaces the two feature panels it replaces.

| Part | What it is |
|---|---|
| Empty state | With nothing selected the whole rail is one muted, centred line — `KeyInspectorViewModel.NoSelectionMessage` — in place of the header, the tabs and the footer. Its own sentence, not one borrowed from a panel: the two panel `NoSelectionMessage`s answer "this panel has nothing to edit" from inside a rail that is already explaining itself, and neither is reachable now |
| Header | A 32 px accent tile carrying the cap's own legend, then `Left half · [1] position` — the half from `KeyboardKeyViewModel.DescribeSection`, the token from the **factory** assignment, because that is what identifies the position however often it is remapped. Under it, `factory [1] · now [esc]`. **No close button** — a permanent column has nothing to dismiss |
| Mode tabs | `Remap` · `Tap & hold` · `Macro`, a 2×2 grid on the section strip's own `TabStrip`/`TabStripItem` themes. `Multi-mod` joins the set only where `KeyboardKey.SupportsMultiModifiers` — absent, never dim |
| Exclusivity | `KeyInspectorViewModel.ExclusivitySentence`, verbatim from `2a`: *"This key does one thing — picking another replaces it."* Drawn in a **hint block** (`Border.hintBlock`, an `IconInformation` mark on the inset surface behind a `SurfaceLine` hairline) rather than as bare prose — and **deliberately not amber**, because amber is the advisory colour and this sentence warns of nothing. The amber warning directly beneath it is unchanged, so the two stop reading as one block |
| Warning | Switching mode while the position already carries a rule raises `ModeSwitchWarning`, **at the point of switching rather than after** (`2h`). The noun moves with what the position is actually carrying. Amber, and it never blocks |
| Body | Whichever `KeyInspectorPanelViewModel` the mode maps to — or, for a locked position, `LockedKeyPanelViewModel` **in place of the modes and the footer** |
| Footer | The position's advisory note (read off `EditorAdvisories.ForKey`, never rescanned), then `Revert key` (the editor's `ResetKeyCommand`) and `Copy to…` / `Cancel copy` (its `CopyKeyCommand` / `CancelCopyKeyCommand`) |

**Construction is eager, in the editor's constructor, and the dialect is what made that a question.** `RemapPanelViewModel` needs a `TokenDialect` to build the picker's catalog, and `Layout` does not exist until `LoadAsync` has run. The resolution: **the dialect is a fact about the device, not about the profile** — `KeyboardLayout.Dialect` is nothing but `KeyboardLayoutBuilder.ResolveDialect(device.Id)`, now also exposed as `KeyboardLayout.DialectFor(DeviceId)`. Asking that function directly is what lets the rail be built once rather than appearing halfway through a load, and `KeyboardEditorViewModelRemapTests` pins that the two answers agree rather than assuming it.

**Everything the rail shows is pushed, from two kinds of place.** Core raises no change notification at all:

- `RefreshLegend()` — the tail of `RefreshCounters()`, which every path that can write the layout already ends in. Hanging the rail there makes "every mutation reaches the rail" true by construction rather than by a list somebody has to maintain.
- `SelectKey` / `SelectKeyDirectly` — the paths that move what the rail is *about* without writing anything, so they never reach the funnel.

`KeyInspectorViewModel.Refresh` then refreshes **every** panel it holds, not only the showing one: a panel the user switches to must already be right, and the alternative is a second refresh path down the mode switch. Every panel therefore has to survive being refreshed with a null key and with the key it already had.

**`Inspector.Open()` is called at the top of `SelectKey` whenever a cap is clicked** — including the cap that is already selected. A second click is a request for the inspector, not only the click contract's promotion to listening; without it, a rail the user pressed Escape on could only be brought back by selecting some other key first. `Refresh` alone cannot tell "the user asked again" from "somebody else's edit went through the funnel", which is why `Open()` exists at all.

**The two `Assigned` handlers are required, not decorative.** A panel writes into `KeyboardKey` and Core announces nothing, so the cap is re-read by hand (`SelectedKey?.RefreshFromModel()`) and the funnel is run.

**Capture.** The rail is a fourth consumer of the keystroke service, and it is handled exactly as the macro panel is — the panel announces `RecordingChanged`, the editor turns the service on and off — with one guard the macro path does not need. `_isInspectorCapturing` tracks whether *this* editor started the capture, because the rail announces its recording state on every mode switch and every selection change too, and answering one of those with an unconditional `Stop()` would deafen a macro recording on the Macros tab. That is "never stop a capture you did not start", made explicit.

`Inspector.Deactivate()` stands the showing panel down **without closing the rail**, and is called wherever the editor takes the keyboard back: a layer switch, a section switch, a save, an import, and a modal panel opening over the board. `Inspector.Close()` — now only `Dispose` — does the same and drops `IsOpen`. **It no longer collapses anything**: the rail is a permanent column, and `CloseCommand` is unreachable from the screen since #119. What `IsOpen` still answers is "is there a position in the rail to act on", which is what gates `InsertSpecialActionCommand`. In `Dispose` the rail is closed **before** its handlers come off, so an armed record button hands the capture service back through the ordinary path; the shell disposes the open editor whenever it is replaced (Home, or another device), so that is the navigation path too.

#### The rail's width, and the seam that moves it

**The width lives on the grid column, not on the rail.** `Border.inspectorRail` carried a `Width` setter until #119, and `LightingModeRailView` carried its own `WidthInspectorRailWide` until #124; a `GridSplitter` resizes a *column*, and a local `Width` on the rail would have outranked whatever the column said, so in both cases the mechanism had to **move** rather than be layered over.

**One width, two tabs, one preference ([#124](https://github.com/migus88/kinesis-edit/issues/124)).** The state lives on `InspectorRailWidthViewModel`, not on `KeyboardEditorViewModel`: `Width` (clamped by `HostPreferences.ClampInspectorRailWidth`, a no-op when it did not move, persisted through `IHostPreferencesStore`), `IsWide` (pushed in from `KeyInspectorViewModel.IsWide`) and `EffectiveWidth`. The editor builds **one** instance, delegates `InspectorRailWidth` / `EffectiveInspectorRailWidth` to it verbatim — so its public API, its bindings and its tests are unchanged by the rehoming — and hands that same instance to `LightingTabViewModel.Rail`. The Lighting tab's mode rail is therefore the *same* resizable column with different contents: a width dragged on either tab is the width the other opens at, and it is stored once, under the existing `inspectorRailWidth` key. There is **no** second preference and no per-tab width; a fix that adds one has undone the point. The reason it had to move at all is that the second tab could not reach the editor's private width state without either a second stored value or a back-reference to the editor.

**One width, one column, two rails ([#128](https://github.com/migus88/kinesis-edit/issues/128)).** #124 gave the two rails one stored number, but they were still two `ColumnDefinition`s in two grids, so the Lighting rail started inside its own tab's padding and the two matched only by arithmetic. There is **one** column now — `EditorColumns` in `KeyboardEditorView`, column 2 — and the two rails are two `IsVisible`-gated children of one `Panel` in it (`RailHost`). Switching between Keys and Lighting therefore cannot move the board by a pixel, because nothing about the column changes.

**The column is driven from code-behind, and that is deliberate rather than lazy.** A `ColumnDefinition` is a bare `AvaloniaObject` — in neither the logical nor the visual tree — so it inherits no `DataContext` and a `{Binding}` written on it has nothing to resolve a path against. `Views/InspectorRailColumn` is that driver: `Sync()` puts the width and the two geometry-token bounds on the column, `Follow(rail)` re-points it at a `DataContext`'s rail (dropping the previous subscription — the shell reuses views), `Store()` reads the column back after a drag and writes `Width`, which clamps, persists ([host-preferences.md](host-preferences.md)) and pushes the clamped result back through `Sync()`. **Four** trigger points since #128, and a view that drops one has a rail that is right until something moves it: attach (the columns do not exist before the XAML is loaded), a `DataContext` change, the rail's own `PropertyChanged`, and **the rail host's `IsVisible`** — the last three subscribed by the driver itself, so the view hands over the grid and reports the seam's drag and nothing else.

**A section with no rail collapses the column outright.** Macros and Settings take the whole content width, and a fixed-pixel column keeps its width however invisible its contents are — so "there is no rail here" has to be spelled on the *column*, not only on the control: `Sync()` zeroes `Width` **and** `MinWidth` when the host is hidden (`MaxWidth` is left alone; it only caps). The host's `IsVisible` is the single source of that answer, gated declaratively in XAML on the open tab, and `Store()` refuses to write a collapsed column back — zero is not a width the user chose. The seam is gated on the same tabs, so an `Auto` column whose only child is invisible measures zero too.

**`WidthSource` now has one call site, and it reads `Effective`.** It used to be the entire difference between the two: Keys passed `Effective`, Lighting `Stored`, because the Macro panel's 300 px floor is the Keys tab's entitlement. One column has one width, so picking a different number per tab would move the seam — and with it the board — every time the user switched section, which is the exact defect #119 and #124 exist to prevent. The floor therefore applies to the column whichever rail is in it. `Stored` is kept on the enum, with **no call site**, because the two numbers are still two different questions and a future second column (a rail on both sides, another board's screen) would have to answer one of them.

The seam itself is a `GridSplitter` on the `RailSplitter` control theme, reached through the `railSplitter` class — 6 px of hit target over a 1 px `SurfaceLine` hairline that lifts to `SurfaceLineHigh` under the pointer, with the standard focus ring and no transition. The body grid is `section * | seam Auto | rail Auto`, and the rail's `ColumnDefinition` carries the width, its `MinWidth` (`WidthInspectorRailMin`, 240) and its `MaxWidth` (`WidthInspectorRailMax`, 520).

**The 300 px macro variant is a floor, not an override.** `handoff.md` § Geometry states two widths — "268px wide on Layout, 300px on the macro-editing variant" — and `KeyInspectorPanelViewModel.WantsWideRail` is still true on the Macro panel and nowhere else, projected by the rail as `IsWide`. What changed is what is done with it: `EffectiveWidth` is `Math.Max(Width, 300)` while the Macro panel is showing. **The width is a fact about the panel, not about the rail** — but a user who dragged the rail to 420 must not be yanked back to 300 when they open a macro, which an override would have done. Recorded as a deliberate deviation in [design-system.md](design-system.md).

It is a plain width change with no transition: the motion budget lists no rail resize and a tab swap is 0 ms on purpose. One consequence, seen only in a captured frame: at the 1000 px default the legend row's counts column loses its last item (`Locked 0` is clipped) while the rail is wide, and a rail dragged past ~400 clips more of it. That is the column's designed degradation — "the actions are what a user reaches for, so the counts are what gets cut" — not a new defect.

#### The panel contract — `KeyInspectorPanelViewModel`

The rail knows nothing about any concrete panel, and a panel knows nothing about the rail beyond this abstract class. A panel owns exactly one `KeyInspectorMode`, its own fields, its own commands and its own writes into `KeyboardKey`. It does **not** own the header, the assignment line, the tabs, the exclusivity sentence or the footer.

- `Refresh(key, layer, layout, advisories)` **re-reads and never writes.** It is called after somebody else's mutation, so a panel that wrote from it would write on every counter refresh — and, because the write would end in another refresh, forever.
- `IsRecording` / `RecordingChanged` are how a panel says it is waiting for a keystroke. **It must be honest**: the editor folds it into `IsCaptureActive`, which is what suppresses ⌘S.
- `IsAvailable` / `UnavailableReason` are how a panel **refuses politely rather than disappearing** — the two sanctioned exceptions to the capability law, a firmware gate (09 §2) and a locked position (05 §5.3).
- `Deactivate()` is how a panel is put down: whatever it has armed stops, and nothing is written.
- **A field that records a keystroke is never a `TextBox`.** Focus inside one auto-suspends capture, so the field would swallow the very keypress it exists to record. The `TokenField` control theme (`Classes="actionField"`) is a `Border` with an `.armed` state written for exactly this. The picker's *search* field **is** a real `TextBox` and is supposed to suspend capture — a query is typed, not pressed.

#### The Remap panel and the token picker

`RemapPanelViewModel` replaces §11.6's Search Keys overlay inside the rail — the same catalog (`KeySearchCatalog`), no longer behind a scrim. Two ways in, and the physical key is still the fast one: `● Record` arms capture and the next keypress becomes the assignment; the picker beside it is for the actions no keyboard can press (a media key, a mouse button, a profile selector) and for the user who would rather type a name.

It assigns through `KeyboardKey.Remap`, deliberately and exactly as the editor's own capture path does — pressing a position's own factory action un-does the remap (04 §2.1). The duplicate advisory is **read** off `EditorAdvisories.ForKey` after the write and is *retrospective*: it appears because an assignment created a duplicate, never as a prediction before one.

`TokenPickerViewModel` is the reusable core — query, live counter, the six category chips plus `Recent`, counted groups, one selected row showing `↵ assign` — and it is hosted at **four** call sites: the rail's Remap panel, the Tap & hold panel's two `Search` actions, `TokenPickerOverlayViewModel` (§11.6's `Search Keys (Macro)`, the one call site that still wants a modal, because an insertion is a question whose answer has to come back to the caller), and — since #128 — the Macro panel's **chord composer**.

**`RecentTokenStore` is one per editor** and shared by every picker the editor hosts, the composer's included, so an action inserted into a macro is offered by the rail's `Recent` chip afterwards and a chord built in the composer is one chip away next time. The Macro panel takes it as an **optional** fourth constructor parameter: a panel built without one keeps a history of its own, which is what a test wants. It is per-session and **in memory**: persisting it is an `app_settings.txt` question that belongs with [#96](https://github.com/migus88/kinesis-edit/issues/96).

#### The Macro panel — `MacroInspectorPanelViewModel` (issue #93)

Mockup `2i`, verbatim: *"selecting a key edits its macro right here — the Macros tab is a library, not the editor"*. The tab used to bridge out to the Macros tab; navigating away from the board when a mode tab is pressed was the placeholder, not the design.

- **There is no Assign button, deliberately.** Editing in place means the first recorded keystroke *is* the macro: `EnsureMacro()` creates it, stamps its trigger and layer the way `MacroLineParser` does (04 §4.2), and puts it in the key's first free slot — or appends it to the Advantage 360's flat list. The old panel's draft-then-assign pair was a modal's shape. It is the only path that *adds* a macro, so it is the only one that asks about the macro count of 06 §6, and a refusal reports itself and writes nothing.
- **The name dropdown picks; it does not rename.** `2i` splits the two: the tab is the library ("rename, see which keys and layers fire each one, duplicate, delete") and the rail is the editor. Picking a name runs `MacroLibrary.AssignTo` — *"assigning a named macro to a second key is a pick from the inspector's own dropdown"* — after emptying the position's current slot, so the pick **replaces** what the key was carrying rather than quietly filling a second slot. The placeholder row (`No macro on this key`) is a state, not an action: a dropdown must never be the thing that deletes a macro. Renaming is `KeyboardEditorViewModel.RenameMacro`, which this panel never calls.
- **The reuse note and the where-else line** are `2i`'s own: `Named, so it can be picked for another key from this same dropdown.` shows only once the macro really carries a name, and `Also on [f7] · Fn` is built from the library entry's *other* sites — the entry **is** the answer to "which keys and layers fire this one", so nothing here rescans.
- **The steps editor** (`MacroInspectorStepsViewModel` / `MacroInspectorStepViewModel`) draws the mock's rows: `01 [lshft] press`, `02 [b] ⇧ held`, `03 [lshft] release`, `04 [e] tap`, `07 [ent] tap · 80 ms`, then a trailing `＋ insert step` numbered as the step the next keystroke lands in. **A row is a step plus the delay behind it**: a delay is its own keystroke in the file (06 §2.2) but a qualifier of the step it follows on screen, and every write rebuilds the whole keystroke list from the rows rather than patching an index — a reorder that moved a step without its delay would silently retime the macro. A delay with nothing in front of it (a macro that opens with one, or two in a row) keeps a row of its own, because the file can hold that and dropping it would be editing behind the user's back.
- **How a row spells a held modifier — marks, not file codes; left unmarked, only right spelled (issue #122).** The row draws `NN [token] ‹marks› action [· delay]`. The **token is tinted `MacroStepKeyBrush`** so the key struck reads out of the row at a glance; the modifiers are `MacroModifierMarks.Split`'s parts, drawn as **two runs in two faces** — the `R` side letter in `monoValueSmall muted`, the mark itself in `.keySymbol muted` — because the key-symbol subset carries no Latin letters and an `R⇧` set wholly in it would fall back for its `R`.

  **The rule is: left is unmarked, right is spelled `R`.** `LS` draws a bare `⇧` and `RS` draws `R⇧`; so `LC held` is now `⌃ held` and `RC held` is `R⌃ held`. Left is the unmarked case because it is the overwhelmingly common one and because it is how a keyboard is spoken about — nobody says "left shift" until there is a right one in the sentence. Prefixing both sides put a letter on every row that distinguished nothing in the common case, which is precisely what the marks were meant to remove.

  **The cost, stated plainly: a generic modifier and a left one now draw alike.** The file tells them apart — `S ` is 05 §5.1's generic code and `LS` the left-specific one — and the row no longer does. It is a **presentation** collision and nothing more: `Mark.Description` (`Shift`, `Left Shift`, `Right Ctrl`, …) is the step row's `ToolTip.Tip`, so the distinction the file really carries is one hover away; and Core is untouched — `Keystroke.FormatModifiers` and `MacroModifierCodes` still read and write exactly what they did, so a macro that arrived with generic codes is re-serialized with generic codes and the file round-trips byte for byte. Capture always produces sided modifiers, so a generic code only ever comes from a file an older app or firmware wrote.

  `held`/`tap`/`press`/`release` stay words, and `held` is decided from the **modifier flags** rather than from a rendered string, so it survives any bit the display drops. **The file's own `LC`/`LS`/`S ` codes appear nowhere in the UI**: they remain `Keystroke.FormatModifiers`'s, which is what goes on the drive (05 §5.1, where the trailing space on a generic code is load-bearing). See [design-system.md](design-system.md) for the third font family and why the marks are a face rather than a geometry.
- **Reorder by drag and by `⌥↑↓`.** Both land on the one method `MacroInspectorStepsViewModel.MoveStep(from, to)`; the drag is a press-and-release gesture in the view's code-behind (the platform drag source is a shell service the headless platform does not have, and a reorder inside one list needs nothing from the OS), and `⌥↑↓` is the editor's grammar — see "The keyboard grammar". **The step list is deliberately not a `SelectingItemsControl`**: gate 3 leaves the arrows to any such control in the focused ancestry, so a `ListBox` here would swallow the very `⌥↑↓` its own header advertises. The rows are plain buttons and the selection is the view model's own.
- **The drag gesture, and the two ways it was broken (issue #122).** Press anywhere on a row — body, grip, or the delay/`×` buttons — move ≥ 4 px, release over the target row; under the threshold it stays the ordinary click that selects the step. It shipped broken twice over, for two independent reasons that are each worth keeping written down because both are Avalonia's defaults working exactly as documented:
  1. **It almost never armed.** `PointerPressed` attached from XAML declines handled events, and the row's body *is* a `Button`, which marks a left press handled. Only the 12 px grip and a few pixels of column gap ever reached the handler. All three pointer handlers are now attached on the view with `handledEventsToo: true`.
  2. **Even from the grip, `from == to`.** The pointer is **implicitly captured to the hit-tested control on press**, so `PointerReleased`'s `e.Source` is the row the drag *started* from, never the one under the pointer — `MoveStep(from, from)` then hit its own guard and returned false. The drop row is resolved by **hit-testing the release position**, never the source.

  Past the threshold the panel takes the capture itself, which is what stops the source row also firing its click; the row under the pointer wears an accent **ring** until release (a ring, not a fill — the selected row already owns `AccentSelectionFill`); and `PointerCaptureLost` disarms, so a capture stolen mid-gesture cannot leave an armed position to fire on the next unrelated release. **The gesture is tested through real headless pointer input**, including a press on the row *body* that the old code could not see — a view-model test of `MoveStep` passes against both defects, which is precisely why they survived.
- **The drag is now *visible*, and that is the third thing that was wrong with it (issue #128).** The drop ring alone left the gesture's **subject** invisible: nothing in the list moved until the pointer came up, which is exactly the reported *"the view is only updated after the movement"*. From the 4 px threshold the source row wears `MacroInspectorStepViewModel.IsDragSource` and **dims in place** (`Classes.dragSource`, opacity 0.35), and a **ghost** — `Border#DragGhost` on `SurfaceRaised`/`SurfaceBorderRaised` with `ShadowPopover` — rides the pointer inside a `Canvas` (`DragLayer`) that is the last child of the panel's root grid. A `Canvas` measures to nothing, so the layer costs the stack no height; being last is what puts the ghost over the list rather than under it. `ShowDragSource` is idempotent (it runs on every move), `MoveGhostTo` writes `Canvas.Left/Top` straight from the pointer, and the grab offset is measured **on the press** — by the time the gesture is a drag the pointer has left the row, and the ghost has to be the row as it was picked up. `Disarm()` clears all of it, so a lost capture drops the ghost too.

  Three things here are load-bearing. **`IsHitTestVisible="False"` on the layer *and* on the ghost**: `FindStepAt` resolves the drop row by hit-testing the live tree at the release position, so a hittable ghost would sit under the pointer and answer every one of those tests itself — the drag would land on nothing, every time. **The ghost's face is the row's own `MacroStepCaption` `DataTemplate`**, a resource used by both, because a second hand-written copy of six runs in two faces is a copy that drifts (the two-run modifier mark became `MacroModifierMarkRun`, now at three call sites: the row, the ghost, and the composer's preview). And **nothing animates** — `Themes/Motion.axaml` is untouched, because the ghost *is* the pointer's position made visible and a transition on it would lag the very gesture the feature exists to show. `MoveStep` itself is unchanged; this is feedback, not a new reorder path.
- **The chord composer — a second way to make a step, with no keypress at all (issue #128).** `MacroInspectorPanelViewModel.Composer.cs`, a partial of the same class: `ComposerLabel` (`COMPOSE A CHORD`) over a `Compose chord` / `Hide composer` disclosure, then eight sided modifier toggles (`⇧ R⇧ ⌃ R⌃ ⌥ R⌥ ⌘ R⌘`, the step rows' own "left unmarked, right spelled `R`" rule and the same `.keySymbol` face), a live preview of the chord as the step row would draw it, `Insert chord`, and the shared `TokenPickerViewModel` over `KeySearchCatalog` — its **fourth** call site, on the editor's one `RecentTokenStore`, so a chord built here is one `Recent` chip away next time.

  **Why it exists, precisely.** `Ctrl+1` cannot be recorded: macOS switches virtual desktop on it, and so does any chord a hotkey utility has claimed. That is not a capture defect and no capture work fixes it — such a chord is consumed above the application and never delivered to the window ([keystroke-capture.md](keystroke-capture.md) § "Permissions and platform reach"; the escalation is [#129](https://github.com/migus88/kinesis-edit/issues/129)). So the fix is not to *hear* the chord but to make pressing it unnecessary.

  The rules that keep it honest:
  - **It writes through `TryAppendKeystroke(Keystroke)`**, extracted from `ReceiveKeystroke`, so a composed step and a recorded step take the identical route — the macro is created on the first insert exactly as recording creates it, the 06 §6 count refusal is the same one, and the same `Assigned` hop reaches the editor's funnel. **There is no second write path.**
  - **Gated on `CanRecord()`** — the panel available and a layout loaded — and deliberately **not** on a macro already existing. Gating on one would make `Ctrl+1` unauthorable as a key's *first* step, contradicting this panel's own rule that the first recorded keystroke *is* the macro.
  - **The preview is read back off a real `Keystroke`**, never off the ticked set, so it cannot promise a modifier the model drops (05 §5.1 attaches none to a modifier key).
  - **Only sided flags are offered.** The generic codes (`S `, `C `) exist so a file an older app wrote round-trips; authoring a new one that does not say which side it means would be writing a worse macro than capture produces.
  - **Insert leaves the composer open and ticked** (the chords that need it come in runs — `Ctrl+1`, `Ctrl+2`, `Ctrl+3`), but a **new key closes it and clears it**: a half-composed chord belongs to the position it was started on, and a modifier left ticked would silently attach to the next one.
  - **The toggles are rebuilt, not mutated.** `MacroChordModifier` is immutable and carries no notification, so ticking one replaces the strip of eight — and it is deliberately not a `ViewModelBase`, for `RecentTokenStore`'s reason: a type rendered only through a `DataTemplate` should not have to be excused in `ViewResolutionTests`.
- **`OsReservedNote` is drawn beside the capture rule, on its own line.** `CaptureRule` is mockup `2i`'s wording verbatim and is pinned as such, so the new sentence is a sibling const rather than an edit to it: *"Some chords never reach this app at all — Ctrl+1, and anything a hotkey utility has claimed, are taken by the system first. Build those with Compose chord below."* It does not apologise, because there is nothing to fix — it points at the affordance that does the job, and both lines sit under the record banner so the sentence is on screen at the moment the limitation is discovered.
- **The per-step delay is edited in place, and that is where §11.3's modal went** — see [feature-dialogs.md](feature-dialogs.md). Every rule survives: `MacroDelayTokens` (`dran`, `d001`..`d999`, always zero-padded), resolution **through the token and never the code**, 1-999 with the arrows clamped and the typed value validated, and `FirmwareFeature.CustomMacroDelays` answered **in place** with 09 §2's own words plus an `Update Firmware` button — exactly as the Tap & hold panel answers its gate. The millisecond field **is** a real `TextBox`, which is the opposite of the action-field rule and correct: a delay is typed, not recorded. Focus landing in it therefore **stands the recording down explicitly** (issue #122) rather than letting the capture service suspend itself silently — the service's `SuspendOnTextInputFocus` is still on and still a safety net, but it must never be the answer on a surface that is *telling the user it is recording*. A banner that stayed up while the keystrokes went into a text box is the panel lying about its own state.
- **`● Record`** arms capture (the editor turns the service on, as always) and the banner names the step being recorded into: `Recording into step 04 — your typing goes here, not into the app. Click Stop, or anywhere else, to finish.` The panel also states what capture does with what it hears: `Arrows = press/release. A bare modifier records as tap. Search and shortcuts are suspended until you stop.` `＋ insert step` runs the same action — a step's content is a keystroke, and recording one is how it is made; the mock draws both affordances.
- **Recording is ended by the pointer, never by a key (issue #122).** Every key belongs to the macro, so no key can also mean *stop* — the mock's `Esc stops.` made Escape both the last step and the thing that ended the take. The one seam is `KeyboardEditorViewModel.StopRecordingOnInteraction()`, guarded on `Inspector.IsRecording` so it is idempotent and silent when nothing is armed, and it is reached from: **`WindowBase.Deactivated`** (the app losing focus — an OS-reserved chord, or anything else stealing it), a **tunnelled `PointerPressed`** on the `TopLevel` (`handledEventsToo: true`, consuming nothing, so the click still does its job) that exempts any `Button` whose `Command` the active panel claims through `IsRecordingControl` — which is what lets `Stop` toggle instead of being stood down by its own click — and **`GotFocus` landing inside a `TextBox`**. The paths that already existed are unchanged: mode switch, tab switch, layer switch, selection change, modal open, `Deactivate()`. Handlers are attached in `KeyboardEditorView.AttachShellHandlers()` and dropped in `OnDetachedFromVisualTree`.
- **`Revert key` asks the showing panel first (issue #122).** `KeyInspectorPanelViewModel.TryRevert()` is virtual and answers `false` by default, so the Remap, Tap & hold and locked panels fall through to the editor's `ResetKeyCommand` → `ClearRemap()` **exactly as before** — the doc comment there deliberately refuses `Remap(OriginalKey)` because it would also clear tap-and-hold and multi-mod, and that reasoning is untouched. The Macro panel overrides it and restores a `MacroKeySnapshot`: the position's macros, the active slot, speed, repeat and co-triggers, back to what they were **when the key was selected**. It leaves a key with no macro when it had none, refuses when there is no baseline, and is idempotent — the baseline is not re-taken on restore. Before this, `Revert key` on the Macro panel was a no-op in both halves: `ClearRemap()` touches only the remap, and nothing anywhere had snapshotted a before-state to restore.
  **The baseline is a fact about the selection**, which is what makes it survivable: it outlives `Deactivate()` (a mode switch stands capture down; it does not move the position) and outlives a **save** (saving writes the profile out; it does not change what the key held when it was clicked). It is replaced when the selection moves — which a load or import does implicitly, since both rebuild every `KeyboardKeyViewModel`, so the next `Refresh` arrives with a new key. The snapshot is taken **only** when `Refresh` sees a *new* key: `Refresh` runs on every editor refresh for every panel, so snapshotting unconditionally would overwrite the baseline with the user's own edit and make Revert a no-op again.
- **The footer meters** (`MacroMeterViewModel`) are `2i`'s three: `Playback speed 3 / 5`, `this macro 128 / 500`, `layout keystrokes 5 140 / 7 200`. The thousands separator is `AdvisoryText.Number`'s space, not a second format. Over budget goes **amber and still saves** — a null limit is "no limit", never zero.
- **Repeat and the co-triggers stay**, below the meters beside speed. `2i` draws only speed; both are supported by the devices this app edits today and there is nowhere else to set them once the Macros tab becomes a library, so dropping them would be dropping a feature silently. Recorded as a deviation in [design-system.md](design-system.md). Each is still absent where the file does not keep it (`PersistsRepeat`, `PersistedCoTriggersPerMacro`). **The six co-trigger toggles read as marks** — `⇧ R⇧ ⌃ R⌃ ⌥ R⌥`, the step list's spelling, with the same "left unmarked, right spelled" rule — rather than the two-line captions (`Left⏎Shift`) they were, which halves the block's height in a 300 px rail; `MacroCoTriggerViewModel.Caption` survives as the toggle's `ToolTip.Tip` (a mark alone is not accessible text, and with left unmarked it is also the only thing on the toggle that says which side it is) and as the face for a co-trigger key that names no modifier. This is **the one site where a font beats vector geometry**, and it is why the deviation is worth its cost: `ToggleSegment`'s `.selected` face sets `Foreground`, which a `TextBlock` inherits and an `Icon` — painting from `Stroke` — cannot. **All six now sit on one row**: with both sides prefixed they needed 282 px against the strip's 276 and wrapped 5 + 1; dropping the three `L`s brings them to 260. The test measures the strip rather than pinning 260, because a font-metric shift on another machine moves the number and what must hold is that nothing wraps and nothing runs off the rail.
- **It writes, then asks to be refreshed.** Every write ends in `Assigned`; the editor answers by re-reading the cap and running `RefreshCounters()`. The panel refreshes only its *own* meters in between — that is reacting to its own write, not writing from `Refresh`.

#### The Tap & hold panel

`TapAndHoldPanelViewModel` is §11.1 rehomed from a modal into the rail — a port, not a redesign. Every rule of the overlay survives (see [feature-dialogs.md](feature-dialogs.md)); what changed is the surface:

- **It takes a keystroke only while it is *armed*.** The overlay took one on being merely *open*, which is spec 10's own wording and right for a modal that nothing may be typed underneath. A rail sits beside a live board, so an unarmed panel that swallowed keys would eat the remap the user was recording on the cap next to it. `WantsKeystrokes` is therefore exactly `IsRecording`.
- **§11.1's two `Search` actions open the picker *inside* the panel**, in place of the two fields. The overlay nested a second modal over the first, which is the only reason `EditorOverlayHost` ever had a `ShowNested`; the rail nests nothing, so that method and its tests are gone.
- **No `Ok`/`Cancel` pair.** One `Assign` button, named for what the rail's exclusivity warning calls the act; nothing is written until it is pressed.

#### The locked-key panel

Shown in place of the modes and the footer when the selected position can never be remapped. **The three tabs are drawn dead, each with its reason** (`Remap — not writable`, …) — the design's own stated exception to "absent features are not shown, not disabled", because the user pointed at this key and a panel that rendered nothing would look broken. `KeyInspectorTabViewModel.Disabled` refuses to build a dead tab without a reason, which is what keeps that legal.

Its informational section, **"What it does on the board"**, comes from Core's `DeviceHotkeyCatalog` rather than from XAML literals — the facts are per device and scattered across `specs/03` §1 (the onboard v-Drive shortcut: `SmartSet + F8` on the Edge RGB), `specs/02:61` (`SmartSet + <n>` profile switching) and the board's own authored silkscreen. Its actions are `Copy from…` (dead) and `Copy to…` (live), which is the copy asymmetry made real by `CanCopyKey`'s relaxation above.

**It is unreachable on the only board with a picture, deliberately.** `Locked()` appears in the Advantage2, TKO and Advantage 360 geometries only; the Edge RGB's index 0 is `hk0`, an ordinary remappable hotkey. The panel is built and tested against `TestLayouts.CreateLockedKeyLayout()` and becomes reachable with #40/#41 — the same precedent as the read-only Settings screen.

## The editor shell — the chrome `KeyboardEditorView` draws

The redesign gives the editor its own chrome (`docs/design/handoff.md` § "Editor shell", mockups `1e`/`1f`/`2a`), and it **replaces the shell's app bar** rather than sitting under it. The seam is two properties:

- `DeviceEditorViewModel.ProvidesOwnChrome` — virtual, `false`; `true` only on `KeyboardEditorViewModel`. The Savant Elite2 pedal editor keeps the shell bar until issue [#53](https://github.com/migus88/kinesis-edit/issues/53).
- `MainWindowViewModel.IsShellChromeVisible` — false while such an editor is open, bound to the app bar's `IsVisible` ([app-shell.md](app-shell.md)). Otherwise there would be 92 px of chrome and **two** status pills.

Home and the status chip are the shell's, so the editor is handed the shell **as data**: `DeviceEditorViewModel.Shell` (an `IShellChrome`), assigned by `MainWindowViewModel.OpenDeviceAsync` before the view swap and cleared by `CloseEditor`. **Not a `$parent[MainWindow]` binding** — every headless suite renders `KeyboardEditorView` standalone, where a visual-tree lookup resolves to nothing and the Home button and the chip would render blank in the tests *and* in the frames used to verify the screen. A view gets its data from its own `DataContext`.

**The shape is four rows over a three-column body, and issue [#128](https://github.com/migus88/kinesis-edit/issues/128) is what made it that.** The chrome — toolbar, tab bar, Demo Mode bar — is **full-bleed**; below it the screen is split into **columns**, so the rail runs from the top of the advisory row to the bottom of the window and everything else lives in the column beside it.

**Two consequences of the columns worth stating outright:**

- **The advisory strip is the *section's* width, not the window's.** It annotates the section, and the section is what is left of the rail; a bar running on under the rail read as chrome for the whole editor. Deviation 18 — one strip, one view-model instance, all four tabs — **survives untouched**; only the width changed. On Macros and Settings, where the rail collapses, it is full-bleed again, which is the section's width there. Its own 24 px padding lines the dot and the sentence up with the content grid's 24 px inset.
- **The rail is outside the padded content area**, so the 16 px the content is inset by no longer shows as dead space above and below it. It carries its own `IsEnabled="{Binding !IsBusy}"` because it is no longer inside the `Panel` that carried that gate — and deliberately **not** `IsVisible="{Binding !IsLoading}"`, which would collapse the column during a load and shift the board.

**Why the body is a grid of its own** rather than four more rows of the root with the rail spanning two of them: Avalonia distributes a *spanning* child's desired size across the definitions it spans, and only `Auto` ones can grow. A full-bleed toolbar spanning `*,Auto,Auto` could widen the seam column, and a rail spanning the `Auto` advisory row plus the `*` content row could push the 30 px strip taller at a small window. The nested body has no spans at all, so neither distribution can happen.

**No eject button**, though mockup `1e` draws one — see "Spec strings and deliberate deviations".

**`Save` turns amber whenever the session is dirty.** The view writes `Classes.dirty="{Binding IsDirty}"` and nothing else; the amber ramp is painted inside the `PrimaryActionButton` control theme ([design-system.md](design-system.md)), which is the only layer allowed to name a template part. It is a property of the **editor shell** rather than of this board, so the pedal editor's Save wears it too ([savant-elite.md](savant-elite.md)) — and mockup `1l` reads it as half of the guard: *"The Save button is amber whenever the session is dirty, so the modal is rarely a surprise."*

`IsDirty` is a **pull** from `IProfileSession.IsDirty`, which compares serialized lines. Core's model announces nothing, so *every* path that can move the layout or the lighting model has to re-ask it. `RefreshCounters()` is the hook for the layout paths and now ends in `RefreshDirtyState()`; the lighting tab has no counter to move and calls `RefreshDirtyState()` on its own. The complete list, each with a test:

| Path | Refreshed by |
|---|---|
| a captured remap (`ApplyRemap`) | `RefreshCounters()` |
| `ResetKey` / `ResetLayer` / `ResetLayout` | `RefreshCounters()` |
| an assignment from either key-inspector panel (`RemapPanelViewModel.Assigned`, `TapAndHoldPanelViewModel.Assigned`) | `RefreshCounters()` |
| every macro-panel write (`MacrosChanged`: assign, delete, paste, steps, co-triggers, speed/repeat) | `RefreshCounters()` |
| a load, and an **import** (both go through `Apply`) | `RefreshCounters()` |
| every lighting write — mode, speed, direction, either colour swatch, a painted key, a painted zone, Reset All | `LightingTabViewModel.ModelChanged` → `RefreshDirtyState()` |
| a lighting **direction normalization** (`RefreshDirections`) | the same, and it is a write like the others — see below |
| a **successful save** | cleared outright, see below |
| a **settings** edit | *nothing, and it cannot be otherwise* — see "Settings are outside the dirty model" below |

**A successful save sets `IsDirty = false` rather than re-reading.** Core captures the dirty baseline at load and `ProfileSession.Save` does not move it ([profiles.md](profiles.md)), so the session goes on reporting itself dirty once it has been written; the next real edit re-asks and gets `true` again. A save that validation stopped, or that threw, leaves the flag set — nothing was written.

**`LightingTabViewModel.ModelChanged`** is new and exists only for this. It may fire for a write that changed nothing (re-reading a layer assigns the speed it just read); harmless, because the consumer re-asks the session rather than trusting the notification.

**The eighth lighting write site is the one that hides.** `RefreshDirections` writes `state.Direction` back whenever the layer's persisted direction is not one the mode offers — Rebound offers only `Left` and `Up` (07 §3), so a file carrying `down` is rewritten the moment that layer is *shown*: a mode pick, a layer switch, or `Attach` during the load itself. It has no counter to move, so it is easy to mistake for a read; it is a write into the profile's `LightingModel` and it raises `ModelChanged` like the other seven. Without that, clicking the **Fn** segment left the session dirty with Save still grey. It only announces a write that actually changed the value, so a layer whose direction the mode already accepts reports nothing.

**The provisional action row is smaller again.** Three of its buttons have now reached their real homes: `Reset Layer` left for the legend row under the board (#91), where it sits beside the counts it acts on and takes the mockups' sentence case; and #92 took `Reset Key` — now the key inspector footer's **`Revert key`** — and `Tap and Hold`, which is a rail panel rather than a modal. Each new home runs the editor's own command instance; nothing was re-implemented.

The five that remain — `Reset Layout`, `Insert Delay`, `Special Action`, `Export` and `Import` — are [#93](https://github.com/migus88/kinesis-edit/issues/93)'s, which owns the editor-level action bar. Since #128 the row sits under the **board**, inside the section column, rather than under the board *and* the rail: it is the section's action row and the rail is not part of the section. It is still under the whole *content* on every tab, so Export and Import stay reachable from the Lighting and Settings tabs.

### The profile picker — `KeyboardEditorViewModel.Profiles.cs`

**Which numbered profile the editor is editing, and the switch that points it at another one** ([#128](https://github.com/migus88/kinesis-edit/issues/128)). Until this, the editor could only ever open `LayoutScheme.FirstProfileNumber` and the drive's other eight `layout<n>.txt`/`led<n>.txt` pairs were unreachable from the app.

**It is `ProfileSession.ProfileNumber`, not `KeyboardSettings.StartupProfileNumber`.** The drop-down chooses which pair is *open in the editor* — the pair `SmartSet + <n>` switches on the board. Which profile the keyboard *powers on into* is a settings key, moved by the Settings tab's own `Active profile` slider, and this switch never touches it: **nothing here writes anything, anywhere.** The two are laid out side by side in [settings.md](settings.md).

Split into a partial of `KeyboardEditorViewModel` for the reason `…Legend.cs`, `…Inspector.cs` and `…MacroLibrary.cs` were — the main file is the largest in the app.

| Member | Is |
|---|---|
| `Profiles` | Every profile of the device, in file order, one per number in `LayoutFileScheme.FirstProfileNumber..LastProfileNumber`; empty where the scheme is not `NumberedProfiles`. Built **in the constructor from device facts alone**, exactly like `Tabs`: a profile exists whether or not it has been opened, so nothing waits for a load |
| `SelectedProfile` | The profile the editor has open — private setter, re-read **off the session** in `Apply` (`RefreshSelectedProfile`), so a first load, an import and a switch all announce it from one place. Null with no session |
| `HasProfiles` | Whether the picker is rendered at all: `!IsDemoMode && Device.Location is not null && Profiles.Count > 1`. Every term is fixed for the editor's lifetime, so it never notifies. Absent, never disabled |
| `SelectProfileCommand` | `IAsyncRelayCommand<ProfileOptionViewModel>` — **the one write path**. The `ComboBox` binds `SelectedItem` one-way and its `SelectionChanged` runs this, the same shape as the two switches beside it |

`ProfileOptionViewModel` is immutable and deliberately not a `ViewModelBase` (like `AdvisoryViewModel`, an option is never edited): `Number`, `Caption` — derived from `KeyboardEditorViewModel.BuildProfileCaption`, so the row and the caption cannot drift — and `IsReadOnly`. There is **no `IsSelected` on the row**: two places holding "the selected one" is how a picker starts disagreeing with the board.

**The switch is a load, not a mutation**, and the order is the whole design:

1. `CanSelectProfile` — a real option, not disposed, `HasProfiles`, not read-only, and the three "busy" terms every editing command carries (`!IsLoading && !IsBusy && ActiveOverlay is null`). It deliberately does **not** test "is it a different profile": the picker renders every row from this, and a row that could not be re-selected would read as broken.
2. **Re-selecting the open profile is a no-op**, inside the command — a reload would throw away unsaved edits to answer a click that asked for nothing.
3. **Unsaved work is asked about**, in `UnsavedChangesPrompt`'s words, through `ConfirmDiscardingUnsavedWorkAsync()` — **extracted from `ConfirmCloseAsync`, which now calls it too**. Opening a different profile abandons the open one exactly as leaving the editor does, so it asks the same question rather than growing a second, differently-shaped one. Demo mode and a clean session answer true silently; only a save that actually landed lets a `Save` answer through.
4. **Every guard is re-read after the question**, because the box is modal but the editor is not frozen behind it and answering `Save` ran a whole save sequence in between — the same re-read `ResetLayerAsync` does.
5. **The `SelectTab` stand-downs fire**: `CancelRemap()`, `CancelCopyKey()`, `DeactivateInspector()`. A listening key and an armed record button both own the next keystroke, and an armed copy is finished with a click on a board about to be rebuilt under it.
6. The read runs **off the UI thread** (`Task.Run`), like the first load, and does **not** re-enter `LoadAsync` — that method's `_hasLoadStarted` latch is once-only and must stay so.
7. **Nothing is half-swapped.** `Apply` mutates unconditionally, so the outcome is decided before it is called: a failed load leaves the previous profile selected, its session intact and its edits still saveable, and says so in a dialog. Unlike the first load, a failure degrades to **nothing** rather than to a factory-default layout — a switch already has a perfectly good profile open.
8. `SwapSession` clears `_hasUnsavedMacroNames` **before** `Apply` (whose funnel re-reads the dirty flag), so the arriving profile is not born dirty; then `Apply`; then the outgoing session is released — **only** then, because `Apply` is what puts the new one in place.
9. A refused, cancelled or failed switch **re-announces `SelectedProfile`** even though nothing moved. The binding is `Mode=OneWay`, so by that point the `ComboBox` is already showing the row the user clicked while the editor is still on the profile it loaded; `SetProperty` would not raise for an unchanged value, so the control has to be told explicitly to snap back.

`NotifyCommands()` re-asks `SelectProfileCommand`, unlike the tab strip: the picker's rows really do come and go with the editor's state. `RefreshSelectedProfile` also raises `ProfileNumber` (`…MacroLibrary.cs`), which scopes a macro name to a profile and which nothing else announces.

**Deviation: profile 0 is not a row.** The Advantage 360's factory profile has no `layout0.txt`, and Core refuses it three ways ([profiles.md](profiles.md), "Profile-0 guard"). It never appears, because every `NumberedProfiles` scheme in the catalog runs **1–9** and the picker is built from that range verbatim — a row whose only outcome is an error dialog is the "absent, never disabled" law's own case. `IsReadOnly` still ships, asked of Core's own rule and enforced by `CanSelectProfile`, and is tested through a synthetic device whose range starts at 0.

### Settings are outside the dirty model, deliberately

**The editor screen has two Save buttons, and the amber one does not cover the other.** `IProfileSession.IsDirty` compares the serialized **layout and lighting** files against the baseline captured at load ([profiles.md](profiles.md)) — the settings file is not in that comparison, and could not be: `KeyboardSettingsViewModel` reads and writes the device's settings file through `ISettingsService` on its own, with its own `SaveCommand` inside the Settings tab ([settings.md](settings.md)). So a settings edit moves nothing the session can see, and the toolbar's `Save` neither turns amber for it nor writes it.

That is the shape spec 08 §5 already has (settings are a separate file with a separate write), and this app keeps it. The consequence to know: the toolbar `Save` is the *profile's*, and **so is the unsaved-changes guard** (below). `IsDirty` is what the guard asks, so a dirty Settings tab is invisible to it: leaving with an unsaved settings row still loses it silently, where an unsaved remap is now asked about. That gap is deliberate — the tab has its own Save, and giving the guard a second, differently-shaped question about a different file would be worse than the gap. `KeyboardEditorViewModelTests.IsDirty_AfterASettingsEdit_StaysFalse` pins the non-path so it cannot become an accident.

## The advisory system — `ViewModels/Advisories/`

**The law first** (`docs/design/README.md`): *"Advisories never block. Amber, never red; nothing is clamped or refused; always shown twice — a mark on the exact key or row, and one calm summary strip per tab."* Everything below is that sentence made mechanical.

Five types, all under `KinesisEdit.ViewModels.Advisories`:

| Type | Is |
|---|---|
| `AdvisoryAnchor` | `EditorTab Tab` + `int? LayerIndex` / `KeyIndex` / `MacroIndex` — where it belongs on screen, and what `Review` selects. `MacroIndex` is the 1-based **slot** (06 §1), null for a flat-list macro |
| `AdvisoryViewModel` | One anchored sentence: `Anchor`, `Message`, `Detail`, and a `Severity` that is **always** `StatusSeverity.Warning`. Immutable, and not a `ViewModelBase` — an advisory is never edited, it is replaced |
| `EditorAdvisories` | The immutable set. `Build(KeyboardLayout?)`, `All`, `Total`, `ForTab(tab, layerIndex?)`, `CountForTab`, `CountForLayer`, `ForKey`, `HasAdvisoryForKey`, `HasAdvisoryForMacro`, `SummaryFor(tab, layerIndex?)` |
| `AdvisoryText` | **Every sentence template, in one static class**, so the wording lives once and is unit-testable on its own |
| `AdvisoryStripViewModel` | The strip itself: `AdvisoryCount` / `AdvisorySummary` / `HasAdvisories` / `ReviewCaption` / **`IsExpanded`**, `ReviewAdvisoriesCommand`, the `_reviewIndex` walk, `Project(set, tab, layerIndex)`, and the static `BuildPostSaveMessage`. It **projects, it never builds** — and it selects through two callbacks (`Action<AdvisoryAnchor>` for a key, one for a macro row), because the board and the macro panel are the editor's. That makes it constructible, and testable, with no loaded editor anywhere near it. Its one dependency is the session's `IAppPreferencesStore` (optional), which it follows until `Dispose` |

### The two sources, and what is deliberately not one

`Build` reads a `KeyboardLayout` and nothing else. Both sources already report rather than enforce:

| Source | Becomes | Anchored by |
|---|---|---|
| `Validate()`'s `TapAndHoldCountExceeded` | `Tap-and-hold count is 11 of 10. Files from older firmware…` | Layout tab, **layout-wide** (the validator reports no layer) |
| `Validate()`'s `MacroLengthExceeded` | `512 of 500 characters — over the device budget. Saved as-is.` | Macros tab, layer + key + slot |
| `Validate()`'s `MacroKeystrokeBudgetExceeded` | `layout keystroke budget 5 140 / 7 200 — over the device budget. Saved as-is.` | Macros tab, layout-wide |
| `Validate()`'s `MacroCoTriggerLimitExceeded` | `6 co-trigger modifiers — legacy budget is 4` | Macros tab, layer + key + slot |
| `DuplicateKeyScan.Find(layout)` | `[esc] is on 2 positions of this layer — 0, 20. Duplicates are allowed.` | Layout tab, **one advisory per position** of the group |

- **The other `ModelViolationKind`s are deliberately skipped.** They describe a model that cannot be written faithfully — a remap on a locked position, a macro on a board with no macros — which is a *failure* the save path reports, not something the amber strip should reassure the user about.
- **`DuplicateKeyScan.Find(layout)`, never `Find(layer)`.** The layer overload defaults to `TokenDialect.None`, which spells the token with whichever dialect the key-table entry carries first — a token the user's file may not contain ([keyboard-model.md](keyboard-model.md)). The layout overload passes `layout.Dialect`.
- **One advisory per position**, not one per finding, so every cap in the group carries the note and mockup 1e's "*3 keys carry advisory notes on this layer*" counts what it says it counts.
- **A flat-list macro gets no row dot.** The Advantage360 keeps its macros in one list and `Validate()` anchors a finding there by layer alone — there is no per-macro identity in the report to match a row against, and marking every row of that layer would say "this macro is over budget" about macros that are not. Those advisories are still counted and still shown in the strip; only the dot is missing, on the one board whose editor is [#41](https://github.com/migus88/kinesis-edit/issues/41).

### Where it is shown — twice, always

| Surface | What |
|---|---|
| `KeyboardKeyViewModel.HasAdvisory` | Per-cap flag, pushed in by `RebuildAdvisories()`. **Exposed and deliberately not rendered** — the design's 12×3 px `StatusAdvisoryStrong` cap bar belongs to the badge vocabulary of [#91](https://github.com/migus88/kinesis-edit/issues/91) (remap bar, macro dot, tap-and-hold corner, the legend row's live counts), and one badge drawn to a different rule than the four beside it is worse than none |
| `MacroLibraryRowViewModel.BudgetAdvisory` / `MacroSlotViewModel.BudgetAdvisory` | The amber sentence on the macro's row and on its slot card. **Self-computed, not pushed** — the row measures its own macro with `MacroLengthMetric` against `MacroCapability.MaxCharactersPerMacro`, which is the same code `EditorAdvisories` uses, so the two cannot disagree; doing it in the row is what lets it carry mockup `1i`'s verbatim sentence with the macro's own two numbers in it. One consequence: **`EditorAdvisories.HasAdvisoryForMacro` currently has no production caller** (only its own tests) — it is the pushed flag the deleted macro-list rows used, kept for the flat-list boards whose editors are still [#41](https://github.com/migus88/kinesis-edit/issues/41) |
| `AdvisoryStripView` | The summary — **one control, one row, all four tabs** |
| The save toast | `AdvisoryText.SavedWithAdvisories(n)`, appended to the device's own post-save wording |

**One strip, not four.** "One summary strip per tab" is satisfied by a single control whose sentence and count are the *open* section's: `AdvisoryStripViewModel.AdvisorySummary` / `.AdvisoryCount` are already narrowed to `SelectedTab` and, on the Layout tab, to `SelectedLayer`. Four copies would be four things to keep in step.

**The strip is its own view model, not a face of the editor's.** The editor keeps `Advisories` (the whole set) and hands the narrowed view to `AdvisoryStrip` — everything the strip shows and does lives there. `AdvisoryStripView` therefore sets `DataContext="{Binding AdvisoryStrip}"` rather than inheriting the editor's, and is one of the few view models `ViewLocator` never resolves by name (it is hosted by property; `ViewResolutionTests` lists the reason).

`SummaryFor` says the least it can: one advisory speaks for itself (`Message`); several are summarised (`LayerSummary` on the Layout tab, `SectionSummary` elsewhere) using the **first** advisory's `Detail` fragment — which is why the layout-wide facts are added before the per-position ones and mockup 1e's sentence comes out in its own shape.

**One preference reaches the strip: `advisory_detail`** ("Explain advisory warnings in full instead of one line", mockup 1j). `AdvisoryStripViewModel` is handed the session's `IAppPreferencesStore` — the editor resolves it from `IDeviceSessionAccessor.Active?.Preferences`, falling back to `NullAppPreferencesStore` when there is no session — and exposes `IsExpanded`, read through `AppPreferenceCatalog.AdvisoryDetail.GetValue(...)` and **never off the stored flag**: it is the catalog's one *display* preference, where `on` means expand, the opposite polarity to every `*_msg` beside it ([settings.md](settings.md)). It re-reads on `Changed`, because the preference is edited on the Settings tab of the very editor the strip is drawn in, and the strip is `IDisposable` so it comes off a store that outlives the editor (`KeyboardEditorViewModel.Dispose`).

In the view this is a **layout change only**: `TextTrimming="CharacterEllipsis"` becomes `TextWrapping="Wrap"` through a `TextBlock.advisorySentence.expanded` class, and the Border's fixed `HeightAdvisoryStrip` becomes a `MinHeight` (`VerticalAlignment="Top"`, so a host that offers more room cannot inflate the bar; the row it sits in is `Auto`). Same tint, same dot, same `Review N`, and **no animation** — the growth is a state the user asked for rather than a transition, and the motion budget is fixed and small. Expanded-with-one-line still measures 30 px, so only a sentence that really wraps moves anything.

**The strip's row is reserved, not collapsed (#119).** The strip sits in the `Auto` row above the section's content and always measures `HeightAdvisoryStrip` (30 px), whether or not the open section has anything to say: only its contents — the dot, the sentence and `Review N` — are gated on `HasAdvisories`. It used to hide itself whole, so an advisory arriving mid-edit grew the row from 0 to 30 and pushed the board, the inspector rail and the legend row down a bar's worth; holding the floor costs 30 px of a screen that already budgeted them and moves nothing, ever. Reserved is not the same as drawn: with nothing to say the bar paints no tint and no hairline, because a permanently amber strip over a clean profile would be a standing false alarm — worse than the reflow it fixes. Both faces are class setters (`Border.advisoryStrip` and its `.hasAdvisories` state) rather than values on the element, since a local value beats a class setter and the clean face would never take. A bottom status bar was considered and rejected: the handoff draws no bottom bar anywhere, and it would have parked the note far from the board it annotates.

### The rebuild hook, and the one place it is not

`RebuildAdvisories()` is called from **`RefreshCounters()`** — the funnel every layout-mutation path already ends in (see the `IsDirty` table above), so a remap, a reset, an accepted tap-and-hold, any macro write, a load and an import all produce a fresh set. It is deliberately **not** called from `RefreshDirtyState()`, the lighting tab's own hook: the set is derived from the `KeyboardLayout` alone, a lighting write cannot move it, and `Validate()` walks every key of every layer — paying for that on each click of the colour picker would be felt for a set that cannot have changed.

`RefreshAdvisorySummary()` is the cheap half: it hands the existing set to `AdvisoryStrip.Project(...)` narrowed to the open tab and layer, and is called from `SelectTab` and `SelectLayer`, neither of which changes the model.

### `Review N`

`AdvisoryStripViewModel.ReviewAdvisoriesCommand` walks the open section's anchored advisories, one per press, wrapping at the end (`_reviewIndex`, reset to −1 by every `Project`, i.e. whenever the set, the tab or the layer moves). It dispatches on the projected tab and calls one of its two callbacks; the editor supplies both. `SelectAnchoredKey` selects the anchored cap **through `SelectKeyDirectly`, never `SelectKey`** — the second-click promotion to listening would eat the user's next keystroke, and reviewing is reading. `SelectAnchoredMacro` runs **`EditMacroAt`** — the same jump the Macros tab uses — so a reviewed macro advisory lands on the board's anchored position with the rail on its *Macro* panel. It deliberately does **not** merely highlight a library row: an anchor names a *site* (layer, key, slot) while the library lists one row per *name*, so a macro that fires from three places would leave the review pointing at all three at once. The command carries **no `CanExecute`**: an advisory never disables anything, so with nothing anchored the press is a no-op. Nothing here has to switch layers, because the Layout strip is already narrowed to the shown layer.

### Amber, never red

- The Macros tab's three budget meters, its slot cards' advisories and its rows' advisories all bind **`Classes.statusWarning`** (→ `StatusAdvisoryTextBrush`), never `statusError`. A budget is reported, never refused; red is for a genuine failure. Neither `KeyboardEditorView.axaml` nor `MacroLibraryView.axaml` names an error role at all, and `AdvisoryStripTests` fails if either changes.
- The strip is `StatusAdvisoryTintBrush` on `StatusAdvisoryTintBorderBrush` with a `StatusAdvisoryBrush` dot; the macro row's sentence is the same family.
- **An over-budget macro still saves, keeps its row and keeps its name.** The one red answer anywhere near this tab is the *delete* confirmation's `DestructiveResult`, which is about erasing a macro from every key that fires it — not about a budget.

## `KeyboardEditorViewModel`

`DeviceEditorViewModel` — the shell's abstract editor base, shared with `EditorPlaceholderViewModel` and `SavantElitePedalViewModel` ([savant-elite.md](savant-elite.md)) — supplies `Device`, `DeviceName`, `IsDemoMode`, `ProvidesOwnChrome`, `Shell` and the virtual `LoadAsync()`/`ConfirmCloseAsync()`; `MainWindowViewModel.Editor` is typed as that base so navigation is independent of which editor a device resolves to. This class overrides **both** — `LoadAsync` for the drive read and `ConfirmCloseAsync` for the unsaved-changes guard (see "Leaving with unsaved work"), which the pedal editor overrides with the same shared question ([savant-elite.md](savant-elite.md)).

State: `IsLoading` (true until the first load finishes), `IsBusy` (a save is in flight), **`IsDirty`**, `Layout`, `Layers`, `SelectedLayer`, `SelectedKey`, `ListeningKey`/`IsListening`, `ProfileCaption`, **`MountPath`/`HasMountPath`**, `ModifiedKeyCount`/`RemapCounterCaption`, `MacroCount`/`MacroCounterCaption`, `InvalidLineMessages`/`HasInvalidLines`, `BoardWidth`/`BoardHeight`, `Tabs`/`SelectedTab`, `MacroLibraryPanel`/`IsMacroLibraryVisible`, `MacroLibrary`/`ProfileNumber`/`HasUnsavedMacroNames`, `ActiveOverlay`/`HasActiveOverlay`/**`IsCaptureActive`** (the keyboard grammar's gate 1), the advisory set **`Advisories`**, and the strip it projects onto, **`AdvisoryStrip`**.

Commands and what gates them (`NotifyCommands()` re-evaluates all of them on every state move):

| Command | Enabled when |
|---|---|
| `SelectKeyCommand(KeyboardKeyViewModel?)` | always (the click contract below) |
| `SelectLayerCommand(KeyboardLayerViewModel)` | always |
| `SelectTabCommand(EditorTabViewModel)` | the strip carries that tab — every tab it carries works (table below) |
| `BeginRemapCommand` | `SelectedKey is not null && SelectedKey.CanEdit && !IsLoading && !IsBusy && !Inspector.IsRecording && ActiveOverlay is null` |
| `CancelRemapCommand` | `IsListening` |
| `ResetKeyCommand` | `SelectedKey is not null && SelectedKey.CanEdit && !IsLoading && !IsBusy` |
| `ResetLayerCommand` | `SelectedLayer is not null && !IsLoading && !IsBusy` — async; confirms under `NotificationKeys.ResetLayer` before erasing |
| `ResetLayoutCommand` | `Layout is not null && !IsLoading && !IsBusy` — async; same key, its own wording |
| `SaveCommand` (async) | `_session is not null && _session.CanSave && !IsDemoMode && !IsLoading && !IsBusy` |
| `InsertSpecialActionCommand` | `Layout is not null && Inspector.IsOpen && Inspector.SelectedMode == KeyInspectorMode.Macro && FindOpenMacro() is not null && !IsLoading && !IsBusy && ActiveOverlay is null` — it inserts into **the rail's** open macro, so the rail's own state is the gate, see below (`InsertDelayCommand` is gone: §11.3 folded into the rail's step editor in #93) |
| `ExportCommand` | `_session is not null && !IsLoading && !IsBusy && ActiveOverlay is null` — **deliberately not gated on demo mode**; an export writes to a folder the user picked, never to the v-Drive |
| `ImportCommand` (async) | `_session is { CanSave: true } && !IsDemoMode && !IsLoading && !IsBusy && ActiveOverlay is null` — `CanSave` is what carries the Adv360 profile-0 guard |
| `OpenSearchCommand` | `Layout is not null && !IsLoading && !IsBusy` — ⌘F, see "The keyboard grammar" |
| `CloseOverlayCommand` | `ActiveOverlay is not null` |
| `AdvisoryStrip.ReviewAdvisoriesCommand` | **always** — an advisory never disables anything; with nothing anchored the press is a no-op |

The three reset commands share the save guard (`!IsLoading && !IsBusy`) because a save serializes the model on a background thread and mutating it mid-save would race it. **Every feature command additionally requires no open modal** — an inline panel is modal and must not be raced by the editor underneath it. **`CopyKeyCommand` deliberately does not**, and `BeginRemapCommand` deliberately keeps its clause; both are explained under "Copy key" and "Remap state machine". Note that `CopyKeyCommand` also no longer requires an *editable* source: a locked position is a legal copy source (05 §5.3) and only the target direction is refused.

Two of those gates are less obvious than they look:

- **Tap and Hold asks whether the *device* has the feature** before the firmware gate and before §11.1's four pre-dialog checks. A board without it also states no delay range, so the panel would open at 0 ms and the assignment would be reported as `TapAndHoldNotSupported` — which blocks the entire save, not just that key ([feature-dialogs.md](feature-dialogs.md)).
- **The insertion command needs the rail's Macro panel on screen**, not merely a macro open — the same rule as before, moved to where macro editing now lives. Selecting any macro-capable key opens an unassigned draft, so with the rail shut or on another mode the picked action would be appended to a macro the user cannot see and never assigns. `SelectTab`, the rail's open/close and its mode switch all re-evaluate it. Note the consequence for the **Macros tab**: it is a library, edits nothing and holds no open macro, so `Special Action` is correctly unavailable while it is the open section (visible in the captured frame as a disabled button).

`SelectedTab` is a two-way-bindable property whose setter runs the same guard as the command, so a binding cannot open a tab the strip does not carry. **Switching tabs cancels an in-flight remap**, because listening belongs to the keyboard picture and capture is never left running (invariant 4). It also cancels an armed `Copy key…` (a section with no board could never finish it) and **deactivates the rail** — stood down, not closed, so returning to the Layout tab finds it as it was left. There is no longer a second recording consumer to stand down: **the Macros tab is a library and records nothing.**

### The tab strip is device-driven — absent, never disabled

`EditorTabViewModel.CreateAll(DeviceDefinition device, bool isLightingSupported)`. **There is no `IsEnabled`.** The design's capability law is "absent features are not shown, not disabled" (`docs/design/README.md`), so a section this app cannot open for this board is not rendered at all:

| Tab | Present when |
|---|---|
| `Keys` (captioned **`Layout`**) | always |
| `Macros` | always — the panel behind it reads `MacroCapability` and says `This device does not support macros.` itself |
| `Lighting` | `device.Lighting.Kind != LightingKind.None` **and** `LightingTabViewModel.IsSupported(device)` — the Freestyle Edge RGB only. Absent on the Freestyle Pro and Advantage2 (no lighting hardware) *and* on the TKO and Advantage 360, whose led files this app cannot edit yet (#40/#41) |
| `Settings` | `device.Settings != SettingsCapability.None` — absent on the Savant Elite2, CROSSFIRE and Advantage 360 Professional |

Three things worth keeping in mind:

- **The enum member `EditorTab.Keys` keeps its name** even though the caption is now `Layout`: the identifier is carried inside `EnumMatch` converter-parameter *strings* in XAML (`ConverterParameter='Keys,Macros'`), so renaming it is a string-coupled change with no user-visible payoff.
- **`Macros` is neither filtered nor gated**: its panel already answers the capability question in its own `Message`, and a second answer here is a second place for the two to disagree.
- **The lighting flag is a device-level question on purpose**: the editor's constructor runs before any profile is read, and demo mode never reads one, so it cannot be `session.Lighting is LightingModel`. The strip is therefore fixed at construction, and `SelectTabCommand`'s predicate reads nothing but whether it was handed a tab, which is why `NotifyCommands()` deliberately does not re-ask it.

`EditorTabViewModelTests` asserts, for every catalog device, that the Settings tab exists exactly when `KeyboardSettingsRows.Create` yields rows and that the Lighting tab exists exactly where the panel can edit the led file — a tab and its panel can never disagree — plus that no strip ever carries a section the editor would have to refuse.

### The Settings tab — `KeyboardSettingsViewModel`

The device-side settings of spec 08 §5, hosted as `KeyboardEditorViewModel.Settings` and rendered by `KeyboardSettingsView` through `ViewLocator`. It is always constructed (cheap, no I/O) and only reachable when the tab exists.

- **Rows come from the capability, never from a device id.** `KeyboardSettingsRows.Create(SettingsCapability)` emits, in spec 08 §2 table order: active profile (1–9), `led_mode` (only in its `ModeString` form), macro speed, status report speed, the v-Drive switch in whichever of its two key forms applies, then game mode / program lock / key clicks / key tones. Every board therefore gets its panel the moment its picture is authored, with no per-device code. Row kinds are `SettingsSliderRowViewModel`, `SettingsToggleRowViewModel` and `SettingsChoiceRowViewModel`, each carrying a reader/writer delegate pair — no row knows a key name, and the `led_mode` options are Core's `LedModeValues.All` (the serializer's own domain) with captions added here.
- **The active-profile row writes through `StartupProfileSettings.ApplyStartupProfile`**, so the paired `led_mode=led<N>.txt` of 08 §5.1 / 07 §1.2 cannot drift from `ProfileSession.SaveAs`.
- **Clamping is the slider's job.** `KeyboardSettingsSerializer` throws on a value outside `SettingsValueRanges`, and an exception must never escape into the UI, so `Value` is clamped in its setter *and* in `ApplyTo`. The "Disable" checkbox writes `0`; it only exists where the slider floor is above 0 (`SettingsCapability.MacroSpeedMinimum`).
- **A key absent from the file reads as its unset default** — spec 08 §2's "missing keys leave zero/false/empty values": speeds load as *disabled*, toggles as off, and the profile number as 1 (it has no zero). The choice row is the exception, and deliberately so: absent means **unset**, not `Options[0]`. `SelectedOption` is nullable, an unrecognised value (a `led_mode` newer firmware wrote) is held in `UnrecognizedValue` for the `ComboBox`'s `Placeholder`, and an unset row writes **null** — which is exactly what preserves the device's line, because a null property emits no pair and a save only passes managed pairs to `UpdateSettingsFile` (08 §1). Handing the unknown text back to the serializer would preserve nothing: it throws outside `LedModeValues`, taking the whole panel's Save with it. Mapping absent → `0` would switch a Freestyle Edge's backlight fully off on the first save.
- **Advantage2 4MB lock** (08 §5.4): `KeyboardSettingsGate.CanEditKeyboardSettings(DeviceId, VersionFile)` false ⇒ `IsLocked`, every row disabled, Save unavailable. **Demo mode passes the gate**, as every firmware gate does (`FirmwareGateService`, 09 §2): it supplies `VersionFileInfo.Empty`, and a 2MB diagnosis about an unattached board would be fabricated. Nothing is written there anyway.
- **The lock is drawn as read-only, never as an error** (mockup 1j). `IsLocked` puts a banner over the section carrying `ReadOnlyBanner` + `ReadOnlyExplanation` (Core's verbatim 1j strings) and `LockHint` (08 §5.4's own wording, kept as the footnote that names the condition the gate actually tested), plus a `Which board do I have?` link — `Button.link` + `IconExternalLink` + `IUrlLauncher` against the catalog's `TroubleshootingUrl`, the same three parts as the empty state's `Troubleshooting tips`. Each row then carries `IsReadOnly`, rendered as `SettingsMessageCatalog.ReadOnlyRowMarker` (`(read-only)`) on muted meta type **outside** the disabled part, so the value stays live and readable, and `ShowsSaveAction` drops the Save button entirely rather than greying it. **Every surface on the screen is on the advisory ramp or a plain muted one; no `StatusError*` brush is reachable from `KeyboardSettingsView`** — a board that refuses writes is a hardware fact, not a failure. `IsReadOnly` is deliberately *not* `!IsEnabled`: a row is also disabled while loading, while saving and after a failed read, none of which may carry the marker.
- **The tab is a list of sections.** `KeyboardSettingsView`'s root is one `StackPanel` whose children are sections; the device rows are the first, headed by `KeyboardSettingsViewModel.DeviceSectionLabel` (`"Written to the keyboard"`) on `.sectionLabel`. The label is a view-layer const rather than a Core string, because it names a piece of screen rather than a settings rule — the split `NoDeviceViewModel.TroubleshootingButtonCaption` already makes.
- **Demo mode never writes, but it does read** (03 §3.5, 08 §3 — the ban is on *saving*): with a `Location` the file is loaded exactly as usual and `DemoModeHint` explains that Save is unavailable, the same rule the colour picker's custom slots follow. Demo mode is entered for a drive that is merely not writable, so inventing values there would be showing wrong settings for connected hardware. Only a device with **no `Location`** reads nothing, and it says so with `NoDriveHint` rather than claiming the rows are the device's — which, since the fixture drive landed, is the six boards without demo content and not the Freestyle Edge RGB: an undetected RGB now has a location and correctly reads `DemoModeHint`.
- **Save is unavailable until a read has succeeded.** `HasLoadedSettings` — not `!IsLoading`, which is also true after a read that threw — gates `SaveCommand` *and* the rows' `IsEnabled`, so the panel can never write its constructor defaults (`v_drive=manual` among them) over a file nobody managed to read.
- **Load and save are total.** `LoadAsync` (fired by the editor's own `LoadAsync`, idempotent) reports a read failure *inline* rather than stacking a second modal on the editor's, and `StatusMessage` is composed from its two independent parts (demo/no-drive hint, read failure) so one never hides the other; `SaveAsync` mirrors the profile save — `IsBusy`, `ShowLoading`/`HideLoading` in a `finally`, failures through `TryShowMessageBoxAsync` titled `Save Settings`, success as a toast carrying Core's `SettingsSavedTitle`/`SettingsSavedMessage`.

#### The tab's second section — `AppPreferencesViewModel` + `Views/AppPreferencesView`

Below the device rows, and unrelated to them in everything but the screen they share: **this app's** per-device preferences and the custom-swatch strip, both in `app_settings.txt` and both over the session's one `IAppPreferencesStore` ([settings.md](settings.md)). `KeyboardSettingsViewModel` **owns** it as `Preferences` and `KeyboardSettingsView` hosts `AppPreferencesView` explicitly (like `KeyboardEditorView` hosts `AdvisoryStripView`) — the section's own markup reaches its owner with `$parent[views:AppPreferencesView]`, which needs the real control in the tree.

- **The store is a required constructor parameter of both `KeyboardSettingsViewModel` and `LightingTabViewModel`, with no default.** A defaulted `NullAppPreferencesStore` is exactly the failure this section cannot survive: a host that forgot to thread it would render a whole screen that reads and writes nothing while every unit test on both classes still passed. A host with no drive passes `NullAppPreferencesStore.Instance` in as many words. `EditorViewModelFactoryTests.Create_ForAnOpenSession_GivesBothPreferenceConsumersThatSessionsOwnStore` walks the composition root's own path — session first, then factory — and asserts one write on the session's store reaches both tabs.
- **It is drawn for every board, including one with no keyboard settings at all.** These preferences describe the app's behaviour on this device, not the hardware's, so the capability gate above has no say over them. `LoadAsync` reads it **first and outside** the device-settings guards, or a board with no settings capability would leave the section on its constructor defaults.
- **Rows come from `AppPreferenceCatalog`**: five featured (mockup 1j's own, in 1j's order) plus the rest behind a disclosure whose caption carries a **computed** count (`+N more`), because 1j's literal `+7` assumed twelve keys and there are seventeen. Each row is an `AppPreferenceRowViewModel` over one descriptor, so the polarity — `on` = *hide* for the `*_msg` prompts, `on` = *expand* for `advisory_detail` — lives in the catalog and never in this class.
- **Demo mode moves the boxes but persists nothing**, and says so with `SettingsMessageCatalog.DemoModePreferencesCaveat`: spec 08 §3 bans *saving* app settings there, not loading them, so the section still shows what the drive carries. The **swatch strip** is the one genuinely frozen part (`CanEdit` = `IsWritable`), so that it agrees with the lighting picker's already-unavailable `Add to Custom Colors`.
- **`CustomSwatchesViewModel` is the second consumer of the twelve `cust_color_N` slots** and the reason the store exists. It and `ColorPickerViewModel` both read `Current` and re-read on `Changed`, so a swatch stored in the lighting picker is on this strip immediately and one cleared here disappears from the picker, with no reload on either side. The colour is typed as `#RRGGBB` in a mono `TextBox` — the mono law's own case — rather than picked from a ring: the ring belongs to the tab where a colour is being chosen *for* something, and this strip exists to manage the twelve values a config file carries.

### The Lighting tab — `LightingTabViewModel`

The per-layer LED editor of spec 07 §3/§4 as design mockup 2f redraws it: **the mode is rendered on the board** — the picture animates it at its real speed and direction, which is still the point of the screen — while the *picker* beside it is a drop-down and the rail under that is a **properties panel**. Hosted as `KeyboardEditorViewModel.Lighting` and rendered by `LightingTabView`. Like the settings panel it is always constructed and only reachable when its tab is enabled; unlike it, **it has no save path of its own** — `ProfileSession.Save` serializes whatever `IProfileSession.Lighting` holds, so mutating that model *is* the save (see [profiles.md](profiles.md)). The editor's `Apply` hands it the model and the same `KeyboardLayerViewModel`s the Keys tab draws.

- **`LightingTabView` is the board column and nothing else ([#128](https://github.com/migus88/kinesis-edit/issues/128)).** It used to own the whole screen; four things moved out, one reason each. Its **columns** — the rail is now one column of the editor, shared with the key inspector, so switching tabs cannot move the board by a pixel (#124 had already given the two rails one stored width; two grids meant they still matched only by arithmetic). Its **seam**, which goes with the column it resizes. Its hosting of **`LightingModeRailView`**, which is the editor's rail. And its **layer switch**, which is in the tab bar's one switcher slot beside the profile picker — it cost this column a row of height it does not have at the window floor, and it put the editor's switcher in two different places depending on the tab. What is left is the picture, its header, the paint line, the zones and the demo/status card: the board and the statements about it, laid out in the content column the editor hands it. The board block is still **vertically centred** exactly as the Keys block is, in the `Auto,*,Auto,Auto` grid #123 gave it, with `HeightBoardMin` on the board's row.
- **The lighting layer switch is a different object from the layout one, and the label says so.** `LIGHTING LAYER` over `Lighting.Layers`, running `LightingTabViewModel.SelectLayerCommand` from `KeyboardEditorView.OnLightingLayerSelectionChanged` — which puts the control back on `SelectedLayer` when the panel refuses (the Fn layer below the LED 1.0.44 gate), guarded by the comparison so the assignment cannot re-enter. The refused segment stays **visible and dimmed** rather than hidden (the layer exists), and the reason — `LayerLockHint` — moved onto the switch as its `ToolTip.Tip`, because a 38 px bar has no room for the sentence the tab used to print beside it. `ToolTip.ServiceEnabled` is bound to `!IsLayerCustomizationAvailable`, which is what keeps an *available* switch from opening an empty tip: the hint is the empty string when the gate is open, and an empty string is not a null `Tip`.
- **Every rule is Core's.** Mode membership and gating are `LightingAvailability.IsKeyBacklightModeAvailable`, what a mode accepts is `LightingModeParameters`, what the board looks like at time *t* is `LightingEffectSampler`, speed→seconds is `LightingSpeedScale`, zones are `LightingZoneCatalog`, speed bounds are `LayerLightingState` ([lighting.md](lighting.md) § "Preview"). **`LightingPanelVisibility` is gone**: `LightingModeParameters` subsumed it (`ShowsEffectColor`→`AcceptsEffectColor`, `ShowsSpeed`→`AcceptsSpeed`, `ShowsPerKeyColors`/`ShowsZones`/`ShowsResetAll`→`HasPerKeyColors`, …), so the §3 table exists once, in Core, and `LightingTabViewModel.Parameters` is the tab's one answer for every control.
- **The rail is a properties panel over a drop-down (#128), and only the selected mode's properties are on it.** 2f drew a scrolled fourteen-row mode list filling most of the column with a fixed parameter footer pinned under it; the list is a `ComboBox` whose item template is the very markup each row drew (the mark, the name, the summary), and under it, in order: **Mode → Colour → Speed → Direction → Picker**, every block below the mode gated on `Parameters` and every one carrying a line of `LightingHintCatalog` copy. The **mode is the rail's pinned header** — it is the one control that decides what the rest of the rail contains, so it does not scroll away — and the properties under it are one scrolling column. **The pinned parameter *footer* is gone**: it existed so a mode picked at the top of a 600 px list could not push its own speed off the bottom, and there is no list; a properties panel whose fields scroll with their labels is the shape the Settings tab already uses. `SelectedModeOption` is what the box binds one-way (**null is a real state**: a led file may carry a mode the device's menu does not offer, e.g. Ripple below the KBD 1.0.121 / LED 1.0.58 gate, and the placeholder is then `ModeCaption`, so the layer still says what it is set to). `LightingModeViewModel.IsSelected` is **gone** — a selector control has exactly one selected item and draws it itself; a second copy of that fact was only ever a way for the two to disagree. `ModeRailCaption` reads `Mode — previewed on the board` rather than 2f's `Mode — click to preview on the board`: the instruction is kept, the gesture it named is not.
- **`SelectMode` carries an identity guard, and it is load-bearing.** Re-selecting the mode already open returns before writing. A `ComboBox` raises `SelectionChanged` **while it binds**, and this tab is hidden rather than unloaded, so without the guard merely opening (or returning to) the Lighting tab ran a write, raised `ModelChanged` and turned the editor's `Save` amber over a profile nobody had edited. Nothing else could have noticed: the mode written is the mode that was already there. Same shape, same reason, as `SelectLayer`'s guard.
- **Mode names are the one thing the app spells**, in `LightingModeCaptions` and nowhere else: 2f renames three of Core's §3 captions — Monochrome→**Solid**, Disable→**Off**, PitchBlack→**Pitch black** — and `LightingModeDefinition.DisplayName` stays untouched, because parsing depends on the catalog and a label must never move it. Every *parameter* of a row is still Core's, including the row's second line (`LightingModeParameters.Summary`: "spd · D/L/U/R", "2 colors · spd", "—"). `Freestyle` stays in the menu although 2f omits it: §3's RGB menu offers it.
- **Every rendered property carries one line saying what it means *in that mode*** — `LightingHintCatalog`, `Classes="meta muted"`, the Settings tab's `SettingsRowViewModel.Description` convention. The question it exists to answer is *"I don't understand what is the difference between Effect and Base color in reactive mode"*, which no per-*property* sentence could answer: in Reactive the base is what every key rests at between strikes and the effect is what a key flashes when struck (07 §2.2 writes the first as the `[mono]` line and the second as the `[reactive]` line). Six hooks — `ModeHint`, `SpeedHint`, `DirectionHint`, `PickerHint` on the tab (all four re-announced from `Parameters`, which is written after the mode and is what decides which of them is on screen) plus `Hint` on each of the two `LightingColorSlotViewModel`s, since a swatch is one row with one meaning. The copy is **this app's own wording** — the handoff prescribes no tooltips or help text anywhere — written from 07 §2.2/§3/§2.4 with the section cited on each entry, and it may go no further than §3's own one-sentence "Visual behavior" paragraph: describing the *sampler* would be documenting this app's approximation as firmware behaviour ([lighting.md](lighting.md)).
- **The effect swatch is renamed where it is not an effect colour at all.** `LightingColorSlotViewModel.EffectCaptionFor(mode)` reads `LightingModeDefinition.WritesEffectColor` — the catalog's own flag, never a restated mode list — and returns `Paint Color` where it is false (Freestyle, Breathe, Frozen Wave). §2.2 writes no effect-colour line for those; their file body is per-key lines, so the value is the picker's colour stored per key, and calling it `Effect Color` names a line the file will never carry. `Caption` became settable for exactly this.
- **The board animates — `AdvancePreview(deltaSeconds)`.** It is the *only* entry point the view's frame timer calls and the only place the elapsed clock moves. It samples `LightingEffectSampler` and pushes the frame plus the layer's paint map onto the caps in one pass (`KeyboardLayerViewModel.ApplyLighting`). The normalised key list is built **once per layer**, from each cap's *centre* — `(X + Width/2) / BoardWidth`, `(Y + Height/2) / BoardHeight` — keyed by **memory key code**, which is what both `LayerLightingState.KeyColors` and `LightingEffectFrame.Cells` use. `LightingBoardPreview` owns the clock and that list; `Draw()` re-samples at the current instant after every model write, so a mode or a colour picked while the clock is frozen still shows.
- **Reduce-motion is read on every `AdvancePreview` call**, not subscribed to: since #96 it is a live user preference (`IMotionSettings.ReduceMotion`, changeable from the Settings screen with the editor open) and the interface raises no notification, so polling once a frame *is* the mechanism. Frozen means the clock is held at 0 and the board shows the mode's **t = 0 frame** — a still of the effect, not a blank board — and `BoardHeader` reads `Wave · preview` instead of `Wave · live preview`. `IMotionSettings` is an optional constructor parameter for the same reason the editor's session is (a panel built for a test or a design scene has no app around it); null means "animate".
- **Two layers, fully independent** (§4). `Layers` is always Top + Fn — the two a led file describes — regardless of how many layers the picture has. A layer switch re-reads mode, colours, speed, direction and the picture from the new state, restarts the preview clock and **empties the paint selection**; the Fn segment **and** the base-colour swatch sit behind `LightingAvailability.IsFnLayerLightingAvailable` (`LightingLayerCustomization`, LED ≥ 1.0.44), read from `DeviceSnapshot.Firmware`. Demo mode reports every gate as passing. The switch itself is the editor's, in the tab-bar row (above).
- **The paint selection is `LightingPaintSelection`, and it is not the editor's selection.** `KeyboardEditorViewModel.SelectedKey`/`KeyboardKeyViewModel.IsSelected` are the Keys tab's *single* selection driving the inspector rail; this is a multi-selection on a board with no inspector, so the cap carries a second flag (`IsLightingSelected`) — the two boards render the same cap view models, and one flag for both would move the inspector. A click **toggles**; a shift-click **extends over the layer's key order** (the layout file's position order, so a run rather than a rectangle) and only ever adds; `Select all` takes the layer; a **zone button** toggles its own keys in or out (below); the caption is `Paint · 2 keys selected`, with `1 key` and `no keys` forms. **The selection survives a mode change** — picking a mode is how you find out what those keys look like under it — and is emptied by a layer change.
- **`LightingPaintSelection.Changed` is how anything else follows the selection.** It fires once per gesture however many caps moved, from *every* source — a click, a shift-click, `Select all`, a zone, an emptying, a layer switch — and `LightingTabViewModel` hangs two things on that one subscription: `PaintSelectionCommand` and `ClearSelectionCommand`'s `NotifyCanExecuteChanged()`. **The zone buttons are no longer among them (#131)**: `IsSelected` was derived over *overlapping* zones (`All ⊃ Left Module ⊃ Game ⊃ WASD`), so one chip's click silently repainted another's face. Same reasoning as `RefreshLegend` on the Keys tab: "they always agree with the board" is true by construction instead of by a list of call sites somebody has to keep complete. It is an event rather than a `PropertyChanged` because it announces a *set*, not a property. The key-code half of the API is `SelectByKeyCode` / `DeselectByKeyCode` / `ContainsAll`, answered off an index rebuilt with `_layerKeys`; `ContainsAll` is what `SelectZone` asks to decide add-or-subtract, and over codes that resolve to no cap on this layer it answers **false**, not the vacuous true, so such a zone goes **in** on the next click rather than silently coming out.
- **A selection gesture on the board paints what it adds — and `Apply` is gone (#128).** `PaintWhatTheGestureSelects(gesture)` snapshots the selection, runs the gesture, and paints `Picker.Color` onto exactly the keys that **were not in it before**. Three commands are wired through it: `SelectKeyCommand` (a cap click), `ExtendSelectionCommand` (a shift-click run) and `SelectZoneCommand` (a zone button) — a user pointing at keys. **`SelectAllKeysCommand` is deliberately not one of them**: `Select all` plus a held colour would repaint the entire layer in a single click with nothing but `Reset All` to undo it, which is precisely the regression #124 removed when `ApplyZoneCommand` became `SelectZoneCommand`. And **only what the gesture *added*** is painted, never the whole selection, so a gesture never re-colours what is already selected.

  The history is worth keeping straight, because the zone button has now meant three things: it painted on the spot before #124; #124 split select from paint and made the rail footer's `Apply` the commit; #128 re-merges the commit **into the gesture**, so every control on the rail writes on the spot and the one thing `Apply` could do that nothing else could is done by the gesture that used to need it. `PaintSelectedKeys`/`PaintSelectionCommand` **remain in the view model** — the command is still the honest name for "put this colour on everything selected" and still gated on `Selection.HasSelection` — but no button binds it. A gesture that paints therefore **is** one of `RaiseModelChanged`'s sites again; `Select all` still is not, because it paints nothing.

  Zone membership is untouched by all of it: the codes are still authored against the top layer and still re-resolved through `ResolveKeyCode` to the same physical positions on the Fn layer, in one place (`ResolveZoneKeyCodes`), so the set a click adds and the set the next click subtracts can never disagree about which keys the zone means. The chip is a **plain button (#131)** and shows no state; the `zoneButton` → `ToggleSegment` bridge stays for the neutral face and its hover/press ramp, and `.selected` is never entered ([design-system.md](design-system.md)). **Dropping that face is a return to the design, not a deviation from it, and it is written down here so nobody "restores" it**: the selected chip was the app's own addition in #124 — mockup 2f draws only `Select all` and `Clear` under the board and no zone state at all, and 07 §4 asks only that "zone buttons color predefined key groups with the selected color".
- **A colour paints the whole selection at once**, announced **once**: the picker's `ColorChanged` writes the selected swatch *and* runs `SetKeyColor` per selected key, then raises `ModelChanged` a single time. `Clear` (`ClearSelectionCommand`) **empties the selection** — it is `Select all`'s opposite and sits beside it (**#131**), and is disabled with nothing selected. It painted the selected keys black until then, which was invisible with nothing selected, over unpainted keys, or under a mode drawing paint at 0 %. Black is still an erase through the picker (§2.1), and `Reset All` still erases the layer. **Nothing on the paint row is gated on the mode** — not the caption, `Select all`, `Clear`, the zones or `Reset All`: the painted colours belong to the *layer*, so the controls that manage them do not come and go with the effect running over them, and mockup 2f draws exactly this row on a board running **Wave**. The same reasoning keeps the **colour picker on the rail wherever paint is possible at all**, including the modes with no swatch of their own: what it edits there is the colour a paint gesture uses, and `PickerHint` (`Parameters.AcceptsAnyColor`) says which of the two is happening. **The one exception is the pair that writes nothing** — Off and Pitch Black, `Parameters.AcceptsPaint` — where the picker is absent too: 07 §2.2 gives those layers no file body, so there is no effect for a colour to show through and no line for one to land on. That gate was **found on a captured frame**, not by a test: the rail drew a colour wheel under *"The backlight is off for this layer, and nothing is written to the file for it"*, promising a write the file cannot hold, in the one control that had been left ungated. Whether the board can paint at all is answered once, by the tab existing (`IsSupported`); what the mode decides is only how the paint is **drawn** — directly, or at 40 % under the effect (`RendersPaintDirectly`, `PaintOpacity`). A colour painted under a paint-ignoring mode is on the layer immediately and reaches `ledN.txt` as soon as the layer's mode is one whose grammar carries per-key lines (07 §2.2) — Wave's own grammar is `[wave]>[spdN][dirX]` and has nowhere to put them.
- **Painting uses `Picker.Color`** (§4). Keys are addressed by **memory key code** (`key.Key.OriginalKey.Code`). **Zone codes are authored against the top layer**, so on the Fn layer each is re-resolved top code → top index → the Fn key at that index (§2.4 item 6): the Function zone lands on the Fn layer's media keys, not on F1–F6 it does not have. Since #124 that resolution serves *selection* rather than painting, but it is the same resolution.
- **One picker, two targets, and it no longer discloses.** `EffectColor`/`BaseColor` are `LightingColorSlotViewModel`s carrying a reader/writer pair onto `LayerLightingState` (the same shape the settings rows use); `SelectColorSlotCommand` points the picker at one, and a mode change re-selects the first *visible* slot, so the picker never edits a swatch the mode does not have. Until #128 the picker was **disclosed** from a swatch and drawn *in place of* the mode list, which was the only part of the rail tall enough to hold it; there is no list to displace now, so the disclosure is gone — `IsPickerOpen` and `ClosePickerCaption` with it — and a swatch click `BringIntoView()`s the picker instead. It is drawn **in every mode whose paint can reach the file**, gated on Core's new `LightingModeParameters.AcceptsPaint` rather than on a swatch, because what it edits is the *layer's* paint colour rather than a parameter of the effect. **It is last in the rail, and a captured frame is why**: the picker is ~460 px tall, and sitting directly under the swatches — where it reads best — it pushed Speed and Direction off the bottom of a 680 px window in every mode that has them (Wave's frame showed a rail whose only visible properties were the mode and a colour wheel). The compact properties come first and the picker takes what is left; the scroll-into-view is what keeps choosing a target from putting its editor out of sight.
- **Speed is nine bars, not a slider** (`LightingSpeedViewModel` + `LightingSpeedSegmentViewModel`): the file's speed is nine discrete values (§2.1), a slider would suggest a continuum, and the readout `Speed 6 / 9` is mono because it is a value a config file carries. `SetSpeedCommand` writes through `Speed`, which is still the one clamp and the one write. The block is gated on `Parameters.AcceptsSpeed`.
- **Only the arrows the mode accepts are drawn, and the block is absent without one (#128) — reversing mockup 2f.** `Directions` is still four long and each entry still carries `IsAvailable` from `LightingModeParameters.Directions`; the *view* binds that to `IsVisible` and the block itself to `Parameters.AcceptsDirection`. 2f said, verbatim, *"Directions a mode can't use stay in place, struck through — the row never changes shape as you move down the list"* — and the list it was talking about is gone. With the mode a dropdown there is no column to scrub, so the cost the exception was bought at no longer exists; what was left was four dead controls under a heading on **eleven of the fourteen** modes, inside a rail whose whole point is now "the controls you see belong to the mode you picked". The app's own law applies again: features a device — or here a mode — lacks are not rendered at all rather than disabled. **`IsAvailable` is still Core's answer and still what `SelectDirectionCommand` validates against**, so an unavailable arrow that somehow reaches the command is a no-op whether or not it was ever drawn; only the drawing changed. `DirectionSegment`'s `.unavailable` state survives in the control theme, now unused. Rebound's two are still relabelled `Horizontal`/`Vertical` (§3). **A direction the mode rejects is normalised** on mode change (§2.4 item 5 writes it as the default anyway), and that write is announced like the rest.
- **"Reset All"** sits with the zones, on screen under the same rule as the rest of the paint row, and calls `LayerLightingState.ClearKeyColors()` after a Yes/No box whose message is §4's wording verbatim. A box that cannot be shown erases nothing.
- **Repainting.** `KeyColorOverlay.BuildPaint(device, lighting, layer)` returns the layer's `KeyColors` map itself — already code-keyed, already black-free — and `KeyboardLayerViewModel.ApplyLighting(frame, paint)` is whole-layer, so a key neither map mentions goes back to unpainted and unlit. It runs ~30×/s over ~76 caps, so it allocates nothing and each cap notifies only for a value that moved: `ApplyPaint`/`ApplyEffect` take a `LedColor?` and format the `#RRGGBB` string only when the colour actually changed — the change check stays on the *stored* colour, so the softening below never runs twice on the same value. Both tabs share the cap view models, so the colours land on the Keys tab's caps too — but that picture draws no lighting at all (`KeyboardView.ShowsLighting`), so none of it is visible there.
- **The drawn face is a *softened* preview, and the stored value is what every number on screen shows.** `LedPreviewTint.Soften` is applied at exactly one seam — `KeyboardKeyViewModel.ApplyPaint` / `ApplyEffect`, the two lines where a `LedColor` becomes `PaintColorHex` / `EffectColorHex` — because the board draws ~95 caps of full-gamut sRGB side by side and a layer freshly painted `#FF0000` renders as a wall of the display's most saturated primary. See "Presentation rules" for the rule itself. What follows from that seam, and is the reason it was chosen: `LitLabelBrushConverter` reads the cap's own hex, so the lit caption's light/dark flip is decided by the face actually drawn; the rail's colour slots and the picker read `LightingColorSlotViewModel.ColorHex` and are untouched, so a value with a number beside it is still the file's, verbatim; `KeyColorOverlay.ToHex`, `HexColorToBrushConverter` and all of `KinesisEdit.Core` are untouched; and **no file state changes** — a profile round-trips to the same bytes it did before.

#### The colour picker — `ColorPickerViewModel` + `Controls/ColorPickerView`

`ColorPickerView` wraps Avalonia's `ColorView` (package `Avalonia.Controls.ColorPicker`, pinned to the same **11.3.12** as every other Avalonia package) for the HSV ring, the R/G/B sliders and the hex field, and adds the two things the stock control has no notion of:

- **The ten premixed swatches of §4**, in the spec's order (white, yellow, red, lime, blue, fuchsia, orange 255/128/0, azure 0/128/255, aqua, black), as a static list on the view model.
- **The twelve custom slots**, `cust_color_1`…`cust_color_12` in `app_settings.txt`. The picker **no longer touches that file itself**: it reads `IAppPreferencesStore.Current` on `LoadAsync` (any drive, even in demo mode — spec 08 §3 bans *saving*, not loading), writes through `Update(settings => settings.WithCustomColor(...))`, and re-reads on `Changed` — so the Settings tab's swatch strip and this picker can never show each other stale slots. Its own read-modify-write is gone; the store owns that now ([settings.md](settings.md)). `LedColorConverter` does the `LedColor` ↔ `SettingsColor` conversion. `Add to Custom Colors` fills the first empty slot, then rotates. **`CanStoreCustomColors` is `IsWritable`** — false in demo mode and without a drive — and the command is disabled rather than silently forgetting the slot. Every I/O failure is swallowed by the store — a picker preference is not worth a dialog.

`ColorView` ships its control theme in its own assembly, so `App.axaml` includes `avares://Avalonia.Controls.ColorPicker/Themes/Fluent/Fluent.xaml` after `FluentTheme`; without it the picker renders untemplated. The `#RRGGBB` ↔ `Color` conversion is `HexColorToColorConverter` (two-way, alpha dropped, `BindingOperations.DoNothing` on a non-colour), so no Avalonia colour ever reaches a view model.

### Lifecycle — `LoadAsync`, `Dispose`

**Construction is deliberately cheap**: it resolves the device's `KeyboardVisual`, builds the tab strip and commands, and subscribes to `IKeystrokeCaptureService.KeystrokeCaptured`. No file is touched, so the shell can swap the view in immediately — `MainWindowViewModel.OpenDevice` fires `_ = editor.LoadAsync()` **after** the view swap and after hiding its own loading splash; the drive read runs against the editor's own `IsLoading`.

`LoadAsync` is **total and idempotent** (`_hasLoadStarted` / `_isDisposed` guards; a second call is a no-op), which is what makes forgetting the task safe:

- The read runs off the UI thread (`Task.Run`, resumed with `ConfigureAwait(true)`).
- **A device with no `Location`** → `KeyboardLayout.Create(Device.DeviceId)` in memory, no session: `ProfileCaption` stays empty, and Save *and* Export are permanently unavailable because there is nothing to write and nothing to serialize.
- **Otherwise — including in demo mode** → `IProfileSessionFactory.Load(Device.Location, Device.DeviceId, Device.Device.LayoutScheme.FirstProfileNumber)`, i.e. profile 1 on every numbered-profile device. See "Demo mode reads the fixture drive" below: `IsDemoMode` is deliberately **not** consulted here. Which profile the editor is *on* stops being fixed after this: the tab bar's picker calls the same `Load` for another number and hands the result to the same `Apply` — see "The profile picker", which deliberately does **not** re-enter `LoadAsync`, whose latch is once-only.
- **Any failure** (vanished drive, unreadable file, unsupported device) degrades to the same in-memory layout plus a `LoadFailureTitle` message box — the editor never crashes the shell. If even `KeyboardLayout.Create` throws (a device with no geometry), `Layout` stays null and the picture is empty.
- `Apply` then sets `Layout`, `ProfileCaption`, `InvalidLineMessages`, announces which profile is open (`RefreshSelectedProfile`, the one place that fact is read off the session), builds `Layers`, **builds the profile's one `MacroLibrary`** (`AttachMacroLibrary`, which stamps the stored names on *before* constructing it — see "The macro library and macro names"), selects layer 0, and refreshes both counters. The Macros tab itself is **not** rebuilt: `MacroLibraryPanel` is constructed once, from device facts alone, and reaches the library through a function, so a load or an import replaces what it reads without replacing it. A successful **import** re-runs the very same `Apply` over the session, because the imported file built a brand-new model exactly as a load would have.

`Dispose` (called by `MainWindowViewModel.CloseEditor` on navigate-home and on re-open, and by `App`'s exit path through the shell) detaches from `KeystrokeCaptured`, drops the Tap and Hold hooks, **closes the overlay host**, detaches the macro panel (stopping any recording) and stops capture. It is idempotent. **Leaving capture started would swallow every keystroke of the dashboard behind the closed editor** — the capture service is app-wide and outlives the editor. The host *cancels* the open panel rather than dropping it, because the one-shot insertion hooks come off on the panel's own `Closed`; the Tap and Hold hooks are dropped **before** that, which is why a half-finished assignment cannot write back into a disposed editor.

#### Demo mode reads the fixture drive

Demo mode used to open an **empty** board: `LoadProfile` short-circuited on `IsDemoMode` and edited a factory-default model, so a user with no hardware saw a keyboard with nothing on it and no way to learn what the app does. **That short-circuit is gone.** A demo `DeviceSnapshot` for a board with authored fixtures carries the synthetic `DemoVDrive` location, and this editor loads it exactly as it loads a real drive — the production layout/macro/led/settings parsers, over a `DemoVDriveFileService` that serves the embedded fixtures and refuses every write back to them ([app-shell.md](app-shell.md) § "The demo v-Drive"; [profiles.md](profiles.md) § "The service seam"). **Nothing in this class knows any of that**, and nothing in it names a device: the whole difference is which `IVDriveFileService` the composition root handed to `ProfileSessionFactory`.

What follows from it, and what each thing is guarded by:

| | |
|---|---|
| The board is **populated** | remaps, macros, a tap-and-hold, the fixture's lighting model and the fixture's settings rows, all through the real parsers |
| `IsDirty` is **genuinely true** after an edit | the session is real; `ConfirmCloseAsync` therefore tests `IsDemoMode` on its own rather than leaning on `IsDirty` |
| `Save` and `Import` stay **refused** | `!IsDemoMode` in `CanSave`/`CanImport`, unchanged. Neither may lose it — "no session" no longer does the refusing for them |
| `Export` is **live** | `CanExport` dropped its `!IsDemoMode`. §11.5 writes to a folder the user picked, never to the v-Drive, so 03 §3.5 has nothing to say about it — and it is the one way a user without hardware gets a file out of the app |
| The mount-path slot stays **empty** | `HasMountPath` is `!IsDemoMode && …`. The demo root is `kinesis-edit://demo/‹DeviceId›`, which is not a place on the machine and so may not sit in a mono slot |
| A board **without** fixtures is untouched | its snapshot has no `Location`, so it takes the in-memory branch above and opens the empty demo editor it always did. Six of the seven do |

The last row is the one to be careful with: every detection scan builds a demo snapshot for **every** undetected catalog device, so "which boards have demo content" is `IDemoDeviceProvider`'s answer and is never asked by id in a view model.

### Remap state machine

One key listens at a time; capture is started **only** on entering listening and always stopped again on the way out.

| State | Input | Next state | Side effect |
|---|---|---|---|
| nothing selected | click key *K* | *K* selected | the key inspector opens on *K* |
| *K* selected | click *K* | *K* listening (only if `CanBeginRemap`) | `capture.Start()`; a dismissed inspector **reopens** |
| *K* selected | click *L* | *L* selected | — |
| *K* listening | click *K* | *K* selected | `capture.Stop()` |
| *K* listening | click *L* | *L* selected | `capture.Stop()` |
| *K* listening | keystroke captured | *K* selected | `Remap`, `capture.Stop()`, refresh cap + counter |
| *K* listening | `CancelRemapCommand` (Cancel button, Escape fallback) | *K* selected | `capture.Stop()`, model untouched |
| any | layer switch | nothing selected | `capture.Stop()` |
| *K* listening | tab switch | *K* selected | `capture.Stop()` |
| any | `SelectKeyCommand(null)` | nothing selected | `capture.Stop()` |
| any | macro recording starts | listening cancelled | `capture.Start()` for the recording instead |
| any | a rail panel arms its record button | listening cancelled, recording stopped | `capture.Start()` for the rail instead |
| any | a modal feature panel opens | listening cancelled, the rail stood down | the panel owns capture from there ([feature-dialogs.md](feature-dialogs.md)) |
| *K* listening | `Dispose` | — | `capture.Stop()`, unsubscribe |

`CanBeginRemap` is false for a locked position (`CanEdit == false`, 05 §5.3), while loading, while saving, **while the macro panel is recording, and while a modal feature panel is open** — the last two would fight over the same keystrokes. **It is deliberately *not* false while the key inspector is open**: the rail is not modal, and clicking the selected cap again must still start a remap. Clicking a locked key twice selects it and does nothing else. `BeginRemapCommand` is the same entry point without the click (bindable, and what the tests use).

**Escape is not the cancel key — this is the single most surprising thing about the workflow.** While a key listens, the capture service previews the window's key events in the tunnel phase and swallows every physical key it resolves, Escape included, so **Escape is assigned like any other key**: a keyboard must be able to carry an Escape remap. The same holds while a Tap and Hold field is armed. Cancelling is a pointer action — the *Cancel* button beside the listening banner, clicking the listening key again, clicking another key, or switching layer. `KeyboardEditorView` registers a tunneled `KeyDown` handler (`handledEventsToo: true`, as in `MessageBoxView`) for the two things Escape may still do. **An open feature panel goes first and is dismissed whatever `e.Handled` says** — capture may be running for something else entirely (a macro recording used to swallow the Escape and leave the panel unclosable), and a panel that cannot be dismissed from the keyboard is worse than an Escape that also lands somewhere. The one exception is a panel that is itself waiting for a keystroke, which the view reads off `KeyboardEditorViewModel.IsOverlayAwaitingKeystroke` — an armed Tap and Hold field takes the Escape and disarms, so the next Escape closes the panel. With no panel open, `CancelRemapCommand` runs if it can: while a key is listening the capture handler on the `TopLevel` above has already assigned the Escape and left listening state, so the command is unavailable and nothing double-fires.

**The listening banner's row is reserved, not collapsed (#131).** It sits inside the centred board block and always measures its 32 px band plus 8 px of air; only the sentence and *Cancel* are gated on `IsListening`. It used to hide itself whole, so arming a key shrank the star row, re-fitted `BoardScaleHost` and slid the board 20 px down at the moment the user was about to press a key for one cap. It is inside the block rather than above it because the column centres the block: a band above it would put the picture permanently half a band below centre.

**Applying a captured keystroke goes through the editor path `KeyboardKey.Remap(keystroke.Key)`**, which means capturing a key's *own original action* clears the remap (04 §2.1), exactly like the legacy apps. `ResetKeyCommand` deliberately calls `ClearRemap()` instead: `Remap(OriginalKey)` also clears the position's tap-and-hold and multi-modifier as a side effect ([keyboard-model.md](keyboard-model.md), "Watch out"), which is not what "reset this key's remap" means. `ResetLayerCommand`/`ResetLayoutCommand` call Core's `KeyboardLayer.Reset()`/`KeyboardLayout.Reset()` (which clear all four rule kinds; `KeyColor` survives) and then re-read every cap.

`ResetLayerCommand`/`ResetLayoutCommand` also `CancelRemap()`, `DeactivateInspector()` and end in `RefreshCounters()` — `Reset()` empties the macro slots too, so the rail and the Macros tab would otherwise both be sitting on macros that no longer exist. `RefreshCounters()` rebuilds the library snapshot and pushes both, which is why neither surface needs a reset hook of its own.

**Both of them confirm first, and the confirmation is the app's first suppressible dialog.** They are `AsyncRelayCommand`s that raise a `Confirmation` / `YesNo` box through `INotificationService` carrying **`SuppressionKey = NotificationKeys.ResetLayer`** and `SuppressedResult = Yes`, so the "Don't ask this again" checkbox appears and the answer is written to `app_settings.txt` as `reset_layer_msg=on` ([settings.md](settings.md)). Four rules hold here:

- **The editor never reads `IsHidden`.** `NotificationService` short-circuits a hidden key to `MessageBoxOutcome.ForSuppressed(request)`; checking the flag at the call site as well would be two policies for one decision. Hence `SuppressedResult = Yes` — a switched-off confirmation means "go ahead", not "do nothing".
- **Anything but `Yes` erases nothing**, a box that could not be shown at all included (the rule the Lighting tab's Reset All already follows).
- **`ResetLayout` shares the key** and differs only in wording (`ResetLayoutConfirmation` names every layer). The catalog models one reset confirmation — "Confirm before resetting a layer", mockup 1j — and a user who switched it off has answered for both scopes; leaving the wider one unsuppressible would put two policies behind one checkbox and leave a prompt the settings screen cannot re-enable. A reset is in-memory either way: nothing reaches the drive until Save.
- **`ResetKeyCommand` stays unguarded**, deliberately. Spec 08's other reset flag (`reset_key_msg`) guards resetting a *macro*, which that command does not do — it drops one position's remap — and the catalog marks it forward-declared. `KeyboardEditorViewModelTests` pins the asymmetry so it cannot become an accident.

This is the **first production call site of the suppression pipeline**; `NotificationKeys`, the checkbox and the store existed before it and were reached by nothing ([app-shell.md](app-shell.md)).

Both counters of spec 10 are recomputed together by `RefreshCounters()`: `ModifiedKeyCount` → `Remap (n)` (`KeyboardLayout.ModifiedKeyCount`) and `MacroCount` → `Macro (n)` (`KeyboardLayout.MacroCount`). It runs after a load or import, after a captured remap, after each reset, after an accepted tap-and-hold, and after every macro write from the rail or the Macros tab — **and it ends in `RefreshDirtyState()`**, which is what keeps the amber Save honest (see "The editor shell" above). It is also where the **macro library snapshot is rebuilt** and pushed into both macro surfaces, which is why neither of them subscribes to anything: `RefreshCounters()` is the one funnel, and being on the tail of it is what makes "every mutation reaches both" true by construction.

### Keystroke routing

The editor owns the **single** subscription to `IKeystrokeCaptureService.KeystrokeCaptured`, so spec 10's routing rule lives in one method (`OnKeystrokeCaptured`) and one keystroke reaches exactly one target, in this order:

1. **An *armed* key-inspector panel** (`TryRouteToInspector`) — the Remap panel's `● Record`, either of the Tap & hold panel's two, or the **Macro panel's**, which appends the keystroke to the macro under edit and stays armed for the next one. It is the most specific claim on the next keystroke there is, so it goes first.
2. **The open modal panel**, if it is an `IKeystrokeSink`. It takes the keystroke on being *open*, which is spec 10's own wording ("forwarded to the Tap and Hold dialog **if that dialog is open**"); an unarmed modal swallows it and drops it, so nothing under a scrim can consume keys aimed at the panel.
3. **The listening key**, applied as a remap.

**There used to be a fourth branch — the Macros tab's own recording — and it is gone.** Since issue #93 that tab is a library: it records nothing, and the rail is the app's **one** recording surface, so macro capture arrives through branch 1 like every other armed panel. Appending a keystroke to the macro under edit, with the modifiers held at that moment folded into the step (05 §5.1), is now the rail Macro panel's job.

**Branch 1 is the only one that tests `WantsKeystrokes` rather than mere existence, and that difference is load-bearing.** A modal covers the board, so nothing underneath it can want a keystroke; the rail sits *beside* a live board, so a panel that is merely showing must let the key fall through to the cap the user is remapping next to it. It is the one real behavioural difference between the rail's panels and the modals they replaced.

**The Escape latch is set in branch 1 too, before the dispatch.** A field disarms as it takes the key, so "nothing is armed any more" must not read as "the rail was idle, drop the selection" — see "Escape — the resolution". The router latches for *every* sink, which is why no panel carries a "I took that one" signal of its own.

Capture is *started* by whichever consumer needs it and by nobody else: `BeginRemap` for a listening key, `OnInspectorRecordingChanged` for an armed rail panel (the panels only announce `RecordingChanged`; the editor turns the service on and off around them), and `EditorOverlayHost` for an armed modal sink. Arming a rail panel cancels a listening key first, and opening a modal ends both.

### The keyboard grammar — `Input/EditorShortcuts`, `KeyboardEditorView.OnPreviewKeyDown`

Mockup `2b`'s shortcut table, verbatim, and the whole of it:

| Keys | Intent | Runs |
|---|---|---|
| `↑ ↓ ← →` | move the key selection across the **physical** board | `KeyboardEditorViewModel.MoveSelection(NavigationDirection)` |
| `⌥1`–`⌥5` | show layer *n* — a number past the layer count is a no-op | `SelectLayerCommand` |
| `⌥↑ ⌥↓` | move the key inspector's selected **macro step** (mockup `2i`) | `MoveMacroStepUp/DownCommand` → `MacroInspectorStepsViewModel.MoveStep` |
| `⌘F` | put the caret in the token search — the key inspector's on the Layout tab, the insertion picker's on the Macros tab | `OpenSearchCommand` |
| `⌘S` | save | `SaveCommand` |
| `⌘W` | back to the dashboard | `Shell.HomeCommand` |
| `Esc` | *not in this table* — see below |

**`Input/EditorShortcuts.Map(Key, KeyModifiers, bool isMacOs)` → `EditorShortcut`** is the whole platform question, in one pure function: ⌘ is `Meta` on macOS and `Control` elsewhere, ⌥ is `Alt` on every platform (Alt *is* Option on macOS, so only the spelling on the layer chip changes). `isMacOs` is a **parameter**, the same shape `KeyCaption.For` uses — a test that only passes on a Mac is a test that fails in CI. `ToDirection` and `ToLayerNumber` are its two projections; `ToDirection` never answers `NavigationDirection.None` for a move, because `KeyAdjacency.Next` throws on it. **The modifier set is matched exactly, never masked**: `⌘⇧S` is not `⌘S`, and an arrow with anything held is not an arrow.

**One handler carries it, and there are deliberately no `KeyBinding`s or `KeyGesture`s anywhere in this app.** `KeyboardEditorView.OnPreviewKeyDown` — tunnelled, `handledEventsToo: true` — is the same handler Escape already used. An accelerator fires wherever it is in scope, and neither gate below is expressible as a gesture.

**The view is focusable and takes focus on attach** (`Focusable = true`, `IsTabStop = false`). A tunnelling key event travels only the chain between the window and whatever holds focus, so a handler on this control sees nothing while focus is outside it — and a freshly opened editor has focus nowhere inside it, which would leave ⌘S dead until the first click. It is not a tab stop, so Tab still walks the toolbar, the tabs, the layer switcher and the board exactly as before.

**Gate 1 — capture wins, always.** `KeyboardEditorViewModel.IsCaptureActive` (a listening key **or** a recording macro **or** an armed sink panel — the three consumers of invariant 5) turns the entire grammar off. A user assigning ⌘S to a key must get `s`-with-Meta recorded, not a save. It is read on demand and is deliberately not observable; nothing binds it.

**Gate 2 — an open modal owns the keyboard.** While `HasActiveOverlay` is true, *no* shortcut fires — `Esc` excepted, which is what closes the panel. Gate 1 does not cover this: a text-entry panel with nothing armed is not capturing, so `⌘S` would otherwise reach the editor **through the scrim**. That is not only a UX slip. The overlay `Border` is a sibling of the content grid, *outside* the `IsEnabled="{Binding !IsBusy}"` panel, so the panel stays interactive while `Task.Run(session.Save)` serializes the model on a background thread; an *Ok* clicked at that moment writes to a `KeyboardKey` the serializer is walking. The rule is therefore the whole grammar, not just the navigation keys.

**`⌥↑↓` is not a fifth and sixth board move.** `EditorShortcuts.ToDirection` answers `None` for both, so neither can ever reach `KeyAdjacency`, and the view dispatches them like `⌘F`/`⌘S`/`⌘W` — past the arrow gate below, which exists to protect a focused one-of-N control. They keep only the text-input clause, exactly as `⌥n` does: nothing else in the editor consumes `Alt`+arrow (the step list is deliberately not a selecting control), and gating them on the wider set would make them die the moment the user clicked a tab or a layer segment. `⌥←` and `⌥→` stay out of the grammar — the design names no gesture for them.

**Gate 3 — the focused surface keeps what is its own, and the two navigation keys are gated differently.** Arrows are left untouched when the focused element's **ancestry** contains a `TextBox`, `NumericUpDown`, `AutoCompleteBox`, `SelectingItemsControl` or `RangeBase` — the tab strip and the layer switcher are one-of-N controls that move their own selection with arrows, and stealing those would break the segmented control outright. **`⌥1`–`⌥5` keep only the text-input clause**: no `SelectingItemsControl` or `RangeBase` consumes `Alt`+digit, and gating the layer jumps on them made them die silently the moment the user clicked a layer segment or a tab with the mouse — the very control the `⌥n` legend is printed on. A focused field still wins, because `⌥1` types `¡` on macOS. Both are ancestry walks rather than lists of control names, so a field nested in a future composite is covered without the view learning about it; the walk stops at the editor view. `⌘S`/`⌘W`/`⌘F` pass this gate by design — a save accelerator that stops working while the caret is in a field is not an accelerator.

**A move lands through `SelectKeyDirectly`, never `SelectKeyCommand`.** The click contract promotes a second hit on the already-selected cap into listening, and arrowing onto a key must never arm the keyboard. `MoveSelection` lives on the view model because the board picture does (`_visual` is the editor's); with nothing selected yet the first cap of the shown layer is where an arrow lands, so the grammar has an entry point that needs no click. The geometry is Core's `KeyAdjacency` ([domain-data.md](domain-data.md)) — rectangle overlap plus centre distance, so **crossing the split halves falls out of the scoring** and needs no special case.

**The cap it landed on takes the focus ring**, through `KeyboardView.TryFocusKey(int)` with `NavigationMethod.Directional` — which is what raises `:focus-visible` (`2b`: "mouse clicks suppress it, arrow/Tab summon it"). Selection and focus then coexist on one cap as concentric bands ([design-system.md](design-system.md), "Focus + selection on a key cap"). `TryFocusKey` reaches a cap's own `Content`, never a template part, and the view picks whichever `KeyboardView` is *effectively visible* — the Layout/Macros board and the Lighting tab's are two pictures over the same layer.

**⌘F is dual-purpose, deliberately, and it finally has somewhere to write.** With a macro open on the Macros tab it *is* the insertion picker (`InsertSpecialActionCommand`) — finding a token there means inserting it. Everywhere else it opens the key inspector and puts the caret in the **rail's own** search field, where `↵` on a row assigns to the selected position; nothing is opened over anything, because the rail is not modal. A modal that is already up keeps the keyboard (⌘F re-focuses its own field if it is the picker, and otherwise never replaces one panel with another). The field is focused by **`TokenPickerView` itself**, not by the caller: the view is materialised by `ViewLocator` a layout pass after the command runs, so `TokenPickerViewModel.RequestFocus` records a *pending* request that the view answers on attach.

**A shortcut whose command cannot run does nothing and leaves the key unhandled**, rather than swallowing it — including `⌘W` with no `Shell` (null in every headless scene that does not assign one, and in the design-time preview).

### Escape — the resolution, and the constraint it is resolved against

The design says (`2b`, verbatim): *"Esc — leaves capture mode first, closes the inspector second."* **This app satisfies the second half and cannot satisfy the first**, and the reason is structural rather than an omission:

> The keystroke-capture service previews the window's key events in the **tunnel** phase and swallows every physical position it can resolve — Escape included — because a keyboard must be able to carry an Escape remap (05 §3). By the time any handler of this view runs, a listening key has *already been assigned Escape* and listening is over.

So Escape is **a remappable key, not a shortcut** (invariant 6). Cancelling a remap is a pointer action: the *Cancel* button beside the listening banner, clicking the listening key again, clicking another key, or switching layer. The branches, all pinned by tests:

| State | Escape does | Why |
|---|---|---|
| A feature panel is open and is **not** awaiting a keystroke | closes the panel, whatever `e.Handled` says | Capture may be running for something else entirely; a panel that cannot be closed from the keyboard is worse than an Escape that also lands elsewhere. Read off `IsOverlayAwaitingKeystroke`, never guessed from `Handled` |
| A feature panel is open and **is** awaiting a keystroke (an armed Tap and Hold field) | goes to the panel's field, which disarms | The next Escape then closes the panel — the two-stage rule, as far as the constraint allows. "Is awaiting" is **two** questions; see the latch below |
| A key is listening, no panel | **is assigned to that key** by the capture service; `CancelRemapCommand` is unavailable by the time the view's handler runs, so nothing double-fires | 05 §3 — an Escape remap has to be expressible |
| A key is listening, no panel, **and nothing consumed the key** | cancels the remap | The documented safety net. It is the state every headless scene is in, because those use a fake capture service |
| A `Copy key…` is armed, nothing else | disarms it, writing nothing | Tried **after** capture, per `2b`'s "leaves capture mode first" — a stated order, not a lucky one, since the two are mutually exclusive by construction. A copy is armed and finished by clicks, so nothing swallows this Escape |
| A **key is selected**, nothing narrower | clears the selection (`SelectKeyCommand.Execute(null)`): the cap loses its ring and the rail falls to its empty state | **Changed by [#119](https://github.com/migus88/kinesis-edit/issues/119).** It used to close the rail — which the rail cannot do any more, because it is a permanent column and dismissing it would collapse that column and shove the board sideways, the very defect #119 removes. Deselecting reaches the same end from the other side, and is still "back out of the narrowest thing I am in". It runs the editor's own command rather than reimplementing the rules |
| Nothing is selected either | **nothing; the key is not handled** | An accelerator that swallows a key it does nothing with is worse than one that does not fire |
| An **armed rail panel** took this keystroke | fills the field, or **becomes a macro step**; the selection stays | Same latch as the modal case, for the same reason. The *next* Escape clears the selection |
| Nothing open, nothing listening | nothing | — |

**The latch is checked once, for the whole handler (issue #122).** It used to guard only the first branch, so an Escape that an armed consumer had *already taken* still fell through to the last one and ran `SelectKeyCommand.Execute(null)`. On the Macro panel that meant one Escape both **recorded itself as a step and stopped the recording** — the reported bug, and the reason the mock's `Esc stops.` looked like it worked. `HandleEscape` now returns early on the latch. The rule it makes true is the one the method's own comment always claimed: **a keystroke an armed consumer has taken is not also a command.**

**The order is four stages now: feature panel → capture → armed copy → inspector.** `2b` asks for "leaves capture mode first, closes the inspector second"; this is that, with the two states the design does not mention (a modal, an armed copy) slotted in by how narrow a claim each one is.

**The armed-field carve-out needs a latch, not just `IsOverlayAwaitingKeystroke`.** The capture service previews on the `TopLevel` **above** this view, so on one Escape it runs first: the sink takes the key and *disarms*, and by the time `HandleEscape` runs the panel looks idle — one Escape both filled the field and destroyed the panel. `KeyboardEditorViewModel.OnKeystrokeCaptured` therefore records that a sink took this keystroke — **before** it dispatches, and for the rail's sinks as well as the modal's — and `KeyboardEditorView.OnPreviewKeyDown` reads-and-clears it (`TryTakeOverlayKeystroke`) on **every** key down, so a latch set by an ordinary keystroke cannot answer for a later Escape. It is also cleared whenever the open modal changes. `e.Handled` is deliberately *not* the signal: capture may be running for something else entirely.

**Escape never comes out of `EditorShortcuts.Map`**, under any modifier — `EditorShortcutsTests` asserts that specifically. Do not add an accelerator that steals Escape anywhere else.

### The Macros tab — a library, not an editor (`MacroLibraryViewModel`, issue #93)

**The tab lists macros; the rail edits them.** Mockup `2i` states the redefinition outright: *"selecting a key edits its macro right here — the Macros tab is a library, not the editor"*, and *"every macro has a name, so the tab lists them once: rename, see which keys and layers fire each one, duplicate, delete"*. So this tab draws **no board, holds no open macro and never captures a keystroke** — there is exactly one recording surface in the app and it is the key inspector rail.

`MacroLibraryPanel` is built **once, in the constructor**, from device facts alone (`MacroCapability`, the display name, the firmware-resolved macro count) and reaches the profile's library through a `Func<MacroLibrary?>`. That is what lets it exist before any profile is read and survive a load or an import, which replace the library instance under it.

**One view model, two branches, chosen by `MacroCapability.UsesFlatMacroList` and by nothing else.** There is no device-specific view and no device id anywhere in the class or the XAML — a board's shape is a fact of its capability record ([domain-data.md](domain-data.md)):

| | Slot branch (`UsesMacroSlots`) | Flat branch (`UsesFlatMacroList`) |
|---|---|---|
| Header | `Macros on {key} · {device}` | `Macro library · {device} · one flat list per profile` |
| Subtitle | `3 of 5 slots used · 1 active` | `24 macros · trigger + layer set per macro` |
| Action | `Pick another key` → the Layout tab | `New macro` → the rail, Record armed |
| Extra | one card per **persisted** slot of the selected key | `Macro / Trigger / Layer / Length` column captions |

**Both stores of 06 §1 are implemented, though only the slot branch can be reached today** — the flat branch is the Advantage 360's, whose board picture is [#41](https://github.com/migus88/kinesis-edit/issues/41), so it is currently proved by its tests rather than by a user. That is deliberate: the branch is chosen by the capability record, so wiring the 360's editor is adding data, not adding a view.

- **Both branches list `MacroLibrary.Entries`, never a walk over the keys.** That is the whole point: a macro on two keys is **one row with two sites**, and the entry *is* the answer to "which keys and layers fire it". `Entries` is a **snapshot** — every mutation rebuilds it — so rows are rebuilt rather than re-marked, and a row held across somebody else's edit is stale (`ArgumentException`, caught and answered with a rebuild, never guessed at).
- **The slot cards** (`MacroSlotViewModel`, one per **`PersistedSlotsPerKey`** — 3 on the Advantage2 and Freestyle Edge/Pro, 5 on the RGB family; none on the flat-list families): the strip offers what the dialect *writes*, not the five the model owns, because a macro put in slot 4 of a Freestyle Edge would be gone after save+reload with nothing said. The active one is badged `ACTIVE`, the rest offer `Make active`, and an empty one offers `＋ Record a macro`. A position that refuses macros (05 §5.3) gets **no cards at all** rather than dead ones.
- **`Make active` does not dirty the session.** `KeyboardKey.ActiveMacroIndex` is an in-memory field that is never serialized (05 §1.3), so it runs the refresh funnel through `RefreshMacroViews()` and deliberately skips the dirty flag — an unsaved-changes prompt for a choice no save could persist would be a lie.
- **`＋ Record a macro` and `New macro` both leave for the rail** (`IMacroLibraryHost.EditMacroAt`): Layout tab, that layer, that position selected through `SelectKeyDirectly` (never the click path, which promotes a second hit into a remap), the rail opened on its *Macro* panel, and Record armed. Mockup `1i` draws a capture-mode overlay on this tab; **not building it is a deliberate deviation** — see [design-system.md](design-system.md).
- **Rename goes through the editor's one path** (`IMacroLibraryHost.RenameMacro` → `KeyboardEditorViewModel.RenameMacro`), which renames every site, marks the session dirty and re-runs the funnel. A **blank name clears** the stored one and the macro derives one from its content again. `MacroNaming.MaxNameLength` bounds the field, so Core never silently truncates what was typed.
- **Delete names its sites before anything goes.** `{name} fires from {sites}. Deleting it removes the macro from {all N keys}.`, on the app's shared message box with outcome-named buttons (`Delete macro` / `Keep it`, mockup `1k`'s rule) and `DestructiveResult`. There is deliberately **no suppression key**: the question exists to name the keys, and an answer the user switched off would take a macro off three positions in silence. A declined question — or a box that could not be shown at all — erases nothing.
- **Duplicate is not refused for landing on the same trigger.** `MacroLibrary.Duplicate` puts the copy on the trigger it copied, which `Validate()` reports as a duplicate trigger (06 §5). Reported, never refused, like every limit in this model ([keyboard-model.md](keyboard-model.md), invariant 1). The one thing it does report is "there was no room": `Every macro slot of this key is taken.`
- **Search matches name, trigger *and* contents** (mockup `1i`: "Search name, trigger, or contents…"), case-insensitively, against a haystack built once per row — which deliberately includes `MacroNaming.DeriveTypedText`, so a macro is findable by **what it types** and not only by the `{a}{b}` tokens the file carries. `All layers ▾` narrows by layer beside it. Both filters write nothing.
- **The meters** are mockup `1i`'s two — `layout keystroke budget 5 140 / 7 200` and `this macro 512 / 500` — plus a third, `macros 24 / 100`, which is the only place 06 §6's profile-wide macro count is readable now the old budget block is gone. The per-macro figure goes through **`MacroLengthMetric`**, so the Advantage360's cap is measured as serialized macro-text characters and every other family's as weighted keystrokes — the same code `Validate()` uses, which is what keeps the readout and the save gate from disagreeing. **A null limit means no limit, never zero** (the Advantage2 states no macro count, so its caption is a bare number). Over budget is **amber and still saves**.
- **Mono is the file's voice.** A macro's keystrokes, its trigger tokens and its length are values that exist verbatim in `layoutN.txt` or are counted against it, so they are mono; its **name is not** — it rides `app_settings.txt` and is the app speaking — so it is sans.
- **Everything is pushed, nothing is subscribed.** Core announces no change, so `RefreshMacroLibraryPanel()` hangs off the tail of `RefreshCounters()`/`RefreshLegend()` — the funnel every mutation already ends in — and off the two selection paths, which move what the slot branch is *about* without writing anything.
- **`MacroLimits.ResolveMaxMacroCount(device)`** is the editor's only firmware-gate read (`FirmwareFeature.ExpandedMacroCount`, 09 §2; demo mode passes). It is a static of its own because **two** surfaces ask it — this tab's count meter and the rail's Macro panel, which refuses a macro that would exceed it.

**What happened to `MacroPanelViewModel`.** It was 1077 lines and the codebase's own anti-example of a god class; issue #93 split it along the seam the redesign drew. Its **editing** half (record, steps, co-triggers, speed/repeat, the open-macro identity) is the rail's `MacroInspectorPanelViewModel`; its **listing and budget** half is this tab. `MacroPanelView`, `MacroEditTarget`, `MacroStepListViewModel`, `MacroStepViewModel`, `MacroBudgetViewModel`, `MacroListEntryViewModel` and `MacroClipboard` are deleted; `MacroSlotViewModel` and `MacroCoTriggerViewModel` survive, re-homed on the tab and the rail respectively; `ResolveMaxMacroCount` became `MacroLimits`. **One capability went with it**: the panel's own per-key macro **Copy/Paste** buttons. Copying a key's macros onto another key is still there — it is the legend row's `Copy key…`, which runs Core's `KeyboardKey.CopyFrom` and carries the macros with it — so what was lost is the *second*, panel-local clipboard for the same job, not the job. One rendering detail also went: the old list drew each row with its **layer prefix** (`fn {q}>{s5}{x1}{a}`); a library row shows the macro's keystrokes and names its layer in its own column instead.

### The macro library and macro names — `KeyboardEditorViewModel.MacroLibrary.cs`

**There is exactly one `MacroLibrary` per open profile, and the editor owns it.** The rail's Macro panel and the Macros tab are two views of one identity — "every macro has a name, so the tab lists them once" (`2i`) — and two libraries over one `KeyboardLayout` would be two snapshots that disagree the moment either is edited. Whoever needs it asks `KeyboardEditorViewModel.MacroLibrary`; nobody constructs a second.

| Member | What it is |
|---|---|
| `MacroLibrary` | The profile's library, or null while nothing is loaded. The **instance** survives every edit; its `Entries` snapshot does not |
| `ProfileNumber` | The open profile (1-9), or **0** with no session at all — demo mode, and a load that failed. It is what scopes a name to a profile |
| `MacroLibraryChanged` | Raised after the snapshot was rebuilt or replaced. Core announces nothing, so a consumer holding an entry re-reads it here |
| `RenameMacro(entry, name)` | The **one** rename path. Returns the fresh entry (every mutation rebuilds the snapshot); null for a stale one. A blank name clears the stored one and the macro derives one again |
| `MarkMacroNamesDirty()` | For the Macros tab's other name-moving edits (a delete, a duplicate) |
| `HasUnsavedMacroNames` | Folded into `IsDirty` — see below |

**Names are not in the layout file.** They ride `settings/app_settings.txt` as `macro_name_<profile>_<layer>_<trigger>_<slot>` (`MacroNameKey`), so a freshly parsed layout always arrives unnamed:

- **On load** (and after an import, which replaces the layout wholesale) `Apply` calls `AttachMacroLibrary`, which stamps the stored names on with `MacroLibrary.ApplyNames` **and only then** constructs the library — grouping is by name, so a name applied afterwards would not be in the snapshot.
- **On save** `PersistMacroNames()` hands `library.EnumerateStoredNames()` to `AppSettings.WithMacroNamesForProfile`, whose tombstones turn a rename, a delete and an unassignment into removals by themselves. Only **explicitly** named macros are in that set; a derived name is recomputed every load and never written. It runs **after** the layout landed, so a save Core rejected cannot leave the file naming macros the drive does not have.
- **The snapshot follows every edit** through `RefreshCounters()`, and is rebuilt *before* the legend pushes state into the rail, because the rail's Macro panel reads it.

**A rename is part of the session's dirty model — deliberately, and it is the one exception.** [settings.md](settings.md)'s rule is that `app_settings.txt` sits outside it: a swatch and a "don't ask again" answer are written the moment they are made. A macro name is not like those — it names something the user is editing, it is meaningless beside a profile that was never saved, and discarding the session has to discard it too. So it marks the session dirty and reaches the drive only through Save. Swatches and suppression answers are untouched and keep writing through immediately.

**It goes through `IAppPreferencesStore` and never a second reader/writer pair.** The store gained one method for it, `UpdateMacroNames(profileNumber, mutate)`, because Core's writer is a second entry point too: `SettingsService.SaveMacroNames` takes the profile number that scopes the deletion — one file holds nine profiles' names and saving this one must never remove another's — and `SaveAppSettings` cannot reach a name at all. A store that cannot write (demo mode, no drive) discards it without throwing; the names still live on `Macro.Name` for the session, so the library and the dropdown behave identically.

### Feature commands (spec 11)

**Three of the five are gone as commands.** §11.1 is a key-inspector panel now, so `TapAndHoldCommand` and `CanOpenTapAndHold` were deleted with the modal — the panel answers both gates in place. §11.6's plain picker is the rail's Remap panel; only its macro-insertion call site is still a modal. And §11.3 went the same way with issue #93: `InsertDelayCommand`/`InsertDelayAsync` are deleted, because a delay is edited on the step it belongs to rather than inserted at the end of a recording. Two commands remain, plus ⌘F; the panels themselves and every rule and message they carry are in [feature-dialogs.md](feature-dialogs.md). The editor's part is the sequencing:

| Command | Sequence |
|---|---|
| `InsertSpecialActionCommand` | show `TokenPickerOverlayViewModel` titled `Search Keys (Macro)`, over the editor's shared `RecentTokenStore`; its `Selected` key is appended the same way |
| `ExportCommand` | show `ExportOverlayViewModel` over the current session |
| `ImportCommand` | cancel listening + stop recording + stand the rail down → `ProfileImporter.ImportAsync` → on success re-run `Apply` and toast, on failure a message box |

`ShowOverlay(overlay)` is the one entry point: it cancels listening, **stops any macro recording**, **stands the key inspector down** (`Inspector.Deactivate()`) and hands the panel to `EditorOverlayHost`. Stopping the other consumers is what hands the capture service back — one of them underneath owns it, the host would then never start or stop it, and every key aimed at the panel would land elsewhere. The rail itself stays *open* behind the scrim; only what it had armed stops. The two insertion panels are wired through `ShowMacroInsertOverlay`, which subscribes the "append to macro" action and **unsubscribes it on the panel's `Closed`**, so a dismissed panel can never write into the macro afterwards.

### Save

**`SaveCommand` runs `SaveAsync`, which is a one-line wrapper: the whole sequence is `private async Task<bool> TrySaveAsync()` and the button drops its answer.** A button press has nowhere to report a failure `TrySaveAsync` has already put on screen; the caller that *needs* the answer is `ConfirmCloseAsync` (below), which may only let a navigation through when the profile actually reached the drive. **`true` means written, and nothing else does** — it returns false at each of its three failure exits (no session or `!CanSave()`, a caught exception, `!result.Success`).

`TrySaveAsync` cancels any listening and stops any macro recording first, then: `IsBusy = true` → `try { ShowLoading("Saving…") → Task.Run(session.Save) }` → `IsBusy = false` **then** `HideLoading()` in a `finally` → report. Everything else is Core's ([profiles.md](profiles.md)): validation gating, file writes, eject, post-save wording. The ordering is load-bearing: both indicator calls fan out to the overlay and can fail, so `ShowLoading` sits inside the `try` (its failure is reported as the save failure it is) and the flag is cleared before `HideLoading`, because a stranded `IsBusy` disables Save and every editing command for as long as the editor is open.

- **Threw** → message box `Save Profile` / `SaveErrorMessagePrefix + message`.
- **`Success == false`** → message box listing `SaveRejectedMessage` followed by one line per `ModelViolation.Message` (04 §5.3's gate, surfaced rather than silently dropped).
- **Success** → toast titled `Save Profile` carrying the device's refresh wording verbatim, plus `Saved with N advisories.` when the profile carries any (`BuildPostSaveMessage`). Either half alone is enough to raise the toast; with neither there is none. **An advisory never stopped the save** — the toast has already been reached only on success, so the count is stated in the same breath rather than warned about separately. It does change the toast's *face*: `Advisories.Total > 0` sends `ToastSeverity.Advisory`, so a message that counts advisories arrives amber instead of on the green success face. It stays a toast and never becomes a message box — advisories never block.

Both boxes go through `TryShowMessageBoxAsync`, which returns `Task<MessageBoxOutcome?>` and yields **null** for a box that could not be put on screen — the editor state already carries the outcome, and a shell that cannot host a card must not bring the app down. Every caller that merely *reports* something ignores the answer; the one caller that asks a *question* — `ConfirmCloseAsync` — reads null as "the user did not answer". (Since issue #89 the box is an in-app overlay rather than a window: with no host registered the presenter answers with the escape outcome rather than hanging, so this guard covers a throw rather than a missing owner — see [app-shell.md](app-shell.md).)

### Leaving with unsaved work — `ConfirmCloseAsync`

The guard of `handoff.md` §2 (*"leaving via Home asks once (modal) unless opted out"*), asked by the shell before Home, another device, or the window's close replaces this editor — all three exits, one question ([app-shell.md](app-shell.md), "The unsaved-changes guard"). The question itself is `UnsavedChangesPrompt`'s, so this board and the pedal ask it in the same words; only the sentence about what the save writes is per-board.

In order:

1. **`IsBusy` (a save in flight) refuses outright, with no question but with a toast** — `Saving` / `Please wait for the save to finish.` Leaving would dispose this editor while `ProfileSession.Save` is still writing, and the question would be the wrong one anyway; the write is short, so the navigation works the moment it finishes. The blocking loading card already covers Home with its scrim, so this is the invariant behind that scrim rather than the only line of defence — a path that is not a click must not appear to do nothing.
2. **Demo mode leaves without a word, and so does `!IsDirty`.** The demo test is explicit — `IsDemoMode || !IsDirty` — and it has to be: a demo session is a real session over the fixture drive, so an edit genuinely marks it dirty, and the question would then offer a `Save` that can never run and a `Discard` for work that was never going anywhere. A load that produced no session is the `!IsDirty` half.
3. `canSave = CanSave()` is read **once** and carried, because it picks the card *and* decides what `Yes` meant. A read-only profile (profile 0) can hold edits it can never write, and offering it a Save would be a question with no working answer.
4. The answer, through `UnsavedChangesPrompt.Interpret`: **Save** → `await TrySaveAsync()`, so only a save that actually landed lets the navigation through — a failed one would discard the very work the question was about, and a profile that turned unwritable while the box was up is caught by `TrySaveAsync`'s own re-check; **Discard** → true; **everything else, including a box that could not be shown** → false.

`canSuppress` is **true** here: the opt-out (`warn_unsaved_msg`) is reversible from the Settings tab's "App & notifications" section, which this board renders ([settings.md](settings.md)). The pedal passes false, for the opposite reason ([savant-elite.md](savant-elite.md)).

**What it cannot see is the Settings tab** — see "Settings are outside the dirty model".

## Presentation rules

**`KeyCaption`** — the caption of `KeyboardKey.ModifiedOrOriginalKey` (so a remapped cap reads its new action), resolved in this order:

1. `GlyphText` (05 §3.7/§3.9) — **only when `IGlyphCoverage.CanPrint` says the app's own type can print every rune of it**. §3.7/§6 gate the glyph column on *capability*, and this app's capability is its embedded families rather than an OS version ([design-system.md](design-system.md), "What the families can print, at runtime"). All 17 distinct glyph values fall through today; a glyph that *is* covered is still preferred, because this is a capability gate and not a ban.
2. `MacDisplayText` when `OperatingSystem.IsMacOS()` (05 §3.3/§3.5).
3. `GetDisplayText(dialect)`.
4. **On the dropped-glyph path only:** the entry's caption in the first *other* dialect that spells one. Exactly one entry needs it — see deviation 52.
5. **The dialect's file token, when every source above is blank.** 05 §3.11 registers `hk0`–`hk8` with `' '` (the physical caps are unlabelled), which would otherwise draw a column of indistinguishable empty caps; the token is what the user sees for that position in the layout file, which makes it the honest fallback rather than an invented label. Those nine carry no glyph, which is why step 4 is scoped to entries that do — it must not divert them.

`\n` is preserved verbatim — splitting it into a two-line cap (05 §1.1) is the view's job.

**`KeyCapCaption`** — a **cap-only** narrowing applied *after* `KeyCaption`, and only by `KeyboardKeyViewModel.ResolveCaption`: `Forward`/`Rewind`/`Record`/`Play\nPause` do not fit a 1U cap, so the legend reads `Fwd`/`Rew`/`Rec`/`Play`. Everything that writes a key's name into prose — the macro rows, the co-trigger captions, the library header, the inspector's token field — calls `KeyCaption` directly and keeps the full word. See deviation 53. `KeyCaption.For(key, dialect, isMacOs, coverage)` takes **both** capabilities as parameters, so the rule stays a pure function of its arguments and every branch is testable on one machine with no toolkit running; `IsMacOs` is resolved once as a static, and all seven call sites pass `EmbeddedFontGlyphCoverage.Instance`.

**`LayerCaptions`** — the geometry's `Name` is the spec-literal file-side name (`Qwerty-top`/`Qwerty-keypad`), which is not what an editor shows. Gen2 keeps the raw names (Base, Keypad, Fn1–Fn3 are already presentation-ready); Legacy/Gen1 map index **0 → `Top`**, **1 → `Fn`** (spec 10 describes both switches that way); anything else falls back to the raw name.

**`KeyColorOverlay`** — projects a profile's lighting onto the picture. `BuildPaint(device, lighting, layer)` returns the layer's painted colours; `ToHex`/`TryParseHex` are the module's `LedColor` ↔ `#RRGGBB` pair, used in both directions by the picker. It lives in one tested place because `KeyboardKey.KeyColor` exists but **no parser ever fills it** (the led file is parsed into the lighting model, never into the layout model), so reading the key would always show nothing — which is also why `KeyboardKeyViewModel.RefreshFromModel()` cannot reach the colours and the Lighting tab pushes a fresh frame in through `KeyboardLayerViewModel.ApplyLighting` instead. Note the keying: `LayerLightingState.KeyColors` is keyed by **memory key code** (07 §4), not by key index, and so is everything downstream of it — the preview's `LightingPreviewKey`, the effect frame's cells and `ApplyLighting`'s two maps. Mixing the two silently mispaints, which is why the code is carried end to end rather than resolved back to an index. Empty unless the device is `LightingKind.PerKeyRgb` *and* `IProfileSession.Lighting` is a `LightingModel` (TKO's `TkoLightingModel` is deliberately not matched yet) *and* the layer is one of the two that model describes — layout layer **0 ↔ `LightingModel.TopLayer`**, **1 ↔ `FnLayer`**. `LedColor.IsBlack` is "no colour" (07 §2.1) and yields no entry; an unknown key code is skipped. `ToHex`/`TryParseHex` are the module's `LedColor` ↔ `#RRGGBB` pair, used in both directions by the picker.

**`LedPreviewTint`** — the colour a *lit cap's face* is painted with, and nothing else ([#124](https://github.com/migus88/kinesis-edit/issues/124)). `Soften(LedColor)` is two fixed affine steps in this order: pull every channel toward the colour's own Rec. 709 luma (`LumaPull` **0.33**) to cut saturation, then scale all three (`BrightnessScale` **0.87**) to take the glare off. Both constants are applied to all three channels, so every channel *difference* is scaled by the same factor and the **hue is preserved exactly** — `#FF0000` becomes `#A41010`, a lit red rather than a glowing filament. Four properties are load-bearing:

- **The weights run on the sRGB-encoded channels, deliberately not linearised.** This is a viewing adjustment, not a WCAG luminance: working in the encoded space keeps the pull's effect on a mid-tone the size the eye expects instead of collapsing every dark colour toward black.
- **Black is a fixed point**, because nothing adds a constant term. Black is "no colour" ([lighting.md](lighting.md)) and an *unlit* cap is absence — a null that never reaches here — while a cap Pitch Black lights black must still read black. A softening that lifted toward mid-grey would turn one into a dim-grey lit key and the other into a whole board of them; off stays **hatched**, never dim grey.
- **It is not idempotent** — softening a softened colour softens it again — which is the second reason for the single seam.
- **The constants were chosen off rendered frames in both variants**, at four settings: at 0.20 the primaries still glare, and by 0.40 with a heavier scale blue has gone navy and yellow olive, which is a *different* colour rather than a quieter one. There is no preference and no per-mode variation.

## Seams and composition

- **`IProfileSession` / `IProfileSessionFactory`** exist because Core's `ProfileSession` is sealed with a static `Load` — unsubstitutable in a test. `ProfileSessionAdapter` is a pass-through with no behaviour of its own; `ProfileSessionFactory` calls `ProfileSession.Load` and wraps it. Same shape as `IMessageBoxPresenter`.
- **`ISettingsService` / `SettingsServiceAdapter`** are the same seam over Core's sealed `SettingsService` ([settings.md](settings.md)), and the app builds **one** instance: the settings panel, the lighting picker's custom slots and the notification-suppression store all go through it, so `app_settings.txt` has a single reader and a single writer.
- **`EditorViewModelFactory`** is the one place that picks an editor: `DeviceId.SavantElite2` → `SavantElitePedalViewModel` ([savant-elite.md](savant-elite.md)); otherwise "can this device be drawn?", answered with `VisualCatalog.TryGet(id, out _) && GeometryCatalog.TryGet(id, out _)`, → `KeyboardEditorViewModel` or `EditorPlaceholderViewModel`. The shell asks for one and swaps in whatever it gets, which is also what keeps every editor's dependencies out of `MainWindowViewModel` — the profile-session factory, the settings seam, the capture-service accessor, `PedalFileService`, and the keyboard editor's feature-panel set: `IFolderPickerService`, `IFilePickerService`, `IVDriveFileService` and `IUrlLauncher`.
- **The capture service is resolved through a `Func<IKeystrokeCaptureService>`**, not held: `AvaloniaKeystrokeCaptureService` attaches to the shell `TopLevel`, which does not exist while `App.BuildServices` wires the graph — the same ordering problem the message-box presenter solves with its `Func<Window?>` owner. `App` builds it lazily on first use, keeps the single instance, and disposes it in `OnExit` **after** the shell (which closes and disposes the editor, which stops capture first).
- `MainWindowViewModel` delegates the choice to `IEditorViewModelFactory`, keeps `Editor` typed as the abstract `DeviceEditorViewModel?`, fires `editor.LoadAsync()` once after the view swap, and disposes the outgoing editor in `CloseEditor()` on both navigate-home and re-open.

Everything else here is this app's wording: the Lighting rail's section labels (`COLOR`, `SPEED`, `DIRECTION`, `PICK A COLOR` — `LightingModeRailView`'s consts; `ApplyCaption` and `ClosePickerCaption` went with the button and the disclosure they named, deviations 60 and 61), **every line of `LightingHintCatalog`** (per mode and per property, written from 07 §2.2/§3 — the handoff prescribes no help text anywhere, deviation 63), `LightingColorSlotViewModel.PaintColorCaption` (`Paint Color`, deviation 62), the two layer-switch labels (`LAYER` / `LIGHTING LAYER`, `KeyboardEditorView`'s consts), the chord composer's four (`COMPOSE A CHORD`, `Compose chord`/`Hide composer`, `ComposerHint`, `Insert chord`) and `MacroInspectorPanelViewModel.OsReservedNote`, `Profile n`, `Saving…`, `Loading profile...`, the `Save Profile` / `Load Profile` dialog titles, `The profile was not saved because it exceeds the device's limits:`, `Line <n>: <text>`, `Press a key to assign it to the highlighted key.`, `Some lines of this profile could not be applied`, the two macro surfaces' other lines (`This device does not support macros.`, `A macro can hold at most {0} co-triggers.`, `This profile already holds its maximum of {0} macros.`, `Every macro slot of this key is taken.`, and the library's own `Pick a key on the Layout tab to see its macro slots.`, `Every macro in this profile`, `No macros in this profile yet.`, `No macro matches this search.`, `Delete this macro?` + `{0} fires from {1}. Deleting it removes the macro from {2}.` with `Delete macro` / `Keep it`), the tab captions `Layout` / `Macros` / `Lighting` / `Settings` (spec 10's RGB app has `Layout` / `Lighting` tabs with the macro editor as an in-window panel and settings in a modal dialog; the four-tab shape gives each of those a home of its own), the two reset confirmations and their outcome-named buttons (`Reset Layer` / `Reset Layout`, `Do you want to clear every remap and macro on this layer? Nothing is written to the keyboard until you save.` and its every-layer twin, `Clear layer` / `Clear all layers` / `Cancel` — the specs give no wording for a reset prompt, and mockup 1k's rule that buttons are named by outcome is followed), and the advisory sentences the mockups do not give: `AdvisoryText.SectionSummary`, the duplicate-key sentence's position list, and `Saved with N advisories.`. The strings the view models own are consts on `KeyboardEditorViewModel`/`EditorTabViewModel`/`LayerCaptions`/`MacroLibraryViewModel`/`MacroSlotViewModel`/`MacroInspectorPanelViewModel`/`AdvisoryText` and asserted by tests; the ones only the view uses are XAML literals.

Recorded deviations:

1. **No per-key Done/Cancel commit step.** Spec 10's Adv2 flow has "**Done** validates and marks the layout modified; **Cancel** reverts". Here a captured keystroke is applied to the model immediately, and Cancel means "stop listening" only. Validation happens once, at save time, where 04 §5.3 puts it.
2. **The layer switch is built from the model's layers**, not from a two-state toggle — two pills on a Freestyle Edge RGB, five on an Advantage 360 (#41) with no change to the view.
3. **Invalid lines are an inline collapsed block**, not the Adv360's modal "Invalid Lines dialog" (spec 10). Same content (04 §5.2), less interruption; `LayoutInvalidLine.Keep` is untouched, so they are still re-serialized as Core decides.
4. **The colour is the cap's whole face on the Lighting board — reversing this entry's own earlier decision.** #91 recorded "the colour overlay is a strip under the caption, not the cap background", because "lighting colour must never compete with remap state". #94 reverses it for one surface and one reason: **a 3 px bar cannot read as a travelling wave.** The design asks that board to animate the mode itself ("the board animates the selected mode at its real speed and direction", mockup 2f), and 95 strips read as a row of ticks rather than as a lit keyboard. So the lighting cap draws three stacked layers over its whole inner area — the hatch, the paint on file at `PaintOpacity` and the sampled effect at `EffectIntensity`, the paint on whichever side of the effect its mode puts it (see above) — and the caption switches to whichever of two variant-independent label roles has contrast with the result. **Nothing competes, because the Keys tab now shows no lighting colour at all**: the strip is gone from it too, so the state ladder and the five badges have that board to themselves and the colour has this one. Both halves are the picture's answer, not the key's (`KeyboardView.ShowsLighting`, `ShowsStateBadges`), since the two boards render the same cap view models. Off is still hatched, never black.
5. **The macro panel is a tab, not a docked strip or a separate window**, and its layout is deliberately plain — spec 10's Adv2 docks it at the bottom and the RGB app opens it in place. The board stays visible beside it because the selected key *is* the trigger; a visual pass over the whole editor is a later change.
6. **The spec 11 dialogs are inline panels over the editor**, not modal windows ([feature-dialogs.md](feature-dialogs.md)).
7. **The settings panel is one list of rows for every device**, not the four different forms of 08 §5.1–§5.4 (a modal dialog on RGB/TKO/Adv360, controls embedded in the main window on FS/Adv2). Same keys, same ranges, one shape — and it is a tab, so nothing is modal and nothing saves as you type.
8. **The status-report slider is always 1–4 plus a "Disable" checkbox** (the §5.1/§5.2 shape). §5.3/§5.4 draw it as a plain 0–4 slider for the FS boards and the Adv2; both write exactly the same values, so one control serves every device. The macro-speed slider keeps its per-device floor, because Core supplies it (`SettingsCapability.MacroSpeedMinimum`).
9. **The RGB/TKO settings panel shows a v-Drive row that §5.1's control table does not list.** It comes from `SettingsCapability.VDriveSetting`, i.e. spec 08 §2's written-by column, where `v_drive` *is* an RGB/TKO key — the panel is capability-driven, so it renders every key the app writes rather than the legacy dialog's subset. Worth knowing because it is also the row with the nastiest failure mode: `v_drive=manual` stops the drive auto-mounting, which is why the panel refuses to save anything until a read has actually succeeded.
10. **"Settings Saved" is a toast, not a modal** — the same deviation the profile save already records. Its wording is Core's `SettingsMessageCatalog` verbatim.
11. **The lighting editor is a tab, not the legacy app's second window mode**, and it has **one Save — the editor's**. Spec 07 §1.3 has the app write layout then led then eject in one sequence; the first two steps are exactly `ProfileSession.Save`, and the third is **deliberately not** — since **#131** no save ejects, and the dashboard card's `Eject` is the only release ([profiles.md](profiles.md), "A save never ejects"). There is no separate "save lighting" action and no `savelighting_msg` notification.
12. **One picker, not two.** Spec 07 §4 describes a shared *dialog* with 10 premixed + 6 custom slots and a *main panel* with 20 premixed + 12 custom. This app has one inline picker with the 10 named swatches (the 20 are never enumerated in the spec) and the full 12 custom slots, because those are the twelve keys `app_settings.txt` actually persists.
13. **The two colour swatches are selectable targets**, not two separate pickers: clicking Effect Color or Base Color points the single picker at it. The spec does not say how the legacy panel routed the picker, and one picker is what fits beside the mode menu.
14. ~~**No animated effect preview** (07 §7) — the mode list is captions only.~~ **Withdrawn** ([#94](https://github.com/migus88/kinesis-edit/issues/94)): the *board* animates the selected mode at its real speed and direction, which is what mockup 2f asks for. What the mode **picker** shows is still captions plus Core's parameter summary — since #128 in a drop-down rather than a list (deviation 58).
15. **No eject button in the editor toolbar**, though mockup `1e` draws one. `docs/design/README.md`'s own law is that *nothing ejects implicitly* and that eject is the dashboard card's deliberate action ([#88](https://github.com/migus88/kinesis-edit/issues/88)); the issue body's toolbar anatomy omits it too. Also recorded in [design-system.md](design-system.md).
16. ~~**The Demo Mode bar carries one action, not the mockup's two.**~~ **Withdrawn** ([#96](https://github.com/migus88/kinesis-edit/issues/96)). The bar now carries both of `1f`'s actions, `Export layout to file…` and `Connect a device`, and the mockup was right all along. The deviation rested on "demo mode opens no session, so `CanExport` is false for exactly as long as the bar is on screen" — true only while demo mode read nothing. A demo board with fixtures opens a real session over the synthetic v-Drive, so Export is live, and it was never a write to the drive in the first place (§11.5 writes to a folder the user picked). The design law it was argued from — *"features a device lacks are not shown, not disabled"* — is satisfied by the button being **enabled**, not by its absence. See "Demo mode reads the fixture drive".
17. **The tab caption is `Layout`, the enum member is `Keys`.** The mockups' caption, and a name the XAML's `EnumMatch` converter parameters are coupled to by string.
18. **The advisory strip is one control, not one per tab.** The design says "one summary strip per tab (max)"; a single row whose sentence and count are the open section's satisfies that with one thing to keep correct instead of four.
19. **A duplicate-key advisory names positions by index, not by place.** Mockup 1e reads *"Esc already exists on the top-left position of this layer"*; no data in this app can produce "top-left" (`KeyVisual` has coordinates, not names), so the sentence is `[esc] is on 2 positions of this layer — 0, 20.` The verbatim half — *"Duplicates are allowed."* — is kept exactly.
20. **The advisory cap badge is drawn, and it is one of four.** `KeyboardKeyViewModel.HasAdvisory` reaches `Border#AdvisoryBar` in `KeyCapButton` — the 12×3 `StatusAdvisoryStrong` rounded bar in the top-right corner — beside the remap bar, the macro dot and the tap-and-hold corner. The design leaves the top-right collision unanswered; this app gives the corner to the advisory bar and steps the macro dot left of it. See "The badge vocabulary".
21. **The Macros/Lighting/Settings strip sentence is this app's wording.** The mockups give copy only for the Layout tab's strip (1e) and for the budget rows themselves (1i); `AdvisoryText.SectionSummary` is built to the same shape so the strip reads the same wherever it appears.
22. **Escape does not "leave capture mode first".** `2b` asks for a two-stage Escape; capture swallows the key and makes it the assignment, because an Escape remap has to be expressible (05 §3). The second stage — closing the panel — is implemented in full. Spelled out under "Escape — the resolution".
23. **~~⌘F opens the §11.6 Search Keys picker, and outside a macro its Ok has nowhere to write.~~ Resolved by #92.** ⌘F now focuses the key inspector's own search field, where `↵` assigns to the selected position — which is what `2b`'s "focus the token search" always meant. On the Macros tab with a macro open it is still the insertion picker. The entry is kept, struck through, because the deviation was recorded and its resolution is part of the record.
24. **The editor view is focusable and takes focus when it is attached.** Not a design decision — a tunnelling handler only sees keys on the chain between the window and whatever holds focus, so without it the whole grammar would be dead until the first click. `IsTabStop` is false, so Tab order is unchanged.
25. **The layer switcher's label ships as `LAYER`, where `docs/design/mockups.md` gives `Layer`.** A copy change, kept: the type scale sanctions 10/600 UPPERCASE mono section labels (`sectionLabel`), and the label sits in a row of them. Recorded here because it is a deviation from the mockup's own wording, not from its type.
26. **`.modified` paints no face, no border and no caption colour — the 2 px accent bar is the whole remap signal.** It used to paint a 14 % accent fill, an accent border *and* lift the caption to the accent, and `.modified` sat in the face ladder. Mockups 1e/2a draw a remapped cap as an ordinary raised cap wearing only the bar (2a, the one board at true mock scale: `background: #EEF0F1; border: 1px solid #C9CFD2` with an absolutely-positioned 2 px accent bar flush along the bottom), and three accent signals for one state on a 26 px cap is noise. `.modified` therefore left the ladder entirely, and `Styles/Keyboard.axaml` no longer carries a `.keyCapText.modified` rule.
27. **`Reset layer` is sentence case**, deviating from spec 10's verbatim `Reset Layer`. The mockups draw the row's actions that way, and the button now lives in that row.
28. **The legend row is scoped to the Layout/Macros board.** The handoff says "every board view carries a legend row"; the Lighting tab's picture draws no state badges (`ShowsStateBadges="False"`), so it counts no states and carries no row. The rule is honoured where state is on screen.
29. **The legend's `Advisory N` is an aggregate, not a third appearance.** Invariant 21 — every advisory appears exactly twice, on its own key and in the summary strip — is about where an advisory is *reported*. This is a tally of how many positions of the layer carry one, the same number the strip's own sentence already names, and it points at nothing.
30. **Both boards lost the outer `Border.keyboardBoard` surround, and the class is deleted.** `KeyboardView` draws its own bordered section panels, and the two together were a visible double frame; the canvas *is* the content area. The Layout board dropped it in #91; the Lighting board kept it only while it sat in a column of controls, and #94 gave it a canvas of its own, so the surround became the same double frame in the same place and the class lost its last call site.
31. **The mockups' board glyphs are substituted with covered text.** Neither embedded IBM Plex family carries `☾` U+263E, `☼` U+263C, `①`–`⑧` U+2460–2467, `▶`, `⏮`, `⏭` or `⌫` — the same coverage gap that forced mockup 1e's `⌕` to be drawn as geometry ([design-system.md](design-system.md)). A keycap legend is **domain data and stays type**, so it cannot become geometry the way an icon can. The substitutes: the hotkey column prints `0 1 2 3 4 5 6 7 8 Fn LED`, and the media keys print `play` / `prev` / `next`. Spec 05 §3.11 names `LED` as its own fallback for `☀`, so that one is the spec's word rather than an invention. `ShapeAndTypeTokenTests.EveryAuthoredKeyLegend_HasAGlyphInBothEmbeddedFamilies` fails the build if any authored legend names a codepoint missing from either family at any weight the scale uses, and a companion test proves the probe is not vacuous by asserting U+263E does *not* resolve.
32. **The sub-legend type step is off the published scale.** `FontSizeKeycapSubLegend` is 7 against the caption's 9; mockup 1e draws 6.5 against 10. Both pairs sit outside the handoff's scale because the scale has **no step for board silkscreen**. It is a token in `Themes/Typography.axaml` all the same — the type scale lives in `Themes/`, and a bare size in a style is the same category of mistake as a hex.
33. **A caption carrying its own line break takes a second step, `FontSizeKeycapLabelStacked` = 8.** The mockups never draw a two-line cap — 2a writes `Caps` and `Shift` on one line at 9, and 30×26 is the box that fits one such line. The app's captions come from the domain data instead, which spells nine of the Edge RGB's in two (`Caps\nLock`, `Page\nDown`; spec 05 §1.1), and two 9 px lines want 23.4 of a 24 px content box, leaving nothing for the LED strip a lighting board draws under them. So a caption that needs two lines is drawn at the step that fits two lines; 8 stays a full point above the silkscreen's 7, and the two never share a cap anyway (no `\n` caption on this board carries a secondary legend). The class comes from `KeyboardKeyViewModel.IsCaptionStacked`, which moves with the caption — remapping `Caps\nLock` to `Esc` puts the cap back on the full step.
34. **The sub-legend is not drawn on a lighting board.** It and the LED strip want the same band under the caption and a 26 px cap has one band to give. Same call, same reason, as the four state badges the Lighting tab already withholds (`ShowsStateBadge`): that surface is about colour. The `Panel` around the legend in `KeyCapView` is what carries it — an invisible panel takes no grid row, so the legend's own "does this position print anything" check stays a plain binding.
35. **The caption's and the sub-legend's line boxes overlap by 2 px, deliberately.** `.keyCapSubText` carries `Margin="0,-2,0,0"`, so the silkscreen's row is 2 px shorter than its own box and hangs up into the leading the caption's last line does not use (Plex reserves 0.275 em of descent below the baseline, and the 7 px legend opens with ~2.3 px of leading above its cap height). It buys two things a 26 px cap has no other source for: the pair costs 20 of the cap's 24 instead of 22, **and the caption sits 2 px lower — out from under the badges.** The advisory bar and the macro dot own the band 2–5 px inside the cap's border, and with the caption leading the stack a cap carrying both a silkscreen and a badge had the mark painted across the top of its own legend. Mockup 1e sets a positive 2 px gap here, but it draws the pair on a 29×31 cap.
36. **Known residual: the stacked caption on a lighting board fits exactly, with nothing to spare.** Two 8 px lines (21 px, after Avalonia rounds a desired size up to the device pixel) plus the 3 px LED strip is precisely the cap's 24 px content box, and the strip therefore carries no top margin of its own — it reads as a gap only because the caption's box ends ~1 px below its last line's ink. There is no fourth thing that could be added to that cap without a step down or a taller cell. `KeycapThemeTests.NoLegendOnTheWholeBoard_IsCutShortByTheBoxItIsDrawnIn` is what holds it: it walks every legend of the real board, on both pictures and in both variants, and fails if any of them is arranged shorter than the text needs at its font's natural metrics.

37. **`Multi-mod` is not drawn on the Freestyle Edge RGB.** Mockup `1e` shows the tab beside a note reading "Multi-modifier is Advantage 360 only", but `handoff.md:137` and issue #92 both say it is "not drawn at all" where the firmware lacks it. The handoff and the issue win; the mockup canvas is illustrating the full tab set. `KeyboardKey.SupportsMultiModifiers` is the flag.
38. **The picker's counter cannot read the mockups' `18/1204`.** Both numbers are derived — the denominator is `KeySearchCatalog.Build(dialect).Count`, which for Gen1 is **200** — and a query for `esc` yields 1 row in 1 group, not the mock's fuller list. The mockups' figures are illustrative; a hard-coded total would be a lie the day a token is added.
39. **`[escape]` is not shown as "alias of `[esc]`", because that alias does not exist.** There is one `KeyDefinition` with two *dialect* tokens, not two registrations. Every **real** alias (a duplicate registration of the same code, 05 §7) shares its canonical's token, so "alias of `[numlk]`" would appear on the `[numlk]` row itself; the row is labelled with the canonical's **name and scope** instead — `Num Lock — keypad layer duplicate`.
40. **`[kp-esc]` and `[hk-esc]` cannot be reproduced.** The mockups show them as scoped result rows ("Keypad layer Esc", "Device hotkey"), but there is **no `kp-`/`hk-` token prefix in the Gen1 dialect** — `kp-` is an Advantage2 layout-file *layer marker*, not a key token. The §3.6 keypad duplicates and the `hk0`–`hk10` hotkeys are real, searchable registry rows listed under their real tokens; the scope labels come from `KeyTable` rather than from an invented prefix.
41. **Mockup `2h` draws the locked panel's copy asymmetry backwards from its own rule.** It draws `Copy from…` live and `Copy to…` dead, which contradicts both its own sentence ("a locked key can still be a copy source, never a target") and mockup `1e`, where the inspector footer's `Copy to…` copies *this* key onto another. Read consistently, the live direction is the one where the locked key is the **source** — `Copy to…` — and that is what is implemented. The semantics are the mock's rule; the drawing is not.
42. **The position header's token is mono, though `1e` draws the header in sans.** `[d]` is literally what `layoutN.txt` contains, and the mono law reserves mono for exactly that. The header's sans half (`Left half`, `position`) is the app talking. No 13/500 step exists in the type scale for the mock's own header face either.
43. **"What it does on the board" is sans, not `2h`'s mono.** A board shortcut is not a value in a config file. Its facts are also spec-correct **per device** (`SmartSet + F8` mounts the v-Drive on the Edge RGB) rather than `2h`'s generic ones, and they come from Core's `DeviceHotkeyCatalog`.
44. **`●` (U+25CF), `↵` (U+21B5) and `⌘` (U+2318) are absent from all seven embedded IBM Plex faces** — verified by parsing their `cmap` tables. The record dot is an `Ellipse`, the assign hint an `Icon` geometry; neither is ever authored as text. Same finding, same treatment, as the board glyphs of deviation 31 and mockup `1e`'s `⌕`.
45. **The `● Record` button sits beside the current-token field, not beside the search field as `1e` draws it.** Two reasons: Record arms keystroke capture, which the reusable picker must not learn about (it is hosted in a modal that has no capture at all); and 244 px of rail content cannot hold a field, a counter and a button on one line without leaving the query box too narrow to read. The pairing that results — a field and the button that fills it — is the one the Tap & hold panel already uses for both of its.
46. **The duplicate advisory in the Remap panel is retrospective, not prospective.** It appears *after* an assignment created a duplicate. The panel contract says read `EditorAdvisories.ForKey` and never rescan, and no Core API offers a per-token prospective scan; a second derivation of one finding would be a second thing to disagree.
47. **§11.1's `Ok`/`Cancel` pair has no rail equivalent.** One `Assign` button, named for what the rail's own exclusivity warning calls the act; nothing is written until it is pressed. A rail is not dismissed by committing.
48. **`Recent` is per-session and in memory, not persisted.** Persisting it is an `app_settings.txt` question — a new key, a parser row, a migration — that belongs with [#96](https://github.com/migus88/kinesis-edit/issues/96); the mockups never require it to survive a restart, and a "recent" list collected on one board would be wrong on the next anyway.
49. **The reduced chip row wraps to two lines at 268 px.** `2a` draws `All · Letters · Nav · Media · Recent` on one line; five chips do not fit 244 px of content, so the `WrapPanel` takes a second. The responsive rule working, not a defect.
50. **At the 680 px default window height the picker's result rows sit below the rail's fold.** The rail's body is a `ScrollViewer` and the rows are reached by scrolling; the preamble alone (tabs, exclusivity, the token field, the query, the chips) is most of a 268 px column at that height. The alternative — no body scroller — would clip the Tap & hold panel outright, which is taller still. Recorded as a known gap rather than fixed by shrinking the rail's own rhythm.
51. **`⌥` (U+2325) is absent from all seven embedded IBM Plex faces too, so the layer switcher's `⌥n` legend is a mark beside a number rather than a string.** Same finding and same treatment as deviation 44's `●`/`↵`/`⌘`, with one difference: this one had nowhere to hide, because a chip printing `⌥1` on macOS drew tofu on the only platform that ever shows it. `Themes/Icons.axaml` gained `IconOption`, traced from the outlines macOS itself ships — the glyph was pulled out of `.SFNS-Regular`, `Menlo-Regular`, `Lucida Grande` and `Arial Unicode MS` with CoreText, and the four agree on one skeleton: a stub at the top left, a diagonal **falling** to the bottom right, a stub along the bottom, and a detached bar at the top right above it. `KeyboardLayerViewModel` therefore splits the legend in two — `ShortcutHint` is the text (`1` on macOS, `Alt+1` elsewhere, `MacShortcutPrefix` deleted) and `ShowsOptionMark` is the flag the `Icon`'s `IsVisible` binds to. The **accelerator is untouched on every platform**: `Input/EditorShortcuts` still maps ⌥ to `Alt`, so only the spelling of the legend moved. `ShapeAndTypeTokenTests.EveryAuthoredChromeString_HasAGlyphInBothEmbeddedFamilies` is what forced it, and what keeps the character from coming back.
52. **`GlyphText` is taken only where the app's own type can print it — which *restores* 05 §3.7/§6 rather than deviating from them; the deviation proper is what code 10019 lands on instead.** §3.7 says the media/LED captions are "Unicode glyphs on Windows 10 and later, otherwise plain text fallbacks", and §6 spells the same rule out as a **capability** gate. The legacy app's escape hatch where a face fell short was a font swap to `'Cambria Math'` (05 §1.1, spec 10 "Fonts, colors, theming"), which this app forbids: its type is the design system's, and a per-key `FontName` override is not on offer. So the honest translation of that gate is **font** capability rather than **OS** capability — `KeyCaption` asks `IGlyphCoverage` and keeps the glyph only where it renders ([design-system.md](design-system.md)). Returning `GlyphText` first and unconditionally, as this app did until [#111](https://github.com/migus88/kinesis-edit/issues/111), was itself the deviation, and it drew tofu on the cap, in the key inspector, in the macro step list, in every co-trigger caption and in the trigger description. Today the gate drops all 17 — none is in any of the seven embedded faces — and the captions become the spec's own text fallbacks: `Mute`, `Vol-`, `Vol+`, `Stop`, `Prev`, `Next`, `Play\nPause` (code 179), `Play` (10044 and 11151), `Forward`, `Rewind`, `Pause`, `Eject`, `Record`, `LED`, `Led+`, `Led-`, `NUL` — identical on every platform and dialect, because no glyph-carrying entry sets `MacDisplayText`. **Words rather than 17 new `Icon` marks**, for a reason that outlives the count: a caption is routinely *composed into a sentence* rather than drawn alone — `MacroLibraryViewModel.BuildSlotHeader` sets it inside `Macros on … · …`, and a macro step row reaches it through `KeyboardKeyViewModel.FormatToken` and prints it beside its modifiers, its action and its delay — and geometry cannot stand inside a string, so the words were needed either way. A mark set would have been a fourth geometry family, a third enum→geometry converter and a changed return type *on top of* them. (When #111 was scoped, the three concatenating sites were `MacroStepViewModel`'s `LS + ▶ ↑`, `MacroListEntryViewModel` and `MacroPanelViewModel.BuildTriggerDescription`; [#93](https://github.com/migus88/kinesis-edit/issues/93) replaced all three while this branch was open, and the argument survived the rewrite unchanged — which is the point of stating it as a property of captions rather than of a file list.) **The genuine deviation is step 4 of the chain**, and it exists for one entry: code 10019 (`[null]`, glyph `⊗`) carries `DisplayText = " "` and spells `NUL` only in `Gen2DisplayText`, so a Legacy or Gen1 cap would fall past the blank check onto the literal token `null` and read as a bug. §3.9's own non-Gen2 fallback is that blank — spec-faithful, and indistinguishable on a cap from an unassigned key — so the Gen2 word is **borrowed for all three dialects** instead. Same finding as deviations 31/44/51, third treatment: those substitute or draw, this one gates. `ShapeAndTypeTokenTests.EveryResolvedKeyCaption_HasAGlyphInBothEmbeddedFamilies` is what forced it and what keeps it closed.
53. **The key cap abbreviates four captions the 1U box cannot hold; nothing else does.** `Forward`, `Rewind`, `Record` and `Play\nPause` are what specs/05 §3.7 calls those keys and what every surface with room still prints — the key inspector's prose, its mono token field, the macro step rows, the co-trigger captions and the macro library's header all resolve through `KeyCaption` and are untouched. Only `KeyboardKeyViewModel.ResolveCaption` runs them through `KeyCapCaption`, which prints `Fwd`, `Rew`, `Rec` and `Play`. Roughly five characters fit a 1U cap at the 9/400 step — the same measurement `Views/KeyCapView.axaml` records for `Pause`, which wrapped to `Paus` in the 24 px box before the negative-margin fix widened it to 28 — and the stacked 8 px step does not rescue them either: `Forward` needs about 35 px there. **The Core table was deliberately not edited**: those words are the spec's, they are what the key is *called*, and shortening them in `KeyRegistry` would shorten them in the macro rows too, where they fit and read better. The cost is the one this trades for: the cap and the macro list call the same key two different things, which `KeyCapCaptionTests.EveryShortenedCaption_IsStillOneTheKeyTableProduces` keeps honest the way the chrome gate's `EveryDeferredChromeGlyph_IsStillNeededByItsView` does. The inspector's `CapCaption` tile follows the **cap**, not the prose, because that tile is a picture of the cap. Found on a rendered frame while verifying deviation 52 — the caps drew `Forwa`, `Rewin` and `Recor` with the whole suite green, which is the case CLAUDE.md's "a green suite is not evidence the screen is right" rule exists for.

## Load-bearing invariants

1. **One visual per device, all layers.** Layers differ only in the tokens bound to a position (05 §7.4), so the picture is rebuilt per layer from the *same* rectangles; a per-layer visual would be data waiting to disagree with itself.
2. **The join is by key index, and mismatches degrade.** `KeyboardVisual.TryGetKey(key.Index, …)`; a miss skips the cap. Core's `Geometry/Visual` tests assert set equality with the logical geometry in both directions, so a mismatch is a data bug caught in CI, not a runtime crash.
3. **Every model write is followed by `RefreshFromModel()`.** Core announces nothing — on the cap (`KeyboardKeyViewModel`), on the layer, and on the macro panel after an outside write. The cap's lighting face is the exception that proves it: it lives in the lighting model, so it is refreshed by `ApplyLighting` — but a lighting write that skips it leaves a stale picture just the same.
4. **Capture is never left running, and the editor owns it.** It is started only by a key entering listening, a macro recording, an armed key-inspector panel, or an armed field of a modal, and stopped on the keystroke, on cancel, on a layer switch, on a tab switch (away from Macros for a recording, on any switch for a listening key or an armed rail panel), on a save, on an import, on a modal opening, and on `Dispose` — which is also the *navigation* path, because the shell disposes the open editor whenever it is replaced. **Never stop a capture you did not start**: `_isInspectorCapturing` is that rule made explicit for the rail, whose `RecordingChanged` also fires on mode switches and selection changes — the app-wide service swallows keystrokes from the whole window while it is on. The macro panel never touches the service; it raises `RecordingChanged` and the editor drives it.
5. **One keystroke, one target.** The subscription to `KeystrokeCaptured` is single and lives here; the precedence (**armed rail panel** → open modal sink → recording macro → listening key) is the one place spec 10's routing rule is written down. A *modal* sink wins on being open, and `ShowOverlay` stands every other consumer down before it appears; a *rail* panel wins only on being **armed**, because the board beside it is still live. That asymmetry is the one behavioural difference between the rail and the modals it replaced.
6. **Escape is a remappable key, not a shortcut** (see "Escape — the resolution") — with one carve-out: an open feature panel that is not itself awaiting a keystroke is always dismissible with it. "Not awaiting" means *both* that no field is armed now **and** that no sink took this very keystroke (`TryTakeOverlayKeystroke`), because the capture service runs above this view and a field disarms as it takes a key. Do not add an accelerator that steals Escape anywhere else, and never let it out of `EditorShortcuts.Map`.
7. **Captured keystrokes go through the editor path, resets through `ClearRemap`.** `Remap` implements 04 §2.1's remap-to-self clearing; `Remap(OriginalKey)` would additionally destroy tap-and-hold and multi-modifiers.
8. **View models expose enums and strings, never brushes** ([app-shell.md](app-shell.md), invariant 6). The overlay travels as `#RRGGBB` and becomes a brush in XAML through `HexColorToBrushConverter`, which converts anything unparseable to `null` rather than throwing inside a binding.
9. **Demo mode never writes to the v-Drive** (03 §3.5) — and that is the whole of it. `SaveCommand` and `ImportCommand` each carry their own `!IsDemoMode`, and neither may lose it; `ConfirmCloseAsync` carries a third. **`ExportCommand` deliberately does not**, because an export writes to a folder the user picked rather than to the drive. Reading is *not* forbidden and never was: the profile, the lighting model, the settings file and the picker's slots all load whenever a `VDriveLocation` exists — which, since [#96](https://github.com/migus88/kinesis-edit/issues/96), includes the synthetic demo drive. `IsDirty` is therefore genuinely true in demo mode after an edit, and the guard against a wrong write is the file service's own path-scoped refusal ([app-shell.md](app-shell.md)), not a mode flag anywhere in this class.
10. **A panel never writes what it did not read.** The settings panel's `HasLoadedSettings` gate exists because its rows have plausible-looking defaults that are pure invention; anything else on this tab that grows a save path needs the same "a read succeeded" flag, not `!IsLoading`.
11. **Keystroke budgets are reported, never refused** — the macro panel shows the breach and lets the edit stand; `Validate()` at save time is what stops the write ([keyboard-model.md](keyboard-model.md), invariant 1). It refuses at input time in exactly three places, all of which `Validate()` would also report: a position that cannot hold a macro (05 §5.3), the co-trigger cap, and the macro count — the counts because there is no meaningful "half-added" macro to leave on screen.
12. **`LoadAsync` is total and idempotent.** The shell fires and forgets it; an escaping exception would be an unhandled crash, and a second call must not re-read the drive.
13. **Adding a device is adding data.** `EditorViewModelFactory`, `KeyboardView`, `KeyCapView`, `KeyboardPanel` and `BoardScaleHost` contain no device identity; only `VisualCatalog` does — and that now covers **how the board is split and what is printed on it** as well as where each cap sits: `KeyVisual.Section` says which panel a key is drawn in and `Legend`/`SecondaryLegend` say what the cap's silkscreen reads. A one-piece board leaves every key at section 0 and the same markup draws it. The macro panel is device-agnostic too — it reads `MacroCapability` and supports both macro stores, and the settings rows come from `SettingsCapability`.
14. **What the panel offers is what the file keeps.** Where the model holds more than the dialect persists — five slots against three, four co-triggers against one, a repeat value the Advantage2 never writes — the panel offers the persisted figure. An edit the next save would silently drop is worse than one the UI never allowed.
15. **The Macros tab lists; the rail edits.** The tab holds no open macro, captures no keystroke and draws no board — every "make or change a macro" action on it ends in `EditMacroAt`, which goes to the rail. A second editing surface for macros is the defect this invariant exists to prevent.
16. **Every path that writes to the model ends in `RefreshCounters()`, and every path that writes to the *lighting* model raises `ModelChanged`.** `IsDirty` is a pull, not a push, so a path that skips either leaves Save grey while the user has unsaved work. This is the same invariant as 3, one level up: 3 keeps the cap honest, this keeps the chrome honest.
17. **Exactly one 46 px bar is on screen while editing.** `ProvidesOwnChrome` + `IsShellChromeVisible` are the whole mechanism; an editor that starts drawing its own bar must set the first, and nothing else may put a second status pill on screen.
18. **The editor reaches the shell through `IShellChrome`, never up the visual tree.** A `$parent[MainWindow]` binding renders blank in every headless scene, which is where this screen is verified.
19. **A tab that exists, works — in the *section* strip.** There is no disabled section tab and no `EditorTabViewModel.IsEnabled`; a section the board cannot carry is simply absent from `CreateAll`. The key inspector's **mode** tabs are the design's own stated exception: a locked position draws all three dead, each with its reason, because the user pointed at that key and a panel that rendered nothing would look broken. `KeyInspectorTabViewModel.Disabled` refuses to build a dead tab without a reason, which is what keeps the exception legal.
27. **One library per profile, and names are session state.** `KeyboardEditorViewModel.MacroLibrary` is the only `MacroLibrary` over the open layout; a second would be a second snapshot. A rename marks the session dirty and reaches `app_settings.txt` only through Save — the one deliberate exception to [settings.md](settings.md)'s "this file is outside the dirty model" — and it goes through `IAppPreferencesStore.UpdateMacroNames`, never a second `LoadAppSettings`/`SaveAppSettings` pair.
26. **The key inspector is never modal, and never collapses.** It does not set, read or otherwise depend on `HasActiveOverlay`; the board stays clickable, `CanBeginRemap` and `CanCopyKey` stay live, and Escape reaches its *selection* only after everything narrower. A change that phrases any rail behaviour in terms of the overlay host has turned it back into the panel it replaced. Since [#119](https://github.com/migus88/kinesis-edit/issues/119) it is also a **permanent column**: nothing may bind visibility — its own or its host column's — to a selection or an open flag, because a column that measures zero is what made the board jump sideways.
20. **No advisory blocks, clamps or refuses anything.** Nothing in `ViewModels/Advisories/` is reachable from a `CanExecute`, a guard or a modal; a layout with advisories saves, and the board truncates. `ReviewAdvisoriesCommand` is the one command with no predicate at all, deliberately. If a future advisory ever needs to stop something, it is not an advisory.
21. **Every advisory appears exactly twice**: a mark on the exact key or row (`KeyboardKeyViewModel.HasAdvisory`; on the Macros tab, `MacroLibraryRowViewModel.BudgetAdvisory` and `MacroSlotViewModel.BudgetAdvisory`, self-computed from the same `MacroLengthMetric`) and one summary strip per tab. A source added to `EditorAdvisories.Build` that no anchor can reach is half-built.
22. **Amber is the only colour an advisory ever has.** No advisory-carrying control resolves to the `StatusError*` ramp anywhere; red means a genuine failure (and the macro Record dot).
23. **Capture outranks the whole keyboard grammar, and so does an open modal.** `IsCaptureActive` and `HasActiveOverlay` are both checked before any shortcut is even looked up. The first is invariant 5 restated for the keyboard: a keystroke that belongs to a listening key, a recording macro, an armed **rail** panel or an armed modal field is never also a shortcut — and the rail's term is the one no other gate covers, because gate 2 never fires for a non-modal surface. The second is the scrim restated for it: what a modal covers, the keyboard may not reach either — including `⌘S`, which would otherwise race the open panel against a background serialization.
24. **An arrow moves the selection and nothing else.** It lands through `SelectKeyDirectly`; `SelectKeyCommand` would promote the second press on the already-selected cap into listening. The same rule `Review N` follows, for the same reason.
25. **The grammar is a pure map plus a dispatcher.** Every platform and modifier decision lives in `EditorShortcuts` and is unit-tested with `isMacOs` as a parameter; the view only dispatches, and respects `CanExecute` on everything it runs. There are no `KeyBinding`s or `KeyGesture`s in this app — a gesture cannot express either gate.
28. **A selector that binds must not write.** Every one-of-N control on this screen — the section strip, both layer switches, the profile drop-down, the lighting mode drop-down — is bound `Mode=OneWay` with its `SelectionChanged` running a command, and **every one of those commands is idempotent by identity**: re-selecting what is already selected returns before it writes. A `ComboBox` raises `SelectionChanged` *while it binds*, and the Lighting tab is hidden rather than unloaded, so without the guard merely opening that tab raised `ModelChanged` and turned `Save` amber over a profile nobody had edited — invariant 16 firing correctly on a write that should never have happened. Nothing on the screen could have noticed: the value written is the value that was already there.
29. **The two rails are two contents of one column, and one width.** Since [#128](https://github.com/migus88/kinesis-edit/issues/128) there is a single `ColumnDefinition`, a single `InspectorRailColumn` and a single `WidthSource`; a change that gives either tab a column, a driver or a number of its own reintroduces the board-moves-when-you-switch-tabs defect #119 and #124 were both about. The column's *existence* is the only thing that varies, and it varies on the open tab alone (`RailHost.IsVisible`), never on a selection.
30. **A profile switch writes nothing.** It is a `Load`, and the outcome is decided before `Apply` — which mutates unconditionally — is called. A refused, cancelled or failed switch must leave the previous session intact, its edits saveable, and must **re-announce `SelectedProfile`** so the one-way-bound control snaps back. Nothing in this path may touch `kbd_settings.txt`: the power-on profile is the Settings tab's slider ([settings.md](settings.md)).

## Deliberately not here

- **Assigning a key from the catalog *is* here now** — the key inspector's Remap panel, where `↵` on a picker row writes the assignment (issue #92). What is still absent is spec 10's categorized *Special Actions* popups (F13–F24, keypad, multimedia, mouse clicks, alt layouts, Hyper/Meh) as a per-key palette, and any right-click menu on a cap; the six category chips plus `Recent` are the app's answer to the same need.
- **No multi-modifier UI (11 §11.2) and no Select Macro dialog (11 §11.4)** — both are Advantage 360 surfaces and follow that board's picture in issue [#41](https://github.com/migus88/kinesis-edit/issues/41). The model supports multi-modifiers, and `ResetKeyCommand` is careful not to destroy them or a tap-and-hold.
- **No Diagnostics report (11 §11.7) or Troubleshoot dialog (11 §11.8) in the editor** — issue [#46](https://github.com/migus88/kinesis-edit/issues/46).
- **No TKO edge-lighting editor and no Advantage 360 indicator editor.** The Lighting tab edits the plain two-layer key-backlight model only (`LightingTabViewModel.IsSupported`: per-key RGB **without** an edge strip = the Freestyle Edge RGB). The TKO's key backlight + 33-zone edge tab needs its board picture first (issue [#40](https://github.com/migus88/kinesis-edit/issues/40)) and the Adv360's six-indicator editor needs its own (issue [#41](https://github.com/migus88/kinesis-edit/issues/41)); both boards' tabs are therefore present but disabled, and Core's `TkoLightingModel`/`Advantage360LightingModel` deliberately do not light the tab up. On those boards an **imported led file** still replaces the session's model without the editor showing it anywhere but the per-key colour strip.
- **No "Lighting Expansion Pack" dialog** (07 §3, §2.6) — `LightingAvailability.HasNoFnLayerLines` and `ExpansionPackDefaults` exist in Core, but nothing offers to mirror the Top layer into Fn or to write the factory pack across all nine profiles.
- **No animated effect previews** (07 §7) and no per-key preview of an effect — the picture shows stored per-key colours only.
- **No `savelighting_msg` suppression** and no separate lighting save — lighting rides the profile save (07 §1.3).
- **No settings beyond the keys spec 08 §2 lists.** The reserved keys (`thumb_mode`, `power_user`, `country`, …) are parsed into state and have no control, as Core intends; there is no eject after a settings save, and **no "Do you want to save changes?" prompt on leaving the tab** — the editor's unsaved-changes guard asks about the profile, and the settings file is outside the session's dirty comparison (see "Settings are outside the dirty model").
- **The profile picker *is* here now** (issue #128) — see "The profile picker": the editor opens `LayoutScheme.FirstProfileNumber` and the tab bar's drop-down moves it to any other of the device's nine. What is still absent is spec 10's **Save As** and **New**: `SaveCommand` always writes back to the slot the session is on, and Export and Import work on that one profile. `ProfileSession.SaveAs` exists in Core and has no consumer ([profiles.md](profiles.md)).
- **No undo buffer.** The unsaved-changes guard is here (see "Leaving with unsaved work"), so no exit drops a dirty *profile* silently any more — but nothing inside the session is reversible: an import, a reset or a captured remap can only be undone by leaving without saving. Two known holes in the guard's reach, both deliberate: a dirty **Settings** tab is invisible to it (see "Settings are outside the dirty model"), and a user who ticks `Don't ask again — always save on leaving` gets a silent save rather than a silent discard, which is the promise that checkbox makes.
- **No `Keyboard Connection Lost` dialog** (03 §3.5) — a drive that vanishes mid-save surfaces as the generic save-error box. Still owned by a later issue, as [app-shell.md](app-shell.md) records.
- **No alternate-layout generators** (Dvorak/Colemak/Workman onto chosen layers, spec 10). Key-data copy/paste **is** here now: `Copy key…` uses `KeyboardKey.CopyFrom` at `KeyCopyScopes.All` (or `KeyData` onto a position that may not hold macros), where the macro panel's own Copy/Paste still uses `KeyCopyScopes.Macros` alone. The key inspector's `Copy to…` and the locked panel's are the **same action** reached from two more places, which supersedes this note's earlier claim that they were different.
- **No per-device visuals beyond the Freestyle Edge RGB** — issues #39–#42, data only. The TKO's 33 edge lighting zones (`KeyCluster.EdgeZone`, `KeyboardLayer.EdgeKeys`) arrive with #40 and are lighting zones, not typing keys.
