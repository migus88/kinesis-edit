# Keystroke capture (Positions, Recorder, Session, Capture Service)

Turns real keypresses into key-table entries for remap and macro recording: physical positions in, `KeyDefinition`s out, with the key event consumed before any control in the window sees it. All decisions live in pure state machines in `KinesisEdit.Core.Input`; the app project holds only a thin `TopLevel` adapter. It is not a global/system-wide hotkey listener, and it does not encode modifiers for files — capture stops at the in-memory keystroke.

Note what "swallowed" means here: the OS has *already* delivered the event to the focused window. Setting `e.Handled` stops the in-app routing (and, backend-dependent, the derived `TextInput` event), so the keystroke never reaches a control or produces text. It does not unhook the OS, and system-reserved combinations never arrive at all.

## Positions — `PhysicalKeyCode`, `PhysicalKeyMap`

- `PhysicalKeyCode` — toolkit-neutral enum of 126 physical positions + `None`. Member names are the W3C `KeyboardEvent.code` names verbatim (which is also what `Avalonia.Input.PhysicalKey` uses); numeric values are this project's own. Only positions the key registry genuinely cannot express are left undeclared (`IntlRo`, `IntlYen`, browser/power/`Lang*` keys); those pass through to the OS.
- `PhysicalKeyMap.Resolve(PhysicalKeyCode)` → `KeyDefinition?` via `KeyRegistry.FindByCode`, so first-match semantics apply (spec 05 §7); `null` for `None` and uncovered positions. `IsModifier(...)` is true for exactly the eight left/right modifier positions.
- Spec-mandated specials: the eight modifiers resolve to their **dedicated** codes 160–165 / 91 / 92 (spec 05 §3.5), never the generic Shift/Ctrl/Alt codes; keypad Enter resolves to internal code **10000**, never main Enter's 13 (spec 10; spec 12 §Programming a pedal step 3); Print Screen → 44, `IntlBackslash` → 226.
- Media/volume positions are declared and map to spec 05 §3.7: `mute` 173, `vol-` 174, `vol+` 175, `next` 176, `prev` 177, `stop` 178, `play` 179, `ejct` 11150. Without them a user pressing Mute to record it would just mute the machine.

## State machine — `KeystrokeRecorder`

`Handle(PhysicalKeyCode, KeyTransition)` → `KeystrokeCaptureResult` (`ShouldSwallow` + optional `Keystroke`); `Reset()` clears held state; `HeldModifiers` snapshots it. It tracks **every** held position (not only modifiers) in the internal `HeldKeySet`, together with a per-position "consumed" flag. Rules, all from spec 10 §Keyboard-input capture unless noted:

- A non-modifier key-down emits the key together with the currently held modifiers, and is swallowed.
- **Auto-repeat never duplicates anything**: a key-down for a position already held is swallowed and emits nothing. The toolkit exposes no repeat flag, so this is recorder-side.
- Print Screen is recognised **only on key-up**; its key-down is swallowed and snapshots the held modifiers, which the key-up then replays — releasing a modifier before Print Screen comes up does not lose it.
- A modifier tapped alone emits on key-up (spec 12 §Programming a pedal step 3). It does **not** emit if it took part in a combination, nor if it was pressed while any other key was already held — an abandoned `Ctrl+Shift` chord emits nothing. Re-pressing a modifier clears its consumed flag, so it can be tapped alone afterwards.
- An unresolvable position passes through untouched on both transitions — but its key-down still consumes the held modifiers, because it is a real physical key press.
- A key-up for a position that is not currently held (a key held before capture started, or one released after `Reset()`) passes through untouched and emits nothing.

`CapturedKeystroke` (record) carries `Key`, the originating `PhysicalKey`, and `HeldModifiers` — deduplicated by key code and **always empty when `Key` is itself a modifier** (spec 05 §5.1), enforced by the type so no caller can build an invalid keystroke.

## Gating — `KeystrokeCaptureSession`

The UI-free owner of *when* the recorder runs, so the rule is testable instead of living in the adapter.

- `Start`/`Stop`/`Suspend`/`Resume` + `SetTextInputFocused(bool)`; `IsCapturing`, `IsSuspended`, `IsExplicitlySuspended`, `IsTextInputFocused`, `HeldModifiers`; events `KeystrokeCaptured` and `StateChanged`.
- `Handle(...)` returns `PassThrough` — nothing captured, nothing swallowed — whenever the session is not capturing or is suspended; otherwise it delegates to the recorder and raises `KeystrokeCaptured` for each completed keystroke.
- **`IsSuspended` is authoritative and computed**: explicitly suspended **or** text input focused. The two sources are independent and neither clears the other; both reset the recorder so nothing leaks into the next recording.
- `Stop` resets the recorder **and** clears an explicit suspension — `Suspend(); Stop(); Start();` must not come back silently deaf. `Resume` on a stopped session only clears the suspension; it never starts capture.
- `StateChanged` fires only when `IsCapturing`/`IsSuspended` actually move, so a UI can refresh its status without polling.

## Adapter — `AvaloniaKeystrokeCaptureService`

- Implements `IKeystrokeCaptureService` by delegating every question to a `KeystrokeCaptureSession`; it re-exposes `StateChanged`. `Dispose` stops and detaches, idempotently.
- Attaches `KeyDownEvent`/`KeyUpEvent` on the `TopLevel` in the **tunnel** phase with `handledEventsToo: true` (both are registered `Tunnel, Bubble`). Tunnel is what makes the window see and consume a key before any focused control — the Avalonia equivalent of spec 10's macOS "main form previews all key events … and consumes the event". `handledEventsToo` is purely defensive: the `TopLevel` is the first node on the tunnel route, so nothing can have handled the event yet.
- Per event: translate `e.PhysicalKey`, push the current focus verdict into the session, feed it, set `e.Handled` **iff** `ShouldSwallow`. No rules of its own.
- Its only platform judgement is "does focus sit in a `TextBox`" (visual-ancestor walk), pushed into the session via `SetTextInputFocused` — before each key event and from `GotFocusEvent`/`LostFocusEvent` handlers on the `TopLevel`, so status updates the moment focus moves. `SuspendOnTextInputFocus` (default `true`) turns that auto-suspend off, which is what lets the harness demonstrate swallowing.
- **That auto-suspend is a safety net and never the answer on its own.** It is *silent*: nothing above the adapter is told, so a surface that arms capture and then lets focus reach a `TextBox` goes on claiming it is recording while the keystrokes go into the box — state that lies. A consumer that **shows** the user it is capturing must therefore stand itself down on text focus rather than lean on this (the keyboard editor does; see the stand-down seam below). What the flag still guarantees is the deterministic half: nothing is captured and nothing is swallowed while the caret is in a field.
- `AvaloniaPhysicalKeyBridge` builds `PhysicalKey` → `PhysicalKeyCode` in one cached, case-sensitive `Enum.TryParse` pass by member name. All 126 declared Core names match Avalonia 11.3.12 exactly, so zero aliases are needed. A future rename gets an alias here, never a rename in Core.

## The consumers — the keyboard editor, its panels, and the pedal editor

`KeyboardEditorViewModel` owns the **single** subscription to `KeystrokeCaptured` for the editor's lifetime and routes each keystroke to exactly one target ([keyboard-editor.md](keyboard-editor.md), "Keystroke routing"): an **open** feature panel that is an `IKeystrokeSink` → a recording macro → the listening key. The sink wins on being open, not on having a field armed — spec 10 forwards a captured key "to the Tap and Hold dialog if that dialog is open". `SavantElitePedalViewModel` is the second consumer ([savant-elite.md](savant-elite.md)), with the same lifetime shape and a single target: `Start()` when an input's entry box opens, every captured keystroke appended to (or, in single mode, replacing) the entry, `Stop()` on Done, Cancel and `Dispose`. One capture service instance is built lazily by `App` over the shell window and shared by every editor; the shell disposes it after the editor.

- **Two things start capture in the keyboard editor, never both at once.** Macro recording (the panel raises `RecordingChanged`; the *editor* calls `Start`/`Stop`) and an **armed Tap and Hold field** (`EditorOverlayHost` follows the panel's `IKeystrokeSink.WantsKeystrokes`) — plus the remap's listening key, which entering either of the other two cancels first. Opening any feature panel ends *both* of the others (`KeyboardEditorViewModel.ShowOverlay` cancels listening and stops recording), so the host always finds the service free and its start/stop bookkeeping is never bypassed.
- **The overlay host never stops a capture it did not start.** It checks `IsCapturing` before calling `Start()` and tracks whether the start was its own before calling `Stop()`, because a macro recording may already own the service and stopping that would silently deafen it ([feature-dialogs.md](feature-dialogs.md)).
- **`Suspend`/`Resume` have two consumers.** Every feature panel that is *not* a keystroke sink — Macro Timing Delays, Search Keys, Export — is opened with an explicit `Suspend()` and closed with `Resume()`, which is spec 10's "capture is suspended whenever a dialog that needs real typing is open"; and the pedal editor wraps every message box it raises — the mid-edit "apply changes?", the unsaved-changes question, the save failure — in the same pair, because a modal window is still inside the `TopLevel` the adapter previews, so an unsuspended capture would swallow the dialog's own Enter and Escape. The keyboard editor wraps nothing of its own: it leans on the presenter's central, depth-counted suspension ([app-shell.md](app-shell.md), invariant 14), which is what makes its unsaved-changes question safe to raise while a key is still listening — the shell asks it on Home, and Home is reachable mid-remap. The adapter's auto-suspend on `TextBox` focus still applies, but it is a platform judgement; the explicit pair is the deterministic guarantee — it is why those panels can be typed into while the editor behind them is mid-edit, and why the pedal wraps *all* of its boxes rather than only the ones raised mid-edit (suspending a stopped capture is a no-op).
- **Recording stands down on any app interaction — `KeyboardEditorViewModel.StopRecordingOnInteraction()`.** One seam, because macro recording is the only editor state that silently claims *every* keystroke in the window, and a user who has moved on must not be left typing into a panel they are no longer looking at. It stands the showing rail panel down (`Inspector.Deactivate()`), which hands the capture service back through the ordinary `RecordingChanged` route; it is **guarded on `Inspector.IsRecording`**, so it is idempotent and announces nothing when nothing moved — without that guard every pointer press in the app would put the service's start/stop bookkeeping through a cycle. `KeyboardEditorView` drives it from three window-level handlers it attaches on the `TopLevel` (and drops again on detach): **`Window.Deactivated`** (the app losing focus — an OS-reserved chord like ⌘Tab never reaches the app at all, so this is what recovers from one), a **tunnelled `PointerPressed`** that consumes nothing and exempts only the showing panel's own record control (`KeyInspectorPanelViewModel.IsRecordingControl` — asked of the `Button`'s *command*, since naming a template part outside `Themes/ControlThemes/` is a bug here; without the exemption the seam would stop the recording on the very press meant to start it), and **`GotFocus` landing in a `TextBox`**, which is the adapter's silent auto-suspend turned into an explicit stand-down (reachable through the §11.3 delay editor's millisecond field, by Tab as well as by click). The pre-existing stand-downs are unchanged and still do their own work: mode switch, editor-tab switch, layer switch, key change, modal open, `Deactivate()` and the panel's own Stop.
- **Capture outranks the editor's keyboard shortcuts, absolutely.** The editor has a shortcut grammar of its own — arrows, `⌥1`–`⌥5`, `⌘F`, `⌘S`, `⌘W` ([keyboard-editor.md](keyboard-editor.md), "The keyboard grammar") — and **none of it is looked at** while any of the three consumers above is live. `KeyboardEditorViewModel.IsCaptureActive` (listening key ∥ recording macro ∥ armed sink) is the gate, and it is checked before the key is even mapped. This is invariant 5 restated for the keyboard: a user assigning `⌘S` to a key must get `s`-with-Meta recorded, not a save, and a macro must be able to record `⌘W` as a step. It is also why the shortcuts are one tunnelled handler on the editor view and **not** `KeyBinding`s: an accelerator fires wherever it is in scope, and this gate is not expressible as a gesture. A panel that merely *suspended* capture (Delays, Search Keys, Export) is not a consumer — the shortcuts are live behind it, which is what makes `⌘S` work while the caret is in its field.
- **The editor's own Escape is a casualty of "swallow everything", by design.** While a key listens — or a Tap and Hold field is armed, or a macro is recording — Escape resolves like any other position and becomes the assignment or the step (a keyboard must be able to carry an Escape remap, and a macro must be able to press one), so dismissal of *those* is a pointer action. The editor view's handler therefore checks the "an armed consumer already took this keystroke" latch **once, for the whole method**: a key somebody has consumed is not also a command, so no stage runs for it. It used to be checked only by the first stage, which meant Escape was appended as a macro step *and* cleared the selection — and clearing the selection refreshes the rail with a new key, which stands the recording down. An **open feature panel is the exception the latch preserves**: with nothing having consumed the event the editor dismisses it on Escape regardless of `e.Handled`, because capture may be running for something else and a panel that cannot be closed from the keyboard is worse. See [keyboard-editor.md](keyboard-editor.md) for the full rule and the tunnel-order reason its Escape handler is a safety net rather than the path. **The pedal editor has no Escape handler at all**: its entry box does not leave the recording state on a keystroke, so an Escape reaching such a handler would be recorded *and* discard the entry — it records Escape like any other key and cancels through its Cancel button.

## Permissions and platform reach (spike findings)

- Avalonia 11.3.12's `KeyEventArgs.PhysicalKey` supplies the left/right modifier distinction natively, so there is **no native interop, no `CGEventTap`, no macOS Accessibility (TCC) permission, and no app-bundle identity work**.
- This beats the legacy app: spec 10 records that the legacy macOS path had to normalize generic modifiers to their left variants because "macOS does not report a generic-modifier distinction usable here". This app distinguishes them for real.
- One implementation covers macOS, Windows and Linux. The legacy Windows `WH_KEYBOARD` low-level hook is unnecessary — it was thread-local and active only while the app had focus, i.e. never a global capture either.
- **Limitation:** capture is focused-window only. OS-reserved combinations (macOS Cmd+Tab, Cmd+Q, Cmd+Space, Cmd+H; Windows Win+L, Ctrl+Alt+Del) are consumed by the OS before the app sees them and can be neither captured nor swallowed. The legacy apps had the same limitation; escalating to a `CGEventTap` would require the Accessibility permission and is deliberately out of scope (re-affirmed by the user on issue #122). What the app does instead is **recover cleanly**: such a chord takes focus away, and the `Window.Deactivated` leg of the stand-down seam ends the recording rather than leaving capture armed for whatever the user does next.
- **Verified status.** Guarded by tests: the Core state machine and the capture/suspend gating (`KinesisEdit.Core.Tests/Input/`). Guarded by the build only: that the solution compiles and that every compiled binding in the harness resolves. **Checked once by hand and guarded by nothing**: that the app launches; the by-name alignment of `PhysicalKeyCode` with Avalonia's `PhysicalKey`; that `KeyDownEvent`/`KeyUpEvent` support `Tunnel`; and that `GotFocusEvent`/`LostFocusEvent` are `Bubble`-only, which is why the focus handlers register `Tunnel | Bubble`. If Avalonia renames a `PhysicalKey` member, no test fails — that position silently becomes `None` and falls through to the OS. Still needs a human at the keyboard: that keys are really swallowed, that left vs right modifiers report distinctly from real hardware, and that focus-based pass-through works. `KinesisEdit.Views.KeystrokeCaptureSpikeWindow` is the issue-#12 harness for exactly that: start/stop, manual Suspend/Resume, live status, a per-keystroke log (code + Legacy/Gen1/Gen2 tokens + held modifiers), and a text box that is a pass-through demo with auto-suspend on and a **swallow probe** with it off (typing produces no text while the log fills). It is kept out of the shipped UI and opens as the main window only on demand: `dotnet run --project src/KinesisEdit -- --keystroke-spike` (no flag → the normal app shell). It builds its own capture service and touches no other app service.
- **The spike window is not exempt from the design system.** Issue #85 proposed exempting it as dev-only; it was put on the tokens instead — its one hardcoded grey (`#40808080`) is now `SurfaceLineBrush` and its radius `RadiusControl`, so it follows the OS theme like every other window. "Never hardcode a hex in a view" has **no** development-only carve-out, and `ResourceReferenceTests.NoView_HardcodesAHexColour` covers this file too. It is also constructed and rendered under both theme variants by the headless smoke suite (as one of the two views allowed a null `DataContext`, since it is self-contained) — see [design-system.md](design-system.md).

## Load-bearing invariants

1. **All decisions in Core.** The adapter only translates, judges focus, and marshals; anything with a rule in it belongs in `KeystrokeRecorder` or `KeystrokeCaptureSession`, which are unit-tested. This is what keeps the untested UI layer defensible.
2. **Physical position, never character.** Capture reads `PhysicalKey`, so the recorded key is layout-independent and left/right modifiers stay distinct (spec 10).
3. **Swallow only what is understood.** `ShouldSwallow` is false for unresolvable positions *and* for a key-up the recorder never saw go down; the app must never eat a key it did not record.
4. **Suspension is total.** While suspended (explicitly or by text focus) nothing is captured and nothing is swallowed (spec 10), and `IsSuspended` reports both sources.
5. **Keypad Enter ≠ main Enter.** Code 10000 vs 13 — a distinction the whole capture chain must preserve (spec 10; spec 12).
6. **A key that capture can claim is never also an app shortcut.** Anything registering a keyboard handler above or beside this service must stand down while it is capturing; the editor does it with `IsCaptureActive`, and it is the reason the app has no `KeyBinding`/`KeyGesture` accelerators at all. The corollary is Escape: it is a remappable position, so it is *assigned* or *recorded*, and cancelling a remap or ending a recording is a pointer action ([keyboard-editor.md](keyboard-editor.md), "Escape — the resolution").
7. **A surface that says it is capturing must never be wrong about it.** Suspension is invisible to the user, so anything that draws a recording banner stands *itself* down when the keyboard stops being its own — text focus, a pointer press elsewhere, the window losing focus — rather than relying on the adapter's silent auto-suspend. "Suspended while claiming to record" is the one capture state the app refuses to produce.

## Deliberately not here

- **No modifier-string encoding.** The spec 05 §5.1 two-character form (`'LS'`, `'RC'`, `'S '` — the trailing space is load-bearing) is a file-format concern for the parser/serializer work; capture emits `KeyDefinition`s.
- **No routing.** Deciding whether a captured key becomes a remap, a macro step, or a Tap-and-Hold action (spec 10 §Routing; spec 11 §Tap-and-Hold) is the editor's job, and all three legs now exist — see [keyboard-editor.md](keyboard-editor.md) for the precedence and [feature-dialogs.md](feature-dialogs.md) for the panel side. This module still knows nothing about any of them: it emits `CapturedKeystroke`s and nothing else.
- **No global capture.** See the limitation above — focused-window only, by design.
- **No pedal specifics.** Spec 12's single-action vs macro edit modes, its Special Actions menu and its `␣` display rule are pedal-editor behaviour built on top of this service — this layer only hands it `CapturedKeystroke`s. See [savant-elite.md](savant-elite.md).
