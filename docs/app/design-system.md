# Design system (Themes, ControlThemes, Styles, Assets/Fonts, motion, icons, the headless test harness)

The implementation of `docs/design/` inside `KinesisEdit`: the colour/shape/type/motion tokens as Avalonia resources, the drawn marks (state icons, device silhouettes, lighting-mode marks) and the leaf control that paints them, the **control-theme layer** that templates every shape the app draws itself, the shared style layer built on them, the two embedded IBM Plex families **and the runtime probe of what they can print**, the reduce-motion switch, and the headless UI test harness that guards all of it. `docs/design/` states the laws; this doc is how they are spelled in the app, plus every place the implementation deliberately differs and why.

**Read this before touching any view, style or user-facing string** — together with `docs/design/README.md`, which is the design source and must never be rewritten to match the code.

They are different kinds of file (`ResourceDictionary` vs `Styles`) merged in different places, so a change made in the wrong one resolves to nothing. `IconCatalogTests.BothIconFiles_AreVisibleToTheseGuards` asserts the test harness reads both and that they differ.

`App.axaml` is **composition only** — 96 lines: data templates, converters, `FluentTheme`, the ColorPicker style include, the fourteen `ResourceInclude`s and the seven `StyleInclude`s. It defines no colour, no size and no style, and it must stay that way.

## How a view consumes it

1. **Name a role, never a value.** `{DynamicResource SurfacePanelBrush}`, never `#16191C`. A hex literal in any file outside `Themes/` is a bug and fails `ResourceReferenceTests.NoView_HardcodesAHexColour`. (The lighting picker's swatches are the one legitimate colour-from-data case and go through `HexColorToBrushConverter`, not through markup.)
2. **`DynamicResource`, not `StaticResource`, for anything theme-dependent.** The app follows the OS variant (`RequestedThemeVariant="Default"`), and a `StaticResource` snapshots one variant at load.
3. **Every colour role is a pair.** `<Role>Color` is a `Color`, `<Role>Brush` the `SolidColorBrush` built from it. Use the brush for `Background`/`BorderBrush`/`Foreground`; the `Color` half exists for `GradientStop`, animation, and for the Fluent keys that are typed `Color`.
4. **Every key exists in both variants.** Asserted, not assumed — see `TokenCompletenessTests`.
5. **Type = scale class + role class.** `Classes="meta muted"` composes the 11/400 sans step from `Themes/Typography.axaml` with the muted foreground from `Styles/Text.axaml`. The scale never sets a colour; the role never sets a size (except `.badge` and `.rowCaption`, which are single-purpose).
6. **Name a class, never a template part.** `Classes="primaryAction"` is the authoring API; a bridge style in `Styles/` points that class at a `ControlTheme` which owns the template and the whole state matrix. A `/template/` selector outside `Themes/ControlThemes/` is a bug and fails a test — see "The control-theme layer".

Two laws that decide which token you are allowed to reach for:

- **The mono law.** *"Mono is reserved for values that exist verbatim in the config file — tokens, delays, drive paths, counters. Sans for everything the app says in its own voice."* If the string is not something a user could find by opening the file on the v-Drive, it is sans.
- **The accent law.** The accent means **exactly two things**: *selection/focus*, and *"you changed this"*. It is not a decoration, not a brand colour, and not "the important one". `Button.primaryAction`, the selected layer pill, the selected tab underline, a modified key cap and the `.badge` tag are the sanctioned uses.

## Colour token registry — `Themes/Tokens.axaml`

47 roles (each a `Color`+`Brush` pair) plus 5 `BoxShadows` = **99 keys per variant**, plus the 4 variant-independent keys declared outside the two dictionaries (the lit-keycap label pair). Counted from `Themes/Tokens.axaml`, not from this sentence's history: `MacroStepKey` arrived with #122 and `AccentKeyRing`/`KeycapRingEdge`/`ShadowKeyHaloStrong` with #128, and the line was one role stale before the last of those. `TokenCompletenessTests` asserts the two variants carry identical key sets; it does not assert the count, so this number is documentation and has to be re-counted when a role lands.

One of the two therefore always contrasts with whatever is underneath, which is the whole reason there are two, and is what no single colour can promise against a value the user chose. Verified on a frame lighting caps navy, white, red, green and `#5B9DF9`.

### Badge hues — variant-independent

They sit on a key cap, not on the window, so they do not flip.

| Role | Value | Use |
|---|---|---|
| `BadgeMacro` | `#C77DD8` | Macro dot, top-right of a cap (5 px) |
| `BadgeTapHold` | `#35A26D` | Tap-and-hold right-triangle, bottom-right (~6 px) |
| `BadgeLightingPreview` | `#57C4D8` | Lighting-preview cyan |
| `BadgeLed` | `#B58CF6` | LED purple |

`BadgeLed` and dark `StatusDemo` are the same colour under two role names, deliberately: neither call site should have to know about the other. They part company on light, where the *status* hue darkens for contrast and the badge does not.

### `MacroStepKey` — the key struck in a macro step row

| Role | Dark | Light | Use |
|---|---|---|---|
| `MacroStepKey` | `#C77DD8` | `#8E45A0` | The pressed key's token in a macro step row (`01 [lshift] press`), so it reads distinctly from the muted modifiers and action words beside it |

**The hue is `BadgeMacro`'s, and that is the whole argument.** Purple already means *macro* in this app — it is the dot a cap wears when it carries one — so the token in the step list and the mark on the cap say one thing in one hue, and the row invents no fifth meaning. On dark it is `#C77DD8` to the letter; `TokenValueTests.TheMacroStepKeyTint_IsTheMacroBadgesOwnHue_AndPartsFromItOnLight` pins both halves of that.

It is a **separate role** rather than a reuse of `BadgeMacro` because the two are different things doing different work: a badge is a 5 px shape on a keycap and is variant-independent, while this is *type* on a near-white row, where `#C77DD8` measures 2.9:1 and is unreadable. So light darkens it to `#8E45A0` at the same hue (288°) — the move the status hues make, for the same reason, and the same way `StatusDemo` and `BadgeLed` part company.

What it is **not**, and why: not `Accent` (the accent has exactly two sanctioned meanings, selection/focus and "you changed this" — a key token is neither); not `StatusAdvisoryText` (amber is the only advisory colour in the app); not red and not a link ramp. And it is a **tint, not a shout**: 6.2:1 on `SurfacePanel`, 6.4:1 on `SurfaceInset`, 5.3:1 on `SurfaceRaised` (dark) and 6.0 / 5.5 / 5.2:1 (light) — above the muted text beside it at 4.7:1 and well under the primary step at 14.7:1. `TokenValueTests.TheMacroStepKeyTint_StaysLegibleOnEveryRowSurface` asserts both bounds on every row surface in both variants, so a re-tint that made it either illegible or the loudest thing in the row fails.

### Lit keycap labels — variant-independent, and declared outside the variant dictionaries

The two roles the Lighting board's caption is drawn in. They are the only colour keys in `Tokens.axaml` that sit in the **plain** dictionary rather than in `Dark`/`Light`.

| Role | Value | Use |
|---|---|---|
| `KeycapLitLabelDark` | `#14181B` | The caption on a **light** fill — the light theme's `TextPrimary` |
| `KeycapLitLabelLight` | `#E8EBED` | The caption on a **dark** fill — the dark theme's `TextPrimary` |

Since issue #94 the lighting board paints a key's colour on the cap's **face**, and that colour is device data: a key can be lit near-white or near-black, and either erases a caption drawn in a theme role — under *both* variants, because the fill is the same colour in both. So the caption takes its colour from the fill instead, and the choice is one no theme dictionary can make. The two values are the app's two `TextPrimary` colours, so a lit caption is never a new colour, only one of the two primaries chosen by the fill rather than by the OS.

`Converters/LitLabelBrushConverter` picks between them at the sRGB relative luminance where a fill's WCAG contrast against black equals its contrast against white — `L = sqrt(1.05 x 0.05) - 0.05` = **0.1791**. Above it the dark label, below it the light one. The fill it is handed is the **softened preview** the face is really painted with rather than the colour on file — see "The hatch tile" — which is the whole reason the softening is applied upstream of it. Three rules ride with it: the **picture** decides whether the fill decides anything at all — `ShowsLighting` is handed to the converter as a fifth value, and a board that draws no lit face converts to `AvaloniaProperty.UnsetValue` whatever colour the key carries (**#131**; a value and not a style, because a local binding on `Foreground` outranks every style setter); a fill covering **less than half** the cap (the 40 % paint wash) is treated as unlit, because what the eye reads there is mostly the hatch; and an unlit cap converts to `AvaloniaProperty.UnsetValue`, so the binding produces nothing and the caption falls back to the ordinary token its style names.

The converter is **handed the two brushes from markup** (`KeyCapView.axaml`'s own `Resources`) rather than resolving them by key: a key resolved in C# is invisible to the markup guards, and a converter is not a `StyledElement`, so a `DynamicResource` on it has no resource host to walk — the same constraint the hatch tile records. Both roles being variant-independent is what makes the `{StaticResource}` there correct.

They are declared once rather than twice for the same reason: a role that is identical in both variants declared in both is two places to change one colour. `TokenCompletenessTests` reads only the variant dictionaries, so these are invisible to the "both variants carry the same roles" guard — which is right, because there is nothing for them to differ about. The badge hues are the counter-example and stay inside the variant dictionaries: they *do* diverge from their status neighbours on light.

**All five keycap badges are drawn**, every one of them a part of the `KeyCapButton` template (`Themes/ControlThemes/Keycap.axaml`): `Ellipse#MacroDot` in `BadgeMacro`, `Path#TapHoldMark` in `BadgeTapHold`, `Border#RemapBar` — the 2 px accent bar along the bottom edge — in `AccentBrush`, `Border#AdvisoryBar` — the 12×3 rounded bar top-right — in `StatusAdvisoryStrong`, and the locked cap's 45° hatched fill + dashed border (`Rectangle#Locked`; see "The hatch tile"). Sizes come from `Themes/Geometry.axaml`'s `Badge*` tokens. Each is restated at legend size in `Views/BoardLegendView`, out of the same token brushes, so a hue that moves moves in both places.

### Elevation and scrim

| Role | Value (both variants) | Use |
|---|---|---|
| `Scrim` | `#9E080A0C` | Modal scrim, `rgba(8,10,12,0.62)` |
| `ShadowPopover` | `0 8 24 0 #80000000` | `Border.overlayCard` |
| `ShadowModal` | `0 24 60 0 #99000000` | `Border.overlayCard.modalCard` |
| `ShadowFocusHalo` | `0 0 0 3 #475B9DF9` | Focus ring — spread only, never an offset outline |
| `ShadowKeyHalo` | `0 0 0 2 #4D5B9DF9` | **The handoff's** selected-keycap halo. Declared, pinned by `TokenValueTests`, and **worn by nothing** since #128 — kept so the specified value stays visible beside the shipped one |
| `ShadowKeyHaloStrong` | `0 0 0 3 #5B9DF9, 0 0 0 1 #14181B` | The ring a selected key cap actually wears |

`ShadowKeyHaloStrong` is **the one entry here that is two shadows rather than one**, and the order is load-bearing: Skia draws outer box shadows **in list order**, so the last entry paints on top, which is what puts the 1 px `KeycapRingEdge` hairline *inside* the 3 px accent band rather than under it. The result is 2 px of opaque accent with a near-black hairline inside it, all of it drawn **inward** from the cap's own edge — see "Focus + selection on a key cap" for the geometry that makes that true, and the deviations table for why it is not simply a louder `ShadowKeyHalo`. `TokenValueTests` pins both values and asserts the shipped ring is fully opaque, two-toned, blur-free and unoffset.

**Flat elevation is a 1 px `SurfaceLine` border and no shadow at all.** Only a surface that genuinely floats casts one, and then it casts `ShadowPopover` or `ShadowModal` — never an invented shadow. The shadows are the same in both variants: dimming a light window uses the same near-black at the same alpha.

**A drag in flight is the one place elevation carries a *meaning*.** The macro step list's carried row lifts onto `SurfaceRaised`/`SurfaceBorderRaised` with `ShadowPopover` while its source dims to 0.35 in place ([keyboard-editor.md](keyboard-editor.md) § "The Macro panel"). That is a **third** vocabulary beside the accent's two — deliberately, because "this row is being carried" is neither *selection/focus* nor *"you changed this"*, and painting it in the accent would have collided with the drop ring, which really is about where a selection lands. It reuses the existing popover elevation rather than adding a token, and nothing about it animates: the ghost is pinned to the pointer, so the motion budget is untouched.

## The four-status vocabulary

`ViewModels/StatusSeverity` is the single enum; views map it to classes through `EnumMatchConverter`. View models never expose brushes.

| `StatusSeverity` | Hue | Means, and only this | Chip class | Text class |
|---|---|---|---|---|
| `Ok` | green | Connected and writable | `.ok` | `.statusOk` |
| `Error` | red | Gone or unwritable | `.error` | `.statusError` |
| `Demo` | purple | Nothing is written — demo mode | `.demo` | `.statusDemo` |
| `Warning` | amber | An advisory: over a limit. Never blocks. | `.warning` | `.statusWarning` |
| `Unknown` | — | Nothing known yet; renders unfilled | (none) | (none) |

- **Amber is the only warning colour.** An advisory is never red. Red is reserved for genuine failure — and for the macro Record dot. Two call sites that could have got this wrong and do not: a toast reporting advisories takes `ToastSeverity.Advisory` (amber dot, amber border) and there is deliberately **no error toast at all** — a failure is a message box the user must answer, never a notice that vanishes; and the editor's post-save toast switches to the advisory face when the profile carries any, instead of shipping "saved with N advisories" on the green one.
- **Demo mode is not a warning.** It is a different thing the app is doing, not a degraded version of working, which is why it gets its own hue and its own enum member rather than borrowing amber.
- **`Error` means "gone **or** unwritable", and "gone" includes "nothing there".** A *completed* scan that found no drive puts the shell chip on `Error`, not on `Demo`: `1a` writes the red state as "gone · unwritable" and `1d` draws the chip that way beside the empty state. `Demo` is reserved for a session that writes nothing. The only exception is the instant before the first scan completes, which stays `Unknown` → `Demo` because "gone" is a finding and there is not one yet ([app-shell.md](app-shell.md)).
- The three `…Text` roles exist because text on a tint needs to be a step further from the tint than the fill colour is. Demo has no `StatusDemoText` — the design source names none — so it labels its chip with the fill colour. Measured: `StatusDemo` on `StatusDemoTint` is 5.1–6.1:1 on dark and **4.2–4.6:1 on light**, depending on the surface behind the chip, where the three roles that do have a text token reach 4.7–5.9:1. The light end sits on the AA boundary rather than clear of it; adding a `StatusDemoText` is the fix if demo mode ever moves onto a lighter surface.

`TextBox.monoValue` is **not** a scale class: a `TextBox` is not a `TextBlock`, so the `:is(TextBlock)` selectors cannot reach it, and the thing it names is a whole control rather than a type step. It bridges to the `MonoValueField` control theme, which carries the mono family and size together with the quiet inset face a table of typed values wants.

Two implementation notes that are not free choices:

- **No style sets `LineHeight` to the font size.** The design's "line-height 1" is the CSS meaning — *add no leading*, glyphs may overflow — but Avalonia **sizes** the line box, pins the baseline at the font's own ascent below its top, and draws nothing past `nLines × LineHeight`. So a literal `LineHeight == FontSize` cuts the descenders off every label in the app. Single-line styles set no `LineHeight` at all and take the font's own metrics (Plex: 1.3 em, ascent 1.025, descent 0.275, no line gap), which is the honest equivalent. Only the two prose styles set one.

  **This rule has been broken once, and it cost the whole keyboard.** `Styles/Keyboard.axaml` set `LineHeight="9"` on the 9 px keycap caption and `LineHeight="7"` on the 7 px silkscreen, quoting the mockups' `font: 400 9px/1` as authority. At 9 px Plex's baseline alone lands 9.225 px down, so a 9 px box cut *above* it: `Esc` read `Fsc`, `Space` read `Snace`, `Q` read `O`, `LED` read `I FD`, and the second line of `Caps\nLock` was gone. **~5 300 tests passed while it did**, because a cropped label desires exactly the box that is cropping it — nothing that asks a control about itself can see the defect, and only a captured frame showed it. The guard that closes it is `KeycapThemeTests.NoLegendOnTheWholeBoard_IsCutShortByTheBoxItIsDrawnIn`, which compares every legend's *arranged* height against a fresh `TextLayout` of the same text at the font's natural metrics. Write that comparison, not an assertion about the setter, for any surface that puts type in a fixed box.
- **`LetterSpacing` is in pixels, not em.** The one tracking rule in the design (0.10–0.14 em on the 10 px uppercase section labels) is pinned to 0.12 em → `LetterSpacingSectionLabel` = 1.2. Avalonia has no text-transform either, so section-label text is authored uppercase at the call site.

**`.keySymbol` is a role too**, and lives in `Styles/Text.axaml` for the same reason `.stepNumber` does: the published scale has no step for "a mark out of a third face", and what the class names is a *meaning* — a key, spelled — rather than a size. It sets the family, `FontSizeKeySymbol` and weight Normal (the family ships one face; a bolder request would be synthesised or substituted) and **carries no colour**, so a call site writes `Classes="keySymbol muted"` and the mark reads exactly as quiet as the words beside it.

`FontSizeKeySymbol` (9) is **arithmetic, not taste**. A mark has no x-height relationship with the mono text beside it, so the only honest match is cap height: the subset's `⇧` and `⌘` top out at **0.754 em** (DejaVu draws its key marks above cap height) against IBM Plex Mono's **0.698 em**. Set at the same size as the 10 px `monoValueSmall` run they sit in, the marks would stand ~8 % taller than the `R` letter beside them and read as a size shout; 10 × 0.698 / 0.754 = 9.26, so 9 — at which the mark's cap is 6.79 px against the mono cap's 6.98 px. It deliberately does not borrow `FontSizeKeycapLabel`, which is also 9 and means "a legend printed on a key cap".

**Only the mark goes in `.keySymbol`.** The `R` prefixing a right-hand modifier is a Latin letter and is *not* in the subset, so a whole `R⇧` set in that class falls back to a system font for its `R`. That is why `ViewModels/MacroModifierMarks` hands out the side letter and the mark as **separate parts** (`Mark.Side`, `Mark.Symbol`) as well as a joined `Text`: a view draws two runs in two faces, and the joined string is for single-face contexts only (tooltip, automation name, log).

**Left is unmarked; only the right side is spelled** — `LS` draws a bare `⇧` and `RS` draws `R⇧`, so `Mark.Side` is empty for a left *and* for a generic modifier and the two draw identically. That collision is deliberate (the reasoning, and the tooltip that keeps the file's real distinction reachable, are in [keyboard-editor.md](keyboard-editor.md) § "How a row spells a held modifier"); what it means for this layer is that **half the marks are a single run**, and a view therefore binds the side run's visibility to `Mark.HasSide` rather than assuming two runs per modifier.

**`.stepNumber` is a role, not a scale step**, and lives in `Styles/Text.axaml` beside `.badge` and `.rowCaption` for the same reason they do. It is the "1." "2." "3." of a numbered instruction — today the empty state's connection steps, which mockup `1d` draws at 10/500 mono inside a small tile — and it names the family, the `FontSizeSectionLabel` 10 px step, weight 500 and `TextBodyMuted`, with **no tracking**. It could not reuse either neighbour: `.monoValueSmall` is the same size but *means* "a value that exists verbatim in a config file", and a step number is the app counting in its own voice (the same argument that gave the logo mark its own size); `.sectionLabel` is 10/600 with 1.2 px of tracking, and tracking is trailing space, which pushes a single centred digit visibly off-centre in a 20 px tile. The tile itself is a surface role (`Border.stepMarker`), not a type one.

`FontSizeLogoMark` (10) is not a step of the scale: it is the "K" of the app mark, alone in the app at weight 700 and alone in being mono type that is **not** a value out of a config file. The handoff grants the weight to exactly this glyph (`handoff.md:86`, "700 only for the tiny logo 'K'") and draws it at 10 px inside an 18 px accent tile (`Border.logoTile`). It stays type rather than becoming a geometry — a wordmark is not one of the three icon families — and it does not borrow `FontSizeMonoValueSmall`, which means "a config value in a tight place".

## Icons and device art — `Themes/Icons.axaml`, `DeviceArt.axaml`, `LightingMarks.axaml`, `Controls/Icon.cs`

The law, verbatim (`handoff.md:162`): **"16px grid, 1.5px stroke, square caps, geometry only."** Nothing in the app is a raster icon, an icon font or a Latin-1 character standing in for one.

### The three families

| Dictionary | Keys | Naming law | Enumerated by |
|---|---|---|---|
| `Themes/Icons.axaml` | 20 | `Icon<Name>` | The 16 state/action/chrome marks are fixed and listed in `IconCatalogTests`; the 4 arrows are enumerated by `LightingDirection` in `IconCoverageTests` |
| `Themes/DeviceArt.axaml` | 7 | `DeviceArt<DeviceId>` | `DeviceCatalog.All.Where(IsProgrammable)` |
| `Themes/LightingMarks.axaml` | 16 | `LightingMark<LightingMode>` | every `LightingMode` member |

All three are plain `ResourceDictionary`s with **no `ThemeDictionaries`** — a shape does not change when the OS flips — merged in `App.axaml` after `Motion.axaml` and before `Controls.axaml`. **They carry no colour and must never carry one**; `IconCatalogTests.NoMarkDictionary_DeclaresAColour` scans the markup for hex and named colours. The call site names the token brush.

- **`Themes/Icons.axaml`** — `IconConnected` (the ring) + `IconConnectedCore` (the dot: two `Icon`s in one cell, because one geometry cannot be both stroked and filled), `IconNotDetected` (the same ring, dashed **by the pen**), `IconCannotAccess`, `IconWarning`, `IconError`, `IconInformation`, `IconConfirmation`, `IconEject` (fill), `IconClose`, `IconRefresh`, `IconExternalLink`, `IconOption`, `IconScanning`, and the four direction arrows `IconArrowLeft`/`Right`/`Up`/`Down`. The seven ring marks are built on the same circle — centre (8,8), radius 7 — and `IconEject` is centred on it too, so a chip's mark sits on the same baseline whichever state it is in. The circle is written out per key rather than shared through an alias, so one mark can diverge later without disturbing the others. `IconEject` and `IconConnectedCore` are the only fill-only marks. **Issue #93 added two, both because the mock's own characters are unprintable here**: **`IconDragHandle`** is the reorder grip mockup `2i` writes as `⠿` (U+283F) — six r=1 dots on columns x=6/x=10 and rows y=4/8/12, and the family's only **fill-only** mark besides `IconConnectedCore` and `IconEject`, because stroking six dots draws six rings; and **`IconInsert`** is the `＋` of its trailing "insert step" row (U+FF0B), two 8-unit strokes on the same 4..12 span as `IconClose` and `IconExternalLink` so the three read at one weight in a column of rows. It is deliberately *not* `IconClose` rotated: they are the same two segments at different angles, and a `+` authored as an `×` would be a dismiss mark wherever a style forgot to rotate it. `IconScanning` is the one mark **not** on the 16 px grid: it is authored in a **14×14** box centred on (7,7), because `SpinnerSize` is 14 and the rotation has to turn about the arc's own centre. The three marks issue #89 added are the ones a call site is most likely to confuse with a neighbour, so each says what it is *not*: **`IconClose`** is the bare cross of a dismiss affordance, deliberately **not** `IconError` (the same cross *inside the shared ring* — the ring is what makes that mark a state, and a dismiss button wearing it would read as "this toast is an error"); **`IconRefresh`** is the static rescan mark, a 290° circular arrow, deliberately **not** `IconScanning` (which is the busy spinner, authored lop-sided in its own box and spoken for by `.spinner`) — this one never moves, so it is drawn balanced on the 16 px grid; **`IconExternalLink`** is the ↗ that ends a link leaving the app, geometry rather than a character because the law leaves no alternative. **`IconOption`** (issue [#109](https://github.com/migus88/kinesis-edit/issues/109)) is the `⌥` of the layer switcher's `⌥1`–`⌥5` legends, for the same reason: U+2325 is in none of the seven embedded Plex faces. Its shape is **traced, not invented** — the glyph was read out of `.SFNS-Regular`, `Menlo-Regular`, `Lucida Grande` and `Arial Unicode MS` with CoreText, and all four agree on one skeleton (a stub at the top left, a diagonal **falling** to the bottom right, a stub along the bottom, and a detached bar at the top right that overhangs it), so the mark follows it at those faces' average proportions, centred on (8,8) like the rest.
- **`Themes/DeviceArt.axaml`** — one plan-view drawing per programmable board, every one authored in the same **92×56** box with the board centred in it, so in those coordinates the seven are at true proportion *to each other* (`IconGridTests.EveryDeviceArt_IsCentredInTheSharedBox`). Each path opens with `F0` (EvenOdd), so the key rects punch out of the body when the drawing is filled. The two catalog entries that are not programmable — the never-shipped CROSSFIRE keypad and the web-configured Advantage 360 Professional — deliberately have **no art**, and the frame that would hold it is hidden rather than drawn empty.
- **`Themes/LightingMarks.axaml`** — one mark per mode, drawing the *motion* rather than the name. Three are **filled** (`Freestyle`, `Monochrome`, `Breathe`); the other 13 are **stroked**. `LightingModeMarkConverter.IsFilled` is the single source of that split.

### The authoring-box rule — why `Icon` fits the box, not the ink

`Icon` scales its geometry by its `SourceBox` (the coordinate box the mark was drawn in), **never** by `Geometry.Bounds`. This is the whole point of having a grid:

- The marks are deliberately inset from their box by different amounts (`IconConnectedCore` is 5.6 units wide; the rings span 1–15). Fitting each one's ink would blow every mark out to the same extent and destroy both the shared centre and the relative weights the set was drawn with.
- `IconScanning`'s ink is lop-sided on purpose — the right quadrant is missing — so ink-fitting would re-centre the arc and the spinner would **wobble** as it turned. `IconGridTests.TheScanningMark_IsLopsided_WhichIsWhyEveryMarkDeclaresItsBox` asserts that lop-sidedness so the rule stays load-bearing.
- A pedal and a contoured board share one 92×56 box; fitting each to its own ink would make them the same width.

Fitting is **uniform and centred**, so a non-square `SourceBox` is letterboxed rather than stretched, and `MeasureOverride` reports the letterboxed rectangle rather than a square with dead margins. A `SourceBox` with no extent falls back to the geometry's bounds — the deliberate escape hatch for a mark with no box of its own.

**The pen does not scale with the geometry.** `StrokeThickness` is a thickness at the *rendered* size: the pen is built at `StrokeThickness / scale` inside the fit transform, so 1.5 measures 1.5 whether the mark is drawn at 16 px or at 92. `StrokeDashArray` inherits that for free, because Avalonia's dash lengths are multiples of the pen width.

`KinesisEdit.Controls.Icon`, a leaf `Control` — no template, no children, no motion of its own.

| `Data` | null | The `Geometry`. Null draws nothing and measures zero. |
| `Stroke` | null | Outline brush. Bind with `{DynamicResource}`. |
| `Fill` | null | Fill brush. |

Square caps and mitre joins are **fixed by the control** (`Icon.StrokeLineCap` / `StrokeLineJoin`) — the law, not a call-site choice. Several marks (the dots of `!`, `i`, `?`) are 0.6-long segments that rely on the square cap to read as dots at all.

`Size`/`StrokeThickness` defaults are written out in C# *and* in `Themes/Geometry.axaml`, because a styled property's default is resolved before any resource dictionary is in scope. `IconRenderTests.TheControlsDefaults_AreTheGeometryTokens` is the only thing stopping the two from drifting.

**An `Icon` with neither brush draws nothing, deliberately.** There is no base `Icon` style and no default colour: the design names no default icon colour, and inventing one would hide a call site that forgot to name a role.

### Call-site patterns

A stroke mark:

```xml
<controls:Icon Data="{DynamicResource IconCannotAccess}"
               Stroke="{DynamicResource StatusErrorTextBrush}" />
```

A fill mark:

```xml
<controls:Icon Data="{DynamicResource IconEject}"
               Fill="{DynamicResource TextSecondaryBrush}" />
```

The connected mark is **two `Icon`s in one cell** — one geometry cannot be a stroked ring *and* a filled dot:

```xml
<Panel Width="{DynamicResource IconSize}" Height="{DynamicResource IconSize}">
  <controls:Icon Data="{DynamicResource IconConnected}"     Stroke="{DynamicResource StatusOkTextBrush}" />
  <controls:Icon Data="{DynamicResource IconConnectedCore}" Fill="{DynamicResource StatusOkTextBrush}" />
</Panel>
```

Marks are drawn at `IconSize` everywhere except a dialog's type mark, which is drawn at `IconSizeDialog` (24) — `MessageBoxView` sets it on both the cell and each `Icon`. Do not reach for an arbitrary size: a mark that is neither 16 nor 24 is a design decision that belongs in this doc first. **Two do**, both marks that stand inside a line of small type and both carrying their size in their class rather than at the call site: `Icon.assignHint` and `Icon.kbdMark` are `Size` 12 — see the deviations table.

The dashed ring — the dash is a **pen** property, so "not detected" is the plain circle plus a dash array, not a second geometry. It has no call site today (see "Known gaps"); this is the shape any future one takes:

```xml
<controls:Icon Data="{DynamicResource IconNotDetected}"
               Stroke="{DynamicResource StatusErrorTextBrush}"
               StrokeDashArray="3,2" />
```

The spinner — the class carries the geometry, the 14×14 box and the rotation, so only the colour is left to name:

```xml
<controls:Icon Classes="spinner" Stroke="{DynamicResource AccentBrush}" />
```

Device art — the class carries the shared box; `Size` stays at the call site because the same drawing is used at two sizes:

```xml
<controls:Icon Classes="deviceArt" Size="92"
               Data="{Binding DeviceId, Converter={StaticResource DeviceArt}}"
               Fill="{DynamicResource SurfaceThumbnailBrush}" />
```

**A fixed set of states is enumerated in markup, not resolved by a converter.** Put every state's `Icon` in one `Panel` and toggle `IsVisible` through `EnumMatchConverter`: the cell then has a fixed width whichever state is showing, and each state names its own token — which a converter cannot do, because it can only swap the geometry, not the pen or the brush.

### Enum → geometry, and the guard blind spot it creates

Two families are driven by *data* rather than by a fixed set of states, so they go through converters (registered in `App.axaml` as `DeviceArt` and `LightingModeMark`), both resolving through `GeometryResources.Find`, which returns null for a missing key rather than throwing:

- **`DeviceArtConverter`** — `DeviceId` → `DeviceArt<Id>`. The mapping is a `switch` spelled out per member, so a device added to the catalog without a drawing is a visible gap here rather than a key that silently fails to resolve.
- **`LightingModeMarkConverter`** — `LightingMode` → `LightingMark<Mode>`, with a **`ConverterParameter` of `"Stroke"` or `"Fill"`**. It answers only the half the mode is drawn in and returns null for the other, so the call site puts two `Icon`s in one cell and exactly one of them draws. Stroking *and* filling would turn every ring in the set into a disc.
- **`LightingDirectionMarkConverter`** — `LightingDirection` → `IconArrow<Direction>`. No parameter: all four arrows are outlines, so there is no stroke/fill split to answer. `LightingDirection.None` converts to null — it is the file format's "this effect has no direction", and an `Icon` handed null draws nothing.

`MessageBoxIcon` is **not** converted — its four marks differ in colour as well as in shape, so `MessageBoxView` enumerates them in markup.

> **Blind spot:** a resource key looked up from C# is invisible to `ResourceReferenceTests` / `AuthoredXaml`, which only read markup. Nothing in the XAML names `DeviceArtAdvantage360` or `LightingMarkRipple`; a typo in a converter's key, or a mark deleted from a dictionary, would resolve to null at runtime and simply draw nothing. **`IconCoverageTests` is what guards those keys instead** — it enumerates the domain (the device catalog, the `LightingMode` enum, the `LightingDirection` enum, `MessageBoxIcon`) and resolves each key through the live application, in both directions: every member must have a mark, and every mark must name a member.

### Adding a new mark

1. Author the geometry in the right dictionary, inside a 16×16 box (or the family's box), origin top-left, y down. Keep the *painted* result — stroke included — inside the box.
2. Name it `Icon…` / `DeviceArt<DeviceId>` / `LightingMark<Mode>`; the prefix is enforced (`EveryDeclaredMark_CarriesItsFamilysPrefix`).
3. No colour, ever.
4. Draw it at the call site with an `Icon`, naming a token brush.

What fails if you skip a step: a mark whose paint leaves its box → `IconGridTests.EveryMark_PaintsInsideItsAuthoredBox` / `…KeepsItsStrokeInsideItsBoxToo`; a mark authored at the wrong scale or emptied → `EveryMark_FillsEnoughOfItsBoxToRead`; a duplicate of an existing shape → `NoTwoMarks_ShareTheSamePathData_ExceptTheNamedPairs`; a device or lighting mode without a mark, or a mark naming neither → `IconCoverageTests`; a dictionary written but never merged into `App.axaml` → `EveryMarkDictionary_IsMergedIntoTheApplicationsResources` (Avalonia does not complain about a `{DynamicResource}` naming a key nobody defined — it draws an icon-shaped hole).

**Two pairs are deliberately the same path data** and are named exemptions in `IconGridTests._sharedShapes`, each with its reason: `IconCannotAccess` == `IconWarning` (both a `!` in a circle, separated by colour — red for failure, amber for advisory) and `IconConnected` == `IconNotDetected` (the shared ring, separated by the pen). A mirror test, `TheDeliberatelySharedShapes_AreStillShared`, fails if either pair diverges, so a stale exemption cannot hide the next real collision.

### The spinner

`Styles/Icons.axaml` `.spinner`: `IconScanning` in its own 14×14 `SourceBox`, `Size` = `SpinnerSize` (14), `StrokeThickness` = `SpinnerStrokeThickness` (1.5), `RenderTransformOrigin` at the centre, and a `Style.Animations` loop rotating 0→360° over **1.1 s, `LinearEasing`, `IterationCount="Infinite"`**.

- The duration is **written out, not bound** — an `Animation` is not part of the logical tree, so a `DynamicResource` on it resolves to nothing and silently yields a zero-length loop. This is the same rule the recording pulse follows. `DurationSpinnerRotation` in `Themes/Motion.axaml` is the budget's record of the number, and `SpinnerMotionTests` is what keeps the two from drifting apart.
- It has **no `…Full`/`…Reduced` pair and no `MotionResourceBinder` alias**: it is a loop, not a property change to interpolate.
- **It keeps spinning under reduce-motion, deliberately.** The spinner is not decoration — it is the only affordance saying the app is still working, and a frozen one reads as a hung app, which is a worse outcome for the very user reduce-motion exists to protect. The reduced budget drops rises, slides and height changes; a status affordance that carries information is not in that category. `SpinnerMotionTests.TheSpinner_UnderReduceMotion_KeepsSpinning` pins that.

Four conventions that recur and are easy to get wrong:

1. **`:is(TextBlock)`, never `TextBlock`.** An Avalonia type selector matches the exact type; several of these roles render on `SelectableTextBlock` (unparsed file lines, the pedal entry box), which a bare selector silently skips.
2. **Never name a template part.** A style here that reached into Fluent's `/template/ ContentPresenter#PART_ContentPresenter` was the *old* way to out-rank Fluent's own state setters; it is now banned outright and asserted against. Paint a control by giving it a `ControlTheme` whose root template-binds its face, then set properties **on the control**. See "The control-theme layer".
3. **Declare states in increasing precedence — but do not rely on it.** Later styles win, and a `ControlTheme`'s own states are applied *before* an app style's, so precedence is spelled with `:not(...)` qualifiers inside a theme rather than left to file order.
4. **Animate through a class, not through `IsVisible`.** `IsVisible="False"` collapses a control instantly and gives a transition nothing to run on; `.open`/`.shown` re-evaluates the `Opacity` setter and the transition plays. `Border.listRow`'s separator is a *top* border on every row but the first (`ContentPresenter:nth-child(1) > Border.listRow` clears it) — a bottom border would leave a trailing hairline under the last row.

**A bridge sets the theme and, wherever it can, nothing else.** A `Style` setter outranks a `ControlTheme` setter, so every extra property in a bridge is a property the theme no longer decides. Two bridges legitimately add one: `Border.entryBox` adds `MinHeight="44"` (a pedal macro wraps over several lines) and `Button.colorSlot.selected` adds the accent ring that says which colour slot the picker is editing.

### The blocking surfaces — how a modal is dressed

The message box and the loading card are drawn **inside the shell window** by `NotificationOverlay` ([app-shell.md](app-shell.md)), and **issue #89 authored no new style, token or motion for them** — the two card widths below are the only style either surface has gained since (issue #52). They are composed entirely from what was already here:

|---|---|

| The card | `Border.overlayCard.modalCard` — the panel face plus `ShadowModal` |

**The message box is the one card in the app with two widths**, and they live in `Styles/Surfaces.axaml` rather than in the view: `Border.messageBoxCard` is 330 — a title, a sentence and a row of answers — and `.messageBoxCard.wide` is 420, which the handoff gives the leave-with-unsaved modal, whose body is a paragraph and whose three answers are named by outcome rather than Yes/No/Cancel. Cancel is not among them; the way out of a dialog can never be the answer that loses data. The suppression checkbox's caption is bound for a related reason — most boxes say `Don't ask this again`, but an opt-out that promises something has to say what it promises.

Two of the surface's own rules follow from that reuse rather than from a setter: the scrim **stays in the tree and toggles `.open`** (convention 4 above — `IsVisible="False"` would leave the 140 ms fade nothing to run on), and the card is opened on the *next* dispatcher pass, because a control that does not exist yet cannot fade in. **There is deliberately no blanket `ListBoxItem` style any more.** One used to sit in `Buttons.axaml` for the Search Keys picker's compact rows and leaked onto every list in the app — including the segmented control's, where, being an app style, it outranked the container theme and gave a segment 8,4 padding instead of the theme's 11,4. ## The Fluent control-alias layer — `Themes/Controls.axaml`

**What it does.** The app classes what it draws itself, but a plain `Button`, `ComboBox`, `TextBox`, `CheckBox`, `RadioButton`, `Slider`, `ToggleSwitch`, `Expander`, `ScrollBar`, flyout, menu or tooltip is drawn by `FluentTheme` from *Fluent's* palette — a different family of greys and a different blue. The result reads as two design systems in one window. Fluent's control themes do not hardcode those colours: every one is a `{DynamicResource}` against a named key (`ButtonBackground`, `ComboBoxBorderBrush`, `SliderTrackFill`, …) declared in the theme's own resources. This file redeclares those keys against our roles.

**Why it must live in `Application.Resources`.** Avalonia consults `Application.Resources` **before** `Application.Styles`, which is where `FluentTheme`'s originals live. Move this file into `Styles/` and Fluent wins every lookup — the aliases resolve, nothing throws, and the controls simply stay grey. That is exactly the silent failure mode the whole file exists to close.

**Three rules it follows.**

- It is an *alias map*, not a palette: every entry is `<StaticResource x:Key="FluentKey" ResourceKey="Role…" />`. There is no colour value anywhere in it, so a role changes in one place. `ControlPaletteTests.EveryControlKey_PaintsADesignToken` enforces this.
- It is scoped to the control types the app actually puts on screen; re-skinning all of Fluent would be a much larger surface with no user in it.
- Both variants carry the same keys (`DarkAndLight_RedeclareTheSameControlKeys`).

**The neutral ramp**, shared by everything that reads as a surface:

| State | Face | Border | Text |
|---|---|---|---|
| rest | `SurfaceBar` | `SurfaceBorderRaised` | `TextPrimary` |
| pointerover | `SurfaceRaised` | `SurfaceLineHigh` | `TextPrimary` |
| pressed | `SurfaceLine` | `SurfaceLineHigh` | `TextPrimary` |
| disabled | `SurfaceInset` | `SurfaceLine` | `TextDisabled` |

A *field* (`TextBox`, `ComboBox`) rests on `SurfaceInset` instead — it is a hole in the panel, not a thing on top of it — and takes the accent on its border when focused. That one rule is what makes the seven themes in `ControlThemes/Fields.axaml` read as one family.

**The accent ramp is the one place the variants diverge.** `AccentText` flips (near-black in dark, white in light), so a state that brightens the fill is legible in dark and illegible in light. Each variant therefore moves the fill *away* from its own label colour: dark brightens on hover (`AccentLinkHover`) and deepens on press (`AccentSelectedRing`); light deepens on hover (`AccentSelectedRing`) and lifts back to base accent on press. Disabled leaves the accent family entirely (`SurfaceInset` + `TextDisabled`) — a Save with nothing to save must not look like a Save that works.

**Two shape aliases** sit outside the variant dictionaries because a radius does not change with the theme: `ControlCornerRadius` → `RadiusControl`, `OverlayCornerRadius` → `RadiusPanel`.

**Extending it for a control type not yet covered:**

1. Find the keys the control theme actually reads — `Avalonia.Themes.Fluent`'s `Controls/<Type>.xaml`, or Avalonia DevTools on a live instance.
2. Add `<StaticResource x:Key="<FluentKey>" ResourceKey="<Role>Brush" />` to **both** variant dictionaries. Never a literal.
3. **Check the type.** Fluent types a scatter of keys as `Color` rather than `SolidColorBrush` (`ExpanderHeaderBackground`, `ScrollBarThumbBackgroundColor`, `SystemAccentColor`, …). Aliasing one of those to a `…Brush` role leaves the control drawing *nothing*. Point it at the `…Color` half and add it to `ControlPaletteTests.ColorAliases`.
4. Add one representative key to `ControlPaletteTests.SharedAliases` (or `ThePaletteCovers_EveryControlTypeTheAppPutsOnScreen`) so the family cannot be dropped wholesale later.

Fluent exposes no key for a few things; those are set as ordinary styles in `Styles/Buttons.axaml` instead — `ProgressBar`'s bar and trough. `ListBoxItem` selection/hover comes from the shared `SystemControlHighlightList*` keys, which is why those are mapped.

**One block of it is now dead.** The 43 `CheckBox*` aliases per variant are read only by Fluent's own `CheckBox` control theme, and nothing uses that theme any more — `Styles/Buttons.axaml` puts every `CheckBox` in the app on the `CheckBox` control theme, which writes its own template. They are kept because `ControlPaletteTests` names `CheckBoxCheckBackgroundFillChecked` explicitly, twice (in `SharedAliases` and in the per-control-type coverage list). Deleting the block means editing those assertions first, not just the markup.

## The control-theme layer — `Themes/ControlThemes/`

`Themes/Controls.axaml` puts FluentTheme's *own* templates on our palette. That is enough for a plain button or drop-down and it is not enough for the redesign: a layer pill, a tab, a key cap and a token field are shapes Fluent does not draw. The pre-redesign answer was a class selector in `Styles/` reaching into Fluent's template through `/template/ ContentPresenter#PART_ContentPresenter` — 22 selectors did that, purely to out-rank Fluent's own `:pointerover`/`:pressed`/`:disabled` setters. It made every restyled control fight the theme underneath it and made state precedence an accident of declaration order.

This directory replaces the template outright instead. **Eight files, 30 `ControlTheme`s**, merged in `App.axaml` under `Application.Resources` **after `Controls.axaml`** — they build on the same roles and, unlike it, replace a template rather than recolour one, so they must be able to name its keys (`PrimaryActionButton` and `CheckBox` both reach for the `AccentButton*` aliases, which is where the per-variant accent divergence is already written down). `Shared.axaml` is first: it carries the hatch tile and `BaseButton`, which the rest reference.

### The authoring contract

`Shared.axaml`'s header comment is the normative copy; this is the condensation.

1. **Write your own template; never reach into a theme you do not own.** Each `ControlTheme` sets a `Template` whose root is a `Border x:Name="Root"` template-binding `Background`, `BorderBrush`, `BorderThickness`, `CornerRadius` and `Padding`. A state then sets those properties **on the control** and the template binding carries them to the `Border`. Nothing outranks a value set on the control itself, which is exactly what the `PART_ContentPresenter` hack existed to fake.
2. **Targeting your own template part is correct.** `^:focus-visible /template/ Border#Root` inside the theme that *declares* that `Border` is idiomatic Avalonia and is what Fluent itself does. The ban is on a selector in `Styles/` or a view reaching into somebody else's template. **Never use a `PART_` prefix** — parts are named `Root`, `Label`, `Ring`, `Underline`, `Glyph`, `Locked`, `Items`.
3. **The focus ring** — see below.
4. **Focus and selection coexist and stay distinguishable.** Selection is the filled face and a ring in the accent family; focus is the halo outside it. A control that is both shows both.
5. **State precedence is explicit, not inherited from declaration order.** Avalonia has no selector specificity — the last matching setter wins — and `BasedOn` styles are applied *before* the derived theme's, so file order is not a safe ordering. Three qualifiers recur: every pointer-state `BorderBrush` setter carries `:not(:focus-visible)` (the focus ring owns the border whenever it is visible); every hover setter on a selectable control carries `:not(.selected)` / `:not(:selected)`; and every selected-state setter carries **`:not(:disabled)`**, because `BasedOn` puts `BaseButton`'s disabled face *first* and an unqualified `.selected` would win over it — a dead control keeping a live accent face and only the dead label colour. `:pointerover` and `:pressed` are both raised while the pointer is down, so hover fills carry `:not(:pressed)` too. The one state that needs no qualifier against `:disabled` is hover: a disabled control is not hit-testable.
6. **`ClipToBounds` stays false on anything that draws the halo.** A `BoxShadow` is painted outside the `Border`'s own bounds; a clip anywhere between it and the window erases it. On a key cap that means the `Button`, `Root`, the inner `Panel`, `Ring` **and** `KeyCapView` itself.
7. **Colours are always `{DynamicResource}`** (they live in theme dictionaries; a `StaticResource` snapshots one variant at load). Shapes from `Themes/Geometry.axaml` are theme-independent and may be `{StaticResource}`.
8. **Nothing here animates.** The motion budget lists every animation the app may have and a button hover is not on it. Writing our own templates also drops Fluent's 75 ms `RenderTransform` press animation, which is why the pre-redesign layer/tab pills had to clear `Transitions` by hand.

One consequence of rule 2 worth knowing: dropping the `PART_ContentPresenter` name means the presenter is no longer registered with the `ContentControl`, so a themed button's content hangs off the presenter rather than off the button in the logical tree. Bindings, styles and `DataContext` are unaffected — but a `{Binding $parent[SomeAncestor]}` written *inside* a themed button's content would be, so put those on the button (`KeyCapView` does).

### The class → `Theme` bridge

Views keep `Classes=` as the authoring API. A bridge is one style, one setter:

```xml
<Style Selector="Button.primaryAction">
  <Setter Property="Theme" Value="{StaticResource PrimaryActionButton}" />
</Style>
```

Extend the pattern rather than inventing one. Three shapes exist, and which to use is decided by whether the app would ever want a second appearance for that type:

- **A class**, for anything with competing variants — every button role, the key cap, the token field, the status pill, the search field.
- **The type itself**, for a type with exactly one appearance in the app: `Slider`, `CheckBox`, `ComboBox`. Inventing a class every instance would carry is only a second name for the same thing. A view that ever needs a second slider adds a class then, and the by-type style stays the default.
- **`Theme=` / `ItemContainerTheme=` at the call site**, where the control already has a theme-shaped API and a class would add indirection with nothing in it: `SegmentedControl`, `TabStrip`, `SelectableListRow`.

A bridge that is missing fails **silently** — the control keeps Fluent's template and merely looks a little wrong, which is exactly what no rendering test can see. `ControlThemeBridgeTests` is what catches it, on the real views.

### The `layerTab` split

`Button.layerTab` was one class doing three unrelated jobs at seven call sites, and `Button.editorTab` a fourth. Both classes are **gone**; `ControlThemeBridgeTests.NoViewStillWrites_AClassTheControlThemeLayerReplaced` fails if either reappears. The mapping, because the old names are still what a stale doc or comment will say:

| Old call site | Now |
|---|---|
| `KeyboardEditorView` — layer switch | A `ListBox` on `SegmentedControl` (containers on `SegmentedItem`) |
| `LightingTabView` — layer switch | The same, plus a scoped `ListBoxItem` style carrying the LED 1.0.44 gate onto `IsEnabled` |
| `KeyboardEditorView` — macro-slot picker | `Button.navPill` → `NavPill` |
| `KeyboardEditorView` — macro co-triggers | `Button.toggleSegment` → `ToggleSegment` |
| `LightingTabView` — direction | `Button.toggleSegment` → `ToggleSegment` |
| `SavantElitePedalView` — Single Action / Macro latch (×2) | `Button.toggleSegment` → `ToggleSegment` |
| `KeyboardEditorView` — `editorTab`, the section strip | A `TabStrip` on `TabStrip` (containers on `TabStripItem`). It carried a scoped `TabStripItem` style binding `IsEnabled` until issue #90; the strip now holds only sections that work, so nothing in it is ever disabled ([keyboard-editor.md](keyboard-editor.md)) |

The split is not cosmetic: a layer switch is **one-of-N** (a `SelectingItemsControl`), a co-trigger is an **independent latch** (a `Button` driven by `Classes.selected`), and a macro slot is neither — it is a nav pill, whose active face is the *raised neutral* surface rather than the accent, because "where you already are" is not one of the accent's two meanings.

Two keyboard consequences of the one-of-N controls, both from Avalonia's own defaults rather than from anything this layer sets:

- The **layer switchers** take **one tab stop for the whole group** (`ListBox` overrides `KeyboardNavigation.TabNavigation` to `Once`) and arrow keys move the selection inside it (`ListBox.OnKeyDown`), where each pill used to be its own tab stop.
- The **section strip** does *not* collapse to one tab stop — `TabStrip`'s `TabNavigation` default is `Continue` and nothing overrides it — but `TabStrip.OnGotFocus` makes **selection follow focus**, so moving focus onto a tab now opens that section. With the old buttons, focus and section were independent.

Neither view binds selection two-way: `SelectedItem` / `SelectedValue` is `Mode=OneWay` off the view model, and a `SelectionChanged` handler runs the very command the buttons used to. The view model stays the single owner of which layer or section is open, which is what lets the lighting tab *refuse* a firmware-gated layer and snap the segment back.

### The focus ring

**1 px accent border + a 3 px 28 % halo, never an offset outline** (`handoff.md:98`). The halo is `ShadowFocusHalo` (`0 0 0 3 #475B9DF9`) — spread only, no offset, no blur — so it hugs the control's own shape and reads on a 26 px key cap without eating its neighbour. Declared once, on `BaseButton`, and copied verbatim into the themes that do not derive from it:

```xml
<Style Selector="^:focus-visible">
  <Setter Property="BorderBrush" Value="{DynamicResource AccentBrush}" />
</Style>
<Style Selector="^:focus-visible /template/ Border#Root">
  <Setter Property="BoxShadow" Value="{DynamicResource ShadowFocusHalo}" />
</Style>
```

Two things follow that save a search:

- **There is no input-source service to find, and none should be written.** `:focus-visible` is Avalonia 11.3's own pseudo-class and already has the semantics the design asks for: a pointer press does not raise it, Tab and the arrow keys do. Every theme also sets `FocusAdorner="{x:Null}"` so Fluent's dotted adorner does not double up with the ring.
- **Text fields ring on `:focus`, not `:focus-visible`, deliberately.** A button clicked with the mouse needs no further confirmation, but a `TextBox` clicked into must still say so — that is where the caret now is and the user is about to type. `SearchField`, `MonoValueField` and `ComboBox` therefore take the accent border on any focus. It is the one place the ring is louder than on a button.

**Where the halo reaches.** Four field themes cannot own their template — `TextBox.OnApplyTemplate` does `NameScope.Get<TextPresenter>("PART_TextPresenter")` and `Get` *throws* when the part is missing; `ComboBox` needs `PART_Popup`, `Slider` needs `PART_Track` and its two repeat buttons. A hand-written template would have to carry a `PART_` name, which contract 2 forbids, so those four derive from Fluent's theme with `BasedOn` and extend it. A halo there would need a setter aimed at Fluent's own `Border#PART_BorderElement`, which is the very thing this layer exists to remove. So:

| Theme | Accent border on focus | Halo |
|---|---|---|
| Every `BaseButton` descendant, `SegmentedItem`, `TabStripItem`, `SelectableListRow`, `CheckBox` | own template, set on the control | **yes** |
| `SearchField`, `MonoValueField` | Fluent's `TextControlBorderBrushFocused` → `AccentBrush`, plus the theme's own `:focus` setter | no |
| `ComboBox` | Fluent's `ComboBoxBackgroundBorderBrushFocused` → `AccentBrush`, plus its own `:focus` setter | no |
| `Slider` | the theme's `BorderBrush`, carried by Fluent's root `TemplateBinding` | no |
| `TokenField` | n/a — a `Border` is not focusable, by design | n/a |

Every row is a visible, non-offset keyboard focus ring, which is the requirement; only the halo is missing on the four, and for a stated reason.

### Focus + selection on a key cap

The hardest case in the app: five faces compete for one 26 px square, four badges compete for its four corners, and the caps are 4 px apart. `Keycap.axaml` settles four things rather than leaving them to file order.

**The pinned ladder** — `listening > selected > :pointerover > locked > rest` — read as "listening's *face* wins over selected's". Every state names the states it loses to, so a reorder cannot change the matrix. Focus sits outside the ladder entirely: it owns the **border** whenever it is visible and touches no face, which is why every state's `BorderBrush` setter carries `:not(:focus-visible)` and no state's `Background` setter does. `:disabled` sits outside it from the other side and beats the whole ladder — the board is dimmed as a unit while a profile loads — so `.selected` and `.listening` carry `:not(:disabled)` and a dead cap wears `BaseButton`'s inset face. `.locked` needs no such qualifier: its face *is* the inset surface.

**`.modified` left that ladder with issue #91.** A remap is a bar, not a face — see the badges below and the deviations table.

**The four badges are facts, not moods**, drawn last in the template's `Panel` so nothing is painted over the mark that is the reason the cap is being looked at. None of them is qualified against `:disabled`, against the ladder, or against each other — with one exception, the collision the design leaves open: the macro dot and the advisory bar are both specified top-right, so **the bar keeps the corner** and the dot steps left of it by `BadgeAdvisoryBarWidth` + `BadgeGap`. Three of the four need no margin at all: the template's inner `Panel` already sits 3 px inside the cap's outer edge (`Root`'s 1 px border + its 2 px padding), which is exactly the mockups' "2 px in from the inside of the border". The remap bar is flush rather than inset and cancels that padding with `Margin="-2"`, the pair `Rectangle#Locked` uses. **Whether they are drawn at all is the picture's answer** — the `.stateBadges` class, pushed down from `KeyCapView.ShowsStateBadge`, which every badge selector is qualified with; the four state classes are written whatever the surface is, because they say what the *key* is ([keyboard-editor.md](keyboard-editor.md)).

**Selection and focus are concentric.** Both are spread-only shadows in the accent family, so laid on the same element — or one outside the other — they merge into a single denser band and stop being tellable apart. So:

- **selection paints the outer 3 px of the cap, inward from its edge** — `Border#Ring`, an empty transparent border with `Margin="0"` and `CornerRadius="1"`, wearing `ShadowKeyHaloStrong`.
- **focus paints 3 px outward from that same edge** — `ShadowFocusHalo` on `Border#Root`, from `BaseButton`.

A cap that is both wears a continuous 6 px band with its own edge at the seam, each half still readable, and nothing of the selection ring lands on a neighbour 4 px away. Mechanically the second element is unavoidable: a `Border` has exactly one `BoxShadow`, `BaseButton` has already spoken for `Root`'s, and two `{DynamicResource}` entries cannot be composed into one `BoxShadows` value in XAML.

**The arithmetic of the inward band, because every number in it is load-bearing.** The ring element sits exactly where the template's inner `Panel` does — 3 px inside the cap's outer edge (`Root`'s 1 px border + its 2 px padding), which is why the margin is `0` and not the `-1` it was. A spread-only shadow is drawn **outside** its element and clipped out beneath it, so from there a **3 px** spread paints exactly the cap's outer 3 px and a **1 px** spread paints only the innermost of those three. Skia draws outer box shadows **in list order**, so the 1 px `KeycapRingEdge` listed second lands on top of the accent's inner pixel: **2 px of opaque accent with a 1 px near-black hairline inside it, all of it inward.** `CornerRadius="1"` rather than `RadiusChip` because a shadow inflates the rounded rect by its spread and the radius is measured where the *element* is: 1 + 3 is the `RadiusKeycap` 4 the cap draws at its own edge, where `RadiusChip`'s 3 would inflate to 6 and bulge the ring's corners past the cap's. It is spelled as a literal for `Rectangle#Locked`'s reason — a `CornerRadius` resource cannot be handed to a `Border`'s shorthand and back out again.

That margin is measured against a **1 px** border, so `.listening` — the one state that doubles the thickness — restates it as `-1`, keeping the band flush with the edge rather than floating a pixel inside it. **Both rings are restated**, `Border#PaintRing` included: since #128 that is not symmetry for its own sake, because a cap can be listening *and* paint-selected at once and a ring left behind by the thicker border would sit a pixel in on exactly the cap being pressed.

**There are two selections, they own different elements, and each is drawn only on its own board.** `.selected` is the Layout board's single selected key — the one the inspector rail is talking about. **`.paintSelected`** is the Lighting board's paint multi-selection (`2f`'s "Paint · 2 keys selected"), and it is drawn in exactly the same grammar: the accent border and the same inward two-tone ring, because a selection is a selection and drawing the paint one differently would say the two mean different amounts rather than that they answer different questions. It gets its own part, `Border#PaintRing`, rather than a second setter on `Border#Ring`, because **both classes can be true on one cap** — the two tabs compute their state on the same cap view models — and two states writing one `BoxShadow` works only for as long as their values agree, which `.listening` already breaks by moving both margins. `.paintSelected` paints no face (on that board the face is the key's colour) and sits outside the ladder entirely; both yield to `:disabled`, because the ring is drawn in the accent and a dead cap wears no accent.

**Separate elements keep the two rings from merging; they do not stop either one appearing where it means nothing, and both did.** That is one defect fixed in two halves, and the qualifiers are now symmetric:

| Class | Drawn where | Part | Fixed by |
|---|---|---|---|
| `.paintSelected` | `^.lighting.paintSelected` — the Lighting board only | `Border#PaintRing` | **#131** — ungated, a key picked on the Lighting board drew a full accent ring and border on the **Layout** board, on caps the user had never selected and could not deselect from there |
| `.selected` | `^.selected:not(.lighting)` — the Layout board only | `Border#Ring` | **#133** — ungated, the inspector's key drew its face, accent border and ring on the **Lighting** board, over a picture whose subject is the key's colour, on a tab that shows no inspector at all |

Read as one rule: **a selection is drawn only on the board that owns it**, and the surface answers it exactly as it answers the four badges (`.stateBadges`) and the lit face. **Neither class is ever cleared and neither selection is ever destroyed** — both stay written on every cap on both boards, because they say what the *key* is; a trip to the other tab and back finds the selection where it was left. `KeycapThemeTests` pins each direction at the glass (`ThePaintSelectionsRing_…` / `TheInspectorsRing_IsDrawnOnTheLayoutBoardAndNowhereElse`), `KeyboardViewTests` pins it as a disagreement between two pictures of one layer, and `LightingTabTests` pins the survival on the real tab.

**A state that *yields* to `.selected` leaks it too, by its absence.** Gating the three `.selected` setters stops the selection being *drawn* on the Lighting board; it does nothing about the states that step aside for it. `.locked`'s face and border both name `:not(.selected)` — correctly, on the board that shows a selection — so a locked cap picked on the Layout tab arrived on the Lighting board having lost its inset face and its transparent edge, and grew a solid neutral border under its own dashed outline. Nothing was added to that cap and it still rendered differently from the identical cap beside it. So both setters are **restated for the surface** without that term:

```xml
<Style Selector="^.locked.lighting:not(:pointerover):not(.listening)">      <!-- the inset face -->
<Style Selector="^.locked.lighting:not(.listening):not(:focus-visible)">    <!-- the edge is the dash -->
```

They agree with the unqualified pair wherever both match — same tokens, same values — so the two can never fight and their order is not load-bearing; the only cap they answer differently for is the one the original pair abstains on. **When adding a state that loses to `.selected`, add its `.lighting` twin at the same time.** `Root`'s **border** is the half that shows: on that board the cap's content paints four fill layers over everything inside the 1 px border, so the `Background` is covered there and the border is not.

Two things are deliberately *not* surface-qualified, and both are asymmetries left standing on purpose:

- **The `.listening` margin setters on both rings.** That setter is where the element sits, not whether it is painted; both parts are in the template on both boards whatever is drawn into them, and geometry that held on only one board is the drift the shared qualification exists to prevent.
- **Hover.** `^:pointerover:not(.selected)` leaves a selected cap at the resting surface instead of lifting it — a `Background`, on the board where no `Background` this theme sets is ever drawn. It is also a state of its own rather than part of `.locked`'s statement, so scoping it would mean editing somebody else's selector to buy a case nobody can see.

**`.paintSelected` is why the ring is opaque, and it is the state that was actually broken.** With no face to fall back on, the ring is the *whole* signal rather than the loudest part of one — and a state with nothing behind it cannot be drawn as an alpha over a colour nobody chose. `.selected` takes the same ring because the grammar is shared, not because the Layout board needed it — and since **#133** that is the whole of it: with the ring surface-scoped, `.selected` only ever lands on the Layout board's neutral cap, over a face this theme paints itself. It never sits on an led colour. Recorded as a deviation from the handoff's *"filled face + 1 px accent border + 2 px halo rgba(91,157,249,0.3)"* in the table below; `ShadowKeyHalo` is left declared and unedited so the specified value stays beside the shipped one.

The selection ring is **not** qualified against `.listening` — the key that is listening is the key that is selected, and losing the ring at the moment the cap starts waiting for a keystroke would read as the selection having moved. The face and border do yield to listening (amber tint, 2 px advisory border). It *is* qualified against `:disabled`, like the face and the border: the ring is drawn in the accent, and a dead cap wears no accent.

**Locked is a fact, not a mood.** The hatch and dashed outline are unconditional on `.locked`: a locked cap under the pointer, or selected, still reads as locked. The old matrix let hover repaint the locked face and lose the signal. Only the *face* follows the ladder. A locked cap is still a live button — clicking it selects it and the inspector explains the refusal — so it is never `:disabled`.

### The hatch tile

`HatchBrush`, in `Shared.axaml`, declared once per theme variant (a brush in a plain dictionary would resolve its colour against the *application*'s variant rather than the window's). 45° at `HatchPitch` 4, painted in `SurfaceLineHigh`.

**It is drawn as filled bands, not stroked lines.** A pen widens a drawing's natural bounds by half its thickness; the tile brush then maps those wider bounds onto `SourceRect` and the pattern drifts out of register at every seam. Filled, the geometry's bounds are exactly the 4×4 tile. Each band is the region where `(x + y)` falls in `[0, 1.5]` modulo 4 — periodic over the tile in both axes, so a stripe leaving the right edge re-enters the next tile exactly where it left, at any control size. The pitch is spelled as the literal `4` inside the brush because a `RelativeRect` and a path geometry are parsed from strings and cannot interpolate a resource; `HatchPitch` in `Themes/Geometry.axaml` is the record of the number, and the two must be kept in step.

Two consumers, one meaning:

- **A locked key cap** — `Rectangle#Locked` in `KeyCapButton`, which both fills with the hatch and strokes the dashed outline, because a `Border` cannot dash in Avalonia 11 and a `Rectangle` can do both in one part. Its `Margin="-2"` cancels `Root`'s 2 px padding so the hatch reaches the inside of the border; the two numbers are a pair. The dash takes the *hatch's* colour, not the border role — locked is one material.
- **A key that is not lit** — the bottom of the three layers of the key cap's **face** on the Lighting board (`KeyCapView`), with the paint and the effect covering it when there are any.

**Off is hatched, never black**, because black is a colour a key can legitimately be lit.

**Since issue #94 that hatch is the cap's whole face, not a 3 px strip.** The colour used to be a bar in a row of its own under the caption; a bar that thin cannot read as a travelling wave, which is the thing `2f` asks the board to show. The face carries three stacked layers, drawn behind the caption and filling the cap's inner area at `RadiusChip` (the same box, and the same radius, as `Rectangle#Locked`):

| Layer | Painted with | Shown when |
|---|---|---|
| hatch | `HatchBrush` | always, on a lighting board |
| paint | `PaintColorHex` at `PaintOpacity` | `HasPaintColor` — 1.0 under a mode that renders the paint, 0.4 under one that ignores it |
| effect | `EffectColorHex` at `EffectIntensity` | `HasEffectColor` — this frame's sampled colour |

**Those two colours are a *softened preview*, not the stored value — and the swatches beside them are not** ([#124](https://github.com/migus88/kinesis-edit/issues/124)). `ViewModels/LedPreviewTint.Soften` pulls each channel 33 % toward the colour's own luma and scales the result by 0.87, at exactly one seam: `KeyboardKeyViewModel.ApplyPaint`/`ApplyEffect`, where a `LedColor` becomes the cap's `#RRGGBB`. The board draws ~95 caps side by side and a layer painted `#FF0000` was a wall of the display's most saturated primary; `#A41010` reads as a lit red instead. Three consequences belong to this layer:

- **`LitLabelBrushConverter` reads the cap's own hex**, so the caption's luminance flip is decided against the fill *actually drawn* rather than against a colour nothing paints. That is the reason the seam is here and not in the converter.
- **The rail's colour slots and the picker are untouched**, because they read `LightingColorSlotViewModel.ColorHex` through `HexColorToBrushConverter`. A swatch with a `#RRGGBB` beside it is the value on file, verbatim — the mono law's own case. So the swatch and the caps it painted are deliberately *not* the same colour, and that is not a bug to "fix" by softening one more place.
- **Black is a fixed point**, so an off key is still hatched and a Pitch Black board still reads black. Nothing here adds a constant term; a softening that lifted toward mid-grey would turn "off" into dim grey and lose the hatch's whole meaning.

`KeyColorOverlay.ToHex` and all of `KinesisEdit.Core` are unchanged, and no file state moves: this is presentation only. The rule itself, its constants and why they are what they are is in [keyboard-editor.md](keyboard-editor.md) § "Presentation rules".

**The hatch answers "this key is off", never "lighting is not on screen".** The face is drawn in three states, and it takes two answers from two different places:

| Lighting on screen? | This key lit? | The face |
|---|---|---|
| no | — | not drawn at all; the cap's ordinary surface shows |
| yes | no | the hatch |
| yes | yes | the colour, over the hatch |

The second answer is the cap's own `HasPaintColor`/`HasEffectColor`. The first is **`KeyboardView.ShowsLighting`**, handed to each cap as `KeyCapView.ShowsLighting` (both were `ShowsLedStrip(s)` until #94; the new name is the honest one — it means "this picture is the lighting board"). It is a property of the *picture* rather than of the key: the editor's Keys tab and the Lighting tab render the very same `KeyboardLayerViewModel` and cap view models (`KeyboardEditorViewModel.Apply` hands its `Layers` straight to `LightingTabViewModel.Attach`), so no view-model state could tell the two surfaces apart. Only `LightingTabView` sets it, so the Keys tab draws no colour at all — which is what the mockups draw. Off by default, so a board opts in rather than out, and a cap hosted alone (a test, a design-time scene) shows none. `KeyboardViewTests` pins the two-surface disagreement; `KeycapThemeTests` pins the three states at the glass.

**The `.lighting` class it writes answers more than the face.** It is the surface's one word, and four things now read it: the lit face above, the caption's colour (`LitLabelBrushConverter`'s fifth value), the locked cap's outline lifting over that face — and, since #131/#133, **which of the two selections is drawn** ("There are two selections…"). The sub-legend reads it too, from the other side. Adding a fifth reader is normal; giving the cap a *second* picture-level class to answer the same question is not.

**A locked cap on that board keeps its outline over the colour.** `Rectangle#Locked` is drawn *before* the cap's content in the template, so a lit locked key would have its hatch and its dashed edge painted over. `.locked.lighting` lifts the rectangle above the fill (`ZIndex`) and drops its `Fill` — the face is already hatched under the colour — leaving exactly the part the colour would otherwise have taken. `.lighting` is the second picture class, the same shape as `.stateBadges`.

## Motion budget — `Themes/Motion.axaml`

A budget, not a suggestion: nothing may animate longer than the table says, and **nothing may animate that is not in the table**.

| Motion | Duration key | Full set | Reduced set |
|---|---|---|---|
| Status cross-fade | `DurationStatusCrossFade` 220 ms | Background + BorderBrush `BrushTransition` | identical (a fade survives) |
| List insert | `DurationListInsert` 160 ms `CubicEaseOut` | `Height` `DoubleTransition` | **empty** |
| **Tab / layer swap** | `DurationTabSwap` **0 ms** | *(none — see below)* | *(none)* |
| Popover in | `DurationPopoverIn` 120 ms | `Opacity` + `RenderTransform` (2 px rise) | `Opacity` only |
| Modal in | `DurationModalIn` 140 ms | `Opacity` | `Opacity` |
| Scrim | `DurationModalIn` 140 ms | `Opacity` | `Opacity` |
| Toast in/out | `DurationToast` 180 ms, dwell `DurationToastDwell` 5 s | `Opacity` + `RenderTransform` | `Opacity` only |
| Recording pulse | `DurationRecordingPulse` 1.4 s `SineEaseInOut`, infinite | a `Style.Animations` opacity loop | same (a slow opacity cycle *is* a fade) |
| Spinner rotation | `DurationSpinnerRotation` 1.1 s `LinearEasing`, infinite | a `Style.Animations` rotation loop | **same — deliberate, see "Icons and device art"** |
| **Lighting preview frame** | `DurationLightingPreviewFrame` **33 ms** (~30 fps) | a **frame interval**, not a transition: a timer in `LightingTabViewModel` repainting the board's ~95 caps | **frozen — the timer does not start** |

### Why the tab/layer swap is zero, verbatim

> "Layer switching is deliberately unanimated — the spec says it will be used constantly, and 200 ms × 200 switches is the difference between an instrument and a website."

Three consequences:

1. **`DurationTabSwap` exists only so the zero is documented.** There is no `TabSwapTransitions` resource and there must never be one — a zero-duration transition still costs a frame of bookkeeping per switch. `MotionBudgetTests.NoTabSwapTransitionsResource_Exists` asserts the absence.
2. **Declaring no `Transitions` is not the same as having none.** Fluent's `Button` control theme ships a **75 ms `RenderTransform` press animation** that every `Button` in the app used to inherit — including the layer pills and the section tabs. Writing our own templates drops it, but `SegmentedControl`, `SegmentedItem`, `TabStrip`, `TabStripItem`, `ToggleSegment` and `ModeOption` still set `Transitions="{x:Null}"` explicitly, because a theme that inherits from Fluent's (or a future one that does) would bring it back. Cleared outright rather than set to a zero duration: a zero-duration transition still costs a frame of bookkeeping per switch. `MotionBudgetTests` counts the containers it found before asserting, so a guard that stopped reaching them cannot pass for the wrong reason.
3. **No container in the app owns a page transition.** The section strip is a `TabStrip` and the layer switch a `ListBox`, over a `Panel` whose children toggle `IsVisible`: neither is a content host, so neither *could* carry one. Avalonia 11's `TabControl` has no `PageTransition` property either; `Carousel` is the only container that does and the app uses none. `MotionBudgetTests.NoAuthoredMarkup_DeclaresAPageTransition` keeps it that way.

### Reduce-motion, and how a style consumes it

Motion.axaml declares each motion **twice** — `<Name>TransitionsFull` and `<Name>TransitionsReduced` — and never declares the bare `<Name>Transitions` key. Views and styles bind only the bare alias:

```xml
<Setter Property="Transitions" Value="{DynamicResource PopoverTransitions}" />
```

`MotionResourceBinder.Apply(application, motionSettings)` writes that bare key into `Application.Resources` itself, aliased to the Full or Reduced set. An entry a resource dictionary owns outranks anything in its merged dictionaries, so the alias always wins; and because the consumers bind *dynamically*, calling `Apply` again re-points every one of them live. The six aliases are listed in `MotionResourceBinder.Aliases` — adding a motion means adding both resources to `Motion.axaml` **and** one row there.

Detection:

- `IMotionSettings.ReduceMotion` is the single switch. `MotionSettings` asks an `IReduceMotionDetector` **once, in its constructor**, and remembers the answer; nothing re-reads the OS while the app runs.
- `ReduceMotionDetector.CreateForCurrentPlatform()` returns `MacOsReduceMotionDetector` on macOS (the primary platform) and `UnsupportedReduceMotionDetector` — always "don't know" — elsewhere. Avalonia 11.3 exposes no reduce-motion API of its own.
- The macOS reader shells out to `defaults read com.apple.universalaccess reduceMotion` through Core's `IProcessRunner`, mirroring `VDriveEject.CreateForCurrentPlatform`. A non-zero exit means the user never touched the switch, which is *not* a failure — it reports "unknown".
- Unknown, and any exception from the detector, resolve to **motion on**. An accessibility lookup is never allowed to matter more than starting up.
- `App.OnFrameworkInitializationCompleted` resolves it and calls `MotionResourceBinder.Apply` **before any window exists**, because the alias resources are what the views' transitions bind to. The `ReduceMotion` setter is public so a later preference screen or another platform's detector can flip it — re-run `Apply` afterwards, the aliases are not recomputed on their own.

The reduced set is **fades only: no rise, no slide, no height animation**. `ListInsertTransitionsReduced` is an *empty* `Transitions` rather than a missing resource — assigning empty is how a control ends up with no animation while the alias stays resolvable; dropping the resource would leave the setter unset.

**The lighting preview is the app's one per-frame repaint, and the budget's one entry that is neither a transition nor an animation.** `2f` asks the Lighting board to *be* the mode — "the board animates the selected mode at its real speed and direction" — which is a colour recomputed for every key on every tick, not a property Avalonia can interpolate. `DurationLightingPreviewFrame` is 33 ms because the effects are slow washes across a keyboard: 30 fps is already past the point where the motion reads as continuous, and every frame costs the whole board's colours and ~95 brushes. The number is written out at the timer and this key is the budget's record of it, exactly as the spinner's and the pulse's are. **It freezes under reduce-motion**, which is the opposite of the spinner's answer and for a stated reason — see the deviations table.

**Two motions are not transitions**: the recording pulse (a `Style.Animations` opacity loop on `Button.keyCap.listening, :is(TextBlock).recording`) and the spinner's rotation (`Icon.spinner`, `Styles/Icons.axaml`). Both durations are **written out rather than bound**, because an `Animation` is not part of the logical tree and a `DynamicResource` on it would resolve to nothing and silently give a zero-length loop; `DurationRecordingPulse` and `DurationSpinnerRotation` are the budget's record of the two numbers. Neither has a `…Full`/`…Reduced` pair or a `MotionResourceBinder` alias — there is no property change to interpolate — and neither is stopped under reduce-motion: a slow opacity cycle *is* a fade, and a frozen spinner reads as a hung app.

## Fonts

IBM Plex Sans 400/500/600/700 and IBM Plex Mono 400/500/600 are vendored under `src/KinesisEdit/Assets/Fonts/` and shipped as `<AvaloniaResource Include="Assets/Fonts/**" />`, so the app never depends on what the machine has installed. `LICENSE.txt` (SIL Open Font License 1.1, which permits embedding) travels with them.

`Avalonia.Fonts.Inter` and `.WithInterFont()` are **removed** — `Program.BuildAvaloniaApp` registers no font package at all. Weight 700 is carried only for the tiny logo "K"; the scale itself uses 400/500/600.

### The third family — `Kinesis Key Symbols`

`Assets/Fonts/KinesisKeySymbols-Regular.ttf`, **4.4 KB**, family name `Kinesis Key Symbols`, one Regular face, exactly **19 codepoints**:

```
U+2190 U+2191 U+2192 U+2193 U+21DE U+21DF U+21E5 U+21E7 U+21EA
U+21F1 U+21F2 U+2303 U+2318 U+2324 U+2325 U+2326 U+232B U+23CE U+2423
```

It carries the characters that **name a physical key** — `⇧ ⌃ ⌥ ⌘ ⌫ ⌦ ⏎ ␣ ⇥ ⇪ …`. Today it has three consumers, all in the macro panel (`docs/app/keyboard-editor.md`): the held-modifier run in a step row, the composer's **four** left-hand modifier latches (`⇧ ⌃ ⌥ ⌘` — since **#139** authoring is left-only, so no latch here draws a side run at all, though `MacroChordModifier` keeps the field because the mark table is shared with surfaces that do spell a side), and the Trigger strip's three co-trigger latches, which are `⇧ ⌃ ⌥` in place of six two-line captions. `ViewModels/MacroModifierMarks` is the mapping and `.keySymbol` is the class. The latch is the site that shows *why* this one is type rather than geometry: `ToggleSegment`'s selected face sets `Foreground`, which a `TextBlock` inherits and an `Icon` — painting from `Stroke` — cannot.

**Not every codepoint in the subset needs this face**, and the distinction matters before anyone "fixes" a working call site:

| Codepoints | Plex carries them? | What to do |
|---|---|---|
| `⇧` U+21E7, `⌃` U+2303, `⌥` U+2325, `⌘` U+2318 | **No — neither family.** This is the whole reason the family exists | Draw in `.keySymbol` |
| `←` `↑` `→` `↓` U+2190–U+2193 | **Yes.** The app already draws them in the ordinary face — `KeyRegistry`'s arrow legends, the step list's `· ↑↓` reorder hint | **Leave them in Plex.** They are in the subset only so a future surface that sets a whole run of key marks can do it in one face; an existing arrow is *correct* |
| `⌫ ⏎ ␣ ⇥ ⇪ ⌦ ⇞ ⇟ ⇱ ⇲ ⌤` | Per codepoint — ask, do not assume | `KeySymbolGlyphCoverage` and the Plex probe answer this; consult them |

**Provenance and licence.** A subset of **DejaVu Sans 2.37**, **renamed on subsetting so it does not claim to be DejaVu** (name IDs 1/4/6/16 all say `Kinesis Key Symbols`, and name ID 0 records what it was cut from). DejaVu was the only freely-licensed face found that covers every wanted mark — Noto Sans Symbols 2, the obvious alternative, has no `⌃`. Licence in `Assets/Fonts/LICENSE-KinesisKeySymbols.txt` (Bitstream Vera / Arev — permissive, redistributable, DejaVu's own changes public domain). Picked up by the same `<AvaloniaResource Include="Assets/Fonts/**" />` glob as the Plex faces, so no project change was needed.

**It is a deliberate deviation from the icon law**, recorded in the deviations table below: the law says *"geometry only"* and nothing in this app is an icon font. The exception is scoped to this family alone — vector `Icon` geometry remains the rule for every affordance mark, and `IconOption` (the `⌥` of the layer switcher's `⌥1` legends) stays a traced geometry.

`KeySymbolFontTests` asserts the asset registers, reports its own family name rather than falling back to the OS, and yields a **non-zero** glyph for every one of the 19 — a `.notdef` answer would pass a `TryGetGlyph`-only check while drawing tofu.

**The name-ID-16 gotcha.** IBM Plex's TTFs carry legacy family names — "IBM Plex Sans Medm", "IBM Plex Sans SmBld" — in name ID 1, which would fragment the family into one entry per weight and make `FontWeight="SemiBold"` resolve to nothing. Avalonia's embedded font collection groups faces by the **typographic** family name (name ID 16), which is "IBM Plex Sans" for every weight, so a single `avares://…/Assets/Fonts#IBM Plex Sans` family key carries them all. `ShapeAndTypeTokenTests.PlexSans_CarriesEveryWeightTheScaleUses` asserts Normal/Medium/SemiBold each resolve to a real glyph typeface, and `Family_LoadsRatherThanFallingBackToASystemFont` asserts the embedded collection registered at all rather than silently falling back to the OS default.

### What the families can print, at runtime — `Services/IGlyphCoverage`, `EmbeddedFontGlyphCoverage`

Coverage used to be a question only the tests asked. It is now queryable in the running app: `IGlyphCoverage.CanPrint(string?)` answers "can this app's own type print every rune of this?", so a **rendering rule** can prefer a glyph where it renders and fall back to words where it would draw tofu. `KeyCaption` is its one consumer — the key table's 17 glyph captions are in no embedded face, so every one of them falls back ([keyboard-editor.md](keyboard-editor.md), deviation 52). The interface exists so the rule stays a pure function of its arguments: nothing outside an implementation knows the answer comes from a font at all, and both branches are testable with no toolkit running (`Tests/Services/FakeGlyphCoverage`).

`EmbeddedFontGlyphCoverage.Instance` is the real probe, and it is **pessimistic**: a rune counts as printable only when **both** families answer yes at **every** scale weight (Normal/Medium/SemiBold), because a caption can be set in either face and Avalonia substitutes a missing glyph silently. It walks **runes, never chars** — five of the key table's glyphs are astral (U+1F568–1F56A, U+1F506, U+1F505), and a char walk would hand each half of a surrogate pair to the font and get a wrong answer twice — and treats whitespace as printable, because a caption's `\n` is a line break the view splits on.

Three of its decisions are load-bearing:

- **Only the per-codepoint `bool` is cached; the `IGlyphTypeface`s never are.** They wrap native handles owned by the running `Application`, and a cached one outlives the session that opened it — which, in a harness that starts and tears a session down around the suite, takes the test host down **natively**, with no managed stack. `FontManager` keeps its own typeface cache, so re-asking is cheap, and the codepoint cache keeps the hot path off it anyway (the caption rule runs across ~100 positions × 5 layers on every refresh).
- **Off the UI thread it answers "not printable" rather than throwing, and does not cache that answer.** Asking `Application.Current` for a resource walks its `Styles`, and every `AvaloniaObject` on that path verifies dispatcher access; `Application.Current` is a process-wide static that outlives any one test, so a caption resolved on a worker thread finds an application it is not allowed to read and throws — which is how this reached the suite the first time, as 6 failures on one run and ~40 on the next. Not caching the miss is what lets a later probe on the UI thread still read the real fonts. It costs the app nothing: every `await` in `KeyboardEditorViewModel` is `ConfigureAwait(true)`, so `Apply` and every view-model construction resume on the UI thread. Absent `Application` is the same answer, for the same reason.
- **`IBMPlexSans-Bold` — the seventh embedded face — is deliberately not probed.** No role in `Themes/Typography.axaml` puts Bold on the sans family (the one Bold role, `.logoMark`, is mono, whose Bold face is not even shipped), so probing it would tighten the gate against a face no caption is ever drawn in. The six probed faces are the same six the legend gate has always used.

**`KeySymbolGlyphCoverage` is a second, separate probe — and the separation is load-bearing.** It answers *"can the key-symbol face print this?"*, which is a different question from *"can the app's body type print this?"*. Adding `FontKeySymbols` to `EmbeddedFontGlyphCoverage.FamilyKeys` is the obvious-looking way to make a `⌘` "pass the font gate", and it would silently gut that gate: `CanPrint` is what `KeyCaption` consults to decide whether a caption may be a glyph, so a `⌘` would then be allowed into a **sans** caption which still cannot draw it. The gate would keep its name and lose its meaning, and nothing else in the repo would notice — so `KeySymbolFontTests.ThePlexGate_DidNotQuietlyAcquireTheKeySymbolFamily` reads the field and pins it to `["FontSans", "FontMono"]`.

The new probe is a copy of the old one's idiom rather than a share of it, on purpose: the common part is a dozen lines, the divergent part is the family set and the weight set (this face ships **one** weight; Plex is probed at three), and the two must be free to disagree. Every hard-won constraint above is preserved in it — the per-codepoint `bool` cached and the `IGlyphTypeface` never held, faces resolved lazily, and "not covered" (uncached) rather than a throw when there is no `Application` or the call is off the UI thread. One consequence worth stating: it answers **false for a Latin letter**, correctly — the subset carries the marks and nothing else, which is exactly why `MacroModifierMarks` hands the side letter out separately.

# Testing UI work in this repo

There *is* automated coverage for the UI now, it runs with **no display**, and it is where every design-system regression is caught. Use it; do not re-derive it.

## The harness

`src/KinesisEdit.Tests` references `Avalonia.Headless.XUnit` and `Avalonia.Skia`, both pinned to the app's Avalonia version (11.3.12 — a headless platform out of step with the framework it boots will not load).

`Headless/TestAppBuilder.cs` carries the assembly attribute:

```csharp
[assembly: AvaloniaTestApplication(typeof(TestAppBuilder))]

public static AppBuilder BuildAvaloniaApp() =>
    AppBuilder.Configure<App>()
        .UseSkia()
        .UseHeadless(new AvaloniaHeadlessPlatformOptions { UseHeadlessDrawing = false });
```

- It boots the **real `App`** — its `App.axaml`, and therefore the actual theme dictionaries, style includes, embedded fonts and `ViewLocator`. A test exercises the composition the app ships, not a stub that merges the same files. `App.OnFrameworkInitializationCompleted` builds no window here (it only wires the shell under `IClassicDesktopStyleApplicationLifetime`), but it *does* run `MotionResourceBinder.Apply`, so the motion aliases are the app's own.
- Only the platform underneath differs: `AvaloniaHeadlessPlatform` replaces the windowing system. `dotnet test src/KinesisEdit.sln` therefore runs the whole UI suite on a machine with no display and no window server — which is what CI is. `HeadlessHarnessTests.TheSession_RunsOnTheHeadlessWindowingPlatform` fails if `Avalonia.Native`/`Avalonia.X11`/`Avalonia.Win32` ever loads.
- Write UI tests with `[AvaloniaFact]` / `[AvaloniaTheory]` (not `[Fact]`/`[Theory]`) — they run the body on a real Avalonia UI thread.
- `Headless/ThemedHost.cs` shows one control under a chosen `ThemeVariant`, pinning the variant **on the window** rather than on the application so a dark host and a light host can coexist in one session without leaking global state into the next test. It runs `Dispatcher.UIThread.RunJobs()` after `Show()`, because `Show()` only *queues* the first layout pass.
- `Design/ViewSceneFactory.cs` builds every view over a realistic view model using the shell tests' own fakes, so no scene touches a drive, a settings file or the OS. A view whose `DataContext` is null renders an empty shell and proves nothing — `ViewRenderSmokeTests.EveryView_GetsADataContext_OrDeclaresItNeedsNone` guards that.
- **Every editor scene opens a `DeviceSession` first**, because the shell always has (`MainWindowViewModel.OpenDevice` calls `Begin` and only then asks the factory for an editor). Without it an editor falls back to `NullAppPreferencesStore` and the Settings tab's preferences section renders its *read-only* face — a state the app only shows for a board with no drive — so the frames would be of the wrong screen. Each editor gets its own manager rather than sharing the shells', since a shell ends the session it holds when its navigation unwinds.
- **`ViewSceneFactory.ViewTypes()` discovers a `Window` or a `UserControl`** — that is, a *screen*: a whole surface the app hosts and hands a view model. It used to be "every `Control` that is not a `Panel`", which also swept up the **leaf controls drawn in code** under `Controls/` (`KeyboardPanel`, `Icon`). Those are not screens: they have no view model, a scene for them would be a fabrication rather than a realistic one, and each would need a permanent exemption on `EveryView_GetsADataContext_OrDeclaresItNeedsNone`. They are covered by their own targeted render tests instead, which can drive the properties a leaf actually has (`Controls/KeyboardPanelTests`, `Design/IconRenderTests`). The narrowing dropped nothing that was discovered before — every type the old filter found is a `Window` or a `UserControl`, and `TheViewCatalog_CoversEveryScreenTheAppCanShow` holds the count and the named screens to that.

## Rendered-frame capture — the key technique

Drawing is deliberately **not** stubbed: `UseHeadlessDrawing = false` plus `.UseSkia()` means the headless window rasterises real pixels offscreen. `HeadlessWindowExtensions.CaptureRenderedFrame()` returns them as a `WriteableBitmap`, which can be saved to a PNG and looked at.

This needs **no display and no macOS screen-recording permission** — nothing is captured from the screen; Skia renders into a buffer. It is the fastest way to answer "what does this actually look like?" while working on a view, and it is far more reliable than launching the app.

Two mechanics that cost real time to discover:

1. **Transitions run on wall-clock time, and ticking the render timer does not advance them.** `AvaloniaHeadlessPlatform.ForceRenderTimerTick()` reports the *stopwatch* elapsed time, so calling it in a loop renders the same instant over and over. A surface whose `.open` class was just set is still at `Opacity="0"` and the PNG comes back blank. **Wait ~300 ms of real time (a `Task.Delay`) before capturing anything that fades in**, then tick and capture. `ThemedHost.Capture()` retries the tick five times, which covers the "first tick was spent on layout" case but cannot substitute for real elapsed time.
2. **Turn `UseLayoutRounding` off in layout-arithmetic tests.** In the app, arranged caps are snapped to device pixels, which is right on screen and useless in a test: it rounds a 0.6 px half-gap to 1 and hides every off-by-a-fraction. `KeyboardPanelTests` sets `UseLayoutRounding = false` on both the panel and its children.

Two more that cost real time when testing a control theme:

3. **Raise pseudo-classes *after* `ThemedHost.Show`, never before.** `Button` re-syncs `:pressed` from its `IsPressed` property when its template is applied, so a pressed state set before the first layout pass is silently wiped and the test asserts the resting face. Set `:pointerover`, `:pressed`, `:focus-visible` and friends on the shown control.
4. **`BoxShadow` is a `BoxShadows` struct, not a nullable list.** It is never null, so "no halo" is `Assert.Equal(0, root.BoxShadow.Count)` and reading one is `root.BoxShadow[0].Spread`. A null check compiles against nothing useful and a `Assert.Null` would never fire.

**Frame capture is a diagnostic, not a suite.** Run it ad hoc, look at the PNG, delete it. **There is deliberately no golden-image comparison anywhere in the tests, and none should be added** — pixel baselines break on a font-rasteriser update, an Avalonia patch release, a different CI runner, and a one-pixel layout change that nobody minds, and the resulting churn buries the regressions that matter. The suite asserts on *resolved values and named pixels* instead (see `FramePixels` below), which is stable.

### The three glyph gates (and a fourth, for the third family)

Nothing in Avalonia complains about a missing glyph — it substitutes silently, or draws tofu. So every string the app can put on screen is walked against the embedded families, from three different directions, all in `ShapeAndTypeTokenTests`:

| Gate | Source it walks |
|---|---|
| `EveryAuthoredKeyLegend_HasAGlyphInBothEmbeddedFamilies` | The **silkscreen** — `KeyVisual.Legend` / `SecondaryLegend` of every catalog board |
| `EveryAuthoredChromeString_HasAGlyphInBothEmbeddedFamilies` | The **app's own words** — every `const string`/`const char` in the `KinesisEdit` assembly plus every literal `Text=`/`Content=` in its markup |
| `EveryResolvedKeyCaption_HasAGlyphInBothEmbeddedFamilies` | The **key table's captions** — every `KeyRegistry.Entries` row × every `TokenDialect` × `isMacOs ∈ {true, false}`, resolved through `KeyCaption.For` with the *real* probe |

The third is the one issue [#111](https://github.com/migus88/kinesis-edit/issues/111) added, and its shape is the point: it gates the **resolved caption**, not `KeyRegistry.GlyphText`. Gating the glyph column directly — which is what the issue proposed — would fail *after* the fix exactly as surely as before it, since an uncovered glyph is now handled gracefully rather than printed. Resolving instead is strictly stronger: one walk covers `GlyphText`, `MacDisplayText`, the per-dialect display text and the token fallback, and it is the string a user actually sees. There is deliberately **no allowlist**: a keycap caption is domain data, so a gap is fixed by the caption rule or by the key table, never excused.

Two companions keep it from passing vacuously — the failure mode a wrong `FontManager` call produces is a probe that answers "covered" to *everything*:

- `TheResolvedCaptionWalk_ActuallyReportsAnUnprintableCaption` plants an entry captioned `moon ☾` and requires U+263E to be reported (and a `Moon` caption not to be).
- `TheResolvedCaptionGate_WouldHaveFailedOnTheUnconditionalGlyphRule` reproduces the pre-fix rule — `GlyphText` first and unconditional — by handing the caption rule an always-covering fake, asserts the walk reports U+23EF, and then asserts the real probe captions that same key `Play\nPause`.

The walk itself also asserts a floor of entries and captions resolved, and that **at least one entry actually fell off its glyph** — without which the drop path never ran and the gate proves nothing.

`ShapeAndTypeTokenTests.IsCovered` — the helper all three gates share — now **delegates to the production probe** (`EmbeddedFontGlyphCoverage.Instance`) rather than re-asking `FontManager` itself. The app now makes a rendering decision on the same question, and two implementations of "can we print this" would eventually disagree, with the gate green while the screen drew tofu.

#### The fourth gate — the key-symbol family

The three above all ask *"can IBM Plex print this?"*. The key-symbol gate asks the other question, and lives in `Design/KeySymbolFontTests`: **can the mark face print every mark the app emits, and is every mark one of the 19 codepoints the shipped asset was cut for?** Both halves are needed — `CanPrint` alone could be satisfied by a fallback family in the chain, so the marks are also checked against a hand-authored list of the subset's codepoints, which is what catches a re-subset that quietly dropped one.

It does **not** widen the chrome gate, which would defeat the point. Instead, `MacroModifierMarks`' constants are exempted from the Plex chrome gate through a **second, narrower list**, `KeySymbolSites`:

- The exemption is **per file** — a `⌘` authored anywhere else still fails, exactly as `▾` does outside the pedal view.
- Within a listed file it reaches **only runes the key-symbol family actually carries** — a `☾` in `MacroModifierMarks.cs` still fails. Both halves are proved by `TheKeySymbolExemption_ReachesOnlyItsOwnFileAndOnlyItsOwnMarks`.
- It is **not a deferral**. The three-entry `ChromeGlyphDeferrals` list means "this will become a geometry when its view is rebuilt"; this one means "this is drawn in a face that can print it". `EveryKeySymbolSite_StillAuthorsAMarkTheKeySymbolFamilyCarries` is its reverse check — when a listed file stops authoring marks, the entry fails and goes.

A view that authors a mark **literally in markup** (rather than binding one) would need its own entry here. Binding is the expected shape: the formatter is a view-model concern.

### Why `ResourceReferenceTests` exists

**A missing `{DynamicResource}` key fails silently at runtime.** Avalonia resolves it to nothing at all, leaves the property at its default, and renders a control that merely looks a little wrong. No exception, no log line — a rendering test cannot see it. (A broken `{StaticResource}`, by contrast, throws while the XAML loads and is caught by the render smoke.)

The only way to catch it is to read the markup and check every key. The app compiles its XAML, so there is no readable copy in the built assembly; `KinesisEdit.Tests.csproj` therefore embeds the app's `.axaml` files as `EmbeddedResource` under `LinkBase="Xaml"`, and `Design/AuthoredXaml.cs` reads them back. It strips XML comments first — these files quote the markup they explain — and scans three forms: `{DynamicResource X}`, `{StaticResource X}`, and the element form `<StaticResource ResourceKey="X" />` that is the whole of `Controls.axaml`.

**If you add a XAML file, it is picked up automatically.** If you add a *new form* of resource reference, extend `AuthoredXaml.ResourceKeysIn` or it silently escapes the guard.

### Asserting a control actually paints a token — `FramePixels`

`Headless/FramePixels.At(frame, x, y)` reads one pixel out of a captured frame, handling both `Bgra8888` and `Rgba8888`. It is the one assertion that reaches all the way through: a token, resolved under a variant, applied by a style, drawn by Skia, read back as the colour the handoff names.

```csharp
using var host = ThemedHost.Show(button, ThemeVariant.Light, 200, 100);
var frame = host.Capture();
Assert.Equal(
    DesignTokens.ResolveBrushColor("AccentBrush", ThemeVariant.Light),
    FramePixels.At(frame, frame.PixelSize.Width / 2, frame.PixelSize.Height / 2));
```

Use it when the question is "does this control *end up* painted with that role", not "does that role resolve" — the two differ whenever a control theme's state setters are in play. Keep the sample point somewhere flat (the middle of a filled face, a corner of the window), never on a border, a glyph or an anti-aliased edge.

`Design/DesignTokens.cs` is the resolver helper. It reaches the tokens two ways on purpose: `DeclaredKeys` loads `Tokens.axaml` directly, which is the only way to see what a variant *declares* (the resource system can only answer about a key it is handed), and `TryResolve` asks the live `Application`, which is what a view does — so a token that is declared but never merged still fails. `ControlPalette.cs` does the same for `Controls.axaml`.

## Adding a screen: the test checklist

1. Nothing extra is needed for `ResourceReferenceTests`, `ViewResolutionTests` or `ViewRenderSmokeTests` — all three discover types by reflection and pick a new view up automatically. But `ViewSceneFactory` must learn to build a realistic view model for it, or `EveryView_GetsADataContext_OrDeclaresItNeedsNone` will fail (which is the point).
2. Bump the count tripwires if you add a batch of views (`TheViewCatalog_CoversEveryScreenTheAppCanShow`, `EveryViewOfTheApp_IsVisibleToThisGuard`).
3. A view model rendered by an explicit `DataTemplate` rather than by the locator goes on `ViewResolutionTests._excluded` **with the reason**; `EveryExclusion_StatesWhy` and `TheExclusionList_HasNoStaleEntries` police that list.
4. New token → `TokenValueTests` row. New motion → `Motion.axaml` (both flavours) + `MotionResourceBinder.Aliases` + a `MotionBudgetTests` row. **A motion that is not a transition** — a loop, or a frame interval like the lighting preview's — gets a bare duration key, *no* `…Full`/`…Reduced` pair, no alias, and a `MotionBudgetTests` row all the same; the number is then written out at the call site, because an `Animation` and a timer are both outside the logical tree and a `DynamicResource` on either resolves to nothing. New Fluent control family → `Controls.axaml` in both variants + `ControlPaletteTests`. New mark → the right geometry dictionary, under its family's prefix; the `Icon*` suites pick it up by reflection, except a new *state/action* mark, which also goes on `IconCatalogTests._stateAndActionMarks`.
5. New **control theme** → the right file under `Themes/ControlThemes/`, a bridge in `Styles/` (or a `Theme=` at the call site), a row in the registry above, and rows in the matching theme suite's `TheoryData`: none of those suites discovers themes by reflection — every key, class and state is enumerated by hand, deliberately, because the expected token per state is the assertion.
6. A screen that **draws a board** must not hang it under a vertically-oriented `StackPanel` (#123) — one measures its children with infinite height, so the picture scales from the width alone and paints its overflow over the rows around it. Put it in a star row of a `Grid`, and remember that every `Auto` row sharing that column is measured *first* and can starve it: the Lighting tab needs `HeightBoardMin` on the board's row for exactly that reason. `KeyboardViewTests` walks every screen for the first half and `BoardFitTests` measures both boards at four window sizes for the second.

## Known gaps handed to later issues

The design system is complete; the *screens* built on it are not. Everything below is a deliberate deferral, not an oversight — the redesign epic ([#57](https://github.com/migus88/kinesis-edit/issues/57)) owns them.

- **`NavPill`'s disabled face is still `BaseButton`'s inset one** — but nothing in the app bar wears it any more. It used to be the face of Settings and Help, which were permanently `CanExecute → false`; issue [#96](https://github.com/migus88/kinesis-edit/issues/96) made both real navigations, so **all three pills are enabled at all times** and each wears the selected face on its own screen (app-shell.md invariant 11). The gap that remains is only the theme's own: where the mock draws a disabled pill as bare `TextDisabled` text, this draws a recessed face inside a hairline. The theme's header states the reasoning and `PillThemeTests` pins it, so flipping it is a design decision with a test row attached rather than a style tweak — it simply has no call site in the app bar today.
- **The device card's explanation is capped at two lines.** The card is a fixed height, so the cannot-access sentence — the only one left — carries `MaxLines="2"` and ellipsizes rather than pushing the buttons out of the bottom. At the 1000 px default nothing truncates; below roughly 820 px it starts to.
- **`IconNotDetected` has no call site.** The dashed ring was the resting card's status mark, and there is no resting card any more ([app-shell.md](app-shell.md), deviation 10). ## Load-bearing invariants

1. **No colour value outside `Themes/`.** Enforced by test.
2. **Both theme variants carry identical key sets** — in `Tokens.axaml` *and* in `Controls.axaml`. The app follows the OS theme; a key present in one variant is a colour that disappears on half the machines.
3. **`App.axaml` stays composition only.**
4. **`Controls.axaml` stays in `Application.Resources`, and the control themes stay after it.** Moving `Controls.axaml` to `Application.Styles` silently un-does the whole control palette; merging the control themes before it leaves `PrimaryActionButton` and `CheckBox` unable to see the `AccentButton*` aliases.
5. **Only `Themes/ControlThemes/` may name a template part**, and never with a `PART_` prefix. Anywhere else, a `/template/` selector is a bug and fails `ControlThemeBridgeTests.NoMarkupOutsideTheControlThemeLayer_NamesATemplatePart`.
6. **A bridge sets `Theme` and, wherever it can, nothing else.** A `Style` setter outranks a `ControlTheme` setter, so every extra property is one the theme no longer decides — and a blanket type style leaks across every list, panel and strip in the app.
7. **State precedence lives in the selector, not in file order.** Avalonia has no specificity, and `BasedOn` styles are applied first. Where two states can be true at once, qualify.
8. **Tab and layer containers carry no `Transitions` at all** — and must clear an inherited one explicitly.
9. **Views and styles bind the bare motion alias**, never `…Full`/`…Reduced` directly.
10. **View models expose enums and strings, never brushes.** `EnumMatchConverter` maps them to style classes, which keeps the view models toolkit-free *and* lets `DynamicResource` re-resolve when the OS theme flips at runtime.
11. **The three geometry dictionaries carry no colour** — even though they live in `Themes/`, which is the one folder allowed to hold hex. A shape is a shape; the call site names the token it is painted with, or the icon freezes at one theme's colour.
12. **An `Icon` fits its authoring box, never its ink.** Ink-fitting destroys the shared centre of the state marks, the relative proportion of the seven boards, and the spinner's rotation centre.
13. **`EmbeddedFontGlyphCoverage.CanPrint` means "both IBM Plex families carry this", and must keep meaning it.** The key-symbol family is a *second* probe, never a third entry in `FamilyKeys` — widening it would let a `⌘` into a sans caption that still cannot draw it, and `KeyCaption` makes a rendering decision on that answer.

## Deliberately not here

- **No design-token generator, no build step.** The tokens are hand-authored XAML; the value tests are the safety net.
- **No golden images.** See above — a deliberate refusal, not a missing feature.
- ~~**No app-level theme picker.**~~ **Overturned by issue [#96](https://github.com/migus88/kinesis-edit/issues/96).** The reasoning was that `RequestedThemeVariant="Default"` follows the OS and pinning a variant is a preference a later issue may add — and that issue arrived. The shell's **Settings screen** now offers Follow system / Light / Dark, stored per user in `preferences.json` and applied to the running `Application` by `Services/ThemeApplier` ([host-preferences.md](host-preferences.md), [app-shell.md](app-shell.md)). Nothing about the token layer changed to allow it: every colour was already a role token resolved with `DynamicResource` and declared for both variants, which is exactly why assigning `RequestedThemeVariant` at runtime re-resolves the whole palette live. `Default` remains what `App.axaml` declares and is what `AppThemePreference.FollowSystem` maps back to. **The same now goes for motion:** `MotionPreference` (Follow system / Reduced / Full) sits beside it, and `MotionSettings.SystemReduceMotion` keeps the OS answer frozen so "follow system" stays reversible — see "Reduce motion" above and `Services/MotionPreferenceApplier`.
- **No animation framework.** Six `Transitions` pairs, two `Style.Animations` loops (the recording pulse and the spinner) and one timer (the lighting preview's frame interval) are the whole motion surface, and the budget says that is all there may be.
- **No custom input-source tracking for the focus ring.** Avalonia 11.3's `:focus-visible` already suppresses on pointer press and raises on Tab and the arrow keys. A service that re-derived that would be a second, divergent answer to a question the framework answers.
- **No `RadioButton`-based segmented control.** Every one-of-N group is a `SelectingItemsControl`; every independent latch is a `Button` driven by `Classes.selected`. The **one** `ToggleButton` in the app is the settings rows' switch (`SettingSwitch`), and it is a `ToggleButton` only because `ToggleSwitch` cannot own its own template — see the deviations table.
